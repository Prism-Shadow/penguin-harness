## Summary
[summary]: #summary

给服务端加一个遥测模块，记三类平台层面的事实：每个请求多大、多久；每条事件从发布到送达经过哪几层、停在哪一层；每次打开会话，服务端和浏览器各花了多少时间。样本只记形状（大小、时长、计数、状态），不记内容，只留在内存里的一个有界环形缓冲中，不落盘、不外发，进程一退就没了。接入靠模块树的接线钩子：booter 把一个接口注入消费者的那一刻可以包一层，方法名和签名都来自 `ifaces.json`，被测的模块一行不改。整套东西默认关，关着的时候没有运行时开销；打开是一次有意识的选择，逐方法的包装再按模块名单独开。

## Motivation
[motivation]: #motivation

### 两件真事

**打开一个会话要十秒。** 一个跑了很久的会话，历史消息有几 MB。点开它，页面白十秒才出来。本地开发从没遇到过，因为本地的会话都不长。

**消息发出去了，屏幕上没有。** 在远程 Machine 上跑的会话里发一条消息，输入框清空了，消息流里没有它。按 F5 刷新，它在，模型也已经在回答。也就是说发送成功了，只是回显没到。这件事在本地 Machine 上从没出现过。

两件事有一个共同点：出事的时候，系统没有一句话能告诉我们时间花在了哪里、消息停在了哪一层。只能猜，猜完改一处，再等它下次发生。

### 今天能看见什么

这套系统已经有三块可观测的东西，各管一件事：

- **Trace 与性能分析**：模型做了什么。逐轮的 Token、用时、工具次数、TPS，最近还加了模型 API 时间与工具 wall time 两个分项。
- **用量落库**：花了多少钱。每次请求的 Token 与成本进 usage 表。
- **异常落库**：什么炸了。HTTP、Session 驱动、LLM、工具、进程级兜底捕到的异常进 error_records，去重、有上限、管理员可清。

它们都盯着 Agent 那一层，也都只在服务端。Agent 之下的平台层——HTTP、SSE、去远程机器的代理、磁盘上的 Trace 读取——以及浏览器那一侧，只有一条东西：`app.ts` 里一个中间件在 stdout 上打的 `GET /api/sessions/x/messages 200 9800ms`。没有响应多大，没有分项，没有请求 id，浏览器那边发生的事一个字也没有。`performance.now()` 在整个服务端只出现这一次，前端一次也没有。再往下数：没有日志器，没有日志级别，没有 `PENGUIN_DEBUG` 这类调试开关，没有 `/api/health`，CLI 没有 `doctor`，桌面端不写日志文件，服务端的输出只有壳的 stdout。

### 第一件事拆开看

顺着「打开会话」这条路走一遍，能列出七八个可疑的地方，每一个都合理：

- 历史接口 `GET /messages` 按 Task 开窗，前端首屏要最近 200 个 Task。一个 Task 里有多少消息、多少字节，没有上限。
- 工具输出以文本嵌在消息里，单条 16k 或 64k 字符；图片以 base64 data URL 原样嵌在 `tool_call_output.images` 里，`read_image` 单张最多 5 MB，粘贴进来的图片最多 20 MB。图片有单张上限，没有总量上限。`attachment-limits.ts` 里的注释自己就写着：一张大图不是一次慢请求，是一个再也恢复不了的 Session。
- 子会话的 Trace 在服务端递归读盘、内联展开到父会话的响应里，最深四层。
- 服务端读分片是整文件读成一个字符串再逐行 `JSON.parse`；分页统计的缓存冷了（重启后第一次打开、缓存版本升过），要从会话第一个分片扫到最后。
- 响应不压缩。`app.ts` 没有压缩中间件，几 MB 的 JSON 按原样走网络。
- 浏览器拿到响应先 `text()` 再 `JSON.parse`，主线程上过两遍；reducer 把全部消息折成 item 留在内存里；消息流没有虚拟化，全部 item 一次渲染；每段 Markdown 首次都要过一遍 micromark、代码块过 Shiki、公式过 KaTeX；图片是普通 `<img src="data:…">`，没有 `loading="lazy"`，全部即时解码。

十秒里哪一项占大头？今天答不上来。这七八项里有的是服务端的，有的是网络的，有的是浏览器的，改任何一项都是一轮工作，改错了就是白干一轮。先猜一项去修，猜错就是一轮白干；这件事得先量出来。

### 第二件事拆开看

先看一条消息怎么走。浏览器 `POST /tasks`，服务端把输入消息交给 Session 运行，响应体只有 `{ sessionId, queued }`，没有那条消息。前端收到响应后清空输入框，**不往消息流里放任何东西**，也没有乐观插入。用户看到自己的消息，靠的是服务端在 `launchTask` 里把输入消息 `channel.publish` 到该 Session 的 SSE 通道，浏览器从流上收到再渲染。F5 之后能看到，是因为历史接口从 Trace 与 `pendingInputs` 里重建。所以「发送成功、回显没到」在这套结构里是一件天然可能的事：写盘与推流是两条路，前者成功不代表后者到了。

再看流本身。设计上它相当周全：事件 id 是 `<epoch>-<seq>`，通道有 1 万条或 8 MB 的环形缓冲，断线重连带 `Last-Event-ID` 补发，补不上发 `resync_required` 让前端重建，服务端每 20 秒写一行心跳注释。远程 Machine 上这条流还要多走两跳：浏览器到本地服务端，本地服务端经 `/server/<id>/api/…` 代理、用 node:http 从 ssh 会话里拨一条 SOCKS 连接到远端服务端，响应流原样管回来。

问题在于这套保障有一个前提：**浏览器得知道连接断了**。前端用的是原生 `EventSource`，重连只在它自己报错之后发生；而 SSE 规范里注释行不产生任何事件，`EventSource` 根本看不见那 20 秒一次的心跳。一条连接要是半死——TCP 还开着，数据不再来——`EventSource` 的状态就永远是 OPEN，`onerror` 不会触发，`Last-Event-ID` 不会发出去，缓冲里的事件一条也不会被要回来。服务端这边同样没有写超时：`writeSSE` 的 promise 链一条接一条排着，写不出去就无限排队，`onAbort` 不会触发，也没有一行日志。前端唯一的错误处理是在 `closed` 为真时探一次 `/api/me`，而半死的连接 `closed` 永远是假。

在本地，这条连接是回环上的一个 socket，不会半死。在远程，它经过 ssh 会话、SOCKS 拨号、代理的两次流转换，任何一层安静地停下来，上面的描述就成立：POST 走的是新连接，照常成功；回显发到了一条没人在读的旧连接上；刷新之后一切都在。

这是今天代码能给出的**最可信的解释**，但它仍然是推断。要把它变成事实，需要四个时刻：事件发布到通道的时刻、写进那条连接的时刻、浏览器收到最后一个事件的时刻、以及浏览器认为连接还活着的依据。今天一个都没记。前端在 SSE 上没有一行 `console`，服务端在订阅、断开、补发命中与否、`resync_required` 上也没有一行日志，测试里也没有一条覆盖「连接没断但不再送达」这种情况。

### 真实环境和模拟环境不一样

这两件事都发生在真实环境：会话跑了几周，Machine 在另一台机器上，中间隔着 ssh。CI 和本地开发复现不了，也没必要去复现——真实环境本身就在天天产生数据，缺的只是在需要的时候把它记下来。要调优的是高压和特殊环境下的系统，数据就得从那些环境里来。这两件事都不是只发生一次的：长会话每次打开都慢，远程的连接过一阵就会再半死一回。所以「出事之后再打开遥测、等它再来一次」是可行的用法，遥测不必为了抓第一次而常开。

## Guide-level explanation
[guide-level-explanation]: #guide-level-explanation

### 三个词

**采集点**是代码里一个记录的位置，有名字，名字点名它在哪一层：`http.request`、`sse.write`、`client.session.open`。**样本**是采集点记下的一条事实：时间戳、时长、字节数、计数、状态，加几个属性。**关联键**是让不同层的样本能对上的 id：请求 id、Session id、SSE 事件 id、机器 id。

遥测只记形状，不记内容。一个 `http.request` 样本知道这个请求是 `GET /api/sessions/:sessionId/messages`、200、9800 ms、响应 4.2 MB，不知道响应里是什么；一个 `client.send` 样本知道 POST 用了多久、回显的事件 id 是几号，不知道用户说了什么。

### 每个样本点名自己那一层

这是从 PRFC-0006 搬过来的规矩：一个事实必须说清自己测量的是哪一层。第二件事之所以查不了，是因为「发布到通道」「写进 socket」「浏览器收到」「渲染出来」四个时刻一个都没记，而「消息丢了」可以发生在任何两个之间。遥测的采集点按层命名，一条消息的旅程于是可以按关联键串成一行：

| 层 | 采集点 | 记什么 |
| --- | --- | --- |
| 服务端通道 | `sse.publish` | 事件 id、字节数、通道 key |
| 服务端连接 | `sse.write` | 这条连接写到了哪个事件 id、写了多少字节、连接何时因何关闭 |
| 代理 | `proxy.forward` | 转发到哪台机器、上游何时以何种方式结束、转了多少字节 |
| 浏览器 | `client.sse` | 连接打开、关闭、错误、重连时带的 Last-Event-ID、收到的最后一个事件 id |
| 浏览器 | `client.send` | POST 用时与状态、响应带回的回显事件 id、回显到达的时刻；超时没到就记一条 `echo_missing`，带上当时收到的最后一个事件 id |

有了这一行，「回显没到」变成一个可以回答的问题：发布了没有？写进了哪条连接？浏览器收到了没有？浏览器最后一次收到任何东西是什么时候？

最后一问今天连数据源都没有：`EventSource` 看不见心跳注释行。所以采集点一落地就会指出第一处要改的地方——心跳得是一个有名字的事件（`event: heartbeat`），浏览器才有东西可记，也才有依据判断连接半死。这是遥测顺手带出来的一个修法。它真正要做的事在别处：让这类盲区自己露头。

### 会话打开的一行

第一件事同理。服务端的 `session.messages` 样本记这次读了几个分片、多少字节、内联了几个子会话、统计缓存冷不冷、各花多久；`http.request` 记响应字节数与总用时；浏览器的 `client.session.open` 记下载、解析、reducer、首次渲染各用多久，以及这一窗里有多少 item、多少张图、图片共多少字节。四个数一摆，十秒的去向就清楚了。

### 开关

遥测**默认关，关着时没有运行时开销**。这是本提案的一条硬决定，理由有两个：遥测是排障用的仪器，不是系统的记录，没人在看的时候不该有人为它付钱；而「不落盘」这一条与它是一体的——不写盘就没有什么要保留、迁移、清理、审计，关掉即归零。

三个开关，都在 machine 一级的 `server_settings` 里（PRFC-0004 的口径：这是这台机器的运维事实，管理员在系统设置里改，改完即时生效）。总开关在「设置 → 通用」里，只有管理员看得到这一行：

- `telemetry.enabled`：固定采集点与内存缓冲。默认关。关着时每个采集点只剩一次布尔判断，缓冲不分配，`/api/telemetry` 拒收。
- `telemetry.client`：浏览器侧采集与上报。默认关。关着时前端不计时、不攒样本、不发请求；开关随 `/api/me` 之类已有的首屏请求下发，前端据此决定采不采。
- `telemetry.instrument`：一个模块名列表，列出的模块的每条接口边都被包一层、逐方法计时。默认空。空的时候 `intercept` 根本不传给 booter，树里没有一个 `Proxy`。这是贵的那种，排查时开，开完关。

### 接线钩子：不碰被测的模块

第三个开关的实现是本提案里最值得说的一处。PRFC-0001 之后，服务端每一个节点要什么都写在 `@Use` 字段上；PRFC-0005 之后，这些字段的类型全是接口类，方法与签名都在 `ifaces.json` 里。booter 启动时逐条解析这些边，把提供方的实例塞进消费者的字段——`bootModules` 里 `use[alias] = apiOf(t.module, t.alias)` 那一行。

那一行就是钩子的位置。booter 多接受一个可选的 `intercept(edge, value)`，`edge` 说明这条边的消费者、提供者、接口名和方法表，返回值替代 `value` 注入。遥测的包装器拿着方法表，给每个方法包一个计时的壳，同步返回直接记，返回 Promise 的等它落定再记。消费者拿到的是壳，提供者不知道自己被包了，两边的代码一行不改。要看 `SessionsModule` 的哪个方法慢，把它写进 `telemetry.instrument`，重启，看 `module.call` 样本。

这么做成立，靠的是 PRFC-0005 那条规则：`@Use` 只能是接口。要是字段还能指向实现类，钩子就得猜哪些属性是方法，猜错要么漏测要么包坏；方法表来自签名数据，就没有猜的余地。

### 看哪

统计中心里已经有「用量」和「异常」，遥测在旁边加一页「性能」：页面顶上有「清空」，下面是缓冲里现有样本按采集点汇总的 p50 / p95 / 最大值，各列都可点表头排序，默认按 p95 从高到低——慢的抱怨说的是尾部，二十次里慢一次的采集点在中位数里看不出来；可按 Session 筛，点一条能看到它的关联键串出来的那一行。页面读的是内存，服务端一重启就空；想留一份，页面上有「导出」——把缓冲当前的样本下载成一个 JSON 文件，由人决定存在哪里，系统自己从不写。远程 Machine 上的服务端各自记自己的，这一页经现有的 `/server/<id>/api/…` 代理看那边的缓冲；请求 id 由代理原样转发，两边的样本因此能对上。

每一行的「名称」是采集点的名字，点开即跳到 GitHub 上该采集点的说明（`packages/server/src/telemetry/probes.<lang>.md` 中它那一节，按界面语言选文件），名称旁的「?」显示这一节的一句概述。说明写清一条样本量的是什么，并以相对链接指向记录它的那一行代码；相对链接与说明处在同一个 commit，行号因此对得上。行号由 `pnpm gen:probe-docs` 按构建所用的同一次扫描写回，测试在行号过时或有采集点缺节时失败。链接所指的 commit 在构建时取得：构建脚本扫描源码里的采集点调用，把「名字 → 文件与行号」连同所扫检出的 repo、commit 与扫描范围内是否有未提交改动一起写进产物（服务端的进平台包，`web.*` 的连同各节概述进前端包，各自对应各自的 commit），读口随按采集点的视图带回服务端那一份。`turn.${segment}` 这类按模板生成的名字记作 `turn.*`，共用一节。产物里没有这张表（未打包的开发运行）或名字查不到时，名字只是文字；扫描范围内有未提交改动时仍给链接，并提示行号可能对不上。

## Reference-level explanation
[reference-level-explanation]: #reference-level-explanation

### 样本

```ts
interface Sample {
  ts: number;            // 记录时刻，epoch ms
  probe: string;         // 采集点名，按层命名
  durMs?: number;
  bytes?: number;
  n?: number;            // 计数类采集点
  status?: string;       // "ok" | "error" | 采集点自定的状态
  keys: {                // 关联键，都可选
    request?: string;
    session?: string;
    event?: string;      // SSE 事件 id
    machine?: string;
  };
  attrs?: Record<string, string | number | boolean>;  // 采集点自己的属性，白名单
}
```

`attrs` 是白名单不是任意对象：HTTP 记路由模式（`/api/sessions/:sessionId/messages`）不记实际路径，不记 query 的值；文件类接口的路径、消息正文、任何用户内容一概不进。样本是给人看性能的，不是第二份 Trace。

### 存储与上限

样本存在一个进程内的环形缓冲里，形状与 SSE 通道的缓冲一样：按条数和字节数双上限，超限淘汰最旧的。默认 5 万条或 16 MB。它不写 web.db，不写任何文件；`telemetry.enabled` 关掉时整个缓冲释放。管理员可以手动清空。

不落盘的代价要说清楚：重启就没了，热推也没了（缓冲随这一代 App 走，新一代从空的开始）。这是有意的。遥测回答的是「现在」和「刚才这一阵」的问题，一份要跨重启保留的性能记录会带来一整套本提案不想要的东西——迁移、容量、清理策略、谁能看历史。要留就导出，见「看哪」。

高频采集点不逐条记。`sse.write` 一条快速的长回复会产生几千个事件，逐条记下来缓冲很快就转满一圈；它按连接每 5 秒聚合成一条：这 5 秒写了几个事件、多少字节、发布到写出的最大延迟。连接打开与关闭各记一条，带上打开时的 Last-Event-ID、补发命中与否、关闭原因（客户端断、上游断、写出错、服务端回收）。

### 固定采集点

服务端：

| 采集点 | 位置 | 记什么 |
| --- | --- | --- |
| `http.request` | 现有的请求日志中间件 | 方法、路由模式、状态码、用时、请求与响应字节数、请求 id |
| `proxy.forward` | `machines/proxy.ts` | 机器 id、上游状态码、用时、转发字节数、流结束方式（正常 / 上游错误 / 客户端断） |
| `sse.connection` | Session 与用户通道的订阅处 | 通道 key、Last-Event-ID、补发命中与否、补发条数、关闭原因、连接时长 |
| `sse.write` | 同上，聚合 | 5 秒内写出事件数、字节数、发布到写出的最大延迟 |
| `sse.evict` | `Channel.publish` | 缓冲淘汰发生时记一条：淘汰到哪个 seq、当时缓冲多大 |
| `trace.read` | `TraceService.readShard` | 分片路径的哈希、字节数、记录数、解析用时 |
| `session.messages` | `TraceService.readMessagesPage` | 窗口单位数、读了几个分片、内联了几个子会话、统计缓存是否命中、各阶段用时、响应字节数 |
| `session.resume` | Session 恢复 | 重放条数、用时 |

请求 id 在请求日志中间件里生成，写回响应头 `x-penguin-request-id`；代理原样转发请求头里已有的 id，远程那侧于是沿用同一个。`AsyncLocalStorage` 把请求 id 带到该请求触发的模块调用里，`module.call` 样本因此能挂到请求上；这是唯一一处跨异步边界的传递，成本要在实现里量一下。

浏览器：

| 采集点 | 记什么 |
| --- | --- |
| `client.session.open` | 下载用时与字节数、`JSON.parse` 用时、reducer 用时、首帧渲染用时（commit 后的下一个 `requestAnimationFrame`）、item 数、图片数与图片字节数 |
| `client.sse` | 打开、关闭、错误、重连及其 Last-Event-ID、`resync_required` 次数、收到的最后一个事件 id |
| `client.send` | POST 用时与状态、请求 id、响应带回的回显事件 id、回显到达时刻；30 秒未到记 `echo_missing`，带当时收到的最后一个事件 id 与最后一次心跳的时刻 |
| `client.fetch` | 其余 API 调用的用时、状态、字节数、请求 id，按路由模式聚合 |

浏览器每 10 秒把攒下的样本 `POST /api/telemetry` 一次，页面卸载时用 `sendBeacon` 发最后一批。服务端给每条盖上用户 id 后放进同一个缓冲。`telemetry.client` 关着时前端不采也不发，服务端也不收。

回显匹配的关联键不必新造：`launchTask` 里 `channel.publish` 每发布一条输入消息都返回带 id 的事件，`POST /tasks` 与 `POST /steer` 的响应把最后一个 id 带回去（`{ sessionId, queued, echoEventId }`）。前端拿着它等：流上出现 id 不小于它的事件即回显到达；等不到就记 `echo_missing`。这个 id 还有第二个用处——前端一看自己收到的最后一个事件 id 落在它后面，就知道流已经落后，可以主动断开重连，而不必等一个永远不来的 `onerror`。这一点属于修法，写在 Future possibilities 里；遥测只要求那个 id 出现在响应里。

心跳改成有名字的事件之后，`client.sse` 多记一项「最后一次心跳的时刻」。前端可据此设一个看门狗：两个心跳周期没动静就主动重连。看门狗本身也是修法，本篇只定采集点。

### 接线钩子

`bootModules` 的选项多一个：

```ts
interface BootModulesOptions {
  // …既有的 ifaces、resources、parked、published
  intercept?: (edge: Edge, value: unknown) => unknown;
}
interface Edge {
  consumer: string;        // 模块名
  alias: string;           // 消费者 @Use 字段名
  provider: string;        // 模块名
  iface: string;           // `<模块>#<接口>`
  methods: readonly string[];   // 来自 provides 表
}
```

booter 在 `use[alias] = apiOf(…)` 处改为先过 `intercept`。它对 exports 的转出与 `provides` 的校验都不生效——校验的是提供者的实例，包的是消费者拿到的引用。今天的 resolver 里没有任何装饰、替换或覆盖的概念：一个需求解析到一个提供者，两个都满足就是歧义错误，所以一个遥测模块没法靠「也提供同一个接口」把自己插到消费者与提供者之间，`intercept` 是新加的、也是唯一的那道口子。它只在模块树这条分支上成立，main 上还是一只 `AppDeps` 包裹，没有边可以包。

遥测的包装器：一个 `Proxy`，`get` 命中方法表里的名字时返回计时壳，否则原样转发（字段、`park`、不在表里的东西都不碰）。壳记 `module.call` 样本，按（消费者、接口、方法）每 10 秒聚合：调用次数、总用时、最大用时、抛错次数。同步方法在返回后记；返回值是 thenable 的在落定后记，拒绝算一次错。壳不吞异常、不改返回值。

包哪些边由 `telemetry.instrument` 决定：列表里的名字与消费者或提供者任一相符即包；`"*"` 全包，只该在开发环境用。`intercept` 由运行时壳在每次 App 创建时传入（`hmr/platform.ts` 调 `bootModules` 的地方），热推之后新一代的树照样被包；缓冲不进 parked 文档，热推与回滚都不碰它，也不带着它。

改 `telemetry.instrument` 要重启或热推一次才生效，页面上要写明。固定采集点与浏览器上报的开关即时生效。

### 与既有机制的关系

- **请求日志那一行留着**，它是 stdout 上最快的一眼；遥测在同一个中间件里多记字节数与请求 id。
- **异常落库不变**。一个失败的请求在 error_records 里是一条异常，在遥测里是一条 `status: "error"` 的样本，回答的是两个问题（出了什么错 / 有多慢多大），不合并。
- **Trace 不变**。Trace 的定义是一个文件对应一个完整的模型上下文，平台事件塞进去会破坏这个定义；遥测有自己的缓冲，而且不落盘。
- **`machines/proxy.ts` 里已有的 `ProxyReport`**——转发一次就顺手把「那边的 API 答了没有」记进机器列表——是同一类东西的先例：被动测量，搭现成的流量。`proxy.forward` 把它一般化。
- **`TraceService` 里的 `observeShardRead` 测试钩子**记的正是 `trace.read` 要记的事，实现时可以让它就是那个采集点。

### 权限

看遥测的是管理员，与异常落库里「无归属异常只对管理员可见」同一个理由：样本里有别的用户的 Session id、请求路由、机器 id，投进任一成员的页面就是跨租户泄漏。普通成员的统计中心不出现这一页。开关、清空、导出都只有管理员。

Agent 自己的命令是另一种读者。服务器驱动的会话交给工具子进程的 `PENGUIN_API_TOKEN` 不是管理员 token，而是这个会话自己的凭据：它以管理员身份过认证，但只能走一张按 session 收窄的路由表。落到遥测上：

- 读 `/api/telemetry` 必须带 `session=`，且指名的是凭据所属 Agent 的会话（或它自己创建的会话），只拿到那个会话的样本；不带、或指名别的 Agent 的会话，得 `403 session_scope`。
- 清空与开关（`DELETE /api/telemetry`、`PUT /api/admin/settings`）对会话凭据一律 403。
- `penguin telemetry` 在会话里默认按 `PENGUIN_SESSION_ID` 过滤、`--all` 取消；有了会话凭据，这个默认从「过滤」变成边界，`--all` 在会话里得 403。

磁盘上也不再有一份读到就等于管理员的 token：启动 token 只留在内存里，用来签会话凭据。会话凭据的形状与整张路由表不属于遥测，见其实现（提案 #146，`Myriad-Dreamin/penguin-harness#121`）。

## Drawbacks
[drawbacks]: #drawbacks

**又一页。** 统计中心已经有用量与异常，再加一页性能，三页各有自己的筛选。

**默认关，就抓不到第一次。** 出事的那一刻遥测多半是关的，只能打开之后等下一次。上面已经说过这两类问题都会重复发生，但总有只发生一次的东西，那种问题这套东西帮不上。

**重启就没了。** 一次排查中途服务端重启，缓冲清空，前面攒的都没了。导出是退路，但得有人记得点。

**包装的开销真实存在。** 一个 `Proxy` 加一层函数调用，对每秒被调几千次的方法不是免费的。默认不包，`"*"` 只在开发环境用，但这是靠文档守的规矩。

**样本不是回放。** 遥测能说「`session.messages` 花了 6 秒里的 4 秒在内联子会话」，说不了那次读的是什么；要看内容仍然得去 Trace。

**「遥测」这个词自带联想。** 用户看到它第一反应是数据要发到哪去。文档、设置页、首次启动都得把「只在本机、不外发」写在最显眼的位置，而且这是一条不能违背的承诺——一旦有一天真要外发，那是另一篇 PRFC，默认关。

## Rationale and alternatives
[rationale-and-alternatives]: #rationale-and-alternatives

**直接上 OpenTelemetry SDK。** 它有成熟的 span、属性、导出协议，也有 Node 的自动插桩。不选它有三个理由：它假设旁边有一个 collector，桌面应用与单机部署没有；它的自动插桩认识 http 与 fetch，不认识 SSE 的环形缓冲、经 ssh 的代理和模块树的边，而我们的未知恰恰在这些地方；它是一个不小的依赖树，为了两张表引进来不划算。样本的形状有意与 span 相近，将来要导出 OTLP 只是加一个出口（见 Future possibilities）。

**多打日志。** 最省事，也是今天在做的事。日志没有关联键，服务端与浏览器各说各的，十秒的分项要人肉从几行里拼；而且浏览器那侧的日志根本到不了服务端。

**只修这两个问题。** 压缩响应、图片懒加载、给发送加确认——每一项都可能是对的，但修哪一项靠猜。本提案不排斥这些修法，它先给出该修哪一项，并在修完之后能量出修没修对。下一个问题来的时候也不必再从零猜起。

**把平台事件写进 Trace。** Trace 已经有性能分析页，顺路加几种事件看起来最省。但一个 Trace 文件对应一个模型上下文，这是恢复与压缩都依赖的定义；HTTP 请求与 SSE 连接不属于任何模型上下文，塞进去这个定义就破了。

**在每个模块里手写计时。** 侵入每一个要测的地方，漏测的地方永远查不到，而且下一个想测的模块又要改一遍。接线钩子只改 booter 一处，之后想测谁改配置就行。这也是 PRFC-0005「依赖机制不依赖实现」之后才能成立的做法——接口成了数据，包装才不用猜。

**落盘、常开。** 像 error_records 那样进 web.db，重启不丢，随时能翻历史。代价是常开就有常开的成本——每个请求多几次写、表要有上限与清理、历史要有人管权限——而这些成本由所有部署一直付，换来的只是偶尔一次的排查方便。遥测是仪器，仪器该在用的时候拿出来；要留一份就导出。

**什么都不做。** 这两件事会继续发生，每次都靠猜。真实环境的用户会先于我们发现下一个。

## Prior art
[prior-art]: #prior-art

**OpenTelemetry** 的 span 与属性是样本形状的来源：时间戳、时长、一组扁平属性、靠 id 关联。这里没有取它的 SDK 与 collector，理由在上面。

**浏览器的 Navigation Timing 与 Resource Timing** 把一次加载切成 DNS、连接、下载、解析、渲染几段，各给一个时刻。`client.session.open` 是同一个思路搬到「打开会话」这个应用级动作上。

**VS Code 的「显示正在运行的扩展」**面板给每个扩展列激活时间与最近一次调用的用时，靠的是宿主在调用扩展 API 的边上计时，扩展自己不知情。`module.call` 是同一个形状：在边上测，被测方不知情。

**Go 的 `net/http/httptrace`** 让调用方在一次请求的每个阶段挂回调（拿到连接、写完请求头、收到首字节），请求逻辑本身不改。按阶段命名采集点、由调用方决定挂不挂，是从它来的。

**Spring AOP 与 Java 的动态代理**在注入时给接口包一层，是接线钩子的老前辈。差别是它们靠运行时反射找方法，这里方法表来自签名数据，跨热推边界也成立。

**本仓库里的先例**：SSE 通道的环形缓冲（条数与字节双上限、淘汰最旧）是样本缓冲的直接原型；error_records 的「只对管理员可见」照抄；`machines/proxy.ts` 的 `ProxyReport` 已经是一个被动测量点；PRFC-0006「事实点名自己那一层」是采集点命名的规矩。

## Unresolved questions
[unresolved-questions]: #unresolved-questions

- 缓冲的上限与聚合窗口（5 万条、16 MB、5 秒、10 秒）是拍的，要在真实环境开着跑几天之后再定。
- `AsyncLocalStorage` 传请求 id 的开销没量过。要是明显，退一步只在 `telemetry.instrument` 非空时开启。
- 心跳改成有名字的事件，旧前端会把它当成一个不认识的 `event:` 忽略掉，没有兼容问题；但它会进环形缓冲、占 seq，要不要走 `sendTo` 那种不入缓冲的路，实现时定。
- `module.call` 要不要记参数的形状（比如第一个参数的字节数）。有用，但离「不记内容」的红线近，第一版不记。
- CLI 要不要一个 `penguin telemetry` 子命令看同一个缓冲、做同一个导出。有用，本篇不定。

## Future possibilities
[future-possibilities]: #future-possibilities

**先会指向哪里。** 有了数据，第一件事大概率会落到这几项里的一两项：响应压缩、图片懒加载与总量上限、子会话内联改成按需、浏览器侧把解析挪到 Worker、消息流虚拟化。哪一项，等样本说。

**第二件事的修法已经能看出轮廓**，三样东西各自很小：心跳改成有名字的事件；前端加看门狗，两个周期没心跳就主动重连；`POST /tasks` 的响应带回回显事件 id，前端据此判断流落没落后。服务端那侧再补一个写超时，写不出去就关连接、记一条样本。这几项不必等遥测落地才做，但做完之后要靠遥测证明它们真的管用。

**CI 里的性能回归。** 同一套采集点在 e2e 里跑，把 `client.session.open` 与 `session.messages` 的数字与上一次比较，超过阈值就红。今天没有这条线，是因为没有数字。

**OTLP 出口。** 样本形状与 span 相近，加一个可选的导出器就能接到用户自己的 collector。默认关，另起 PRFC。

**按 Task 的预算告警。** 一个 Task 的工具 wall time、请求次数、响应字节数超过某个数就在会话里提示。数据都在，缺的是口径。

**前端那棵树。** PRFC-0001 提到前端也有自己的模块清单；浏览器侧的采集点今天是手写的几处，将来可以走同一个接线钩子。
