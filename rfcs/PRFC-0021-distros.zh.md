# PRFC-0021 发行通道：harness 抵达一台机器的共用词表

[English](PRFC-0021-distros.md)

- Feature Name: `distro-channels`
- Start Date: 2026-10-23
- PRFC PR: none yet (native to this repository)
- Implementation PR: —（本 RFC 固定词表；它喂养的各通道工作——harness meta 落位与 CLI 解析——由各自的 RFC 承载）

## Summary
[summary]: #summary

本 RFC 定义 **distro channel**（发行通道）：一台机器最终跑起这套 harness 的一条可复现路径。今天有六条：npm 包、发行 tarball（含 universal 变体）、Docker 镜像、桌面应用、源码检出，以及 machines 功能装出的对端机器。每条通道用同一组四个侧面描述，关于发行面的问题因此可以一次提出、逐通道作答。清单开放：新的发行方式列进来就加入。

## Motivation
[motivation]: #motivation

### 发行面的讨论需要一组共用名词

关于发行面的讨论需要一组共用名词，来回答「这台机器是怎么拿到 harness 的」。今天每个话题各自列一遍安装方式，或者跳过清单泛谈「安装」，而几乎所有发行问题的答案都是「看是哪条通道」。没有一份固定清单，「看是哪条通道」就没有可指的对象。

### 通道在无人记录的事实上分叉

一次只读盘点逐侧面比较了各条通道，发现它们在无人记录的事实上分叉：npm 包与发行 tarball 带推送 CLI 加载器，Docker 镜像与桌面应用不带；harness 的记录只在收到热推送或从对端安装时写下，其余通道的根从「无记录」启动。分叉本身是现状；缺陷出在比较方式上——这场比较只能从代码往上做，因为更早的文档里没有这份清单。

### 两份 RFC 需要这份清单当前提

同一方向下的 RFC——harness meta 常在（PRFC-0023）为代表——要「在每条通道上」作断言。它们需要一份可引用的通道清单与可引用的侧面名，否则各自再列一遍，清单会漂移。

## Guide-level explanation
[guide-level-explanation]: #guide-level-explanation

### 通道是什么

一条 **distro channel** 是一台机器最终跑起这套 harness 的一条可复现路径。它描述发行方式：同一台机器可以同时带着来自几条通道的安装，通道按「harness 是怎么到那儿的」区分。

### 每条通道回答的四个侧面

每条通道按同一组四个侧面描述：

1. **入口**——一个人，或一个监督进程，从这条通道怎样启动 harness 的 CLI。
2. **数据根**——这条通道装配哪个数据根、由谁装配。
3. **推送 CLI 可达性**——热推送的 CLI 在这条通道上能否被找到、加载、再运行。
4. **随包携带的镜像**——这条通道的产品是否自带一份完整的、push 格式的 harness 镜像。

侧面是问题，答案是关于现状的事实。固定的部分是侧面的名字；后续 RFC 改变某条通道时，改的是它的事实。

### 清单是开放的

新的发行方式会出现，清单靠列出它们生长。新通道加入已列出的通道，并记进文档的修订；已列出的通道保持原义。这条规则叫 listed, but not limited，也是本文档的一条 invariant。

### 清单回答什么

清单回答「这条路径算不算 harness 抵达机器的一种方式」。一条通道在列，意味着任何「每条通道」的断言都要说清它对这条通道的含义；功能齐全与否、支持到什么程度，由别的文档回答。

## Reference-level explanation
[reference-level-explanation]: #reference-level-explanation

以下是六条通道的现状。事实取自一次只读盘点，会随后续 RFC 变化；这份文档持久的部分是通道的身份与侧面的名字。

### npm 包

从包 registry 安装。**入口**：包声明的两枚 bin 链接——主 CLI 与推送 CLI 加载器。**数据根**：默认 profile 根，首启装配。**推送 CLI 可达性**：两枚入口都在、加载器可解析，从这条通道启动的 server 能经推送 CLI 再运行。**随包携带的镜像**：无，包不自带预构建的 harness 镜像。

### 发行 tarball 与 universal bundle

由发行脚本装进一个目录：launcher、库，以及捆绑运行时；universal 变体不带捆绑运行时。**入口**：安装出的 CLI 对旁的 launcher 脚本。**数据根**：默认 profile 根。**推送 CLI 可达性**：加载器随入口并排发行，经推送 CLI 再运行可行。**随包携带的镜像**：有，发行目录携带一份自己构建的 push 格式 harness 镜像，今天只用于机器安装。

### Docker 镜像

**入口**：`PATH` 上一枚无扩展名 symlink，指向镜像内的 CLI。**数据根**：一个卷，容器首启装配。**推送 CLI 可达性**：加载器在镜像里，没有东西解析它，所以这条通道上今天推送的 CLI 改动不生效。**随包携带的镜像**：无。

### 桌面应用

**入口**：桌面外壳直接从打包的 server 入口起 server 进程。**数据根**：共享的 release profile 根，首启装配。**推送 CLI 可达性**：当前产品不带推送 CLI 加载器，推送的 CLI 不可达；用户可见的命令 shim 指向打包的 CLI。已有一条实现线示范了带加载器、启动前先查记录的形态。**随包携带的镜像**：有，应用包携带一份自己构建的 push 格式镜像。

### 源码检出

开发通道。**入口**：源跑走 dev 脚本；构建跑用构建出的 CLI 对。源跑没有可再运行的入口，这是一条文档化的边界。**数据根**：dev profile 根。**推送 CLI 可达性**：构建出的 CLI 对可行；检出还能按需构建 harness 镜像，它被刻意铺给机器安装用，不铺进 dev 数据根。**随包携带的镜像**：按需构建。

### machines 安装出的对端

由 machines 功能从某对端安装出的远端机器。**入口**：安装出的对端的加载器是它唯一的 CLI 面，远端命令直接调用它。**数据根**：安装时装配，由复制发送方的 harness 记录来播种，所以对端的根从安装完成那一刻起就带着 harness meta。**推送 CLI 可达性**：整条通道就是推送 CLI。**随包携带的镜像**：不携带，记录在安装时从发送方复制。

### 事实会变，通道留下

上面的小节回答「你指哪条通道」，四个侧面回答「关于一条通道能问什么」。后续 RFC 改变事实时——harness meta 落位会改每条通道的数据根侧面，CLI 解析会改其中两条的可达性侧面——这里的小节随之修订，通道本身还是那些通道。

## Invariants
[invariants]: #invariants

### 清单保持开放

> 无论 harness 的发行方式增加多少，通道清单仍然是一份共用词表：新的方式靠被列进来加入，已列出的通道保持原义。

清单是词表，一份会关闭的词表会让未列出的发行方式在设计面上不可读。新通道加入时，既有通道的含义保持原样，修订机制承载这次加入。

### 每条通道回答同一组侧面

> 无论一条通道的支持范围扩大还是缩小，它的描述仍然回答与其它通道相同的四个侧面。

一条停止回答某个侧面的通道，或者改答另一组侧面的通道，毁掉的是这份清单存在的理由：可比性。发行面的断言之所以能「在每条通道上」成立，只因为通道们能被问同样四个问题。

## Drawbacks
[drawbacks]: #drawbacks

一份清单会招来误读：在列被读成功能对齐，六条被读成永远六条，侧面答案被读成支持承诺。粒度也会被争论——universal 变体与普通 tarball 共用一个节，machines 装出的对端算作通道，而它其实是某条通道的下游。清单还需要维护：一条新通道，或一个变化的事实，都要一次修订。

## Rationale and alternatives
[rationale-and-alternatives]: #rationale-and-alternatives

**一份独立的词表 RFC**：两份 RFC 都要引用通道；被几份文档引用的清单不属于其中任何一份，得住在有自己锚点的地方。

**侧面固定、事实放开**：把事实写成规范会把现状冻进设计面；侧面是可复用的一半，事实是易腐的一半。

**六节、近亲归并**：universal bundle 与普通 tarball 只在运行时捆绑上有别；machines 对端单列，因为它的入口与数据根形态和每条发行通道都不同。

**不做的代价**：每份发行面 RFC 都非正式地重列通道，枚举之间漂移。

## Prior art
[prior-art]: #prior-art

操作系统很早就有发行通道的概念，包矩阵是后来的事。浏览器把通道（stable、beta、dev）与每条通道支持什么分开命名。Electron 及其同类把分发目标记成每个 release 的闭集，同时保留「可以出现新目标」的观念。共同的做法是先给发行方式命名，再谈每种方式承诺什么。

## Unresolved questions
[unresolved-questions]: #unresolved-questions

几处细节留待实现或后续修订。

- universal 变体单列一节，还是继续并入 tarball。
- 通道算发行路径还是运行环境：Docker 镜像两边都像，本 RFC 按发行路径记一次。
- machines 装出的对端算通道还是通道的消费方；这里按通道计，边界留待后续 RFC 再过一遍。
- 四个侧面之外是否还需要第五个，例如更新通道；本 RFC 固定四个。

## Future possibilities
[future-possibilities]: #future-possibilities

一张通道 × 特性的支持矩阵，维护在发行面上，不放进 RFC。发行断言可以按通道措辞（「每条通道的产品都带可加载的 loader」）。一条新通道——未来的包生态、设备镜像——先在这里入列，再继承姊妹 RFC 的断言。
