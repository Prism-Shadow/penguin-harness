## Summary
[summary]: #summary

The HTTP endpoints the server already has **are the API server**: a set of transport-agnostic operations, for which HTTP is one transport and a single WebSocket is another. Between a browser tab and its server there is **exactly one WebSocket** (opened on the terminal stream's upgrade path under a reserved id named for the logged-in user; see "Transports and handshake"), and what runs on it is not a new protocol but **equivalent asynchronous API calls**: each frame is one call to an existing endpoint (method, path, query, body, headers) that receives the same endpoint's response. **Authentication goes through the same gate too**: every call on the socket carries the session credential authenticated at handshake time — held only by the server, never entering a frame — and enters routing through the same cookie gate as HTTP, with authorization, `sessionVia`, and error shapes identical to HTTP call by call; the only difference is that the socket's responses carry no Set-Cookie (the current implementation never writes one on upgrade or frame responses anyway, and this design does not depend on writing one there), so the socket **never renews** the session — revocation and expiry take effect on it per call, and idle connections are reaped by the heartbeat within one period. Endpoints that return event streams (`/api/events`, `/api/sessions/:id/stream`) are, on this transport, one call that never ends: frames are delivered one by one, and to cancel is to unsubscribe. This server's user-level events, the machines' user-level events, and any number of Session streams are therefore all concurrent calls on the same socket; `Last-Event-ID` resumption, bounded buffering, and `resync_required` carry over unchanged. Not one HTTP endpoint is removed: the CLI keeps using them, and so does the browser while the socket is not established. Calls to machines are forwarded by the server, in the same manner, over the ssh sessions it already holds — so there is also exactly one socket per machine. The terminal stream remains a separate WebSocket and is **not** folded in (see Rationale for the reasons).

## Motivation
[motivation]: #motivation

**The symptom.** On desktop and on mobile alike there have been incidents of "one forwarded-to-machine request hangs, and then all requests hang". The investigation showed the fault is not in the server: the Web App opens one `GET /api/events` against this server, one `/server/<id>/api/events` per connected machine on top of that (through the same-origin proxy), and each open session page opens yet another `/api/sessions/:id/stream` — each of these is an HTTP response that never ends. The server speaks only HTTP/1.1 (no TLS on loopback, hence no HTTP/2), and a browser allows only six concurrent HTTP/1.1 connections per host; two or three machines plus one session page exhausts the quota, and the sidebar's own list requests then queue behind those long-lived connections, showing up as Stalled in DevTools. Once a forwarded-to-machine request goes half-dead at the far end (the ssh channel is gone while TCP still stands), `EventSource` sees no error, and that slot never comes back.

**The structural cause.** The number of long-lived connections grows linearly with "number of machines + number of open session pages", while the quota is constant. Any scheme shaped as "one connection per thing" will hit that constant; changing transports only pushes it farther away (the WebSocket quota is on the order of two hundred). For the count not to grow with the number of objects, the connection has to be **one**, with the objects as subscriptions on top of it.

**What this fixes along the way.** Machines' events being fetched by the browser, machine by machine, means one long-lived HTTP response through ssh and one SOCKS dial per machine — while the ssh sessions are already in the server's hands. With the server subscribing and merging them in, the browser half drops from `1 + N` connections to 1, and the far-end half drops from "N per tab" to "1 per machine". Half-dead connections are pronounced dead by the socket's protocol-level ping/pong, not by an SSE comment line that nobody receives.

**Scenarios.**

1. The Web App is opened on a phone, with three machines connected under the Project. Before: four SSE long-lived connections immediately take four of the six quota slots, and the sidebar's dozen-plus list requests, grouped by Workspace, queue up two at a time. After: one socket, with all list requests concurrent.
2. The user switches between session pages. Before: close one Session SSE, open another. After: cancel one subscription and add another on the same socket — no handshake.
3. A machine's ssh session drops and reconnects. Before: the browser's `/server/<id>/api/events` hangs or breaks, gambling on `EventSource`'s automatic reconnection. After: the server pushes "not connected" down that machine's channel and the browser marks the machine offline; after ssh reconnects, the server re-subscribes carrying the last event id, the gap is filled from the machine's buffer, and the browser never notices.

## Guide-level explanation
[guide-level-explanation]: #guide-level-explanation

**First, get one concept straight.** Today's `packages/server` is an API server; it just happens to have only one transport: HTTP. Every endpoint is an operation — `GET /api/projects` is "list Projects", `POST /api/sessions/:id/tasks` is "send a Task", `GET /api/sessions/:id/stream` is "subscribe to this Session's stream". HTTP encodes operations as request/response; SSE encodes a "stream" as one never-ending response. This proposal adds a **second transport**: a single WebSocket on which every frame encodes the same operation. The operation itself, its authorization, and its response shape are defined in one place and served over two transports, with neither having a single feature the other lacks; the sole exception is session renewal: only HTTP responses renew (a renewal always comes with a Set-Cookie on that same response), and socket responses never renew — the invariant is under "Entry, identity, and platform".

**For frontend authors.** The API client is still `apiFetch(path, options)`, and the paths are still the same paths. Only the transport changes: when the socket is up, calls go over the socket; when it is not, they go over HTTP — callers cannot tell the difference. Event streams likewise: `openSessionStream(sessionId)` and `openUserEvents(machineId)` keep their signatures, and inside they go from `EventSource` to one never-ending call on the socket. The frames look like this:

```jsonc
// client → server: one call
{ "id": 7, "call": { "method": "GET", "path": "/api/projects" } }
{ "id": 8, "call": { "method": "POST", "path": "/api/sessions/session-…/tasks", "body": { /* … */ } } }
{ "id": 9, "call": { "method": "GET", "path": "/api/sessions/session-…/stream", "headers": { "last-event-id": "41" } } }
{ "id": 10, "call": { "method": "GET", "path": "/server/m-…/api/events" } }     // an operation on a machine; same path as the same-origin proxy
{ "id": 9, "cancel": true }                                                     // ending a streaming call = unsubscribing

// server → client
{ "id": 7, "status": 200, "body": { "projects": [ /* … */ ] } }                  // one-shot response, one frame
{ "id": 9, "status": 200, "stream": true }                                       // streaming response begins
{ "id": 9, "event": "message", "eventId": "42", "data": { /* OmniMessage */ } } // one frame per event thereafter
{ "id": 9, "event": "server_event", "eventId": "43", "data": { "type": "task_state", /* … */ } }
{ "id": 9, "end": true }                                                         // the stream ends (cancelled, server shutdown, or backpressure drop; the reason says which)
{ "id": 10, "status": 503, "body": { "error": { "code": "not_connected", /* … */ } } } // machine not connected: the same answer as the HTTP proxy
```

On disconnection the client reconnects by itself (with backoff); once reconnected, it re-issues every streaming call still in progress, with `last-event-id` carrying each one's last received `eventId` — the same thing today's per-SSE reconnections do, now gathered into one place. One-shot calls end with an error on disconnection and are handled by callers along their existing error paths (most UI already retries or prompts). The server's tightened authentication needs no further cooperation from the frontend: the `/api/me` response says who the page currently is (`identityIs`), sign-in and sign-out flip the identity (`identityChanged`), and a 401 from this server triggers global logout on **both transports** (the check in `api/client.ts` does not distinguish transports) — a revoked or expired tab is carried back to the login page by these existing linkages; the fixed sets of `sessionKindPath` and `httpOnly` stay as they are.

**For server authors.** Endpoints stay put, handlers stay put, authorization stays put; the runtime's changes converge to two. The runtime has exactly one upgrade entry, the terminal stream: `GET /api/terminals/<id>/stream` — verify the Cookie, ask the platform's terminal manager for `<id>`, check that its owner is the logged-in user, and hand the socket to the platform's `attachStream`. Everything in this chain except the handshake is platform code; terminals on machines already travel it with ids of the form `<tid>@<machine>@<user>` (the manager's `beyond` hook). The API socket is just one more id that `beyond` recognizes: `api-socket@<userId>`, answered with a reference whose owner is that user; the runtime checks owner as usual, so "whose socket this is" is proven by the runtime. The runtime's two changes: first, the handshake's authentication switches to a **non-renewing** validation (`Auth.validate` — everything `authenticateWithMeta` ascertains, minus renewal), so the handshake no longer quietly extends the session row; second, after the owner check, the **session token authenticated at handshake** is handed to the platform (`attachStream` gains an optional fifth parameter `credential`; terminal streams still pass nothing — only the reserved-id api-socket passes it). Thereafter, on each `call` frame received, the platform assembles a `Request`, stamps that credential onto it (the `cookie` header) **after** frame-header whitelist filtering, and routes it through **the same cookie gate as HTTP** into its own routes (`Http.fetch(request, { renew: false })`: the same set of route groups, the same gate logic, only without renewal and without writing Set-Cookie) — who the user is is always read by the gate from the credential, and `Http.fetchAs` plus the per-user cached route trees cease to exist. The `Response` is encoded into frames and sent back. One-shot responses encode as one frame; `text/event-stream` responses are encoded frame by frame, one per event, with comment lines (SSE heartbeats) dropped since the socket has its own ping; paths the platform refuses (`/api/auth`, `/api/hmr`, plus the `sessionKindPath` batch) answer 421, and the client switches to HTTP. In other words, one push delivers the socket to every installed shell; the handshake, the Origin check, and the owner check remain the very ones the runtime already has, and the only additions are the two: "hand the authenticated credential down" and "the handshake does not renew".

**For the machine layer.** Calls whose path begins with `/server/<machineId>/` go through the same forwarding layer as today's same-origin proxy, except that the forwarding layer maintains **one** socket per machine (dialing the terminal-stream path of `api-socket@admin` on the machine, dialed out over that machine's ssh session and authenticated with a minted 1-hour `cli` session — after the machine-side runtime checks owner, it likewise hands the session token to the machine's platform, whose gate validates per call; the `cli` session reads as `password` under the existing semantics, with permissions unchanged from before, only now earned by a real credential and bounded by the 1-hour minting cap); streaming calls are always forwarded through it, and frames coming back from the machine are passed verbatim to the browser socket that issued the call. When the machine is not connected, the answer is the same as the HTTP proxy's (`not_connected`); when the ssh session drops, all in-flight streams on that machine end with `end` and a reason, the browser re-sends with `last-event-id` per the reconnection flow, and the gap is filled from the machine's buffer. The machine-side `web_updated` is still ignored by the frontend (that is that machine's web, not this window's) — the forwarding layer is a transport and does not understand events.

**For users.** There is nothing new to look at. What changes: with more machines and more open session pages, the page no longer slows down; when a machine goes offline, its group in the sidebar grays out at once instead of sitting at a stale state until some refresh; when the session is revoked (password change, sign-out everywhere) or expires, the page returns to the login page within one call or one heartbeat period, instead of sitting there working as if nothing happened.

## Reference-level explanation
[reference-level-explanation]: #reference-level-explanation

### Two transports, one API

- Operations are defined as today's routes: method + path + query + body → status + body, or → an event stream. This proposal adds no new operations and removes no HTTP endpoint.
- **HTTP transport**: the status quo, preserved as is. The CLI uses only it; the browser uses it while the socket is not established, while it is reconnecting, or when the deployment environment (a reverse proxy that does not pass Upgrade through) blocks the socket.
- **WebSocket transport**: opened on the runtime's existing terminal-stream upgrade entry — `GET /api/terminals/api-socket@<userId>/stream`, `Upgrade: websocket` (`apiSocketPath(userId)` from `@prismshadow/penguin-server/api` does the spelling). The handshake is the terminal stream's handshake: session Cookie, Origin check (a WebSocket handshake is not subject to CORS; without the check, any page the user visits could open a socket with their Cookie), and the id's owner must be the logged-in user themself — an admin's Cookie cannot open `api-socket@alice`; the handshake's authentication uses the non-renewing `Auth.validate` (see "Entry, identity, and platform"). The server-to-machine hop dials `api-socket@admin` with a minted 1-hour `cli` session. Thereafter every call on the socket carries the session credential authenticated at handshake and enters the platform's routes through the same cookie gate; no credential is carried in frames, and none is accepted.
- At most one socket per tab; any number of concurrent calls ride it, each identified by a client-assigned `id`, and `id`s are never reused within the socket's lifetime.

### Frames

- Text frames only, one JSON document per frame. Binary frames are not used at this stage and are left for the terminal (see Future possibilities).
- Client → server: `{ id, call: { method, path, headers?, body? } }` starts a call; `{ id, cancel: true }` ends a streaming call in progress. `path` includes the query string; `headers` accepts only a whitelist (`last-event-id`, `accept`, `content-type`) — credentials come from the handshake, are not carried in frames, and are ignored if present; `body` is a JSON value; multipart bodies (attachment uploads) do not travel this transport and go over HTTP.
- Server → client: one-shot response `{ id, status, headers?, body }` (the body is encoded per the response `content-type`: JSON verbatim, text as a string; binary responses — file downloads — do not travel this transport: the caller receives `415` and falls back to HTTP); a streaming response first sends `{ id, status, stream: true }`, then one `{ id, event, eventId, data }` per event (`event` and `data` are SSE's `event:` / `data:`, and `eventId` is its `id:`), and finally `{ id, end: true, reason? }`. SSE comment lines are not forwarded.
- The server's handling on one socket is concurrent: calls do not queue behind one another, and streaming calls do not block one-shot calls.

### Entry, identity, and platform

- The handshake is the terminal-stream entry the runtime **already has** (`terminal/ws.ts`: Upgrade, Origin check, session Cookie, ask the platform for the id, check owner, hand over the socket). This proposal's runtime changes converge to two, both on this chain: **first**, the handshake's authentication switches from the renewing `authenticateWithMeta` to the new `Auth.validate(token)` — everything `authenticateWithMeta` ascertains (the row exists, is not expired, the user exists, the normalized `via` reading: `remote`→`token`, `cli`→`password`, `desktop`/`setup` verbatim) **minus renewal** — so the handshake goes from "opening a connection" to the same standing as an SSE heartbeat, "check once, no renewal"; **second**, after the owner check, the **session token authenticated at handshake** is handed to the platform verbatim: `PlatformApi.attachStream` gains an optional fifth parameter `credential?: string` (terminal streams still pass nothing; only the reserved-id api-socket passes it). The `PlatformIface` version is bumped along with the signature; the parameter is a pure addition — an old platform ignores it, a new runtime passes one more actual argument, and both sides hold at the JS layer. The credential is held only by the server and never enters a frame.
- Three places on the platform side: the terminal manager's `beyond` hook recognizes the reserved id `api-socket@<userId>` (`socket/ref.ts`) and answers with a reference whose owner is that user; `attachStream` recognizes the reference and runs the socket protocol for it (`socket/serve.ts`) — the shell's api-socket branch **fails closed**: if the handoff carries no credential (an old runtime), the socket is closed and no frame is served; `serveApiSocket` stamps the credential onto every `Request`'s Cookie header **after** frame-header whitelist filtering (`headers["cookie"] = SESSION_COOKIE + "=" + credential` — even a `cookie` header stuffed into a frame is dropped by the whitelist first; what gets stamped is the server's own copy), with the rest of the normalization unchanged (URL as canonical App host + `path`; method; JSON body; whitelisted headers). There are no new credentials, secrets, or authentication algorithms: the precondition for holding this socket is that the runtime already admitted the handshake, and what is handed down is the existing token the handshake already authenticated.
- Every `call` frame, once assembled into a `Request`, enters routing through **the same cookie gate as HTTP**: `Http.fetch` gains an optional `opts?: { renew?: boolean }` (the default allows renewal; the socket passes `false`); `authMiddleware` gains the same option — its cookie branch switches to `Auth.validate` and writes no Set-Cookie (the Bearer branch is naturally dead under the frame-header whitelist). `fetchAs`, the per-user cached route trees (`asUser`), and `enteredAs` are deleted — there is no longer a second entry taking a trusted `userId` as an argument; who the user is is always read by the gate from the credential. `HttpModule.setup` assembles two trees per server from the same set of route groups: the HTTP entry behind the renewing gate, the socket entry behind the same gate logic with `renew: false`. Authorization, validation, and error shapes are therefore identical to HTTP: a `404` on the socket is HTTP's `404`, and `403 human_required` is exactly HTTP's; `sessionVia` is the **true reading** the gate reads from the session row (no longer hardcoded `password`) — a Remote session obtained with a token stays token-level on the socket, and the human-exclusive writes guarded by `requireHuman` are rejected just as HTTP rejects them. `Response` encoding depends only on `content-type`: `text/event-stream` is encoded frame by frame per event (parsing the `id:` / `event:` / `data:` lines), everything else is handled as a one-shot response; paths the platform refuses (`/api/auth`, `/api/hmr`, plus the `sessionKindPath` paths — `/api/me/password`, `/api/desktop*`, `*/dirs/access`, `*/reveal`) answer `421 not_on_socket`, and the client switches to HTTP; `/api/me` and `/api/install` remain pinned to HTTP by the client. The whole protocol lives in the platform layer: one push reaches every installed shell, and every change from then on is also a push.
- **The renewal invariant (normative).** Only HTTP responses renew, and a renewal always comes with a Set-Cookie on that same response (`authMiddleware` already behaves so today and keeps it); the handshake does not renew (`Auth.validate`), socket calls do not renew (`renew: false`), the heartbeat does not renew (existing discipline). Socket responses carry no Set-Cookie — meaning here that **the current implementation does not write one on upgrade or frame responses, and this design does not depend on writing one there**; it is not a normative prohibition. As a result the row and the Cookie never fall out of sync: they expire together, or are refreshed together. A tab whose traffic is entirely on the socket has its session refreshed by **the batch of calls pinned to HTTP** — `/api/me` (`probeSession` on load and on focus), sign-in and sign-out, the `sessionKindPath` streams — and the Cookie refresh rides back with those responses; a page that uses only the socket all day and never regains focus logs out when the TTL runs out. This is the plain consequence of the "connected ≠ touched" policy, and it shares its origin with the SSE discipline.
- **Identity belongs to the session that opened it**: what is validated per call is the token handed down, not the browser's current Cookie. Another tab signing in as a different user replaces the browser Cookie, but an already-open socket's identity is unchanged and its original session row is not revoked — per-call validation passes as usual, semantically identical to today, where an SSE stream opened before the Cookie was swapped out keeps flowing; what carries the page over to the new identity is the client's own linkage (the `/api/me` response names the new user → `identityIs` closes the old socket, and the next call reopens under the new user). Multiple tabs of the same user = one Cookie, several sockets, not interfering with one another; one revocation (sign-out) reaps only the connections of that same session, while the other sessions carry on as usual.
- **Threat model and non-goals.** A holder of a local API token (a tool subprocess, anyone who can read the api-token file — i.e., administrator privileges): can exchange it for a Remote session, but stays token-level on the socket, gets 403 from `requireHuman` routes, and the 1-hour cap applies to open sockets. A holder of a revoked/expired session: the very next call gets 401, and with no calls the heartbeat closes the socket within at most one period (see "Reclamation and revocation"). Cross-origin pages: the handshake Origin check, unchanged. A modified client forging frames: frames cannot smuggle credentials in (whitelist drop comes first, stamping after), and the socket serves only the session that opened it. The platform itself (the plugin) is already trusted — `AuthService` lives in the platform, minting new sessions is already a platform capability, and handing it an existing token broadens no permission (this judgment is recorded under Drawbacks for challenge). Other OS users on the same machine are out of scope (the data root is the boundary). Non-goals: per-Session credentials (design PR #235, the structural successor), per-call proof of human presence, a new authentication service / credential type / registry / timer, changes to the frame protocol, changes to the CSRF model (`jsonOnlyWrites` applies to the stamped `Request`).

### Reclamation and revocation

- **Signing out of this session.** Row deleted → the socket's **very next call** gets 401 (a 401 on either transport triggers the client's global logout, which closes the socket); subscribed streams are `finish`ed by their own SSE heartbeat within at most one period.
- **`signOutEverywhere` (password change, user deletion).** All rows deleted, and sockets registered in the current-generation registry are closed **on the spot** (within the same call stack): sockets are registered in the **existing** `LiveStreams` registry (`end` = close the socket; registered into the registry of the App alive at attach time, deregistered when the connection closes), so `signOutEverywhere` now reaps API sockets as well, with no new registry added. The registry is generational with the App and rebuilt each generation: **sockets registered in the old generation are not in the new table, and reclamation across generations is not guaranteed to be immediate** — this is SSE's existing best-effort semantics, adopted here as is, with no separate rebinding designed. The backstops are the per-call 401 and the socket heartbeat's liveness check — neither goes through the registry, both ask the row directly, and both App generations read the same web.db, so a generation change cannot displace them.
- **Row expiry** (30-day TTL; Remote 1 hour). The next call gets 401; an idle socket with no calls is closed by the heartbeat's liveness check within at most one period — the existing heartbeat (20-second tick) gains one step, `sessionIsLive` (explicitly non-renewing), closing when not live, with no new timer. Reclaiming streaming calls needs no new code: `streamRevocation` already reads the Cookie from the request, and what it reads now is the stamped real token, so SSE's two-layer reclamation holds verbatim for streams on the socket.
- **Time-limit semantics (uniform throughout).** One period = `HEARTBEAT_MS` (on the order of 20 s); every upper bound is "at most one period after the event", and it is **not hard-real-time** — process scheduling and event-loop delays count separately; "on the spot" means only that the registry path initiates synchronously within the same call stack. On the same standing as SSE's reclamation.

### Resumption, heartbeat, backpressure

- A streaming call's resumption is the endpoint's own resumption: the `last-event-id` header goes into the `Request`, the endpoint replays from the bounded ring buffer, and when events have been pushed out of the buffer it first emits a `resync_required` event — exactly as on the HTTP transport. The client remembers the last `eventId` for every streaming call and re-sends with it after reconnecting.
- The server probes liveness with protocol-level pings, at the same constant interval as the SSE heartbeat, and each tick also runs one `sessionIsLive` check (non-renewing); if the row is gone or not live, the socket is closed per the "Reclamation and revocation" discipline; consecutive missed pongs close the socket, and all calls on it are treated as cancelled (streaming calls unsubscribed, one-shot calls' responses dropped). If no frame arrives within the same timescale, the client closes and reconnects on its own; reconnection uses exponential backoff, capped on the same order as the machine ssh reconnection cap.
- Backpressure: each socket has a send-buffer watermark. When the backlog crosses the watermark, the server ends the streaming call with the largest backlog (`end` with `reason: "lagging"`), and the client re-sends with `last-event-id` per the reconnection flow — what can be filled is filled from the buffer, what cannot goes through `resync_required`; there is no unbounded queuing, the same principle the terminal stream applies to lagging viewers.

### Machines

- Calls whose path begins with `/server/<machineId>/` enter the existing machine forwarding layer (the criteria and answers of `machines/proxy.ts` unchanged: a machine that is not connected gets `503 not_connected`; the browser's credentials do not cross over, the machine's do not come back).
- The forwarding layer maintains **at most one** socket per connected machine, to the `api-socket@admin` terminal-stream path on `ws://127.0.0.1:<remotePort>`: dialed out over that machine's connection (the dial in `transport/connection.ts`), authenticated with a 1-hour `cli` session minted by `remote-token.ts` — after the machine-side runtime checks owner, it likewise hands the session token to the machine's platform, whose gate validates per call: `via` reads as `password` under the existing semantics of `auth-token.ts`, with permissions identical to the bypass era, only now earned by a real credential and bounded by the 1-hour minting cap (minting expiry closes it via the heartbeat liveness check, the relay's next dial re-mints, and the ≤50-minute cache re-mints anyway) — established on first need, rising and falling with the ssh session; held machines persist with the session, unheld ones close under the same idle rules as sessions.
- Streaming calls are always forwarded over the machine socket: the `/server/<machineId>` prefix is stripped and the call is sent to the machine as a `call`, and frames coming back from the machine are forwarded with the browser-side `id` restored. If the ssh session drops, all in-flight streams on that machine end with `end` (`reason: "not_connected"`); the browser maintains its set of offline machines (`offlineMachineIds`) accordingly and re-sends per the reconnection flow once the session is back.
- Streaming calls **do not fall back to HTTP forwarding**: that would be one channel per machine per stream, and with many machines it walks right back into the wall this proposal tears down. When the socket cannot be had, the answer comes back immediately with a reason, and the browser re-sends on that stream's own backoff (doubling from 1 s up to 30 s, resetting once open): a machine refusing the handshake — no socket in the build, or an old runtime that opens and closes without serving a single frame (**this interpretation is newly proposed by this document**: the forwarding layer today does not distinguish "opened and immediately closed" from a mid-service closure; it must be added along with this document, after which the existing memory applies) — is remembered for one minute as needing an update, answering `502 machine_socket_refused`; a dial that neither opens nor fails within 10 s is torn down, answering `502 machine_socket_unavailable`; if the stream does not open within 8 s on an already-open socket (the socket still heartbeats but does not serve), the socket is torn down, answering `504 machine_stream_not_opened`. The two deadlines sum to less than the browser's own 20 s stream-open deadline.
- Sockets are cached by "machine + the ssh session that dialed it", not by machine alone: once the transport reopens the session, sockets on the old session (or dials not yet completed) are invalidated and closed, and the next stream re-dials over the new session. Every wait has a deadline — one stuck dial must not hold up every subsequent stream for that machine.
- One-shot calls may still take the existing HTTP forwarding at this stage (one SOCKS dial per request); moving them onto the machine socket is a pure optimization with no semantic change, left to the implementation as needed.

### Frontend

- `apiFetch` in `api/client.ts` issues calls over the socket when it is available and over HTTP otherwise; the two paths have the same error shape (`ApiError` with status and body), and callers are oblivious. Multipart bodies and binary responses are pinned to HTTP.
- `api/sse.ts` is superseded by the socket client: a singleton, opened lazily, its lifetime managed by a count of in-flight calls; the signatures of `openUserEvents` / `openSessionStream` are unchanged. The effect in `state/sessions.tsx` that was "one stream per machine" becomes "one streaming call per machine".
- The socket closes on page unload or when the last call ends; it stays up while the tab is in the background, kept alive by the heartbeat.

### Upgrades, mismatches, and release units

- **Plugin reinstall (new inner App, same shell) and hot push (new shell) are two different things.** Plugin reinstall: neither the shell nor open sockets break, and each call keeps resolving "the App of this moment" — the new generation takes over in-flight calls at once, the `renew: false` front gate is entered as usual, and permissions synchronize with the facts of the rows in the shared web.db; but a reinstall, like a push, **rebuilds the App-scoped `LiveStreams` registry** (rebuilt each generation; the previous generation is not in the new table) — sockets registered in the old generation are not guaranteed to be reaped immediately by `signOutEverywhere`, with the backstops under "Reclamation and revocation". Hot push: the new shell's `create` claims the previous shell's socket resources and, after the grace period (`RECONNECT_GRACE_MS`), closes all of its API sockets with 1012; the previous shell's inner has already been disposed of by the push, and calls within the grace period answer 503 per the shell's existing semantics; the client reconnects carrying each stream's `last-event-id`, and the reconnect hands the credential over again through the fresh handshake — the closure does not migrate across shells; reconnecting is the handoff.
- **Mismatch matrix (fail closed).** Runtime = the application build carrying `terminal/ws.ts`/`PlatformApi`; platform = the pushed bundle:

| Runtime | Platform | Behavior |
| --- | --- | --- |
| Old | Old | The status quo (no degradation) |
| New | Old | The old platform ignores the fifth parameter and keeps going through the old gate — equivalent to the status quo, with no side effects from the new runtime |
| Old | New | The platform gets no credential → the api-socket closes immediately; browser tabs fall back to HTTP/SSE along the existing give-up path; machine dials are read as refused → `502`; **no path serves calls without a credential** |
| New | New | This design |

- **Release units (atomic acceptance).** The moment `fetchAs` is deleted, the platform code cannot compile unless the caller rewrites are in the same tree — **interface deletion, caller switchover, credential stamping, and the tests belong to one atomic, acceptance-testable release batch**; we do not claim each editing step can be green on its own. Hence only two release units: **the platform unit** (one hot push: all platform-side changes and tests compile and pass the suite in the same tree, and the "old runtime + new platform" behavior of the mismatch matrix is verified — where "opened-and-immediately-closed = refused" is an interpretation newly added by this unit, not an existing guarantee); **the runtime unit** (one application build: `terminal/ws.ts` switches to `Auth.validate`, the fifth `attachStream` parameter, and the `PlatformApi`/`PlatformIface` version bumps). The two units may land in either order (the mismatch matrix catches it), and neither unit is split internally.
- The editing order only says which lines move first within a unit: ① `auth/service.ts`: `Auth.validate`; ② `auth/middleware.ts`: `{ renew: false }`; ③ `http/app.ts`: delete `fetchAs`/`asUser`/`enteredAs`, two trees for two entries; ④ `hmr/platform.ts`: the shell's api-socket branch (fifth parameter, fail closed, the stamping closure); ⑤ `socket/serve.ts`: stamping, registry registration, and the heartbeat gains `sessionIsLive`; ⑥ `machines/machine-sockets.ts`: add the "opened but serves no frame, then closed = refused" interpretation; ⑦ `api/types.ts`: update only the comment and rationale of `sessionKindPath` (the set does not move); ⑧ tests: rewrite the bypass assertions as credential-gate assertions and extend them per the matrix below, with not one existing case deleted; the frontend has no mandatory changes (the linkages already exist).

## Drawbacks
[drawbacks]: #drawbacks

- Reconnection and resumption logic moves from the browser's built-in `EventSource` into our own code: backoff, re-sending, and `eventId` memory all have to be written and tested.
- One socket is a single point: when it breaks, all calls break at once. But it also resumes all at once — easier to reason about than today's N connections each breaking, resuming, and gambling on its own.
- The socket enters through the terminal stream's doorway: the address has the shape of a terminal id (`api-socket@<userId>`) rather than a path of its own. That is the result of putting "no new upgrade entry" ahead of "a pretty path"; if the runtime is ever rebuilt for other reasons, a `/api/socket` alias can be added, but the reserved id must stay — installed shells recognize only it.
- Frame encoding has to parse SSE text and re-encode it as JSON, one extra encode/decode round; the cost is negligible next to the N connections it saves, but it is indeed a layer.
- The machine forwarding layer holds one more class of long-lived connection (one per machine), whose lifetime must be strictly aligned with the ssh session, or "the session is dead, the socket lives on" ghost calls appear.
- **Per-call cost**: each socket call pays one extra row lookup + user lookup — HTTP already pays the same on every request, and SSE pays it per stream per tick; but this is indeed an addition relative to the bypass era's "one cached tree per user, one `findById` at the gate".
- **The credential enters the platform**: the handshake token is handed to pushed code. The threat-model argument shows no privilege broadening — `AuthService.issueSession` is already in the platform's hands — but "the platform holds a ready-made token" and "the platform can mint new rows" are still two different things on paper; this judgment accepts review.
- **Two trees**: the same set of route groups is mounted twice per server (one gate per transport); far cheaper than "one per user", but still duplicate mounting; if that feels heavy, an implementation can explore a single tree + discrimination inside the gate (it needs an unforgeable in-process marker; this document does not make that choice for the implementation).
- **A tab on the socket all day that never regains focus logs out at TTL**: the plain consequence of the "connected ≠ touched" policy, and a UX regression for the occasional long-open page; the alternative (a reminder frame triggering an HTTP refresh) would let idle pages renew too, contradicting the same policy, so it is not taken.
- **The upgrade window**: while an old runtime carries the new platform, sockets refuse to open, and those installations fall back to the 1+N SSE shape (the very problem this document solves comes back temporarily) until the application is updated; a degradation, not a breakage.

## Rationale and alternatives
[rationale-and-alternatives]: #rationale-and-alternatives

- **A dedicated subscription protocol (`subscribe { channel }`), parallel to REST.** This proposal's previous draft. Not chosen: that would be a second API surface — channels with their own identifiers, their own authorization logic, their own error codes, each a restatement of existing endpoints, and from then on the two would have to evolve in lockstep. Making the socket a **transport** keeps the endpoints as the only API surface, with authorization and error shapes consistent by construction, and the runtime needs to understand no endpoint.
- **Server-side fan-in only, with SSE still the transport.** The browser drops from `1 + N` connections to `1 + open session pages`; the six-connection quota usually suffices, and the change is minimal. Not chosen as the end state: the count still grows with session pages, folding in the terminal is out of the question, and half-dead connections still get no protocol-level liveness probing.
- **HTTP/2.** Multiplexing many streams over one connection is its whole job, and the frontend would not change a line. Not viable: browsers speak HTTP/2 only over TLS, while the desktop sits on loopback and the phone goes through a tunnel — all plaintext HTTP; bringing in certificates for this is another problem set entirely.
- **One WebSocket per thing.** The quota goes from six to two hundred-odd and the symptom disappears; but the same-origin proxy would have to learn to pass Upgrade through, machines would still be dialed from the browser one by one, and liveness probing of half-dead connections would have to be done once per connection. The wall is pushed farther away, not torn down.
- **Do nothing.** Many machines plus many session pages makes the page slow; this has already happened.

We choose "one socket + equivalent asynchronous API calls" because it turns the connection count from a variable that grows with objects into the constant 1, introduces no second API surface, and hands the machine half back, as a freebie, to the layer that already holds the ssh sessions.

**Why identity goes through the front gate.** This document's previous draft let the socket enter as "a user proven by the runtime": `Http.fetchAs(userId, request)` re-mounted the whole set of route groups behind that user's gate, hardcoded `sessionVia` as `password`, and never consulted the session — sold as "zero runtime changes". Checked against the implementation (impl #912), it was judged untenable, with four gaps sharing one root: a Remote session obtained with a token passes `requireHuman` with a human's permissions on the socket (privilege escalation); after a password change or user deletion, already-open sockets keep serving (no revocation); the session row expires under an open socket with no one noticing (no expiry check); the handshake renews while socket responses cannot carry Set-Cookie back (renewal mismatch — the row can outlive the Cookie that proves it). The root disease is structural: a second entry taking a trusted `userId` as an argument forces every future route to remember that "the `password` on this path is an assumption"; the server-side `sessionKindPath` blacklist exists for the sole reason of shielding, on behalf of that assumption, the paths whose answers vary with `via` — and it has already leaked the `requireHuman` batch. Blacklists keep growing; credentials need no blacklist — permissions are not patched up with a sensitive-route blacklist.

- **Keep `fetchAs`, pass the true `via` in with the handshake** (fixes only the escalation): `password` becomes honest, but the trust shape is unchanged — still "a trusted userId at the door" — and revocation and expiry would still need bolt-on mechanisms. Fixing one stamp does not remove a doorway.
- **Check liveness only in the heartbeat, no per-call gate**: calls between a revocation and the next tick are still served, and `sessionVia` between ticks remains an assumption. SSE can accept tick-level because its streams are read-only; the socket carries writes. The per-call cost is equivalent to HTTP's, and there is no reason to be looser than HTTP.
- **Mint a socket-specific session at handshake**: a new credential type, a new revocation surface, one copy each for the relay and the machines — precisely violating "no new credentials"; "no new credentials" was itself a selling point, and it stays.
- **Write Set-Cookie on the upgrade response to even out renewal**: the current implementation does not do this, and this design does not stake the authentication model on "browsers process the Set-Cookie inside an upgrade response", a behavior this repository does not rely on; "renewal rides only with ordinary HTTP responses" is easier to state and easier to test — the simpler side wins.
- **Do nothing**: the escalation and the non-revocation stay as they are.

We choose "credentials through the front gate" because it collapses the bypass era's four gaps into the removal of **one and the same** cause: identity is read from the credential inside the gate, and authorization, `via`, and the per-call revocation/expiry checks are all natural extensions of existing machinery — reclamation outside the current registry generation follows the existing best-effort semantics, backstopped by per-call checks and the heartbeat — requiring no blacklist to keep pace and no new trust surface.

## Prior art
[prior-art]: #prior-art

- This repository: the terminal stream's frame header has carried a `slot` byte since day one, with a comment noting that "multiplexing all of a page's terminals onto one socket is the obvious next step"; `machines/terminal-relay.ts` already bridges the browser's terminal sockets to machines server-side with the `ws` library — machine fan-in follows its shape; `ChannelHub`'s monotonic ids and ring buffer, and SSE's `resync_required`, are this proposal's resumption contract.
- This repository's own SSE (`http/sse.ts`, `auth/live-streams.ts`): the three disciplines of registry reclamation + re-check every tick + never renew, all adopted by the socket one by one — on this same server, the authentication discipline for long-lived connections was settled long ago, and the socket is merely late. The cookie gate itself (`auth/middleware.ts`; the route-group-gate revision): the socket joins it rather than copying it in parallel.
- VS Code Remote: one connection between the editor and the remote, multiplexing every service over it; the extension host, terminals, and the file system are all channels on it.
- Phoenix Channels / Socket.IO: one socket, subscribe by topic, each message tagged with its topic; after a reconnect, the client re-joins.

## Unresolved questions
[unresolved-questions]: #unresolved-questions

- ~~Whether the terminal folds in as part of this proposal's batch~~ Resolved: **the terminal does not fold in** — the terminal stream is a throughput-first data plane, the API socket is a latency-first control plane, and one TCP stream cannot deliver both (head-of-line blocking, one shared send buffer, backpressure measurable only per whole connection); and a WebSocket does not consume the browser's six-HTTP/1.1 quota anyway, so folding it in gains nothing for the problem this proposal solves. Each open terminal panel gets its own WebSocket, the count bounded by the number of panels.
- Whether one-shot calls go over the socket in the first batch. The recommendation is yes: the transport switch in `apiFetch` is one change, and it makes "zero HTTP connections while the socket is up" true; but if the implementation order demands it, migrating only the streaming calls first is also coherent.
- Whether machines' one-shot calls migrate onto the machine socket (see the last item of "Machines") is left to the implementation.
- The concrete values of the send-buffer watermark and the ping interval are left to the implementation, to be aligned with the terminal stream's and SSE's existing constants.
- The fate of `sessionKindPath`: once `via` becomes a true reading, its original server-side reason (shielding, on behalf of the "assumed password", the paths whose answers vary with `via`) disappears; keeping it serves as a client contract (identity discovery and the Cookie-setting flows stay on HTTP) and defense in depth. The recommendation for this round is to **freeze it in place, no further growth**, and abolish it together once per-Session credentials (design PR #235) land — whether to accept this pace is for reviewers to decide.
- Close codes and reason strings: the code values for revocation closure, no-credential refusal, and expiry closure (and the "opened but never served, then closed = refused" interpretation) are left to the implementation round, to be set per the `ws` library and the existing close semantics; the behavioral requirements are already fixed in the Reference section.
- Whether `Auth.validate` should also replace the `sessionIsLive` currently used by the SSE heartbeat (the latter does not check the user row) — unnecessary: when a user is deleted, the row goes with the foreign-key cascade, so the two readings are equivalent; left to the implementation round should a counterexample appear.

## Future possibilities
[future-possibilities]: #future-possibilities

- **Multiplexing the terminal, if ever needed.** The terminal does not fold into the API socket (see Unresolved questions), but if "one WebSocket per panel" itself ever becomes a problem, the right shape is **all terminals sharing one separate binary socket** — the `slot` byte in the frame header has been reserved for this since day one — not folding into this JSON control plane.
- **The socket on the CLI.** It speaks the same API, so switching transports is just switching clients; long-running conversations like `penguin chat` could then reuse the same client. Even then the HTTP endpoints need not go away — they are one of the transports.
- **A third transport.** An API server with two transports can have a third: stdio (for editor plugins on this machine), or a Unix socket (for the local CLI, with no authentication). This proposal does not do it; it only notes that the shape allows it.
- **per-Session credentials (design PR #235).** Once landed, `requireHuman` becomes a structural judgment ("a Session's credentials are refused, a human login is not" — quoting the original comment), and the socket needs no further change: a per-Session token is just one more `via` the gate will honestly read out. At that point, `sessionKindPath` and the maintenance of the "human-only writes" blacklist can be abolished together.
