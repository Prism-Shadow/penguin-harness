## Summary
[summary]: #summary

The authorization model of the harness splits capability boundaries across two surfaces: the **CLI surface** for local system permissions and the **HTTP surface** for application-level Penguin permissions. The **CLI surface** executes locally in the caller's process with the current operating system environment (terminal, TTY, filesystem) as its permission core, and obtains Penguin capabilities by calling the HTTP surface. The **HTTP surface** executes in the server process, enforcing Penguin permissions through named route `id`s, declarative role trees, context-aware auth refiners, and role-bound authorization sessions. Local read access to the Penguin Home Root (`PENGUIN_HOME`) is equivalent to Penguin administrator authority (`Access to Penguin Home Root = penguin admin`).

## Motivation
[motivation]: #motivation

### Two surfaces guard two distinct trust boundaries

Terminal commands and server endpoints run in different contexts and draw authority from different sources. The CLI runs inside the caller's own process and working directory, governed by the operating system user, TTY, and filesystem namespace. The HTTP surface runs inside the server process, facing callers across processes or networks, and relies on request credentials to identify the caller and bound what it may touch.

### Direct data-root mutation from the CLI bypasses HTTP authorization

When business commands read or write configuration files and databases directly inside the CLI process, the role and scope checks on the HTTP surface cannot intervene. Routing all Penguin capabilities through the HTTP surface — leaving only local server lifecycle, web launcher, and local token/version inspection commands to run directly on the host — concentrates application authorization in a single enforcement point.

### Agent calls need credentials scoped by route ID

Agents with different responsibilities need different slices of the HTTP surface. As an example, a default conversational Agent manages sessions, workspaces, and its own schedule and workbench; an Agent creator or plugin maintainer manages skills, models, or plugins; an organization employee Agent calls organization collaboration endpoints. Issuing role-bound session tokens to each Agent and registering every HTTP route with a stable `id` allows the authorization layer to grant access by route `id` sets, context refiners, and project boundaries.

## Guide-level explanation
[guide-level-explanation]: #guide-level-explanation

### Permission philosophy: CLI = system permissions, HTTP = penguin permissions

Two rules anchor permissions across the harness: **CLI = system permissions**, and **HTTP = penguin permissions**.

- The **CLI surface** runs locally with the current system environment (terminal, TTY, fs) as its permission core. Which local files it can read, which terminal stream it attaches to, and which local sockets it can reach are determined by the operating system permissions of the current process. Whenever the CLI performs Penguin operations (managing Agents, sessions, model configurations, vault secrets, schedules, plugins, or runtime version reports), it acts as an HTTP client of the server.
- The **HTTP surface** guards all Penguin capabilities. The server authenticates the credential on each request, resolves the caller's identity and role grant, and checks the target route's `id`, project scope, and bound auth refiners before running the handler.

### Three credential classes on the HTTP surface

The HTTP surface recognizes three classes of credentials:

1. **Human login sessions (`auth_sessions`)**: issued when a human user signs in through `/api/auth/login` or `/api/auth/setup`, carried via the `penguin_session` cookie or a session Bearer token, and resolved to the human user's identity and administrator flag.
2. **Local instance API token (`<root>/api-token`)**: generated by the server inside `PENGUIN_HOME` with mode `0600`, accepted as a Bearer token on both `"token"` and `"user"` routes with administrator authority.
3. **Role-bound authorization sessions (`pga_...` in `auth_role_sessions`)**: issued to an Agent (or a role-scoped caller) with a bound role and permission generation, accepted as a Bearer token on `"user"` routes and governed by route-level authorization checks.

### Access to Penguin Home Root = penguin admin

Read access to the Penguin Home Root (`PENGUIN_HOME`) on the local filesystem is equivalent to holding `penguin admin` authority for that instance.

When the server starts, it writes `api-token` (mode `0600`) and `server.lock` inside the home root. Any local process that can read the home root can read `api-token` (for example via `penguin auth token`) to call the HTTP surface as an administrator, and can manage the local server lifecycle directly. Environments that restrict a caller below administrator isolate the home root at the filesystem level.

### Example: dual-surface cooperation inside a Sandbox

An example of an Agent running commands inside a sandbox illustrates how the two surfaces work together:

1. **Provisioning the sandbox view and Agent token**: When the host spawns a tool subprocess inside a sandbox, it mounts a restricted filesystem view (the workspace and sandbox temp directories are accessible, while the host's Penguin Home Root is unmounted) and injects the Agent's role-bound session token `PENGUIN_API_TOKEN` (`pga_...`) into the environment.
2. **Executing system operations from the sandbox perspective (CLI = system permissions)**: When the Agent invokes shell commands or the `penguin` CLI inside the sandbox, the CLI runs locally inside the sandboxed process and operates within the sandbox's terminal and filesystem view.
3. **Acquiring Penguin capabilities over HTTP (HTTP = penguin permissions)**: When the CLI inside the sandbox calls the server, it authenticates with `PENGUIN_API_TOKEN`. The server verifies the Agent role, route `id` grant, and refiner rules attached to that token, permitting only the endpoints granted to that role within the Agent's own project.

### Route ID registration and the declarative Role Tree (`ROLE_TREE`)

Every HTTP route contributed to the `HttpModule.routes` slot carries a dotted `id` that serves as a leaf permission in the role tree. The following example shows two route contributions in the `session` domain:

```ts
@Component({
  contributes: {
    "HttpModule.routes": [
      { id: "session.list", method: "GET", prefix: "/api/projects/:projectId/agents/:agentId/sessions", auth: "user", order: 250 },
      { id: "session.create", method: "POST", prefix: "/api/projects/:projectId/agents/:agentId/sessions", auth: "user", order: 250 },
    ],
  },
})
```

A route component binds single-endpoint contributions to handlers on its `Hono` router using `endpointOf(group, method, subPath)`.

Role presets are organized as a declarative directed acyclic role tree (`ROLE_TREE`):

- **Three-tier domain role nodes**: Every domain (`session`, `workspace`, `agent`, `memory`, `schedule`, `skill`, `plugin`, `workbench`, `model`, `vault`, `trace`, `benchmark`, `org`, `browser`, `machine`, `agents.messaging`, `messaging`, `project`, `command`, `system`, `admin`) defines `<domain>.read`, `<domain>.maintain`, and `<domain>.all` nodes. `<domain>.maintain` inherits `<domain>.read` and adds day-to-day write and execution routes; `<domain>.all` inherits `<domain>.maintain` and adds deletion and administrative routes.
- **Composite workflow role nodes**: Built-in workflow personas (`none`, `readonly`, `general`, `general-with-ask`, `agent-creator`, `plugin-maintainer`, `workbench-maintainer`, `system-maintainer`, `admin`, `full-permissions`) sit higher in the same tree, composing domain role nodes through their `children` array.
- **Auth Refiners (`<roleOrRoute>@<refinerId>`)**: Any role reference or extra grant entry may carry an `@<refinerId>` suffix (for example `agent.maintain@self` or `agent.maintain@withAsk`), binding the granted write routes to a named `AuthRefiner` component.

Each role-bound session binds a role identifier and a generation-cached grant. `expandRoleGrant(role, extraGrants)` walks the role tree to build the effective `ReadonlySet<string>` of route `id`s (`apiIds`), pre-compiled refiner bindings (`routeRefiners`), and the capability flags (`allEndpoints`, `agentApi`).

## Reference-level explanation
[reference-level-explanation]: #reference-level-explanation

### HTTP route contribution shape and `endpointOf`

The data shape for the `HttpModule.routes` slot contains the following fields:

- `id: string` — the unique identifier of the route or route group, named by `<domain>.<action>` or `<domain>.<subdomain>.<action>` (for example `session.list`, `workspace.readFile`, `command.run`, `model.updateConfig`, `vault.set`, `org.ticket.start`).
- `method?: "GET" | "POST" | "PUT" | "PATCH" | "DELETE" | "ALL"` — an optional single-method constraint. When present, the host mounts the handler only for that HTTP method and path; when omitted, the host mounts the sub-router for the prefix.
- `prefix: string` — the path pattern mounted on the HTTP application.
- `auth: "user" | "token" | "none"` — the authentication gate for the route (`"user"` accepts a human login session, the local API token, or an authorized role-bound session; `"token"` accepts only the local API token; `"none"` is public).
- `order: number` — the mount order on the HTTP application.
- `role?: string` and `roles?: readonly string[]` — optional role bindings (supporting `<roleId>@<refinerId>`, such as `"readonly"` or `["myPlugin.maintain", "general@self"]`) that grant this route directly to the named role nodes. Route IDs and role bindings use explicit identifiers; wildcard patterns (`*`) are rejected.

When a component defines several endpoints on one `Hono` group, `endpointOf(group, method, subPath)` builds a single-route `Hono` wrapper that copies the group's top-level `ALL /*` middleware and `errorHandler` while dispatching only the declared method and path. This keeps related handlers in one component while giving every endpoint its own route `id` in the manifest.

### Extensible Role Registry (`RoleRegistry`), `roles`, and `roleBindings` slots

The role tree and route bindings are assembled through declarative module contributions (`AgentAuthPermissionProvider` contributes the built-in composite persona roles, and each feature module or external plugin contributes its own domain roles, route `role` declarations, and `roleBindings`):

1. **Role node contributions (`HttpModule.roles` / `AgentAuthPermissionProvider.roles`)**: Components contribute `RoleContribution` entries to define new role nodes or extend existing roles additively. The following example shows a plugin contributing `.read` and `.maintain` role nodes and attaching them to composite parent roles:

```ts
@Component({
  contributes: {
    "HttpModule.roles": [
      {
        id: "myPlugin.read",
        routes: ["myPlugin.items.list"],
        parents: ["readonly"],
      },
      {
        id: "myPlugin.maintain",
        children: ["myPlugin.read"],
        routes: ["myPlugin.items.update"],
        parents: ["general@self", "plugin-maintainer", "system-maintainer"],
      },
    ],
  },
})
```

- `role?: string` — the target role ID, defaulting to the contribution entry's `id`. When multiple modules extend the same existing role (such as `"readonly"`), each keeps a globally unique contribution `id` while targeting the shared role via `role`.
- `children?: readonly string[]`, `routes?: readonly string[]`, `flags?: RoleFlags` — merged by set union into the target role node. Every route and role identifier is explicit; wildcard patterns (`*`) are rejected at registration and grant evaluation time.
- `parents?: readonly string[]` — attaches the target role into each named parent role's `children` (supporting an optional `@<refinerId>` suffix on the parent entry, for example `"general@self"`, which injects `<role>@self` into `general`).

2. **Unified `role -> http` binding contributions (`HttpModule.roleBindings` / `AgentAuthPermissionProvider.roleBindings`)**: Modules can contribute `RoleHttpBindingContribution` entries separately from route definitions to bind roles to HTTP route IDs in one place:

- `role?: string` and `routes?: readonly string[]` — binds a single role node (supporting `<roleId>@<refinerId>`) to an explicit list of HTTP route IDs.
- `bindings?: Readonly<Record<string, readonly string[]>>` — batch-maps multiple role identifiers to their explicit lists of HTTP route IDs.
- `aliases?: Readonly<Record<string, string>>` — registers route ID prefix aliases.

### Declarative Role Tree (`ROLE_TREE`) and permission scopes

Each node in the role tree (`RoleTreeNode`) consists of child role references (`children`), directly granted leaf route IDs (`routes`), and capability flags (`flags`).

Every functional domain follows a three-tier progression:

| Domain Role Tier | Tree Children (`children`) | Directly Granted Leaf Routes (`routes`) |
| --- | --- | --- |
| `<domain>.read` | `[]` | Read-only queries, listings, and event streams in the domain (for example `session.list`, `session.get`, `session.stream`) |
| `<domain>.maintain` | `["<domain>.read"]` | Creation, update, execution, and collaboration routes in the domain (for example `session.create`, `session.runTask`, `session.steer`) |
| `<domain>.all` | `["<domain>.maintain"]` | Deletion, purge, and administrative routes in the domain (for example `session.delete`, `session.deleteArchived`) |

Composite roles combine these domain nodes and capability flags into standing workflow personas:

| Composite Role | Child Roles (`children`) | `allEndpoints` | `agentApi` (passes `requireHuman`) |
| --- | --- | --- | --- |
| `none` | `[]` | `false` | `false` |
| `readonly` | All domain `*.read` nodes | `false` | `false` |
| `general` (default) | `readonly` + `session.maintain`, `workspace.maintain`, `agent.maintain@self`, `memory.maintain@self`, `schedule.maintain@self`, `workbench.maintain@self`, `org.maintain`, `browser.maintain` | `false` | `false` |
| `general-with-ask` | `general` + `agent.maintain@withAsk`, `memory.maintain@withAsk`, `schedule.maintain@withAsk`, `workbench.maintain@withAsk`, `skill.maintain@withAsk`, `plugin.maintain@withAsk`, `model.maintain@withAsk`, `vault.maintain@withAsk`, `trace.maintain@withAsk`, `benchmark.maintain@withAsk`, `machine.maintain@withAsk`, `agents.messaging.maintain@withAsk`, `messaging.maintain@withAsk` | `false` | `false` |
| `agent-creator` | `general` + `agent.maintain`, `memory.maintain`, `schedule.maintain`, `skill.maintain`, `model.maintain`, `vault.maintain`, `agents.messaging.maintain`, `messaging.maintain` | `false` | `false` |
| `plugin-maintainer` | `general` + `plugin.maintain`, `skill.maintain`, `workbench.maintain` | `false` | `false` |
| `workbench-maintainer` | `general` + `workbench.maintain` | `false` | `false` |
| `system-maintainer` | `general`, `agent-creator`, `plugin-maintainer`, `workbench-maintainer` + `trace.maintain`, `benchmark.maintain`, `machine.maintain` | `false` | `true` |
| `admin` | `system-maintainer` + all domain `*.all` nodes | `true` | `true` (inherited from `system-maintainer`) |
| `full-permissions` | `["admin"]` | `true` | `true` |

### Auth Refiners (`<roleOrRoute>@<refinerId>`) and priority-ordered overrides

An Auth Refiner (`AuthRefiner`) is a lightweight authorization component contributed to the `HttpModule.authRefiners` slot and referenced via `<roleOrRoute>@<refinerId>` (for example `agent.maintain@self` or `agent.maintain@withAsk`). The following example shows the built-in `self` refiner:

```ts
@Component({
  contributes: {
    "HttpModule.authRefiners": [
      { id: "self", scope: ["agent.", "memory.", "schedule.", "workbench."], order: 1001 },
    ],
  },
})
export class AuthSelfRefiner {
  @Bind("self") readonly refiner: AuthRefiner = this;
  async authenticate(
    ctx: AuthRefinerContext,
    action: AuthRefinerAction,
    request: Request,
  ): Promise<boolean> {
    if (action.params.agentId !== undefined) {
      return action.params.agentId === ctx.agentId;
    }
    return !action.routeId.startsWith("agent.");
  }
}
```

- **Explicit `scope` declaration and O(1) dispatch**: Each refiner declares the route IDs, role node names, or domain prefixes (such as `["agent."]`) it covers. `AuthRefinerRegistry` compiles these scopes into hash sets and prefix tables at startup and evaluates only the `refinerId`s bound to the matched `routeId`. For self-scoped `agent.*` write routes, `self` requires a verified `action.params.agentId === ctx.agentId` target and fails closed when `agentId` is absent from the route parameters (such as project-level `agent.create`), allowing `@withAsk` or an explicit `agent-creator` role grant to govern new-Agent creation.
- **Priority-list override**: Contributions to `HttpModule.authRefiners` are collected in module `children` list order and stably sorted by `order ?? 0` (built-in `AuthWithAskRefiner` and `AuthSelfRefiner` use `1000+` so custom and plugin refiners override them by default). Earlier entries in the list override later entries with the same `id` whenever their declared `scope` matches the route, falling back to later entries for routes outside a narrower custom scope.
- **Multi-refiner evaluation and `@withAsk` escalation**: When a route is bound to multiple refiners (such as `["self", "withAsk"]` on `agent.maintain` under `general-with-ask`), non-interactive refiners (`self`) run first; if a non-interactive refiner approves the action, the request succeeds immediately without prompting. Only when non-interactive refiners decline does evaluation fall back to `AuthWithAskRefiner` (`@withAsk`), which requests human approval and supports three decision scopes: `allowed_once` (permits the current call), `allowed_for_agent` (persists a session-scoped grant for the current Agent session), and `always_allowed` (persists the grant into `auth_generations.allowed_apis` and bumps the subject's generation).
- **Failure and mismatch safety**: Referencing an undefined `@<refinerId>` is rejected immediately with `403 auth_refiner_undefined`. If a refiner in the session fails to match the target action's scope or throws an error, the server returns `403 auth_refiner_mismatch` and instructs the user to start the Agent with `admin` permission to repair its authorization configuration. Inherited `<domain>.read` tiers remain unconditional when expanding `<domain>.maintain@<refinerId>`, and any unconditional grant on the same route supersedes a refined grant.

### Authorization sessions and generation re-derivation

The authorization session mechanism decouples **session credentials** (`auth_role_sessions`) from the subject's **current permission generation** (`auth_generations`), serving Agent sessions today and extending naturally to role-scoped human user sessions:

- **Session records (`auth_role_sessions`)**: store only the SHA-256 hash of the raw token (the raw `pga_...` token is returned only once at issuance), the subject identity (`subject_id`, `subject_kind`), `project_id`, `agent_id`, the `role` and `generation` at issuance, `created_at`, `expires_at`, and `last_used_at`.
- **Permission generation records (`auth_generations`)**: track the subject's current `generation`, current `role`, and `allowed_apis` (a JSON array of persisted grant expressions, which may include route IDs, role IDs, and `<roleOrRoute>@<refinerId>` entries).

When a request arrives with a role-bound session Bearer token, the authentication layer verifies that the session is unexpired, reads the subject's current generation record, and resolves the cached expanded grant (`{ role, generation, allEndpoints, agentApi, apiIds, routeRefiners }`) partitioned per subject (`subject_id` / `(projectId, agentId)`) and keyed by `(subject_id, generation, role, registryVersion, sessionExtraKey)`. As long as that subject's `generation`, role, role registry version, and session-scoped extra grants are unchanged, requests reuse the subject's cached grant for O(1) lookups; updating a subject's role or `allowed_apis` via `bumpGeneration` invalidates that subject's cache on the next request without re-issuing the token. Deactivating or deleting a subject revokes all of its active sessions and its generation state in one step.

### HTTP authentication and route-level authorization

Every protected request entering `HttpModule` passes through two checks:

1. **Authentication**:
   - A request carrying a valid human login session (`penguin_session` cookie or Bearer token in `auth_sessions`) or the local instance API token (`<root>/api-token`) authenticates with that human user's identity (`c.var.user`).
   - On `auth: "user"` routes, a Bearer token matching `AgentAuthService.authenticate(bearer, now)` populates `c.var.agentAuth` with `{ tokenHash, projectId, agentId, grant, agentApi }` and maps the project owner (or admin fallback) as `c.var.user` (preserving `isAdmin: true` at authentication time only when `grant.allEndpoints === true`).
2. **Route Authorization**:
   - Human user requests proceed under standard user and administrator checks.
   - Role-bound Agent requests (`c.var.agentAuth` present) run `checkRouteAuth(c, route.id)` before the route handler:
     - Endpoint check: requires `grant.allEndpoints === true` or an exact `grant.apiIds.has(routeId)` match, returning `403 permission_required` otherwise.
     - Project isolation check: when `grant.allEndpoints === false` and the route carries a `:projectId` path parameter, `:projectId` must equal `agentAuth.projectId`, returning `403 permission_required` otherwise. Collection routes that do not carry a `:projectId` parameter (such as `project.list`) are gated by their route `id` grant (`project.read`) and filter returned records to `agentAuth.projectId` unless `grant.allEndpoints === true`.
     - Auth Refiner check: when the route carries refiner bindings (such as `<domain>.maintain@self` or `<domain>.maintain@withAsk`), evaluates the bound `AuthRefiner` components according to the multi-refiner order described above.
     - Post-gate user context elevation: once a route passes endpoint, project isolation, and Auth Refiner checks, for routes outside `session.*` and `usage.*` the gate elevates `c.var.user.isAdmin = true` so downstream handlers authorized by the route tree and refiners can execute without legacy admin-only rejections.
     - Human-only gate (`requireHuman`): permits Agent requests only when `agentAuth.agentApi === true` (`system-maintainer`, `admin`, or `full-permissions`), returning `403 human_required` otherwise.
     - Source module diagnostics on failure: every role, route, `role -> http` binding, and `AuthRefiner` registration records the contributing module's identifier (`sourceModule`, populated from the kernel contribution source `c.from`). When authorization fails, the server logs the failure and attaches structured `sourceModule` diagnostics (`sourceModule`, `routeSourceModule`, `roleSourceModules`, `bindingSourceModules`, `refinerSourceModule`, and `requiredRoles`) to the `403` error response `details`.

### Boundary of the CLI surface

CLI commands fall into two categories by where they execute:

- **Local system commands**: interact directly with the local operating system and home root, comprising `penguin server` (start, stop, status, and reset-admin-password), `penguin web`, `penguin auth token` (reading the local `api-token`), and `penguin version` (printing the local build identity).
- **HTTP commands**: cover all remaining Penguin commands, including `penguin chat`, `penguin agent`, `penguin session`, `penguin send`, `penguin cost`, `penguin schedule`, `penguin org`, `penguin plugin`, `penguin exec`, `penguin config model`, `penguin config vault`, and `penguin version --json`. These commands resolve the target server and credentials through `resolveConnection` (using the session token `PENGUIN_API_TOKEN`, or resolving `server.lock`, `cli-session.json`, and `api-token` under `--root` or `PENGUIN_HOME`) and call the HTTP surface through `ServerClient`.

## Invariants
[invariants]: #invariants

### Penguin capabilities are authorized on the HTTP surface

> However a caller invokes Penguin — from the terminal CLI or from an external client — operations that read or mutate Penguin business state execute through the [HTTP surface](#guide-level-explanation) and are governed by the same route-level authorization rules.

The CLI holds the local process's system permissions, while the server guards Penguin state. Routing business operations through the HTTP surface ensures that user sessions and Agent role boundaries hold uniformly across every entry point.

### Home root access is administrator authority

> Wherever the harness runs, a process with local read access to the [Penguin Home Root](#guide-level-explanation) can obtain administrator credentials; any environment that restricts a caller below administrator isolates the home root at the filesystem level.

The home root holds the instance's `api-token`, database, and secret files. Defining filesystem access to the home root as the system-level administrator boundary aligns local administration and sandbox isolation with native operating system file permissions.

### Every protected HTTP route is identified by a unique ID

> Whether contributed by a core module or by a plugin, every route registered on `HttpModule.routes` carries a unique [route `id`](#reference-level-explanation), and Agent role endpoint grants are evaluated against that `id`.

The route `id` decouples URL structure from authorization policy. When path parameters or mount prefixes evolve, role grants continue to reference endpoints by a stable identifier.

## Drawbacks
[drawbacks]: #drawbacks

Business CLI subcommands (including `penguin config model`, `penguin config vault`, and `penguin version --json`) require a reachable server process to fulfill requests. Splitting multi-action route groups into per-method, per-subpath contributions also increases the number of entries in the `HttpModule.routes` manifest.

## Rationale and alternatives
[rationale-and-alternatives]: #rationale-and-alternatives

**Splitting permissions by surface (CLI = system, HTTP = penguin)**: the operating system enforces process, TTY, and filesystem isolation, while the HTTP server enforces roles, route allowlists, and project isolation, each using its native primitives.

**Authorizing by route `id` instead of URL regular expressions**: route `id`s are projected into `ifaces.json` at build time, remain stable across path refactors, and can be enumerated statically.

**Generation counters plus server-side sessions instead of stateless tokens**: re-deriving grants from the current generation allows immediate revocation or live permission updates across all active tokens belonging to a subject when the subject is deleted or its role changes, while preserving per-session revocation.

## Prior art
[prior-art]: #prior-art

**Docker CLI / Daemon and Kubernetes `kubectl` / `kube-apiserver`** use the same dual-surface split: the CLI runs in the caller's local system environment under local file permissions, all daemon and cluster state changes happen over an authenticated HTTP API, and local read access to the daemon socket or admin kubeconfig file is equivalent to administrator authority.

**AWS IAM Action IDs** use named `<service>:<action>` identifiers rather than raw URL paths as the unit of policy grants; route `id`s play the same role here.
