# PRFC-0010 UI Modules: The Web App Is a Module Tree; Pages and Global UI Are Contributions

## Summary
[summary]: #summary

The Web App's frontend is no longer one monolithic block pulled in through imports, but a **kernel module tree**: the same mechanism as the server side (PRFC-0001's `@Interface` / `@Component` / `@Module`, the same `ifaces.json` generated by `gen-ifaces`, and the same boot that "validates the whole tree before the first node runs"). This PRFC settles six things:

1. **Boot before the first render.** The composition root `web-root.ts` is the only file that imports the various `module.ts` files; `bootWeb()` assembles the whole tree and hands back the root component for the app to mount. Boot makes no network requests and takes a few milliseconds.
2. **The composition module is named WebApp.** `WebAppModule` provides the interface `WebApp` (member `webApp`, holding the root component `Root`) and lives in the `web-app/` directory. The app layout, routing, and the page table belong to it; **all routes come from the `pages` slot**, with contribution keys addressed by module name: `"WebAppModule.pages"`.
3. **All of a feature's UI arrives through named slots; the base imports no feature.** The signed-in session's providers (`sessionProviders`), the layers mounted once beside every page (`layers`), and the renderers of builtin pages (`pageRenderers`) hang under WebAppModule; claim-based dispatch of the user event stream hangs under SessionsModule (`userEvents`); the sidebar's sections, modes, and badges hang under SidebarModule; dock panels hang under DockModule; the tab strip beside a chat hangs under ChatModule. The session list's row actions (`SessionListModule.rowActions`) and the drafts interface (`ChatDrafts`) are likewise obtained only through interfaces.
4. **Server-contributed pages fold into the same page table.** `GET /api/contributions` has only one reader left (`web-app/contributions.tsx`): fetching, failure handling, and merging all happen in this one file; the router and the sidebar read the merged table via `useWebAppPages()`, not knowing where a page comes from. `iframe` pages are drawn by WebApp itself; `builtin` pages take their component from the `pageRenderers` slot by name, with conflicts skipped and compile-time pages taking precedence.
5. **The rescue surface lives permanently outside the composition root.** The app's single command palette and safe-mode marker hang outside the router root's error boundary; when boot assembly fails, a fallback root renders the same rescue panel. The rescue entry never disappears along with a broken page or a broken tree.
6. **The boundaries of naming and compatibility.** The composition module's internal addressing (module class name, interface, member, directory, contribution keys) migrates to the WebApp vocabulary in **the same bundle** in one go, with no alias kept for the old ShellModule addressing; the already-published `frame: "shell" | "bare"` is a **layout discriminant**, not a module address, and stays as-is; the terminal page itself remains a `frame: "bare"` page contribution, and the real PTY, terminal, and desktop/server host shells are entirely outside this design and unchanged.

## Motivation
[motivation]: #motivation

Before the rework, the frontend was four ledgers of debt:

- **Adding a page meant touching the base.** `router.tsx` had to import each feature's page component to mount a route, and the page inventory was a hand-maintained manifest; the sidebar's titles and icons were looked up by key in a table inside the base. A page should have been a feature's declaration, yet it grew inside the assembler's code.
- **Things mounted once were named by the base.** `RequireAuth` hard-coded `CompanyProvider`; `AppLayout` imported four features' runtime components just to mount the dock runtime, hotkeys, the builtin browser, and the command palette; the moment a user event arrived, the dispatch function directly called the respective publish functions of company, the builtin browser, and scheduled tasks. The base knew every feature, so no feature could ever be moved out — and these very seams are what company will be missing when it migrates out into a plugin someday.
- **Features imported each other's internal files.** Workspace browsing and model selection were referenced as chat's internal files by a dozen or so features; chat, dock, traces, and messaging named one another; the sidebar and the chat page each grew to around three thousand lines, so any change meant reading the entire file first.
- **Vocabulary collision.** The composition module was previously called shell: the terminal page itself is a shell, and the host side has its own desktop/server shell besides, so a search for "shell" hit all three — reading and writing code always began with asking "which shell?"

This is the same set of problems PRFC-0001 solved on the server side — the frontend incarnation of that carry-everything `AppDeps` is precisely the router's import table and the name-by-name mounting. After the server gathered its business surface into one tree, the frontend is the next site: the mechanism is ready-made (PRFC-0014 already let Workflow's tab pages contribute to the Web as data via `WebModule.sessionTabs`); what is missing is the frontend itself standing on the same mechanism, so that "contributing a page" and "contributing a route" become one and the same thing.

## Guide-level explanation
[guide-level-explanation]: #guide-level-explanation

### The composition root

`web-root.ts` is the frontend's `platform.ts`: a `@Module` whose `children` lists `WebAppModule` and the feature modules, and the only file that imports any `module.ts`. `bootWeb()` walks the generated interface table through `moduleDefOf` + `bootModules` (the tree's resource registry is a no-op implementation — the frontend tree parks nothing) and returns the root component; `main.tsx` and friends install scopes and mount only after all of it completes. The demo app shown in-frame in `packages/ui-gallery` goes through the same `bootWeb()` and assembles no separate set of its own.

`ifaces.json` is statically read out of this package's source by `gen-ifaces` and not checked in; `dev` / `build` / `typecheck` / `test` all generate it first. Boot makes no network requests and takes a few milliseconds — the kernel and its validation dependencies are a fixed volume in the entry chunk; see Drawbacks.

### Adding a page

Add one contribution and one binding to the feature's `module.ts`, with zero changes to the base:

```ts
@Module({
  contributes: {
    "WebAppModule.pages": [
      {
        id: "terminal.page",
        key: "terminal",
        path: "/terminal",
        frame: "bare",
        nav: "none",
        admin: false,
        released: true,
        order: 100,
      },
    ],
  },
})
export class TerminalModule {
  @Bind("terminal.page") page = TerminalPage;
}
```

The data half declares the route and ownership (key, path, frame, nav, admin, released, order); the code half is the component that draws the page. Both the sidebar and the router read the page table, and a page's order in the table is the order of the navigation.

### What the base gets from slots

- **`sessionProviders`**: providers of the signed-in session, mounted inside `Project + Sessions` and nested outermost-first by `order`. Company's state is contributed by the company module itself and no longer named by `RequireAuth`.
- **`layers`**: overlays and headless runtimes mounted **once** beside every page — the dock runtime, hotkeys, the builtin browser, the command palette — which `AppLayout` mounts in sequence at the original positions, taking no props and forming no closures.
- **`userEvents`**: claim-based dispatch of the user event stream (`/api/events`). Each feature binds its own handlers and declares which events it claims; the list still handles its own events first as before, and on `resync_required` it first clears and refetches, then calls each handler's `resync`.
- **Sidebar**: sections (`sections`), work modes (`modes`), row badges (`navBadges`). The framework draws only the switcher, the page navigation, and the account row; what gets installed is decided by contributions.
- **Dock panels** (`DockModule.panels`) and the **tab strip** beside a chat (`ChatModule.sessionTabs`): panels and tabs are contributed by their owning modules; chat and dock no longer name each other.
- **Interfaces**: the session list's row actions (`rowActions`) and chat's drafts (`ChatDrafts`) — anything that must be handed between the base and a feature goes through an interface, never an import.

### Server-contributed pages

The server's modules and plugins can also contribute pages to the Web: the response of `GET /api/contributions` folds into the same page table. It is fetched once per signed-in user, discarded and refetched the moment the user changes; while the request is in flight the fallback route does not render, so directly opening a contributed page's URL does not get bounced away; failures are not retried, and the table retains only the compile-time pages — **no contributed page is load-bearing**. A builtin page takes its component from the `pageRenderers` slot by name; names not shipped in this build are skipped; iframe pages are drawn by WebApp's own FramePage.

### The rescue surface

The command palette hangs outside the router root's error boundary, the app's single copy; safe mode is recorded per tab in sessionStorage (`?safe` takes effect before the first render and is removed from the address bar, falling back to memory when storage is unavailable); when boot assembly fails, a fallback root draws the same rescue panel. In safe mode, fetching of contributions is disabled and cleared, in-flight stale responses are rejected, and a refetch happens after leaving.

### What is not called "shell"

The composition module is called **WebApp**. The two values of `PageData.frame`, `shell` / `bare`, are **published layout discriminants** — "with or without the app layout" — not the name of any module, and they stay as-is. The terminal is a `frame: "bare"` page in the page table; PTY, terminal session shells, desktop/server host shells, and host permission words such as `desktop_shell_only` are all outside this design.

## Reference-level explanation
[reference-level-explanation]: #reference-level-explanation

### Boot

```ts
export async function bootWeb(): Promise<ComponentType<AppRouterProps>> {
  const tree = await bootModules(
    moduleDefOf(WebRoot, { manifests: table.modules as unknown as ManifestTable }),
    { ifaces: table as unknown as IfaceTable, resources: NO_RESOURCES },
  );
  return tree.api<WebApp>("WebAppModule", "webApp").Root;
}
```

- The composition root `WebRoot`'s `children`: `WebAppModule` and the feature modules (chat, agents, models, plugins, machines, ports, usage, benchmark, dashboard, terminal, workflows, company). Adding a feature module = adding one line to `children`; nothing else changes.
- `ifaces.json` is not checked in: `gen-ifaces` goes into web's `gen:ifaces`; `dev` / `build` / `typecheck` / `test` run it first; the root-level `gen:ifaces` generates the web table at the same time.
- Decorators are not downleveled: the Vite configs of web and ui-gallery specify `target: "es2022"` for esbuild.
- Size: the kernel dependencies add about 184 kB to the production entry chunk (about +55.5 kB gzipped, of which arktype is about 47 kB) and cannot be tree-shaken; boot takes about 2–3 ms. Accepted; see Drawbacks.

### WebApp and its slots

```ts
@Interface()
export abstract class WebApp {
  /** The whole routed app, everything it renders under WebApp's bindings. */
  abstract readonly Root: ComponentType<AppRouterProps>;
}

export interface WebAppSlots {
  /** A routed page; its component is the code half. */
  pages: Slot<PageData, ComponentType>;
  /** Providers of the signed-in session, mounted inside Project + Sessions, outermost first. */
  sessionProviders: Slot<Ordered, ComponentType<{ children: ReactNode }>>;
  /** Mounted once beside every page: overlays and headless runtimes. */
  layers: Slot<Ordered, ComponentType>;
  /** A builtin page the server can name in a contribution; resolved by its name. */
  pageRenderers: Slot<PageRendererData, ComponentType>;
}
```

- Slot keys are addressed by the **providing module's name** (`"WebAppModule.pages"`), and the slot declarations hang on the **interface** it provides (`WebAppSlots` accompanies `WebApp`) — the same split as the server's `HttpModule.routes` / `HttpSlots`: the module name is the stable address, and the interface is where the types live.
- `Ordered` has a single member `order`: contributions to the same slot are sorted by it in ascending order, first come, first mounted. Order is data, not the shape of the tree (the same sentence as in PRFC-0001).
- In `setup()`, `WebAppModule` binds the contributions on three fronts (pages organized via `pageTableOf`, providers and layers by `order`), together with the user-event handler table, into the root component; it also `@Use`s the sidebar interface `Sidebar` and the drafts interface `ChatDrafts`, passing in everything the layout needs.

### `PageData` and the page table

```ts
export interface PageData {
  key: string;
  path: string;
  /** "bare" mounts outside the app shell (no sidebar, no Project context): the terminal, a workflow's app page. */
  frame: "shell" | "bare";
  nav: "main" | "none";
  admin: boolean;
  /** Built but not yet offered: reachable by URL and tests, hidden from the nav. */
  released: boolean;
  /** The page's place in the table, and so in the nav. */
  order: number;
}
```

- A `frame: "bare"` page is mounted under a bare layout that **still requires sign-in** (no sidebar, no Project context): the terminal page and a workflow's full-page app. A `frame: "shell"` page is mounted under the app layout. The two values are published discriminants and stay unchanged.
- `pageTableOf` arranges the contributions into a `WebAppPage[]` by `order` (filling in the contribution id and the bound component); `navPagesOf` picks out the main-navigation pages. Titles and icons live in the data (`title` / `titleZh` / `icon`, where `icon` is a name in the UI package's icon registry); the base no longer holds a key-indexed lookup table.
- Routing: pages inside the app layout are mounted under the sign-in gate, `bare` pages under the bare gate; `/login` and the fallback route are unchanged. The home page is instead a `path: "*"` page contributed by the company module (`HomeRedirect`, redirecting per the current mode); the router no longer carries its own index and catch-all, nor reads company state.

### Folding in server contributions (`web-app/contributions.tsx`)

- **store**: `createContributionsStore(fetch)` fetches once per signed-in user; when the user switches, the previous user's response is dropped and refetched, and late stale responses are discarded; sign-out clears; failures are not retried, and the table falls back to the compile-time pages. `refresh()` refetches for the current user (after a plugin is installed or removed) and keeps the existing response on failure.
- **Merge**: server pages are appended after the compile-time pages with `frame: "shell"`, keeping their declared renderer and `released`. Entries whose key or path conflicts with a compile-time page (or with `/login`) are skipped — **plugins add pages; they do not shadow the app's pages**. `iframe` pages are drawn by `FramePage` (reusing the workflow iframe's theme copy, key forwarding, and sandbox attributes); `builtin` takes its component from `WebAppModule.pageRenderers` by name, and names with no contributor are skipped. Company-mode pages (`nav: "org"`) have organization-relative paths, which get the root prepended before conflict detection.
- **pending gate**: `WebAppPagesProvider` is mounted inside the router; while the request is in flight, the fallback route (company's `home`, `path: "*"`) does not render, so a contributed page reached directly is not bounced away.
- **Readers converge into one**: the router, the sidebar, and company mode all read only this table; `useOrgPages()` becomes a pure selector over the table (the `nav: "org"` server pages); the proposals page is contributed by `ProposalsModule` into `pageRenderers` under the name `OrgProposalsPage` and is drawn by it both inside and outside company mode; the unread count is anchored on the renderer's name, not hard-coded to a particular page key.

### The user event stream (`SessionsModule.userEvents`)

```ts
export interface UserEventHandler {
  event(ev: Opaque<"ServerEvent", ServerEvent>, source: string | null): void;
  resync?(source: string | null): void;
}
```

- `SessionsModule` provides the interface `UserEventHandlers` (a handler list sorted by `order`); each feature binds its own handlers (company, the builtin browser, scheduled tasks, ...), and the event types they claim are mutually disjoint.
- `applyUserEvent`: the list's own events (`web_updated`, `session_*`) are handled first as before; on `resync_required` it first clears and refetches, then calls each handler's `resync(source)` in turn; the remaining events go to the handlers first, and the list then handles the share concerning itself (scheduled tasks refresh the list; workflow events are dispatched to the window).
- `source` is the machine the event came from, `null` for this server: the builtin browser honors resyncs only from this server, while company honors all sources — this difference is declared by each handler itself and not written into the dispatch.

### The sidebar (`SidebarModule`)

- The interface `Sidebar` gives three things: `Column` (the whole sidebar), `Rail` (the collapsed narrow column), and `useColumnState()` (for the layout's surroundings to read: whether in the default mode, the drawer button's name, the aggregate badge caption).
- Three slots:
  - **`sections`** (data half `{ mode, place: "header" | "body", order }`): one section. The code half is `{ Scope?, Overlays?, Full, Rail? }` — `Full` / `Rail` are mounted only when their mode is the current mode; `Scope` and `Overlays` stay **mounted the whole time the sidebar lives**, carrying the state that must survive mode switches (the session list's controllers, dialogs), so switching between dev/company mode resets nothing.
  - **`modes`** (data half `{ key, title, titleZh, icon, order }`): work modes beyond the default dev mode; the code half provides `useMode()` (availability, whether current, switching and returning the route to navigate to, the mode's nav rows).
  - **`navBadges`** (data half `{ anchor, order }`): markers on the nav rows (page keys), the account row (`account`), and the mobile drawer button (`menu`); the code half is `useNote()` (a dot and its caption) or `Mark` (a row-end component).
- The shapes a contributor must implement live in a library file (`lib/sidebar-contributions.ts`); contributors do not import the sidebar framework; `DEFAULT_MODE` is `"dev"`.
- The session list: `SessionListModule` contributes the dev-mode section to `sections` and `@Use`s `ChatDrafts`; its `rowActions` slot takes row menu items, row badges, and workspace grouping menu items, with contributed items inserted between rename and archive. Drafts belong to chat's interface `ChatDrafts` (`newChatId`, `useParked()`, `prepareNewChat()`, `useNewChat()`, ...); the session list and the narrow column no longer reference chat's internal files.

### Dock and session tabs (`DockModule.panels`, `ChatModule.sessionTabs`)

- `DockPanelData`: `{ kind, title, titleZh, icon, order }`. `kind` is the tab key in the dock layout store, **stable across versions**; `icon` is a name in the icon registry. The code half is `DockPanel = ComponentType<{ active: boolean }>` — the body stays resident for as long as the tab exists, and `active` means "the tab is front and the dock area is open"; polling is gated on it.
- In `setup()`, `DockModule` organizes the contributions into a panel registry and binds it into the React tree via `WebAppModule.sessionProviders`; the eight panels are contributed by their owning modules (chat's agents and memory, workspace, trace, message bindings, scheduled tasks, the builtin browser, port forwarding). **The Browser tab (`browser:<id>`) is not a panel kind**; the chat page renders it directly.
- The format of already-saved layouts is unchanged: loading keeps every tab, contributed `kind`s are registered at boot, `kind`s with no contributor are dropped in memory (the active item falls back per the existing rules), and **the store is never rewritten**.
- The session context lives in a library file (`lib/chat-session.ts`; workspace and chat import each other, so putting it on either side's `index.ts` would form a cycle): `ChatSession` carries only the fields external panels actually use, and `ChatSessionProvider` supplies both the session context and chat's internal controller context.
- `ChatModule.sessionTabs`: `Slot<SessionTabData, SessionTab>`, with `SessionTab` receiving `{ projectId, agentId, machineId }`. The builtin workflows module contributes the tab strip component (including the iframe that overlays the chat); the **data half of the tabs** — the page list of an Agent's workflows — arrives via `/api/contributions`, which is the slot hung in the server-side tree for plugins and Workflow (PRFC-0014's `WebModule.sessionTabs`); the frontend only consumes the data and does not replicate the mechanism.
- Once this is done, chat no longer imports traces, messaging, workflows, or ports; dock no longer imports chat.

### The rescue surface (`rescue`)

- The command palette and the safe-mode marker hang **outside the router root's error boundary**, the app's single copy of each, isolated from one another. The error panel offers: the error text, reload, reload without loading contributions, and Harness history. Workflow's full-page exit action registers with the shared palette and is unregistered on unmount.
- `palette.toggle` defaults to `Mod+Shift+P`, can be triggered even over dialogs, and preserves user rebinding; Firefox may claim this key first — we make no claim that it is the unique escape path across browsers.
- Safe mode is stored per tab in sessionStorage; `?safe` takes effect before the first render and is removed from the address bar; when storage is unavailable it falls back to memory; it can be exited from the palette and the marker. In safe mode, fetching of contributions is disabled and cleared, in-flight stale responses are rejected, and a refetch happens after leaving.
- When boot assembly fails (tree validation not passing, the interface table stale), `bootFailedRoot` renders the **same** rescue panel.
- The command palette and the Harness history components are **not module-level contributions**: the rescue surface lives outside the tree and stays resident across page loads; their directory placement is one pure move (smuggling no behavior along), while the safe-mode and boot-fallback **behaviors** belong to a separate behavior layer — the two are delivered separately and verified separately.

### Boundary rules

- Any `module.ts` (including `*.module.ts`) is imported only by the composition root.
- `web-app/`, `state/`, `lib/`, `api/`, and `app.tsx` import no feature's internal files; features reference each other only through the other's `index.ts` and take part in cycle detection.
- Every one of the above is a **ratchet baseline**: the source-scan test records the current edges, decreasing only (new edges must be declared explicitly along with the change); as files move into place, the baseline sees only path rewrites and deletions.

### Layering and hot push

- The Web bundle is part of the platform payload and arrives atomically with an online hot push (05, "Install and release"); the frontend tree reassembles **on every page load** and has no hot-swap mechanism of its own — this PRFC changes neither the HMR layer nor the runtime.
- No persistent data migrates: the nav collapse and resident keys in localStorage, the dock layout store format, page keys, HTTP data, and storage keys all stay unchanged.

### Naming and compatibility

- The composition module's internal addressing (`WebAppModule` / `WebApp` / `webApp` / `web-app/` / contribution keys) migrates in one go with **the same bundle**; callers and contributors ship in the same bundle, and **no alias is kept for the old names** — this is an in-memory contract with no persistent consumers, so a hard cutover costs least (the same judgment PRFC-0002 made for registry ids).
- `frame: "shell" | "bare"` is a published data value, not a module address, and stays as-is.
- The terminal page, PTY, terminal session shells, desktop/server host shells, the `desktop_shell_only` host permission word, and the UI package's `AppShell` layout component: all of these are outside this design and unchanged.

### Migration and merge order

The design lands first: merging this PRFC is the precondition for merging each layer's code. The code proceeds as one stack, and each layer's net change is checked section by section against this document before approval; the order is decided by dependencies:

1. **Boundary ratchet and file placement** — establish the scan baseline first, so every later layer has a "decrease only" rule to stand on.
2. **Composition root and the `pages` slot** — the tree stands up first, and pages become contributions first.
3. **Global slots** (`sessionProviders` / `layers` / `userEvents`) — the three places where the base did the naming become contributions.
4. **Sidebar split**, then **sidebar slots** — split by responsibility first, and only then slot-ify.
5. **Chat page split**, then **dock and session tab slots** — the same rule.
6. **Folding in server contributions** — the two readers converge into one, relying on the page table already being in place.
7. **Rescue surface directory placement** — the move goes last; its behaviors (safe mode, boot fallback, palette registration) have already been delivered in a separate behavior layer and are not repeated along with the move.

Three cross-cutting rules: **pure refactor layers smuggle no behavior along** (their acceptance is whole-tree equivalence before and after the move, not new tests); **behavior changes ride only in behavior layers**; **renames ride in the same bundle** — code referencing the new addressing ships in the same bundle as the rename, with no alias kept for old names; the rename's release is therefore gated on the genuine fix of the boundary ratchet: no release while the red gate stands, and no buying green by editing the baseline.

## Verification strategy
[verification strategy]: #verification-strategy

This section is a list of **planned verifications**: it states what each layer will use to prove it has broken nothing when it merges. As of this writing, not one of them has been run — each layer's readings are filed with that layer's implementation review, not pre-filled here, nor replaced with historical numbers. Grouped by verification subject:

- **Boundaries and cycles (the ratchet)**: the source-scan test records the current import edges and cycles item by item, and the baseline only decreases — new edges are declared explicitly along with the change, and deleting a baseline entry must come with the verification of "why this edge really no longer exists," not mechanical additions and deletions just to force green; cycle detection runs as usual. The rename candidate is currently parked on exactly one such verification (two cases red): no release while the red gate stands.
- **Assembly and pages**: unit tests boot with the real composition root — uniqueness of the page table, each key's code half bound, the `frame` split, the main nav's order and `admin` / `released` matching the pre-rework behavior, contributed pages with conflicting key / path skipped, and boot returning a mountable root component.
- **Slot lifecycles**: sessionProviders nest outermost-first by `order`; layers mount exactly once per page; userEvents' dispatch order, handlers' claims being disjoint, `resync(source)`'s source difference (the builtin browser honors only this server, company honors all sources); the sidebar sections' `Scope` / `Overlays` staying resident across mode switches (switching resets no state) and `Full` / `Rail` mounting only when their mode is current; dock panels registering at boot, saved layouts loading back completely (kinds with no contributor dropped only in memory, the store never rewritten), `active` gating polling; the session tab strip binding per contribution.
- **Contributions and user switching**: store semantics item by item — fetched once per signed-in user, discarded and refetched on user switch, late stale responses dropped, sign-out clears, failure leaves only the compile-time pages, `refresh` failure keeps the existing response; the fallback route not rendering while the request is in flight; safe mode disabling fetch, clearing, rejecting in-flight stale responses, and refetching after leaving.
- **Pure refactor layers**: source before and after the move verbatim-equal under the explicit path replacements, callers changing only imports, and the resulting whole tree equivalent — **the equivalence itself is the acceptance**, with no new tests added; existing guard tests keep their original assertions after path changes.
- **Dynamic surface (honestly untested)**: the normal socket stream, real browser interaction (focus / Escape / dialogs), Electron, hot-push rollback; SSR or hand-crafted-state checks prove only the fallback text and do not pass as real-client verification. These must be run on real machines, and as of this writing none has been.

## Status
[status]: #status

**Design first, implementation advancing layer by layer; this document describes the target contract, and unpublished candidates do not pass for landed implementation.**

- The first layer (module boundary ratchet and file placement) has an open implementation PR; the remaining layers advance one by one on an unmerged branch stack, and not all implementation PRs have been opened yet. Before any layer merges, its net layer must be checked section by section against this document.
- The composition module was previously implemented in Shell vocabulary on an unmerged branch; the rename candidate following this PRFC's chosen **WebApp** name is prepared and **unreleased** — no branch has been pushed carrying the new name yet, the release is blocked by one boundary-ratchet baseline verification (two cases), and the fix is in progress on another line. This document writes the contract uniformly in WebApp vocabulary.
- The rescue surface's behaviors (safe mode, boot fallback, palette registration) have been split out of the directory move and delivered and verified as a layer of their own; the two implementation bases (the non-modularized prior fix and the modularized adaptation included) are registered separately, and neither passes for the other.
- This PRFC covers only the eight surfaces above: composition root and pages, global slots, the sidebar, the chat page split and dock/tab slots, folding in server contributions, and rescue surface ownership. Further growth of the same page table (page parent-child, per-page file renderers, server-driven page removal) belongs to later layers and is out of scope here.

## Drawbacks
[drawbacks]: #drawbacks

- **The entry chunk's fixed cost**: the kernel dependencies add about 184 kB to the entry chunk (about +55.5 kB gzipped). This is the price paid for "validate the whole tree before running it"; accepted.
- **Contribution keys are addressed by module name, so a rename demands whole-bundle synchronization**: the composition module's own move from Shell to WebApp this time is the proof — pick the right name the first time; that is also why no alias is kept for old names (keep an alias, and the next rename has two sets to synchronize).
- **The migration is a multi-layer stack**, not a one-shot replacement: for a while, the "design vocabulary" (this document) and "the current names on unmerged branches" coexist; the merge order of the layers is decided by the delivery surface, and this document does not lock it.
- **The values of `frame` and the module name live on two different layers**, and the word `"shell"` stays in `PageData` — it is a published discriminant, kept in exchange for storage and data compatibility; readers must remember that it is not a module address (this document states so in two places).

## Rationale and alternatives
[rationale-and-alternatives]: #rationale-and-alternatives

**Why the name WebApp.** The composition module was previously called Shell, colliding with three places: the terminal page (a shell), the host shell (desktop/server/HMR), and the UI package's existing `AppShell` layout component. Among the candidates weighed: **Workbench** (strong product semantics, but its Chinese translation would read like Workspace); **WebFrame** (leans toward the layout frame, fails to cover the page table and the global slots, and collides with `PageData.frame`); **WebHost** (collides with the host layering yet again — the worst); **AppShell** (keeps the Shell root, and conflicts with the UI package's component of the same name). WebApp covers the composition module's full duties — root component, routing, the page table, the global slots to come — without suggesting a command interpreter, and it is the only candidate that collides with no existing layering vocabulary.

**Why reuse PRFC-0001 instead of the frontend building its own dependency injection.** The frontend's problems are the same shape as the server's (who declares needing what, how to swap, how to judge across compilations), and the mechanism being ready-made means: signature-level data in one and the same `ifaces.json`, one and the same whole-tree validation, one and the same contribution addressing. A homemade lightweight DI looks like it saves kernel size, but the cost is that when third parties (plugins, Workflow) someday contribute to the frontend, cross-compilation interface comparison has to be invented a second time — PRFC-0014 has already brought Workflow to this point via the server-side tree.

**Why the page table belongs to the composition module, and why server contributions fold into the same table.** The same endpoint previously had two readers, each fetching and merging on its own, and the proposals page was hard-imported separately by the router and by company mode. Converged into one place, swapping the endpoint touches one file; "one page, two origins, one table" also eliminates a second criterion for "should contributed pages enter the main nav" — it is simply a row in the table.

**Why the rescue surface lives outside the tree.** If the command palette were a module-level contribution, a broken page or a broken tree would take it away too, and the rescue entry would vanish with it. Hung outside the error boundary, with a separate fallback root for boot failures, the rescue path depends on none of the objects being rescued. The cost this brings — the command palette cannot be extended by feature contributions — is made up by the other half, host action registration (workflow's full-page exit).

**Why no aliases are kept for the old addressing.** The frontend tree's addressing is in-memory and bundle-internal: callers and callees come out of the same build and ship in the same bundle. Aliases buy real compatibility only at "boundaries between two independent compilations" (plugins, Workflow), and those two sides use data (`/api/contributions`), not the frontend tree's addressing. Carrying a permanent double name for a name with no persistent consumers is the same ledger PRFC-0002 already rejected.

## Prior art
[prior-art]: #prior-art

- **PRFC-0001 "Module"**: the mechanism itself and its first application on the server side; this document is the landing of "the frontend's tree" — its Guide foreshadowed this step.
- **PRFC-0014 "Workflow"**: the first Web slot genuinely reached by a third party (`WebModule.sessionTabs` in the server-side tree, arriving at the frontend as data via `/api/contributions`); this document gathers its frontend landing point into the unified shape of `ChatModule.sessionTabs`.
- **The server's `HttpModule.routes`**: the split of slots hung on interfaces and keys addressed by module name; WebApp's slots are the same shape.
- **PRFC-0002 "HMR"**: the same judgment about not keeping aliases for in-memory contracts.

## Unresolved questions
[unresolved-questions]: #unresolved-questions

- The shape in which third-party code (plugins, Workflow) will someday contribute frontend halves **directly** to the frontend tree: today server contributions always fold in as data, with render components carried by the platform bundle; if third parties are to carry component halves, how cross-compilation interface validation would run on the frontend side (how much of PRFC-0014's judgment mechanism could be reused) remains open.
- Whether the command palette's default key is unique across browsers: Firefox may claim `Mod+Shift+P` first; the rebinding surface already exists, and whether a default that does not fight the browser's native behavior is needed is left for the user to decide.
- Whether the frontend tree needs runtime extension of its own (swapping individual frontend modules without a whole-bundle hot push): today the Web bundle arrives atomically with the platform and the tree rebuilds on every page load, so there is no demand surface for separate hot-swapping.

## Future possibilities
[future-possibilities]: #future-possibilities

- **The same page table keeps growing**: page parent-child (indentation levels of nav rows), per-page file renderers, server-driven page removal — later layers of the same slot family, directly reusing this document's merge and conflict rules.
- **Server contributions extend beyond pages**: sidebar sections, badges, and dock panels arriving from the server as data (today these slots accept only compile-time contributions).
- **A plugin carrying a frontend half**: the natural endpoint once cross-compilation validation lands — a plugin contributes data in the server-side tree and components in the frontend tree, with the same manifest on both sides.
