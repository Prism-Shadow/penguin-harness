## Summary
[summary]: #summary

同一个插件，两个 Project 想要不同的版本，怎么办？本提案的回答是：不在一个安装里解决。版本属于安装——一个安装一棵模块树、一份插件清单，同一个包只有一份；Project 一级的配置只说这个插件在这里怎么工作，从不说要它的哪一版。

## Motivation
[motivation]: #motivation

### 背景

插件是给这套 harness 加能力的 npm 包，由部署方在数据根的 `plugins.json` 里列出，服务端启动时把它们接进平台的模块树。仓库里现有的五个是四个沙盒后端和一个语言包。既然是 npm 包，它就有版本，会升级，也会有改坏了兼容性的那种升级。

一台服务器同时承载多个 Project。PRFC-0004 已经定下插件的作用域：注册全局，分级的是配置，machine 一级放机器事实，project 一级放 Project 的意愿。紧接着的问题就是版本落在哪一级。

### 问题：一台服务器，两个 Project，两个版本

设想一台服务器上开着两个 Project。沙盒插件发了 v2，把遮蔽路径的默认语义改了——v1 里没列出的路径默认可见，v2 改成默认隐藏。A 团队的配置是照 v1 的语义写的，跟着升上去会把他们构建脚本要读的东西全挡掉；B 团队则需要 v2 才有的一个新隔离维度。运维手上只有这一台服务器，怎么办？

如果版本可以写进 Project 的配置，答案看起来很直接：A 写 `version = "^1"`，B 写 `version = "^2"`，各取所需。本提案要说明的正是这条路走不通，以及为什么不能让它看起来可行。

### 为什么现在就得回答

回答的时机决定了这个问题的难度。假如版本成了 project 配置里的一个字段，系统就有了表达这种冲突的能力，而模块树没有承载它的能力——谁写下这个字段，运行时唯一能做的就是失败。反过来，把版本钉在安装上，冲突根本无从表达，要处理的就只剩「怎么让人在装的时候就知道」。

## Guide-level explanation
[guide-level-explanation]: #guide-level-explanation

一个安装就是一套一致的版本。想知道某个 Project 在用哪一版，看它跑在哪台安装上。

Project 不声明版本，只声明配置。`[plugin.foo]` 那一节说的是 foo 在这个 Project 里怎么工作，不是这个 Project 要 foo 的哪一版。

真需要两个版本同时可用，有三条路，按用得上的可能性排。

第一条也是绝大多数情况的答案：把破坏性版本当作新插件发布。换个包名和模块名，两版并存，各占各的接口键，Project 各配各的。语义上它们本来就是两样不兼容的东西，用现成的命名空间如实说出来就行，不需要任何新机制。

第二条，把差异表达成配置而不是版本。「A 要旧行为、B 要新行为」九成是一个配置键的事；节里的 schema 怎么演进，用 Module 已有的 `migrations`，新版读得懂旧版写下的东西。

第三条，拆成两个安装。Machine 本来就是「一份供给集」的单位，各有自己的数据根和 `plugins.json`，安装推送会把目标缺的插件负载一并带过去。这是隔离版本的正规办法，不是绕路。

装第二份同名包的时候会被当场拒绝，并且说清楚已经装着的是哪一版，不必等到下次启动才知道。

## Reference-level explanation
[reference-level-explanation]: #reference-level-explanation

### 树里为什么容不下两份

平台与插件之间的每个接口都登记在一张全局的表里，键就是 `<包名>#<导出名>`；启动时的整树校验，做的就是拿这张表逐个核对谁要什么、谁给什么，签名对不上就具名报错。

挡住两份的是三道各自独立的关卡，都不是疏漏。模块名在树内唯一，贡献 id 在树内唯一，而那张接口表的键没有版本这一维。

第三道是真正致命的那道。同一个包的两版同时在树里，同一个键下会出现两份不同的签名，整棵树的签名级校验就此失去意义。前两道即使放宽，比如给模块名加个版本后缀，第三道也拦得住。

### 版本不进 project 配置

`[plugin.<模块名>]` 那一节里没有版本字段，也不接受。这不是漏了，是本提案的核心约束：能表达出来的冲突，就是必须解决的冲突。

### 冲突在安装时报出

安装面在写进 `plugins.json` 之前先比对已装清单，同名包已经在了就具名拒绝，说明装着的是哪一版，以及一个安装只能有一份。

今天 `PluginHost.use` 和整树校验都在启动期抛错，装的时候一声不吭，下次重启才失败。把判断前移到安装面，也和这套代码库其他地方的失败方式一致：挡下来，并说清是谁挡的。

## Drawbacks
[drawbacks]: #drawbacks

升级插件是整个安装一起升。一个 Project 需要新版，同一台安装上的其他 Project 跟着一起换；回滚也一样，插件版本和配置一起回，没法只回滚一个 Project。缓解办法是 PRFC-0004 的分级配置——改了行为的新版留一个 project 一级的开关，让旧 Project 保持旧行为——但这要插件作者主动去做，平台强制不了。

还有一条要认：「两个 Project 要不同版本」这个诉求，本提案没有直接的答案，只给了三条间接的路，其中最彻底的那条成本不低。

## Rationale and alternatives
[rationale-and-alternatives]: #rationale-and-alternatives

模块树的价值在于整棵一起做签名级校验。任何允许同一个接口键下出现两份签名的方案，都要拿这次校验去换，而校验是这棵树值得信任的原因。把版本钉在安装上，是唯一不动这个前提的位置。

树内按版本命名空间，比如 `foo@1` 和 `foo@2`，要给 `requires` 加一维版本轴：每条依赖声明、每次解析、每份 ifaces 表都得带上版本语义。为一个罕见情形改动整张签名表，不划算。

每个版本一个进程，用 worker 或子进程隔离，需要新增序列化边界和一套生命周期管理，而且跨过边界之后就没有签名级校验了。它把问题挪走了，没有解决。

project 一级的版本 pin 前面说过：它凭空造出一个运行时满足不了的表达。

什么都不做的话，冲突照样发生，只是发生在启动期，报错来自树校验，操作者看到的是「模块名重复」，而不是「你装了同一个插件的两版」。

## Prior art
[prior-art]: #prior-art

四个生态给出的答案分成两类，而分界不是「愿不愿意同时装两份」，是宿主有没有一张全局的、按名字索引的表。没有这张表的可以装两份，代价是两份东西彼此不认；有的只能一个安装一份。

npm 走的是没有表的那条路。嵌套 `node_modules` 允许同一个包的多份副本共存，谁用哪一份由路径决定，代价是类型和实例不通：`instanceof` 失效，本该是单例的东西变成多例。值得注意的是 npm 自己也知道这条路在插件场景下走不通，所以专门有 `peerDependencies`，让一个插件声明「这个依赖必须由宿主那一份满足，别给我装我自己的」。在最愿意容忍重复的生态里，插件恰恰是那个必须去重的场景。

Cargo 的规则更细，也更接近我们要回答的问题。它在同一个 semver 兼容区间内强制统一：两个要求写成 `=0.4.11` 和 `=0.4.8` 撞在一起时，Cargo 直接报错，而不是各建一份。只有跨越不兼容区间才允许共存，比如 rand 0.6 与 0.7 同时出现在依赖图里。随之而来的问题 Cargo 文档单列一节叫 version-incompatibility hazards：两份 crate 的类型一旦出现在彼此的 API 边界上，编译器就会报出「expected X, found X」这种看着像疯了的错误。Cargo 愿意建两份，但它承认这只在两份互不照面时才成立。

Cargo 还有一处更直接的对应，是 `links` 键。一个包声明 `links = "foo"` 表示它链接名为 foo 的原生库，而 Cargo 规定每个 `links` 值至多一个包，禁止两个包链同一个原生库，理由是防止符号重复。这正是我们的情形：在一个愿意为大多数依赖建多份的构建系统里，仍然存在一类全局唯一的名字，它的唯一性在解析期就被强制，并且以具名的错误拒绝。我们的接口键 `<包名>#<导出名>` 就是这一类，前面说的「安装时具名拒绝」，形状与 `links` 的拒绝是同一个。

VS Code 在有表的那一边，也是与本提案最贴近的一个。扩展的身份是 `publisher.name`，一个安装里同一个身份只有一份，没有多版本共存的概念。`extensionDependencies` 列的是扩展 id，不带版本区间；唯一的版本约束是 `engines.vscode`，而它约束的是与宿主的兼容性，不是与其他扩展的关系——宿主版本不够新时，市场装的是一个仍然兼容的旧版，而不是让两版并存。破坏性改动在这个生态里的实际走法，就是本提案的第一条出路：换一个 id 重新发布，老的留在原地。

Helix 提供的是另一个角度。它的扩展点是 tree-sitter grammar，而 grammar 在 `languages.toml` 里以 `[[grammar]] source = { git = …, rev = … }` 钉死在一个确切的 commit 上，一个 grammar 名一条记录。这里根本不存在版本冲突，因为 grammar 是数据：没有东西链接它，也没有签名要对齐，「版本」退化成「取哪个 commit」。这条对我们有直接用处——语法高亮的 grammar 贡献在我们这里同样是数据，本提案的约束对它并不适用，这也正是它该直接投平台的槽、不读配置节的原因（见 PRFC-0004）。

反面的教训来自 OSGi：它是少数几个既有全局注册表、又坚持要多版本共存的宿主，办法是每个 bundle 一个 ClassLoader，换来的正是「同一个类在另一个 bundle 里不是同一个类」这类长期被诟病的问题。

综合起来，本提案取 VS Code 的身份模型——一个安装一份，身份即名字，破坏性版本换名字重发——和 Cargo `links` 的拒绝形状：全局唯一的名字，在解析期具名拒绝。不取 npm 与 Cargo 对普通依赖的宽容，因为那份宽容建立在「两份互不照面」之上，而我们的接口表恰恰要求所有东西在同一个命名空间里照面。

## Unresolved questions
[unresolved-questions]: #unresolved-questions

安装面拒绝到什么粒度，还没定。同名不同版一律拒绝，还是允许「升级」作为一个显式动作，先卸后装？后者顺手，但要说清楚正在被使用的插件能不能原地换版。

拆安装够不够用，要看实际。如果「一个 Project 一台机器」从逃生口变成常规做法，Machine 那边的开销——每台一份数据根、一次安装推送——会成为主要成本，到那时要重新评估进程内隔离。

## Future possibilities
[future-possibilities]: #future-possibilities

既然一个安装只有一份，「装的是哪一版、从哪来」就是个确定的答案，值得直接显示在插件页上。

多台 Machine 各有一份供给集时，一张「哪台装了什么版本」的对照表，能让「拆成两个安装」这条路好走很多。

如果「破坏性版本即新插件」成了常规做法，插件目录可以为它提供约定，比如把同一作者的 `foo` 和 `foo2` 显示成一条线上的两代。不过那属于目录的设计，不构成接受本篇的理由。
