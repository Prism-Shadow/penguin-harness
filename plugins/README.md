# Built-in plugins

The PenguinHarness plugin library. Each plugin is its own npm package — `@penguinharness/<name>`, a directory under `plugins/` — whose `package.json` is its manifest: npm's own fields (`name`, `version`, `description`, `keywords`, `license`, `repository`) plus a `penguin` block for everything that is the product's (`title`, `description_zh`, `short_description(_zh)`, `category`, `icon`, `preinstall`, `quick_start`, `hooks`, `mcp_servers`; every key optional, a missing one shown as missing). Beside it are an `icon.svg` (the icon of everything the plugin ships, which its installed skills and hook package inherit) and the content, found by convention: **skills** (`skills/<name>/SKILL.md`, installed into an Agent's `agent_state/skills/`) and/or a **hook package** (`hooks/*.mjs`, installed into `agent_state/hooks/<plugin>/` with a generated `hooks.json`). A plugin may also declare **MCP servers** in `penguin.mcp_servers` — entries in the `tools.mcpServers` shape of `system_config.yaml`, with `${KEY}` references to the Agent's vault for anything secret — which installing it appends to that Agent's `tools.mcpServers`. There is no `plugin.json`. The loader lives in `@prismshadow/penguin-core`, which depends on these packages and reads their directories at runtime — the files are the source of truth — and a shipped package must read with no warning (core's `plugins.test.ts` checks every one).

A plugin's version is its npm version (`package.json`, which follows the release). Dated versions — `YYYY.MM.DD.N` — belong to what an Agent may edit locally: every skill's `SKILL.md` frontmatter carries its own `version`, and a hook package's is `penguin.hooks.version` in `package.json`, which the installer writes into `hooks.json`. Change a skill and raise its `version`; change a hook script or the `penguin.hooks` commands and raise `penguin.hooks.version` (CI checks both against the base commit, `scripts/check-plugin-versions.mjs`). Skills follow the "index first, body on demand" design: only their metadata is injected into an Agent's system prompt; the Agent reads the full `SKILL.md` via shell when it actually needs it. Hook scripts are plain Node (builtins only): the harness runs them as subprocesses at the loop's hook points with `{ hook, session_id, trace_path }` on stdin and reads their JSON answer from stdout.

Included plugins, by category (`PLUGIN_CATEGORIES` in `packages/core/src/plugins/index.ts`; a plugin with no or an unknown category lands in an "Other" group). A plugin built around someone else's product carries a `use-` prefix — `use-firecrawl`, `use-bento-slides`, `use-claude-code` — so the package name says what it is for rather than claiming the product; the skills inside keep their own names:

| Category | Plugins |
| --- | --- |
| Agent Self-Evolution | `default-rsi-toolkit`, `opro-rsi-toolkit`, `ape-rsi-toolkit`, `ace-rsi-toolkit`, `awm-rsi-toolkit` |
| Office Productivity | `a2ui`, `data-analysis`, `use-firecrawl`, `browser-automation`, `use-bento-slides`, `humanizer`, `goal`, `continual-learning`, `agent-company`, `penguin-support` |
| Software Development | `software-development`, `use-claude-code` |
| AI App Development | `agent-development`, `agent-evaluation`, `model-development`, `skill-porting` |

The four `sandbox-*` packages are not library content but server modules: Agent Sandbox backends that confine every command an Agent runs (`sandbox-bwrap` on Linux, `sandbox-seatbelt` on macOS, `sandbox-wsl` on Windows, `sandbox-dsh` on all three, file writes only). Each carries a `penguin` block in its `package.json` (descriptions and the `sandbox` category; no skills or hooks) and an `icon.svg` for its card on the Plugins page, where an admin installs it on the server.

`humanizer`, `use-claude-code`, `continual-learning`, `agent-company` and `penguin-support` carry `preinstall: false`, so `default_agent` does not get them at initialization — they are installed from the library on demand (`agent-company` by the organization itself, when it creates the CEO and hires employees, or by hand onto any Agent that should be able to create one). `goal` is the stop hook behind goal mode: its `start.mjs`, a `user_prompt` command marked `"trigger": "host"` so that it runs only when a goal starts, writes the Session's `GOAL.json` and composes round 1; its `stop.mjs` reads the Trace after every Task and injects the next round or ends the goal. `continual-learning` hands a long task's condensed excerpt to a background subagent that folds the findings into the agent's skills.

`a2ui` makes replies easier to read and act on: a choice, a form with every basic control (one or several lines of text, a number, a slider, one or several options, a dropdown, a switch, a date and a time), a procedure in steps, a callout, a Mermaid diagram, a basic chart drawn from data (line, area, bar, pie, scatter, histogram or gauge), or a weather, clock, countdown, metrics or system-resource widget (the data widgets are built on the basic charts) written as a fenced block inside ordinary Markdown, which the Web App renders with its own components (a pick fills the composer as plain text) and every other surface shows as readable text. The skill carries STE-style writing rules for Chinese and English, two hand-written, dependency-free scripts that print ready-made blocks from real data (`scripts/weather.mjs` reads Open-Meteo, `scripts/sysinfo.mjs` the machine it runs on), and `scripts/check.mjs`, a self-contained bundle of core's `@prismshadow/penguin-core/a2ui` grammar (`pnpm build:a2ui-check` regenerates it; a core test fails when it is stale) that validates every block, scores the draft and prints the self-review rubric before the reply is sent.

`browser-automation` drives the agent browser through `penguin browser` — the desktop app's built-in browser, or the user's own Chrome through the PenguinHarness Browser extension: GenericAgent's scan → act → check loop over simplified HTML, trusted clicks and typing, and the user's own sign-ins, with Amazon orders as the worked example.

`agent-development` is building on PenguinHarness itself: `agent-initialization` sets an agent up from a requirement, `penguin-sdk` connects a program to an agent (embedded with the SDK or over the Agent API), `penguin-plugin` builds the workbenches an agent keeps beside its chat, `unified-llm-api` calls any model through one API, and `penguin-config` and `penguin-orchestration` drive settings, agents, Sessions, costs and schedules from the shell.

`default-rsi-toolkit`, the Default RSI Toolkit (RSI: recursive self-improvement), is the trial → reflect → improve loop in one Skill, `agent-optimization`: it improves the Target Agent to version N+1 from measured Benchmark results, with a snapshot before every round. The loop's other steps sit with their audience: creating the Target Agent is `agent-development`'s `agent-initialization`, and designing a Benchmark (`benchmark-design`) and running and scoring its cases (`agent-evaluation`) are the `agent-evaluation` plugin, Agent Evaluation, which the loop measures through. All four were previously published together as `agent-tuning`; the Skills kept their names, and only `agent-initialization`, whose text changed, a new version.

`opro-rsi-toolkit`, `ape-rsi-toolkit`, `ace-rsi-toolkit` and `awm-rsi-toolkit` are the algorithm toolkits: each ships one Skill of the same name that runs OPRO, APE, ACE or AWM the way its paper does. Each is self-contained — it creates the Target Agent's learning slot itself, runs every measurement through its own `references/evaluation.md` and records each complete evaluation in the Benchmark's `scoreboard.yaml` — so it runs with no other plugin installed. That reference is byte-identical in all four toolkits, and a core test pins the copies together: change one, change them all. A self-evolution toolkit's name ends in `-rsi-toolkit` (`default-rsi-toolkit`, `opro-rsi-toolkit`), and an algorithm toolkit's one Skill carries the plugin's name. Reproducing a Benchmark is not a plugin concern: reproduced Benchmarks live in [penguin-harness-benchmark](https://github.com/Prism-Shadow/penguin-harness-benchmark) and are imported into a Project, and a Benchmark's own run procedure is written in its case statements and that repository's README, never in a plugin. Importing a reproduced Benchmark's package is `benchmark-design`'s job (`reference/package.md`).

`agent-company` is the whole toolkit of company mode, entry point included. `company-setup` is that entry point: the skill that creates an organization with the user, asking one question at a time and ending at `penguin org create`, leaving hiring and tickets to the CEO. `company-employee` is the protocol every desk and ticket session follows — including the rule that whatever touches the user's machine, spends money or reaches outside the organization is asked of the board in the all-hands channel first — and `company-ceo`, `company-hr` and `company-finance` are the playbooks of those titles. `company-research` is what a research organization's authors and reviewers add: fix the harness and the metric, run the experiment loop inside a resource envelope the board approved, keep only improvements, and put every claim through a reviewer who tries to break it. `company-mirror` is the seventh: the protocol a company of digital twins runs on instead, where every employee mirrors a real colleague and the company relays between people rather than filing tickets. Because the plugin is `preinstall: false`, `company-setup` is no longer on every Agent by default — an Agent gets it by installing `agent-company` from the library (the Agents page), and the CEO and the employees carry it already.

## Development

The plugins are data, not code — there is nothing to build here. The loader, its types and their tests live in `packages/core`:

```bash
pnpm --filter @prismshadow/penguin-core build       # includes the plugin loader
pnpm --filter @prismshadow/penguin-core test        # loader, README tables, the hook scripts against fake Traces
```

`penguin-support` supplies the default Project's customer support agent with a documentation Skill and the `workbenches/support/` app. It is not installed on General Agent. Workbench code is copied through the same plugin install path as Skills; updates preserve `state.json` and workbench history. Each workbench declares a dated `penguin.version` in its own package.json. A workbench-only package can also be installed from the library.

Each plugin that ships skills also has its own `test/skills.test.ts`: it runs every `skills/<name>/` through [`@prismshadow/skills`](../packages/skills) (its `SKILL.md` must pass the parser vendored from vercel-labs/skills), so `pnpm -r test` covers them. The loader's own rules on top of that — a one-line description, skill names unique across the library — are core's test.
