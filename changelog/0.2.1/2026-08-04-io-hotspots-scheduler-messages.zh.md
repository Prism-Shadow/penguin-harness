那次产出了 Trace 索引的磁盘 IO 审计留下了两处热点；两处都已关闭。

## 调度器心跳与 Project 配置读取

30 秒一次的调度器心跳此前会重新读取每个 Agent 的每一个定时任务文件，并为每个定时任务文件重新解析同一份 `.project_config.toml`，永无止境，且不做任何变化检测——这是该进程中唯一一处无条件的周期性磁盘负载。定时任务扫描现在按 Agent 缓存，以定时任务目录的 mtime 加上逐文件的 mtime/size 检查为键（逐文件的 stat 堵住了 POSIX 的那个盲点：原地编辑不会触动目录 mtime，因此手工编辑过的文件在下一次心跳时仍能被拾取）；Agent 目录的枚举本身也以同样方式设闸，而那条「刚刚变化的 mtime 绝不缓存为干净」的哨兵移入了共享的 `internal/mtime-gate.ts`，Trace 索引现在也导入它——契约只存在于一处。`.project_config.toml` 在 `ProjectConfigService` 内部获得一份已解析表的缓存，复用前先做 stat 检查，并由每一条服务写入路径同步失效，因此调度器校验、定时任务路由与用量定价三者对磁盘上的每一个版本共用一次解析，而手工编辑仍然能生效。稳定状态下每次心跳：若干次 stat，零次文件读取；调度行为、列出顺序与校验语义逐字节一致，而测试以 fs 探针固定住这个零读取的稳定状态。

## 聊天历史分页

`GET /api/sessions/:id/messages` 此前为每个请求重建整个会话的对话记录——每个分片整份读入，递归包含子 Agent 会话，而且每次 SSE 重新同步都要重做一遍。该端点现在接受增量式的游标参数：`tailLimit` 返回最新的窗口（并带上运行中会话的实时附着内容，捕获语义不变），`before=<shard>:<ordinal>` 则往回翻更早的历史；不带参数时响应与此前逐字节一致，并由一个原始字节测试固定。窗口只在 Task 边界处切分——工具调用配对、压缩跨度与成组发送绝不会被切开——而且只读取与该窗口重叠的那些分片，分片清单来自 Trace 索引，更早分片的轮次数与 Token 总量则由逐分片的 `page_stats` 前缀缓存提供（这是一个派生的、带版本的列，以幂等方式加进已有数据库；用户无需任何操作）。Web 端先加载尾部（200 个单位），并在向上滚动时每次回填 100 个、以锚定方式前置插入；而一次重新同步只有在纪元与游标连续性可证明时才拼接到保留的前缀上，任何存疑情形都回退到旧的整份重新拉取。对话大纲通过服务端提供的「更早轮次数」，在部分历史上仍保持全局正确的轮次编号，而头部的 Token/已用时间数字则通过带种子的前缀统计保持真实。
