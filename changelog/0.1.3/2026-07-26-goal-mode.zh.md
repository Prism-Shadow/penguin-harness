# 目标模式：在一个 Session 上循环执行 Task，直到目标达成

- **Date:** 2026-07-26
- **Type:** feature
- **Scope:** `core`, `server`, `web`, `cli`, `docs`
- **PR:** [#66](https://github.com/Prism-Shadow/penguin-harness/pull/66)

[English](2026-07-26-goal-mode.md)

普通 Task 在模型停止调用工具并作答时结束——对一次请求而言没问题，对一个目标而言则是错的。目标模式把这个约定反了过来：用户陈述一个目标，系统就在同一个 Session 上持续驱动 Task，每一轮都重新注入该目标，直到目标进入终止状态。沉默不再意味着工作结束；模型必须通过一套协议宣告完成，其余情况一律继续循环。

## 一个 API：`session.run(input, { goal })`

目标模式是 SDK 那一个入口的一个选项，而不是独立的驱动器：`session.run(input, { goal: { budget } })` 把输入的文本当作目标，在该调用内部循环若干轮，并以恰好一条携带结果的 `goal_finished` 事件消息结束消息流（同时写入 Trace）。宿主消费的仍是它们本就在消费的那条消息流；轮次边界即被注入的轮次输入，可通过 `isGoalRoundInput` 识别。

## 协议

该循环创建 `scratchpad/<session_id>/GOAL.yaml`（与 PLAN.md 约定同级）——两个字段，由系统在创建时恰好写入一次：`objective`（其权威取值存在循环的内存中，并在每一轮的区块中重新陈述）与 `status`，即模型回传给循环的信箱（只能写 `complete` 或 `blocked`，每轮之后读取）。系统侧的结束方式只体现为 `goal_finished` 的结果以及服务端状态；该文件始终保留模型自己最后一次写入的内容——那正是一个被打断的目标所需要的恢复点。读取是宽松的：文件缺失、YAML 损坏，或状态不在协议内，都归一化为 `blocked`，使循环停止而不是空转。

每一轮的用户消息是一个 `[goal]` 协议区块（与 `[use_skills]` / `[user_steering]` 同属方括号标记族），其后跟一段普通正文：第 1 轮逐字携带调用方的消息——包括 Skill 调用区块在内——之后各轮则重新注入目标（即第 1 轮文本剥去开头的标记区块；GOAL.yaml 中记录的是同一套推导结果）。该区块内嵌 GOAL.yaml 的内容（由创建该文件时所用的同一批取值组装而成），因此模型看到的正是它被要求编辑的那个文件，并在单独一行上携带当前的预算数字。由于内嵌的 `objective` 属于用户数据，`[goal]` 的闭合标签采用行锚定匹配：YAML 序列化会让字符串内容远离第 0 列（块标量有缩进，单行取值处于行中），因此一个精心构造、包含 `[/goal]` 的目标无法在任何解析它的地方（前端折叠、标题剥离）提前终止该区块。

该区块还携带工作规则：一份完成度自检（提示词层面——系统不校验被宣称的 `complete`）、不得把目标缩水为更容易的子集、进度须记入 PLAN.md 以便在压缩中存活，以及一条阻塞规则——同一个阻塞条件必须连续三轮持续存在，模型才可以宣告 `blocked`，因此一次瞬时障碍不会终结目标。以中止收场的一轮——或被引擎在逐 Task 的 `max_turns` 上限处截断的一轮——会停止整个循环且不再重新触发，磁盘上的目标保持 `active`，成为一个干净的恢复点；另有一道 100 轮的硬性兜底，用于约束那些模型压根不写该文件的目标。

## Token 预算

计量是增量式的——非缓存输入加输出（`request.total − cache_read`），在每一次请求上累加，包括 `run_subagent` 的子会话；这是一份花费估算而非账单（缓存读取的成本只是非缓存输入的一小部分，未计入）。预算（可选；`-1` 表示无限，即默认值）在轮次之间检查；额度耗尽会触发最后一轮收尾（做总结、列出剩余工作、不做客套的 `complete`），然后系统以 `budget_limited` 结束该目标。

## 各接触面

- **CLI 聊天**：`/goal[:<budget>] <objective>`（支持 `500k` / `2m` 后缀）；Ctrl-C 中止整个循环，逐轮的统计行维持正常的聊天节奏。
- **CLI run**：`--goal [budget]` 把 `-m` 变为目标；只有目标真正完成才以 0 退出。
- **Server**：`POST /api/sessions/:id/tasks` 接受 `goal: { budget }`（同一请求上的 `thinkingLevel` 会搭乘每一轮）；整个目标作为一段 `running` 跨度运行（既有的中止端点与定时任务排队因此自然表现正确），进度落入新的 `goal_state` 表，并以 `goal_started` / `goal_round` / `goal_finished` SSE 事件流出，`GET /api/sessions/:id/goal` 可还原最近一次运行。
- **Web App**：输入区新增一个「+」扩展菜单（面向输入附加功能的通用入口，目标模式是它的第一项，也可经斜杠菜单的 `/goal` 到达），启用后出现带行内预算输入框的目标芯片；在输入区选中的 Skill 会像普通发送一样，以 `[use_skills]` 区块前置到第 1 轮消息上；每一轮都渲染为普通的用户气泡，下方带一行「Goal · 第 N 轮」的说明，输入区上方另有一条实时横幅跟踪轮次、Token 与终止状态。
