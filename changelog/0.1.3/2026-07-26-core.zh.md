# Core：恢复时忽略旧的思考等级；空压缩摘要不再算作成功；read_file 的密钥守卫加固

[English](2026-07-26-core.md)

自思考等级变为逐轮运行参数（0.1.2）以来，`session_meta` 就不再记录它——但恢复流程仍会尊重旧 Trace 的 meta 中出现的 `thinking_level` 字段，并把它还原为被恢复 Session 的默认值。这项兼容读取已被移除：恢复现在一律从 Agent 的当前配置取等级，旧字段被直接忽略。唯一的行为后果是：被恢复的旧子 Agent 会话不再保留它在派生时继承的等级——它像其他一切一样跟随执行恢复的 Agent 的配置。实时运行中的派生继承、逐轮拾取器，以及 meta 记录的内容，均未改变。

## 空的压缩摘要是失败，而不是结果

一个只返回了思考内容或一次工具调用、没有文本的压缩请求，此前会被判定为 `completed`，于是包出一个空的 `<context_summary>` 并丢弃旧上下文：这正是压缩绝不能做的事，因为 Agent 会因此丢失任务状态（issue [#83](https://github.com/Prism-Shadow/penguin-harness/issues/83)）。三处修复堵住了它。压缩请求保持其配置——包括工具——**与普通请求逐字节一致**（同一个冻结的配置对象，由测试固定）：省略或改动工具列表会改变请求前缀，从而恰好在上下文最大的时刻打爆 Provider 的提示词缓存，使压缩成本翻数十倍。凡是 `completed` 响应但其抽取出的摘要 trim 后为空、或以工具调用作答的，一律拒绝：任何已提交的工具调用会先被**修复**——为每次调用合成一条失败的 `tool_call_output`，采用普通工具失败的形态，写入 Trace 并前置到重发的输入中，使 Provider 侧的配对保持完整（而如果压缩被放弃，这些修复会转入结转内容，因此实时的 LLM 对象绝不会留下悬空的 `tool_use`）——然后请求重试，并配有独立于共享传输重连预算的 5 次拒绝上限；额度耗尽后，压缩以 `compaction_end(failed)` 失败，原上下文与 Trace 文件均予保留。而恢复流程也不再从一个无文本的压缩闭合中编造出空摘要：这样的闭合视为无效，原上下文照常回放，因此已被该缺陷咬到的 Trace 也能找回其任务状态。

## 任务中途的压缩不再重发 AgentHub 已有的内容

空摘要的修复留下了一个有界的隐患（issue [#85](https://github.com/Prism-Shadow/penguin-harness/issues/85)）：当自动压缩在任务中途触发时，待处理的本轮输入会搭上压缩请求——而一旦某次尝试被**提交**进 AgentHub 的历史，在重试时（或放弃之后）重发该输入，就会把重复的 `tool_result` 递给严格的 Provider 并被拒绝。现在的规则是基于一个事实的干净二分：只要有任何一次压缩尝试已提交，结转内容即被消耗——重试只重发配对修复加提示词，放弃之后下一个请求从已提交状态继续，不再重发本轮的输出；如果什么都没提交，则逐字（对象层面同一）还原此前的结转内容。压缩窗口内的中止会并入待处理状态而不是覆盖它，重放在重启后也会重建出同样的吸收状态，因此实时会话与被恢复的会话结论一致。

## read_file 的密钥守卫堵住大小写与符号链接绕过

内置的 `read_file` 按 basename 拒绝密钥存储（`.vault.toml`、`.project_config.toml`）——这是它自己的守卫，因为 `permission: "r"` 使该工具在只读审批下自动获批，而 shell 工具仍受读写门禁约束。此前那次检查是对词法 basename 做大小写敏感比较，留下两条绕过路径：大小写不敏感的文件系统（macOS/Windows）上 `.VAULT.TOML` 就能打开 vault；而符号链接自身的名字并不能说明它解引用到什么。该守卫现在会转为小写，并同时检查词法 basename 与 realpath 目标的 basename。在大小写敏感的文件系统上，这种小写比较可能拒绝一个大小写不同、实际并非密钥存储的同名兄弟文件——对一个守卫而言，这个误报是正确的取舍。
