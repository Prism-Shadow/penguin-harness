# The direct GPT-5.6 row displays the Sol variant it reaches

- **Date:** 2026-08-19
- **Type:** fix
- **Scope:** `model-catalog`, `core`
- **PR:** [#348](https://github.com/Prism-Shadow/penguin-harness/pull/348)

[中文版](2026-08-19-gpt-5.6-sol-display-name.zh.md)

The built-in catalog's direct OpenAI `gpt-5.6` row is shown as **GPT-5.6 Sol** instead of **GPT-5.6**, so its label names the variant the id actually reaches. The model id is untouched.

## Details

- The bare `gpt-5.6` id routes to `gpt-5.6-sol` upstream and is priced as that tier, while `gpt-5.6-luna`, `gpt-5.6-terra` and OpenRouter's `openai/gpt-5.6-sol` listing all displayed their codename already — this row was the only one whose name left the variant unsaid.
- Only the display name changed. The row still sends `gpt-5.6`, and its pricing, context window, vision flag and client routing are as they were, so nothing about the request or the cost estimate moved.
- The catalog test that pins one display name per model across a direct group and its gateway listing was extended to the three GPT-5.6 rows, which had been left out of it while the sol row's two names disagreed.

## Compatibility

A preset is copied into a Project's `.project_config.toml` without a `display_name`, and the field is resolved as the stored value falling back to the catalog, so an existing Project shows the new label straight away — no preset sync needed. A model whose name was edited by hand keeps that name, because the stored field still wins. Since the id never changed, a stored model and a default model set to `gpt-5.6` keep working either way.
