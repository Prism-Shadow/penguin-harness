# 更大的附件，以及交到管理员手上的上传限制

- **Date:** 2026-08-19
- **Type:** feature
- **Scope:** `server`, `web`, `docs`
- **Issue:** [#345](https://github.com/Prism-Shadow/penguin-harness/issues/345)

[English](2026-08-19-larger-attachments.md)

输入框的文件附件此前限制为单个 10MB、单条消息合计 12MB。现在默认放宽为**单个 100MB、单条消息合计 120MB**，并且管理员可以直接在用户菜单里调整这两个数值，既不必改配置文件，也不必重启。

## 整条链路要么一起动，要么都不动

10MB 这个数字原本写在四个彼此独立的位置——输入框的预校验、服务端的单文件上限，以及两种语言各自的拒绝文案——之间没有任何东西保证它们同步。此时单独抬高其中一个，比原样不动更糟：客户端一旦比服务端更宽松，用户得到的就不再是一句清晰的「文件过大」，而是一次跑完整程、最后死在通用报错上的上传。

所以这个数字现在只有一个归属。它由服务端持有，经 `GET /api/me` 的 `uploadLimits` 下发，输入框据此校验——提示文案里引用的也是同一个数字，因此不会再出现提示中的上限早已失效的情况。

**请求体上限**同理，改为推导而非固定值。草稿会话尚无 Session 可供上传，附件因此以 base64 `data:` URL 随 Task 请求一起送达，体积膨胀 4/3；若上限仍停在 20MB，100MB 的附件会在 HTTP 层被拒，报出的还是「请求体」而非「文件大小」形态的错误。现在它等于 `base64(单条消息合计上限) + 一张内嵌图片与 JSON 外壳的余量`，默认约 190MB，并在管理员调低上限时随之回落——不会出现上限明明很低、服务器却仍然照单全收 300MB 请求体的情况。

## 上传限制（管理员，用户菜单）

新增的**上传限制**弹窗与「代理选项」并列，做法也完全一致：一个表单，由一次 `PUT /api/admin/settings` 写入，仅管理员可见，校验权在服务端。

- **单个附件上限**与**单条消息附件合计上限**，均以整数 MB 填写，取值范围 **1–200MB**。管理员若把「100GB」按 MB 填成 102400，会被拒绝并在输入框下方给出原因，而不是照单接受。这个天花板划在传输真正失效的位置：请求体被整体缓冲并作为单个字符串 JSON 解析，而 V8 对字符串长度的上限约为 512MB。
- 合计上限不得低于单个上限，且校验针对**生效后**的组合——因此只抬高单个上限、或只调低合计上限，同样会被拒绝，而不是悄悄产生一种「单个合法的附件反而发不出去」的配置。
- 校验一律先于写入，因此一个字段不合法不会影响其余字段；改动在下一次请求即生效，无需重启：校验逻辑与请求体上限都在每次请求时读取该设置。

有两个数值刻意不开放。单条消息的附件**数量**仍固定为 20——它约束的是小卡片一行还好不好用，而不是服务器扛不扛得住，后者是字节预算该管的事。

## 对话内嵌图片保留自己那条低得多的上限

附件并不是多模态输入：它被写入会话 scratchpad，以 `[attached file: <路径>]` 一行交给模型，由普通文件工具按路径打开。下游没有任何环节的开销随它的体积增长，这正是 100MB 得以成立的前提。

内嵌图片恰恰相反。它进入对话，被原样写进 Trace JSONL，而该文件在每次翻阅历史、每次恢复会话时都会被整体读回——读成一个 JS 字符串。一张过大的内嵌图片带来的不是一次慢请求，而是一个再也恢复不过来的会话。何况图片此前根本没有做过大小校验：50MB 的粘贴之所以会失败，只是因为请求体上限恰好卡在那里，而且失败发生在标签页已经把文件 base64 并上传完之后。

因此图片被明确限制在 **20MB**（超出返回 413 `image_too_large`），客户端与服务端同时把关，且不随附件上限一起放宽。这个数值高于旧请求体上限实际允许的体积，所以此前能粘贴成功的图片不会因此失效。需要说明的是，它只是传输层的上限，并不代表模型一定会接受：供应商通常在 5MB 左右，`read_image` 工具同为 5MB，介于两者之间的图片可以顺利上传，仍可能被模型拒绝。
