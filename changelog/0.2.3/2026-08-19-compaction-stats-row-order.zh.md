# 收尾压缩在横幅出现之前就结算本轮统计行

- **Date:** 2026-08-19
- **Type:** fix
- **Scope:** `web`

[English](2026-08-19-compaction-stats-row-order.md)

对话结束之后才跑的压缩，现在在压缩开始的那一刻就结算本轮的统计行，横幅因此直接诞生在统计行下方，而不是事后再被挪到它下面。

## 详情

统计行原本最终也会排在收尾压缩横幅之上——压缩自成一轮，负责陈述这轮对话的统计行理应在前——但它是在 Task 转入 idle、也就是压缩跑完之后才被放到那个位置的。压缩请求面对的是整个会话最大的上下文，那几秒里横幅就紧贴在回复下面，等统计行插到它上面时再往下跳一格。

- Task 仍打开时开始的压缩，若刚跑完的这一轮没有产生工具输出（引擎判定「任务中途压缩」用的同一条依据），**且**本轮最后一个条目是模型的回复，即视为收尾压缩。两个信号必须一致；任何一个拿不准就沿用此前「结算时再定位」的行为，它仍然覆盖中途加入的流和回复未落成条目的轮次。
- 任务中途的压缩不受影响：该轮保持打开，其账目（含这次压缩的 Token）照旧在 Task 结束时结算。
- 收尾压缩期间排队的 steering 会在压缩之后送达并让 Task 继续；此时 steering 小块会开启续跑自己的一轮，续跑的回复因而保有自己的页脚，而不是并入一个已经结算的轮次。
