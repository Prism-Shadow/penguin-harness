# 从已完成的回复分叉会话

- **Date:** 2026-08-15
- **Type:** feat
- **Scope:** `web`, `server`, `docs`
- **PR:** [#297](https://github.com/Prism-Shadow/penguin-harness/pull/297)
- **Issue:** [#293](https://github.com/Prism-Shadow/penguin-harness/issues/293)

[English](2026-08-15-session-fork.md)

已完成的主线模型回复旁边新增了「分叉」操作。新建的 Session 沿用同一个 Project、Agent、模型、Workspace、审批模式和标题，历史则截断到所选的那个已完成 Task。

分叉出来的会话拥有独立的 Trace 分片和递归复制的 scratchpad 快照。本地图片与附件的标记路径会改写到新的 Session id 上，因此任意一侧的会话被删除后，附件仍然能正常显示。服务端会拒绝伪造或越界的 Trace 位置，并且在源会话运行中或压缩中时拒绝分叉。

## 分叉前先确认

分叉操作位于**复制按钮的右侧**，点击后先弹出确认框（复用共享的 `ConfirmModal`），说明该操作会把对话截至这条回复复制成一个新对话。只有点击确认才会真正发出分叉请求；复制本身仍然是不需要确认的一次点击。

## 删除会话不再回头请求它

删除当前正在查看的对话——也就是丢弃刚试过的分叉时最自然的做法——每次都会留下一条 `[http] session_not_found` 记录，在成本中心的错误面板里可以看到。

对话页在遇到「路由指向的会话不在已分页的列表里」时会直接发一次查询：这对深链接是对的，但对本客户端刚刚删掉的那一行来说，必然只会拿到 404。现在会话列表会为自己删除的 id 记下墓碑标记，那次查询会先检查墓碑并直接跳过请求。列表裁剪与路由切换之间的先后顺序有意不再作为修复手段：列表状态放在 zustand store 里，其更新不受 React transition 车道的约束，靠调度顺序无法可靠地排出先后。
