# Trace 索引：mtime 闸门捕获落在非最新日期目录中的压缩轮转分片

- **Date:** 2026-08-11
- **Type:** fix
- **Scope:** `server`, `trace-index`
- **PR:** [#271](https://github.com/Prism-Shadow/penguin-harness/pull/271)

[English](2026-08-11-trace-index-compaction-rotate.md)

## 缺陷

上下文压缩会调用 `TraceWriter.rotate()` 把 Trace 切分为新的分片（`_002`）。新文件写入的是该 Session **最初**的日期目录（Writer 的 `dateDir` 在构造时即固定、此后不再改变），而该目录可能比磁盘上最新的日期目录更旧。

`TraceIndexService` 的 mtime 闸门为优化热路径，在确认根目录 mtime 未变之后，**只**对最新的日期目录做 stat 检查。注释中假定「实践中总是最新的那个（Writer 按当前本地日期命名目录）」。压缩的 `rotate()` 打破了这个假设：新分片落在一个更旧的目录里，而闸门从不检查该目录的 mtime，于是索引永远不会登记它。

`locateAll()` 只在索引对某个 Session 返回**零**行时才强制对账；由于 `_001` 已被索引（`rows.length = 1`），强制路径永远不会触发。结果是：`GET /messages` 只返回到 `compaction_end` 为止的消息，界面停留在「压缩完成」的横幅上。该分片会一直缺失，直到有别的事情为这个 Agent 触动了闸门——次日的第一个 Session（新的日期目录会改变根目录 mtime）、最新目录中出现任何新分片、一次导入或 Session 删除，或者一次强制遍历——因为闸门一旦真的去看，差异循环对被 rotate 触碰过的目录的跳过判定就会失败。实践中这把窗口限制在了午夜，而不是下一次重启。

## 修复

闸门现在对**每一个已知的日期目录**做 stat，而不再只看最新的那个。最新目录仍然被最先 stat，因此常见情况（今天的目录中出现新分片）依旧一次 stat 即可确定；其余目录并发 stat，只用于判定 rotate 这种情况。该做法仍然不需要 readdir，且树未变化时的快速返回路径依然有效。

这里显式做出的权衡是：安静状态下的热路径不再是固定的两次 stat，而是一次根目录 stat 加上每个日期目录一次 stat；而 Agent 每运行一个日历日就会创建一个日期目录，且没有清理机制——所以 N 会随 Agent 的生命周期增长，而不是停留在「屈指可数」。这些 stat 并发执行，而在多个 Agent 或子 Agent 子节点上扇出的调用方会成倍放大它。这也取代了 `changelog/0.2.1/2026-08-04-traces-page-scaling.md` 中对热路径的描述（「热路径是两次 stat——对 traces 根目录和最新日期目录各做一次 mtime 闸门检查」），那份已冻结的条目至今仍是这么写的。

仍有两个盲区，二者都源于按目录 mtime 而非文件 mtime 来把关：**原地追加**根本不会改变任何目录的 mtime（只有创建或删除目录项才会），而这正是被恢复的 Session 所做的事——core 会固定分片与日期目录，于是本次运行只是让既有文件变大，它已记录的 `size_bytes` 随之失效；以及**回填时间戳的写入**，即外部进程修改文件后又把其所在目录的 mtime 重置为缓存中的值。`locateAll()` 的强制重试只在整个 Session 未命中（索引行数为零）时触发，因此对于已有分片被索引的 Session，这两种情况都不在覆盖范围内：它会一直陈旧下去，直到出现一次无关的强制对账、一次显式的强制重建，或者一次重启。
