# schema 变更改由迁移表达，并随 platform 一同送达

- **Date:** 2026-08-27
- **Type:** feature
- **Scope:** `server`
- **PR:** [#383](https://github.com/Prism-Shadow/penguin-harness/pull/383)

[English](2026-08-27-schema-migrations.md)

`schema.ts` 声明的是一个全新数据库被创建时的形状，它无法表达一次变更。反复执行 `CREATE TABLE IF NOT EXISTS` 只会让数据库朝当前声明收敛，却始终不知道它从哪个状态而来，因此没有任何构建能区分 0.2.4 与 0.2.7 的库，也因此每次变更都必须是加性的才谈得上安全。现在 schema 变更是有序迁移，各自记入 `PRAGMA user_version`；推送的 platform 携带自己的迁移——一张表正是这样抵达一个比它所属功能更旧的运行时。

## 详情

- 迁移写明自己那份冻结的 DDL，绝不引用 `SCHEMA_SQL`：引用活动声明会让一条旧迁移在每次 schema 变动后悄悄改变含义。版本号自 1 起连续，发布后既不重编号也不再修改，因此一个版本戳指向的状态毫不含糊。
- 迁移与其版本戳在同一个事务中提交，因此中断的执行只会停在最后一个完整应用的版本上——绝不会出现迁移到一半的数据库。
- `swapSafe` 是热更新所要求的那个维度。推送的 platform 在活动数据库上启动，失败即回滚到前一个 platform，而后者要面对迁移已经造成的既成事实。加性变更能被它安然容纳，收窄性的则不能。运行时自身的打开过程可以应用任何迁移；而正在启动的 platform 只应用 `swapSafe` 的迁移，遇到其余的则在触碰数据库之前**整体拒绝**，抛出 `RestartRequiredError`。
- 目前有两条迁移，均为加性：0.2.4 → 0.2.7 新增 `messaging_bindings` 表与三个索引，0.2.7 → 0.2.8 为该表新增 `final_reply_only` 与 `render_markdown` 两列。一个 0.2.4 的库执行完它们之后，其 schema 与当前构建从零创建出来的一致——表、列、类型、约束与索引都相同。列的*顺序*可能不同，因为 `ALTER TABLE ADD COLUMN` 追加在末尾，而全新库中该列位于声明所在的位置；要让顺序一致就得重建表，那不是加性操作。
- 每条迁移都声明 `down`，或声明为 `null` 以表明它没有回退——这是必填而非可选，因此"没有回退"是作者明确说出的，而不是遗漏掉的。`rollbackTo` 从最新一条开始倒序执行，若范围内存在不可逆的迁移则**整体拒绝**。它是运维工具，且具有破坏性（撤销"新增一张表"会连同表中的行一起删除）；它刻意**不是**热更新的回滚机制：platform 启动失败回滚的是 platform，而非 schema。在一个刚刚启动失败的进程里撤销 DDL，等于对一个只知道一半的状态执行破坏性语句，而 `swapSafe` 的存在正是为了让"不撤销"本身就是安全的。
- 在迁移机制出现之前形成的数据库，版本号一律读作 0，实际形状却各不相同，因此迁移必须容忍"要做的事已经做过"。这不只是第 1 条迁移的问题：`schema.ts` 仍然完整声明当前形状，`openDatabase` 仍然执行它那份 `ensureColumn` 列表，因此一个数据库到达任何一条迁移时，该迁移的工作都可能已由声明式那条轨道完成。在 `SCHEMA_SQL` 被冻结为 baseline 之前，这里的每条迁移都保持幂等。
