# Plugins with no dependencies install and uninstall on a machine without npm

- **Date:** 2026-11-19
- **Type:** feature
- **Scope:** `server`
- **PR:** [#1664](https://github.com/Prism-Shadow/penguin-harness/pull/1664)

[中文版](2026-11-19-plugin-install-without-npm.zh.md)

The desktop app's server runs under Electron's utilityProcess, with no npm beside it, so installing a plugin from the market, through the published index's release channel, from a zip or a package directory, and removing one, all failed there. The installer now looks for npm before every operation. When it finds npm, npm does everything, as before. When it finds none, a package that needs nothing npm does is installed and removed by the server itself; a package that does is refused, saying why.

## Details

- A package needs npm when its version declares `dependencies`, `optionalDependencies`, `bundleDependencies` or a `peerDependencies` entry not marked optional, an install script (`preinstall`, `install`, `postinstall`, or the registry's `hasInstallScript`), or carries `binding.gyp` without `gypfile: false`. A `prepare` script does not count: npm runs it only for git and directory sources. An `os`, `cpu` or `libc` list that excludes the machine refuses the install, as npm's EBADPLATFORM does.
- By name: the server reads the package's abbreviated document from the registry the Plugin sources setting names (the official registry when it names none), each address followed by the mirrors the Plugin mirrors setting rewrites it into. The version follows npm's rules for tags, exact versions and `^`, `~` and x-ranges; other range forms are refused with a request to name a version. A name or version the registry does not have falls through to the published index's release channel, as npm's E404 and ETARGET do.
- Downloads are capped (a 32 MB document, a 64 MB tarball), each address has its own window, and the whole tarball or release asset is checked against its pinned sha512 before it is unpacked; an address serving other bytes hands over to the next one, and a version that pins no sha512 is refused. An address must be https, or http on the loopback, checked on the parsed URL, and so must every redirect hop; nothing redirects from https down to http.
- After the download, the package's own package.json and files are checked by the same rule, so a tarball that needs npm is refused even when the registry's document did not say so.
- Unpacking writes regular files only. Directories, symbolic links, hard links and device files are skipped, as npm skips links; an entry that is absolute or contains `..`, a backslash or a colon refuses the whole package, as do a file that is also a directory and two names equal but for case or Unicode normalisation; extended headers, global headers and lone zero blocks are read as node-tar reads them; a package may unpack to 256 MB and 20,000 files. The package's own package.json must be the name and version asked for. Every `bin` target is left executable.
- A zip or package directory installs exactly the files `npm pack` would publish from it, by npm's own rules (npm-packlist): `.npmignore` in each folder or else its `.gitignore`, the `files` field, npm's always-ignored names, and package.json, the README, the licence, `main`, `browser` and every `bin` target always. A git-ignored `.env` therefore stays out of the prefix and out of `archives/`. The server packs them into the `archives/` tarball `npm pack` would have written.
- A release channel's verified asset is kept in `archives/` and recorded as `file:archives/<asset>`, so a later npm run installs it from disk instead of fetching the release URL.
- The files are staged under `<prefix>/.staging/` and swapped in by renaming the installed directory aside first; on Windows a rename answered EPERM, EACCES or EBUSY is retried with backoff for up to a minute, as npm's graceful-fs does. A swap that fails puts the installed version back and refuses the install; when that move fails too, the old version is kept where it is, marked so the sweep leaves it, and the refusal says where. Staging older than an hour is swept at the next install. A file system failure along the way (no space, a name or a path too long, a prefix package.json that will not parse) is a refusal, answered 400 by the route. The prefix's package.json records the install as npm would (`^<picked version>`, or the range asked for when that version would leave it, or `file:archives/<tarball>`), and npm's hidden lockfile is removed so a later npm run reads the tree from disk.
- Removal without npm takes the directory and its package.json entry away and prunes tarballs nothing names any more.
- A package that needs npm, on a machine without it, is refused with its dependencies or scripts, where npm was looked for, and "Install Node.js, which includes npm (https://nodejs.org), then restart PenguinHarness so it finds npm." A link (a git repository or an https tarball) still needs npm. Failures that did not come from npm no longer start with `npm:`, and a package the route takes back out after an install without npm is not said to have run install scripts.
- A machine where npm was not found looks again at the next operation instead of keeping the answer until a restart.
