## 安装脚本为 0.1.6 之前的发布保留一条旧的程序压缩包路径

从本批次起，规范的 Release 产物是一个扁平的安装包，其载荷以 `payload.tar.gz` / `payload.zip` 的形式置于其中。直到 v0.1.5 为止的发布，在同样的产物名下直接提供程序目录树（顶层为 `penguin/`），而用户仍然可以固定到那些版本，或在本地保有这类文件。

**被容忍的旧形态：** 任何顶层没有 `payload.*` 的压缩包都被当作程序压缩包处理。以 `--version` 固定到 0.1.6 之前的发布会下载旧的原始产物并经这条路径安装；`--archive` / `-ArchivePath` 既接受新的安装包或其内层载荷，也接受旧的原始压缩包（仍要求相邻的 `.sha256`，被改名的文件仍回退到规范产物名的校验和加上清单规则）。

**生效范围：** 仅限 `install.sh` 与 `install.ps1` 中的形态探测与程序压缩包分支。发布打包、CI 与文档只描述新形态；不涉及任何磁盘上的用户数据（`~/.penguin/data` 从来就不属于安装或升级的范围）。

**用户需要做的：** 对于文档中记载的流程，无。

**移除：** 只要 0.1.6 之前的发布仍可能成为 `--version` 的目标，这条旧分支就应保留。当某次发布决定不再支持安装 0.1.6 之前的版本时，由准备那次发布的人删除程序压缩包分支，连同 `tar -tzf` / zip 条目探测一并删除；两个安装脚本中的相应位置都引用了本文件。

## 从 v0.1.5 及更早发布中保存下来的安装脚本无法安装新产物

这是一次刻意的不兼容，而非被处理掉的兼容：旧安装脚本会以同样的名字下载产物、通过外层校验和，然后以它那句「unexpected archive layout: top-level penguin/ missing」报错失败，因为新产物是一个安装包。文档中记载的安装命令不受影响——penguin.ooo 的转发脚本在运行时抓取的是附加在最新 Release 上的安装脚本——而对于一份保存下来的旧脚本，修法就是重新抓取一次。旧发布自己的产物不受触碰：一个固定在旧版本上的旧安装脚本可以永远正常工作。

## Windows 载荷去掉了它的 penguin.ps1 启动器

这是一次带自清理升级路径的刻意移除，而不是被容忍的旧形态。输入 `penguin` 不受影响——PowerShell 与 cmd.exe 都会解析到 `bin\penguin.cmd`，而它豁免于那条曾在默认客户端 Windows 上拦住 `.ps1` 启动器的执行策略。只有直接调用 `.\penguin.ps1` 的用法需要改为 `penguin` / `penguin.cmd`。本次改动之前完成的安装会保留其旧启动器直到下一次升级：安装脚本整体替换 `bin\`，因此重新运行它会连同旧 `bin\` 的其余内容一起移除陈旧的 `penguin.ps1`——这也正是那些已经出现「running scripts is disabled」错误的机器的修法。已经没有任何东西读取或重新生成该文件；无需后续的移除动作。
