## 把英文定为仓库工作语言

将所有残留的非 i18n 中文（注释、错误/日志信息、测试标题与固定数据、包元信息、e2e mock 内容）翻译为英文；中文仅保留在 i18n 词条、zh 文档，以及以 CJK 为目的的测试数据中。

## 细节

- 包元信息：`package.json` 的 description（根 / server / web / landing）以及 `link:cli` 的回退 echo。
- 源码注释：所有残留中文注释，包括 `packages/server/src/db/schema.ts` 中的整套 SQL 注释。
- 硬编码的非 i18n 用户可见文案（用户可见的语言变更；错误码、占位符与上限未动）：server 的 HTTP / 校验 / 409 信息、schedule TOML 校验错误、server 日志、core SDK 错误、CLI 回退错误、web 的 Provider 不变式。
- 测试：所有中文 describe/it 标题与语言无关的固定数据均已翻译，断言同步对齐到新的英文源字符串。
- e2e：mock LLM 对话内容与跨文件分支标记一致翻译（mock 的 `includes()` 分派所依赖的子串关系被保留）；zh 语言环境的 UI 断言保留；`e2e/README.md` 已翻译。
- 按要求保留的中文：zh i18n 词条与字段（`strings.ts` 字典、CLI 的 `i18n.ts`、`titleZh`、`short_description_zh`、zh 语言名标签、`*.zh.md` 文档），以及断言 zh i18n 输出或验证 CJK 专有行为的测试字面量（显示宽度、CJK id 校验、标题语言一致性、zh-CN e2e UI 断言）。
- 已知遗留：web 的 `formatTaskStats` 仍硬编码中文统计行片段；正确的修法是让它们走语言词条。

## 串行化开发预构建，修复 dev:server / dev:web 并发互相覆盖的问题

dev:server 与 dev:web 现在共用一次带锁串行、且去重的 skills 与 core 预构建，因此同时启动两者不再会破坏 dist/（此前两个开启了 clean:true 的 tsup 构建会在同一输出目录中竞争）。

## 细节

- 新增 `scripts/dev-prebuild.mjs`：围绕 `pnpm --filter skills --filter core build` 取一把磁盘互斥锁（在 `node_modules/` 下用原子 mkdir 实现）；并发调用会等待而不是互相覆盖。若持锁进程已死亡，或锁的存在时间超过 10 分钟，则崩溃残留的锁会被抢占。
- 一个 5 秒的成功时间戳用于合并重复构建：同时启动 dev:server 与 dev:web 只会构建一次（等待方直接跳过），而 dev:server 内部的再次调用是空操作。这个窗口被刻意设得很小，以保证「编辑后重启」的循环总会重新构建——「绝不基于陈旧依赖启动」的行为未变。
- 根级 `dev:server` 现在只是委托给 server 包的 `dev` 脚本（后者通过共享脚本完成预构建），从而去掉了历史上对 core 的重复构建；`dev:web` 则先经脚本预构建再启动 Vite。
- 在 `packages/server` 中单独运行 `pnpm dev` 现在也会构建 skills（此前只构建 core，尽管 server 在运行时会导入 skills）。
- 已验证：并发调用能正确等待 / 跳过并释放锁；同时启动 dev:server 与 dev:web 只执行一次构建，两个服务均能干净启动。

## 新增合并的 pnpm dev 与 dev:landing 快捷命令

`pnpm dev` 现在会同时启动后端与 Web 应用并带日志前缀（工作区依赖经共享预构建锁只构建一次），`pnpm dev:landing` 则从仓库根目录启动落地页的开发服务器。

## 细节

- `pnpm dev` 执行 `concurrently -n server,web "pnpm dev:server" "pnpm dev:web"`。此前合并这两者并不安全：每条命令都会用开启 `clean: true` 的 tsup 把 skills/core 预构建到同一 dist/ 目录，并行构建互相覆盖。带锁串行的预构建（见上文串行化预构建条目）消除了这一竞态，其成功时间戳还会把合并启动时的两次预构建收敛为一次。
- `pnpm dev:landing` 委托给 landing 包的 Vite 开发服务器（端口 7366，补齐 7364/7365/7367 的开发端口family）。landing 包没有工作区依赖，因此不涉及预构建。
- `concurrently` 加入根级 devDependency；README.md 与 README.zh.md 中的开发命令列表现在覆盖 `dev` 与 `dev:landing`。
- 已验证：合并启动恰好执行一次 skills+core 构建（另一次预构建等待后跳过），server 位于 127.0.0.1:7364、Vite 位于 localhost:7365；落地页开发服务器在 localhost:7366 响应。注意 Vite 绑定的是 localhost（IPv6 ::1）——用 curl 探测 Vite 端口时请用 `localhost` 而非 `127.0.0.1`。

## 开发命令自动保持 pnpm install 为最新

在执行开发命令前忘记 `pnpm install` 不再会导致启动失败：每条开发命令的前置步骤都会检查安装新鲜度（基于 lockfile 哈希的时间戳），并在 node_modules 缺失或 lockfile 变化时自行执行 `pnpm install`。

## 细节

- `scripts/dev-prebuild.mjs` 在其既有的锁内新增一个安装新鲜度步骤：安装成功后记录 pnpm-lock.yaml 的内容哈希，因此常规的开发启动不付出任何代价；而全新克隆或拉取到的 lockfile 变更会自动触发 `pnpm install`（并发的开发命令依然只安装 / 构建一次）。
- 锁与时间戳从 `node_modules/` 移到按仓库路径作键的操作系统临时目录——它们必须在首次安装之前就能存在（旧位置在全新克隆时会崩溃），而按检出目录隔离则由这个键来保证。
- `dev:docs` / `dev:landing` 没有需要构建的工作区依赖，但仍需要最新的安装：它们现在以 `--install-only` 运行该前置步骤。

## 升级 AgentHub 到 0.4.0，采用不透明的 fidelity 载荷

@prismshadow/agenthub 0.3.3 -> 0.4.0（agenthub [#159](https://github.com/Prism-Shadow/agenthub/pull/159)）：内容项以一个不透明的 `fidelity` 对象取代原有的项级 `signature` / `phase` 字段，OmniMessage 现在端到端原样携带它——包括 Trace、回放与恢复；`agenthub-dev` skill 加入内置库。

## 细节

- OmniMessage 的完整载荷（text、thinking、inline_data、inline_thinking、tool_call）以 `fidelity?: Record<string, unknown>` 取代 `signature?: string` / `phase?: string | null`——这是一个不透明的线路保真载荷，原样写入 Trace 并在回放时原样传回（Claude 的思考签名、GPT-5 的加密推理 `{id, encrypted_content}` 与 `{phase}` 标记、OpenAI 兼容协议的 `{reasoning_field}` 字段名）。构造器直接接收该对象；空对象视同不存在。
- GenerativeModel 的流式转换器与 AgentHub baseClient 的聚合行为保持一致：一个 thinking 块由其 fidelity 载荷收尾，且一串相同 fidelity 构成一个块（OpenAI 兼容客户端会给每个 thinking 增量都打上相同的 `{reasoning_field}`，这不能用来切分块——此举把 agenthub 的 reasoning-field 回放修复贯通到 PenguinHarness，使得面向严格 OpenAI 兼容上游的多轮对话得以存活）；文本片段在 `fidelity.phase` 不同时切分，在 `fidelity.signature` 出现时收尾，并合并 fidelity 的键。跨片段的文本 phase 粘性已移除（与 baseClient 一致）。
- `agenthub-dev` skill（AgentHub 自身的模型支持开发流程）被安装进内置库的 Penguin Development 分组，并按库的约定补齐（version/updated frontmatter、简短描述、一节「Before you start」，以及一个自定义图标）。
- 面向 0.4.x 的畸形分类修复：agenthub 现在把流式工具调用参数被截断的情况作为它自己的 `ToolCallArgumentParseError` 抛出（此前是裸的 `SyntaxError`），把仅有思考内容的补全作为 `EmptyResponseError` 抛出；`isMalformedJsonParseError` 能识别这两者（instanceof + name 回退 + cause 链），因此它们仍会归为 `malformed`，引擎会重连重试而不是让该轮失败（由 malformed e2e 覆盖）。
- 文档（omni-message、interfaces、sessions-and-traces；中英）与设计规格同步更新到 fidelity 语义。
- 本次改动之前写入的 Trace 在载荷上携带的是 `signature` / `phase`；按发布前不做迁移的策略，它们不会被转换（回放时旧字段被忽略——恢复这类 Session 会丢失 Provider 保真信息；如有需要请删除后重建）。
