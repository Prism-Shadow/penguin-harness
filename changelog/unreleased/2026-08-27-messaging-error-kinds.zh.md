# 消息通道里已经在聊天中解释过的拒绝，不再计为缺陷

- **Date:** 2026-08-27
- **Type:** fix
- **Scope:** `server`
- **PR:** [#511](https://github.com/Prism-Shadow/penguin-harness/pull/511)

[English](2026-08-27-messaging-error-kinds.md)

消息桥接捕获的每一个失败写入 `error_records` 时都没有带 `kind`，而记录器对非 HTTP 来源的默认值是 `unexpected`。于是两件既不意外、也不是谁的 bug 的事被归成了「不该发生、需要人介入」：

- 尚未开通 `im:message` / `im:message.history:readonly` 的飞书应用，其拒绝（错误码 99991672）本就会连同所需权限名与开通链接一起送到聊天里；
- 发往 QQ 的文件——该平台只接受挂在公网可达 https URL 后面的媒体，而本服务端无法提供这样的地址，因此每次都会得到完全相同的拒绝。

两者都改归为 `expected`。记录器的判据是**「是否需要人介入」**，而这两种情况的答案都是否：唯一能处理的人已经在聊天里拿到了办法，或者根本没有办法可施。

## 细节

- 新增 `runtime/messaging/error-kind.ts` 承载这条规则，并把每一种情况的理由写在旁边。它被写成一份按**类型**、且限定**捕获位置**的小白名单，而不是文案匹配：连接器未分类的一切都保留为 `unexpected`——这是安全的方向，真实故障被误计为常态会隐形，而常态噪声被误计为故障只是吵。按类型而非措辞判定，也让计数不依赖各平台如何遣词。
- 三种失败类型被放行：`MessagingPermissionError`（待开通的权限，聊天里已点名）、`MessagingMediaTooLargeError`（发送方换个更小的文件即可）以及新增的 `MessagingUnsupportedError`（该通道在结构上就承载不了）。QQ 的出站媒体拒绝改为抛出后者，而不再是裸 `Error`。
- 捕获位置与类型同样要紧，因为飞书的每一个调用抛出的都是同一种权限拒绝。只有入站图片下载与出站文件上传会把这条拒绝以通知的形式送进聊天，因此也只有这两处被允许记为 `expected`。发送、任务没能起来的入站消息、以及始终建不起来的连接，无论抛出什么都保留为 `unexpected`：那些位置上聊天什么也听不到，否则一个开通了接收权限、却没有 `im:message:send_as_bot` 的应用，会照单全收每一个问题、一个也不回答，而任何地方都不会有提示。
- 记录本身在其他方面全部照旧，包括仍然被写入：没人去开通的权限依然值得在看板上被发现，只是它不是缺陷。

## 兼容性

已经写入的错误记录保持写入时的分类——不会改写历史。本次改动之前记录的飞书权限拒绝仍是 `unexpected`，直到它随时间移出视图，因此升级后既有的「未预期错误」计数不会立刻下降。
