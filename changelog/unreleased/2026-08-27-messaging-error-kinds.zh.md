# 消息通道里已经在聊天中解释过的拒绝，不再计为缺陷

- **Date:** 2026-08-27
- **Type:** fix
- **Scope:** `server`

[English](2026-08-27-messaging-error-kinds.md)

消息桥接捕获的每一个失败写入 `error_records` 时都没有带 `kind`，而记录器对非 HTTP 来源的默认值是 `unexpected`。于是两件既不意外、也不是谁的 bug 的事被归成了「不该发生、需要人介入」：

- 尚未开通 `im:message` / `im:message.history:readonly` 的飞书应用，其拒绝（错误码 99991672）本就会连同所需权限名与开通链接一起送到聊天里；
- 发往 QQ 的文件——该平台只接受挂在公网可达 https URL 后面的媒体，而本服务端无法提供这样的地址，因此每次都会得到完全相同的拒绝。

两者现在都归为 `expected`。记录器的判据是**「是否需要人介入」**，而这两种情况的答案都是否：唯一能处理的人已经在聊天里拿到了办法，或者根本没有办法可施。

## 细节

- `runtime/messaging/error-kind.ts` 承载这条规则，并写下每一种情况的理由。它是一份按**类型**列出的小白名单，而不是文案匹配：连接器未分类的一切仍是 `unexpected`——这是安全的方向，真实故障被误计为常态会隐形，而常态噪声被误计为故障只是吵。按类型而非措辞分类，也让计数不依赖各平台如何遣词。
- 三种失败属于预期：`MessagingPermissionError`（待开通的权限，聊天里已点名）、`MessagingMediaTooLargeError`（发送方换个更小的文件即可）以及新增的 `MessagingUnsupportedError`（该通道在结构上就承载不了）。QQ 的出站媒体拒绝改为抛出后者，而不再是裸 `Error`。
- 被通道拒绝的发送——例如限流吃掉了回复中的一行——仍是 `unexpected`：那会丢失内容且无人被告知，与聊天里解释清楚的拒绝正好相反。
- 记录本身在其他方面完全不变，包括仍然被记录：没人去开通的权限依然值得在看板上被发现，只是它不是缺陷。

## 兼容性

已经写入的错误记录保持写入时的分类——不会改写历史。本次改动之前记录的飞书权限拒绝仍是 `unexpected`，直到它随时间移出视图，因此升级后既有的「未预期错误」计数不会立刻下降。
