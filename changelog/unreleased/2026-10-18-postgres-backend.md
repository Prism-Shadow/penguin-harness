# The platform database can run on PostgreSQL

- **Date:** 2026-10-18
- **Type:** feature
- **Scope:** `server`
- **PR:** [#1192](https://github.com/Prism-Shadow/penguin-harness/pull/1192)

[中文版](2026-10-18-postgres-backend.zh.md)

`PENGUIN_DB=pg` moves the server's own database — Sessions, usage records, settings, the Trace
index — from the data root's `web.db` onto PostgreSQL. SQLite stays the default: unset the
variable and the next start is back on the file, because the database holds no record of which
engine wrote it.

## How the data layer reaches PostgreSQL

- The platform's data layer keeps its synchronous `node:sqlite` API. A shim answers that API
  from PostgreSQL: the asynchronous `pg` driver runs in a worker thread of its own and the
  calling thread waits on `Atomics.wait`, so the repos' prepared statements, `SCHEMA_SQL` and
  the ordered migrations run unchanged. One handle is one connection, so a transaction spread
  over several `exec` calls stays one transaction, exactly as `node:sqlite` behaves.
- Statements are translated on their way out — the SQLite-isms the platform actually writes,
  and nothing else. Anything the translator does not recognise passes through, which is what
  PostgreSQL accepts for plain CRUD, CTEs, `ON CONFLICT` and `RETURNING`.
- The schema is created on first connect inside one PostgreSQL schema (`PENGUIN_PG_SCHEMA`,
  default `penguin`), through the same `CREATE TABLE IF NOT EXISTS` + `ensureColumn` +
  migration path a fresh `web.db` takes. `PRAGMA user_version` becomes a row of a `_pg_meta`
  table, so the migration ladder keeps its version stamp.

## What the translator rewrites

| SQLite | PostgreSQL |
| --- | --- |
| `?` / `:name` placeholders | `$n`, one placeholder per distinct name |
| `INSERT OR REPLACE` / `OR IGNORE` | `ON CONFLICT (<primary key>) DO UPDATE` / `DO NOTHING` |
| `PRAGMA journal_mode` / `foreign_keys` / `busy_timeout` / `synchronous` | dropped |
| `PRAGMA user_version` (get/set) | a `_pg_meta` row |
| `PRAGMA table_info(t)` | `information_schema.columns` |
| `BEGIN IMMEDIATE` / `EXCLUSIVE` / `DEFERRED` | `BEGIN` |
| `ALTER TABLE … ADD COLUMN` | `ADD COLUMN IF NOT EXISTS` |
| `INTEGER PRIMARY KEY AUTOINCREMENT` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` |
| scalar `max(a, b)` / `min(a, b)` | `GREATEST` / `LEAST` (one-argument aggregates untouched) |
| value-form `a IS b` / `a IS NOT b` | `IS NOT DISTINCT FROM` / `IS DISTINCT FROM` (`IS NULL` untouched) |
| `LIKE` | `ILIKE` |
| `strftime` / `date(…)` bucketing | `to_char` / `date_trunc` |
| a bare selected column under `GROUP BY` | appended to the `GROUP BY` list |
| an FTS5 virtual table and `MATCH` | a table with a generated `tsvector` column, `@@ to_tsquery` |

## Reads that repeat

Every read pays for the synchronous bridge: the calling thread blocks while one worker and one
connection serialize the work, so a handful of small lookups per request adds up. Reads that
repeat within 300 ms are served from a table-aware LRU inside the worker, and a write drops
every entry that touches the tables the statement names — so read-after-write is correct
within the process, and a writer outside it is at most 300 ms stale. A read that is still
running when the same shape is asked for again is joined rather than started twice, which
matters when a call gave up on its deadline and the app retried.

## Configuration

| Variable | Meaning | Default |
| --- | --- | --- |
| `PENGUIN_DB` | `pg` selects the PostgreSQL backend | unset: SQLite at `PENGUIN_WEB_DB` |
| `PENGUIN_PG_DSN` | full connection URL, `?schema=` included; overrides the components below | unset |
| `PENGUIN_PG_HOST` / `PENGUIN_PG_PORT` | host and port | `127.0.0.1` / `5432` |
| `PENGUIN_PG_DB` / `PENGUIN_PG_USER` / `PENGUIN_PG_PASSWORD` | database, user, password | `penguin` / `penguin` / empty |
| `PENGUIN_PG_SCHEMA` | the PostgreSQL schema holding the platform's tables | `penguin` |
| `PENGUIN_PG_TZ` | zone used where SQLite's `localtime` appears | the server's own zone |

## Scope

- One server per database, as with `web.db`: the shim holds a single connection, and the
  instance lock is still what keeps two servers off one data root.
- A `web.db` and a PostgreSQL schema are separate stores. Moving an existing installation is a
  copy of its rows, not a setting, and this change ships no migration tool between them.
