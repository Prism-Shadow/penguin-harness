# A rate-limited Session moves to the next model of the Project's fallback chain

- **Date:** 2026-10-13
- **Type:** feature
- **Scope:** `core`, `server`

[中文版](2026-10-13-429-failover.zh.md)

A turn whose model answers **429** spent the whole same-model reconnect ladder — five reconnects, ~60 s of backoff by default — on a quota that was exhausted, and then ended the turn anyway. It now finishes the turn on the next model of the Project's fallback chain instead, in the same conversation.

## The chain

`[[model_fallback_chain]]` in `.project_config.toml` is an ordered list of paired references, highest priority first:

```toml
[[model_fallback_chain]]
provider = "anthropic"
model_id = "claude-sonnet-4-6"
```

It is read and written through the models API (`fallbackChain` on `GET` / `PUT /api/projects/:p/models`), and an entry naming a model the same request does not keep drops out rather than dangling. **Unset (or empty) = no failover**: a rate-limited turn retries on its own model exactly as it always has, which is what every Project does until it opts in.

## The move

- The outcome of a 429 is `retryable` with `error_code: rate_limited`, which is what tells this apart from a transport drop (see the entry above).
- When a run ends on that outcome and the chain has an entry the Session is not already on and has not already been moved onto, the host queues the move **and the resent turn**, ahead of anything the user queued.
- The move happens at the next Task boundary, by driving `Session.switchModel` exactly as `POST /switch-model` does — so it is the ordinary in-session switch (context closed, compacted, opened on the new model), the switch's events reach the channel and the Trace, and the `model_switch` record makes it survive a restart. Nothing migrates history by hand.
- **Bounded**: a model is tried at most once per Session, so a chain that is rate-limited everywhere stops instead of cycling, and the turn then ends as it did before.
