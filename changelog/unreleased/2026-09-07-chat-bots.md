# Chat bots: a bot that starts agents from chat, and the Discord plugin that ships it

- **Date:** 2026-09-07
- **Type:** feature
- **Scope:** `server`, `plugins`, `docs`
- **PR:** [#641](https://github.com/Prism-Shadow/penguin-harness/pull/641)

[中文版](2026-09-07-chat-bots.zh.md)

A messaging binding ties one bot to one Session somebody already opened in the Web App. A
**chat bot** inverts that: the bot is configured once, with a credential and a target Agent,
and every chat that writes to it — a direct message, a channel it is mentioned in, a thread —
gets a Session of its own, opened on the first message and reused for the rest. Nobody opens
the Web App first; the Sessions still appear there, under the target Agent. The first chat bot
is Discord's, shipped as the plugin `@prismshadow/penguin-plugin-discord-bot`.

## Details

- The host landed in `runtime/messaging/chat-bots.ts`, channel-neutral: it takes the channel's
  connector from the messaging bridge, opens one inbound connection on the bot's credential,
  routes each message by its chat id to that chat's Session — creating one through the same
  path a scheduled task uses — and relays each completed assistant message back through the
  connector's client, Markdown rendered, chunked under the channel's cap, threaded onto the
  inbound message in a group. Pictures and files a chat attaches reach the Agent as the
  composer's two attachment shapes.
- **Commands in the chat.** `/new` opens a fresh Session for that chat. `/approve` allows the
  tool call the Agent is waiting on and `/deny` refuses it — the bot says when one is waiting,
  since the person asking has no Web App in front of them. `/status` names the chat's Session.
- **A slot for plugins.** `ChatBotsModule.bots` takes a manifest entry naming the bot's id,
  channel and label, and a code half that may seed its configuration. The Discord plugin's
  seed reads `PENGUIN_DISCORD_BOT_TOKEN`, `PENGUIN_DISCORD_PROJECT` and
  `PENGUIN_DISCORD_AGENT` from the server's environment; a bot with all three starts enabled.
  What the settings store holds wins over the seed, and a bot the operator switched off stays
  off.
- **An admin API.** `GET /api/chat-bots` lists every contributed bot with its masked credential
  and live status; `PUT /api/chat-bots/:id` saves the credential document (in the connector's
  own shape, refused when the connector cannot read it) and the target Project and Agent;
  `POST …/state` is the connection toggle; `POST …/test` probes the credential. Everything is
  stored under `chatbot:<id>` in the server settings, the chat → Session table beside it, so
  both survive a restart and a hot swap.
- The `Messaging` mechanism now exposes `connectorFor`, and the plugin surface exports the
  chat-bot vocabulary (`ChatBots`, `ChatBotsSlots`, `ChatBotContribution`, `ChatBotBinding`,
  `ChatBotDefaults`).
- The plugin ships with every build, listed in the builtin registry and not installed by
  default; its README carries the portal steps and the two ways to configure it.
