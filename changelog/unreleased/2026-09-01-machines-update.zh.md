# 把这次构建交给一台机器，并让它重启到手上的东西上

- **Date:** 2026-09-01
- **Type:** feature
- **Scope:** `server`, `cli`
- **PR:** [#576](https://github.com/Prism-Shadow/penguin-harness/pull/576)

[English](2026-09-01-machines-update.md)

一台机器若已经带着正确的发行版、只是推送状态不同，那就是一次**热更新，而不是安装**。它现在走那台机器自己的更新通道，由通道去问机器，并把机器的回答如实报出来——拒绝也照报。

## 为什么不直接把文件拷过去

把 store 流过去再重启进程，等于在从未问过对方能不能跑的情况下，替换掉一个正在服务的服务端的代码。比推送过去的 platform 更旧的运行时会给出警告、回退到自带的默认版本、继续服务——于是从这边看，重启是成功的，而机器被记成了一个它并没有在跑的版本。去问机器，意味着一个无法认领此 platform 的运行时会**用话拒绝**。

这次交接带的是 platform、CLI、web 三份 bundle**以及原生资产**：platform 只从自己的 assets 目录里解析 `node-pty`，别处都不看，所以少了它们的交接会让那台机器上的每一个终端都起不来。exec 位随文件一起过去，`spawn-helper` 除按模式外还按**名字**处理，因为 Windows 那侧根本没有 exec 位可读。

## 文件不等于进程

安装替换的是**磁盘上**的程序。原本在跑的服务端随后会被重启到新程序上，否则它会报出新版本、却按旧的行事。而原本**没在跑的就让它继续不跑**：装软件并不等于决定这台机器应当开始服务。

这也正是**重启**要成为一个独立操作的原因——一台机器的文件可以在它运行时被更新（复制过去的 store、一次版本本就相同的安装），而只有重启才能让进程与之相符。停止这一步是**要核实的**：在一次并没有发生的停止之后去启动，会发现端口仍被那个没死的进程占着，而只问「有没有服务端在应答」的就绪探测会把这读成成功。

重启会把自己撤掉的那条转发重新拉起来。否则它就是一次悄无声息的断连——代理会对发往那台机器的每一个调用回 503，直到有人去按连接。

## 版本已经一致、更新却仍然失败时

任务会回来**提议**照装不误（`replaceProgram`）：那边的发行版是一致的，所以安装器被跳过了，而此时唯一还能改变这台机器的动作，就是无论如何装一遍——因为安装会顺路把更新通道所需要的 store 复制过去。是提议而不是径直去做，且从不推断：它会停掉一个别人可能正在用的服务端。

App 启动时还会把自己的构建交给每一台记录版本不同的机器，并发 5。

## `penguin server stop`

```bash
penguin server stop
# {"ok":true,"pid":41233}
```

和 `penguin server status` 一样，它面向机器：控制端要重启一台机器的服务端，就需要停掉它并确知它停了，而去问机器自己的 CLI，能把这个答案留在有 Node 的那一侧。本来就没有东西在服务的数据根目录会得到 `{"ok":true}`——那正是调用者要的结果，不是失败。

这里刻意**不发 SIGKILL**。SIGTERM 之后 15 秒仍不放开锁的服务端会被如实报出来，并附上它仍占着的端口；它可能正握着一个数据库、或正在收尾一项任务，而在超时后销毁这些，不是一个控制端该替它做的决定。

## 细节

一次构建要随身携带的「跑在别处」的脚本——安装器与应用器——现在来自同一份清单（`scripts/far-side-scripts.mjs`），打包构建与热推共用它。两份手工维护的副本已经飘移过一次了。
