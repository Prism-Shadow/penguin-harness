# Company proposals: a person reads one while agents build it

- **Date:** 2026-09-21
- **Type:** feature
- **Scope:** `server`, `web`, `cli`, `plugins`
- **PR:** [#825](https://github.com/Prism-Shadow/penguin-harness/pull/825)

[中文版](2026-09-21-company-proposals.zh.md)

Company mode gained a **proposal**: a short, abstract, paragraph-commentable description of a change, written by an employee for a person to read while it is being built — by that employee itself, or by a colleague it hands the build to. Anyone in the organization starts one: a person delegating, or an employee proposing on its own. It ships as a plugin pair that is off by default — a module plugin `@prismshadow/penguin-plugin-company-proposals` (`plugins/company-proposals`: the ledger, the routes, the page contribution) and a skills plugin `@penguinharness/agent-company-proposals` (`proposal-author`, `proposal-implementer`, `proposal-tester`; `preinstall: false`). Design: penguin-harness-design [#210](https://github.com/Prism-Shadow/penguin-harness-design/pull/210) (PRFC-0016).

## Details

- A proposal has a number per organization, an author (the employee named, else the employee that asked), an optional implementer (the author itself unless it names a colleague), the principal that started it (`user:<id>` or `agent:<id>`), a `scope` of `<file, optional name pattern>` pairs — the only place a file path appears — and sections (change / purpose / one test). A comment is on a passage: a range of the section's Markdown source, stored as offsets with the quoted passage, and re-anchored by that quote on every revision (a passage that is gone leaves its comment listed on the revision it was last in); agents never see offsets — `penguin org proposal comments` prints the text with each commented passage wrapped in `⟦<id>⟧…⟦/<id>⟧` and the comments by id. Comments written on whole paragraphs by the first build are anchored to the paragraph's span at fold time. A body that links to a file is refused.
- States: `drafting` → `ready` → `approved` → `merged`, or `rejected`; a request for changes puts `ready` back to `drafting`. Revisions never change the state.
- A person's comments are pending until they request changes; the batch reaches the author as one `@mention` in the organization's `proposals` channel, which the plugin creates with the first proposal and invites the people involved into. Feedback from the implementation, runtime feedback from the test team, and the approval travel the same way — no new trigger kind.
- `implement` opens an implementation session for a colleague the way a ticket session opens, with the proposal text as its first input; the PR it produces is attached as material (`pr`, `issue`, `branch`, `doc`, `ticket`, `url`).
- Every event is recorded with a sequence number; each person has a read position per proposal, and the events after it are that proposal's unread count.
- The ledger is `<orgDir>/proposals.jsonl`, append-only and replayed at start; read positions are in `server_settings`. Where the body comes from — an issue, an RFC file in the workspace — is the company's choice; the ledger holds what was published.
- The pages: one company-mode route contributed by the plugin (`pages.nav: "org"`) — the queue as a full-width list (unread first, then by number), and a proposal as its own page (a breadcrumb back, head, materials, scope, the body with the comments as marks over their passages a "Comment on selection" chip for a selected passage, and a Comment button on every paragraph's hover for the whole paragraph, timeline, and the actions **Request changes**, **Approve and request merge**, **Reject**). Its sidebar entry carries the unread total. `proposal:<n>[#<pattern>]` in any Markdown surface renders as a capsule with the title and the unread count.
- CLI: `penguin org proposal ls | show | create | publish | ready | implement | material add | feedback | comments | resolve | merged | approve | reject`. An organization without the plugin answers a plain 404, which the CLI reports as the plugin being missing.
- The skills plugin is installed by the code plugin on whoever writes or builds a proposal, at the moment it is asked to — nothing is installed by hand and no position is hired for it. Channel messages are spoken by whoever acts (an employee from its session, a person otherwise); an employee's own proposal @-mentions nobody.
- Platform seams the plugin builds on: an `OrgGateway` exported to plugins (read an organization, attribute a write, ensure a channel and speak in it, open an employee's session, notify the Project), a generic `plugin` server event, the `org` value of a contributed page's `nav`, and the proposal DTOs in the server's API types.
