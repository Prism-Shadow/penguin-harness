# Company proposals: a person reads one while agents build it

- **Date:** 2026-09-21
- **Type:** feature
- **Scope:** `server`, `web`, `cli`, `plugins`
- **PR:** [#825](https://github.com/Prism-Shadow/penguin-harness/pull/825)

[中文版](2026-09-21-company-proposals.zh.md)

Company mode gained a **proposal**: a short, abstract, paragraph-commentable description of a change, written by an employee for a person to read while it is being built — by that employee itself, or by a colleague it hands the build to. Anyone in the organization starts one: a person delegating, or an employee proposing on its own. It ships as a plugin pair that is off by default — a module plugin `@prismshadow/penguin-plugin-company-proposals` (`plugins/company-proposals`: the ledger, the routes, the page contribution) and a skills plugin `@penguinharness/agent-company-proposals` (`proposal-author`, `proposal-implementer`, `proposal-tester`; `preinstall: false`). Design: penguin-harness-design [#210](https://github.com/Prism-Shadow/penguin-harness-design/pull/210) (PRFC-0016).

## Details

- A proposal has a number per organization, an author (the employee named, else the employee that asked), an optional implementer (the author itself unless it names a colleague), the principal that started it (`user:<id>` or `agent:<id>`), a `root` (the repository's directory in the shared workspace) and a `scope` of `<kind, file, optional name pattern>` entries — the kind is `edit`, `new`, `delete` or `rename` (with `from`) —, sections (change / purpose / test), and a `tests` list, last in the frontmatter: `<file, optional name pattern, kind, group, description>` entries, the kind `existing` (default), `new` or `delete` (a test the change removes), the group one the plugin's configuration declares (`unit` by default; a publish with an undeclared group is refused with the declared list, 400 `tests_group_undeclared`), the description — what the test tests — required (400 `tests_invalid`). The scope and the tests are the only places a file path appears. A comment is on a passage: a range of the section's Markdown source, stored as offsets with the quoted passage, and re-anchored by that quote on every revision (a passage that is gone leaves its comment listed on the revision it was last in); agents never see offsets — `penguin org proposal comments` prints the text with each commented passage wrapped in `⟦<id>⟧…⟦/<id>⟧` and the comments by id. Comments written on whole paragraphs by the first build are anchored to the paragraph's span at fold time. A body that links to a file is refused.
- The scope is checked against the working tree at `publish`: an `edit` or `delete` file, or a `rename` source, that is not under `root` refuses the revision and names the likely path (the path without a `legacy` segment, or files of that name found by a bounded search); a `new` file or a `rename` target that already exists is published with a hint. A merged proposal is not checked. Every read reports each entry's state — `exists`, `new`, `missing`, `deleted` or `renamed` — and the resolved directory. Ledgers written before the kinds existed are read as `edit`, without rewriting the file (see [2026-09-24-backward-compatibility.md](2026-09-24-backward-compatibility.md)). The tests are checked the same way: an `existing` or `delete` test whose file is not under `root` refuses the revision (400 `tests_missing`, with the likely path); a `new` test in a file that already exists is published with a hint; every read reports each test's state (`exists`, `new`, `missing`). A revision written before the tests existed reads with none.
- The test groups are a plugin config: the plugin declares a **Company proposals** settings group with a `testGroups` list — one `id: description` line per group, in display order, defaults `unit`, `integration`, `e2e`, `bench` — that an admin edits under Settings → Plugins. It is server-wide; a save applies to the next publish and the next read without a restart. `GET …/proposals/test-groups` answers the declared groups, and a proposal read carries them as `testGroups`. A revision published with a group that is later taken out keeps it (see [2026-09-24-backward-compatibility.md](2026-09-24-backward-compatibility.md)).
- States: `drafting` → `ready` → `approved` → `merged`, or `rejected`; a request for changes puts `ready` back to `drafting`, and the author's `ready` is refused (409 `changes_pending`) until a revision was published after the batch and every comment in it is resolved — the refusal lists the open comments; a person may mark it ready regardless. An approval covers one revision: a publish after it puts the proposal back to `ready`, tells the implementer to wait for a new approval, and the page marks what changed since the approved revision where it is — the title's words in the heading; each scope and test row added (tinted), removed (struck, in its old place, not a link) or changed (the old value struck beside the new); removed paragraphs struck, added ones tinted, an edited paragraph with its words changed in place — under one line naming the approved revision and its approver, with a Changes | Latest switch (Latest shows the head plain) (`GET …/revisions[/:rev]` reads any revision back; `show` prints `approved: r<M>`).
- A person's comments are pending until they request changes — theirs to reword or withdraw until then, fixed once sent; the batch reaches the author as one line put straight on its desk — `[proposal #<n>]`, what happened, the command to run — in nobody's name and without any channel. Every step that tells an employee travels the same way: a delegation to the author, a request for changes and feedback to the author, runtime feedback to the author and the implementer, an approval to the implementer (else the author), a revision after approval to the implementer, a rejection to the author and the implementer; an employee is never told of its own act. A line that cannot be delivered (the organization or the employee paused, no desk) is recorded as a `notify_failed` event and returned with the write as a hint, which the page shows as a toast and the CLI prints.
- `implement` opens an implementation session for a colleague the way a ticket session opens, with the proposal text as its first input; the PR it produces is attached as material (`pr`, `issue`, `branch`, `doc`, `ticket`, `url`).
- Every event is recorded with a sequence number; each person has a read position per proposal, and the events after it are that proposal's unread count.
- The ledger is `<orgDir>/proposals.jsonl`, append-only and replayed at start; read positions are in `server_settings`. Where the body comes from — an issue, an RFC file in the workspace — is the company's choice; the ledger holds what was published.
- The pages: one company-mode route contributed by the plugin (`pages.nav: "org"`) — the queue as a full-width list (unread first, then by number) searched GitHub-style — `is:open` by default, so merged and rejected proposals are a chip away; `is:`, `author:`, `implementer:`, `by:`, `unread:`, `no:implementer`, negation and quoted phrases, the query in `?q=` —, and a proposal as its own page (a breadcrumb back, head, materials one per row — a GitHub pull request shows its state, draft / open / merged / closed, read from GitHub on every read and never stored —, scope as a list under its root — each row its kind and state, name patterns wrapping; a file that exists is a link that opens it read-only in a panel to the right of the proposal (a sheet on a phone; `?file=` keeps it across a reload, Back closes it), served by the plugin from the organization's server and confined to the proposal's root, with the lines its name pattern matches marked, and a missing one says so —, the body with the comments as marks over their passages a "Comment on selection" chip for a selected passage, and a Comment button on every paragraph's hover for the whole paragraph, the tests grouped in the declared order, each group with its description, and a group no longer declared last under "Undeclared groups" — each group folds, a group over 12 rows shows the first 12 and "Show N more", each row its kind, its file (a link while it exists), its name pattern and what it tests —, timeline, and the actions **Request changes**, **Approve and request merge**, **Reject**). Its sidebar entry carries the unread total. `proposal:<n>[#<pattern>]` in any Markdown surface renders as a capsule with the title and the unread count.
- CLI: `penguin org proposal ls | show | create | publish | ready | implement | material add | feedback | comments | resolve | merged | approve | reject | groups`; `groups` prints the declared test groups as `id: description`. `show` prints the root and each scope entry as `<kind> <file>` (`rename <from> → <file>`) with its state, and the tests after the sections by group, in the declared order with an undeclared group marked, as `<kind> <file> [<name>] — <description> (<state>)`; `publish` prints the server's hints. An organization without the plugin answers a plain 404, which the CLI reports as the plugin being missing.
- The skills plugin is installed by the code plugin on whoever writes or builds a proposal, at the moment it is asked to — nothing is installed by hand and no position is hired for it. The plugin uses no channel.
- Platform seams the plugin builds on: an `OrgGateway` exported to plugins (read an organization, attribute a write, deliver a line to an employee's desk — `deliverToDesk`, queued behind a running Task, refused while the organization or the employee is paused —, open an employee's session, notify the Project), a generic `plugin` server event, the `org` value of a contributed page's `nav`, and the proposal DTOs in the server's API types.
