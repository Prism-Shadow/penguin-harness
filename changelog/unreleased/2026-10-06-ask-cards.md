# An assistant reply can ask a question, and the card it draws is answerable

- **Date:** 2026-10-06
- **Type:** feature
- **Scope:** `web`
- **Issue:** [#991](https://github.com/Prism-Shadow/penguin-harness/issues/991)

[中文版](2026-10-06-ask-cards.zh.md)

An assistant reply that asks the user to choose now renders as a card they can answer in place: one
question per card, single or multi select, an always-present free-text row, and Skip and Submit at
the bottom right. A round that asks several questions at once draws them all and offers one
"Submit all". The answer travels as an ordinary user message — no new message type, no
pending-request protocol, no turn the agent is blocked inside.

## Details

- **The shape is a fenced block**, ` ```ask `, whose body is line-oriented: `title:` (required — the
  question itself), `select: single|multi`, numbered option lines, and `recommend:` naming option
  numbers. An unrecognized info string degrades to a plain code block, so a client that predates
  this feature shows the text instead of losing it, and a body that does not parse (no title, fewer
  than two options, a repeated option number) leaves the fence in the message rather than rendering
  a broken card. Unknown keys are ignored, so a later version can add them without breaking this one.
- **The trailing "Other" row is not authored.** Every card gets one, so the instruction to write it
  can never be forgotten and can never be written twice.
- **A card never pre-selects its recommendation.** `recommend:` puts a light-blue `推荐` badge on the
  row and nothing more: a pre-selected option turns a stray double-click on Submit into an answer
  the user never gave. Multi-select cards ignore `recommend:` entirely — "all of them" is not a
  recommendation.
- **Submit refuses an empty answer** and shows the hint instead ("请先选择一项，或点「跳过」"),
  because Skip is the deliberate way to pass. Skip records the question as answered-but-skipped
  (`跳过，未作答`) rather than quietly adopting the recommendation, so the model can tell "the user
  passed" from "the user never saw this". Both are sent through the same send path the composer
  uses; a send that fails leaves the draft editable and lets the sender's own error toast explain.
- **One message can carry several cards.** Each is submitted on its own, and while any of them is
  still unanswered the message also offers a "Submit all" button with the `n/m 题待回答` count,
  enabled only once every remaining card has an answer.
- **A card is answerable once its turn has ended**: while streaming, the block is still being
  written, so the message renders plain Markdown and the card appears when the turn settles. The
  consequence, stated plainly: the agent cannot wait for an answer inside the same turn — it ends
  its turn and reads the answer as the next one. After a card is sent it shows what was sent and
  offers "Answer again" (`重新回答`), since a submit cannot be recalled.
- **A nested conversation's transcript shows the cards too**, but with their rows inert: nothing in
  a subagent panel can send a message on that conversation's behalf.
- `test/ask-block.test.ts` covers the parser, the splitter and the composed answer; the card itself
  carries `data-ask-card="pending|sent|readonly"`, which is the hook the notification path reads.
