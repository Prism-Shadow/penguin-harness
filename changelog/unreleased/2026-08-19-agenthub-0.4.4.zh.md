# AgentHub 0.4.4：新增 max 思考等级，网关心跳不再中断流式响应

- **Date:** 2026-08-19
- **Type:** feature
- **Scope:** `core`, `server`, `web`, `cli`, `docs`
- **PR:** [#334](https://github.com/Prism-Shadow/penguin-harness/pull/334)
- **Issue:** [#286](https://github.com/Prism-Shadow/penguin-harness/issues/286)
- **Breaking:** yes — 在 DeepSeek 模型上，`low` 与 `xhigh` 两档发送的 effort 比此前更浅；想保留 `xhigh` 原先的思考深度，请改选 `max`。

[English](2026-08-19-agenthub-0.4.4.md)

`@prismshadow/agenthub` 跨两个版本从 0.4.2 升到 0.4.4：0.4.3 会跳过网关注入到流式响应中的心跳事件，而不是让整条流失败（agenthub [#174](https://github.com/Prism-Shadow/agenthub/pull/174)）；0.4.4 在 `XHIGH` 之上新增了 `MAX` 思考等级，并把各 client 的 effort 取值重新映射到加宽后的档位阶梯上（agenthub [#176](https://github.com/Prism-Shadow/agenthub/pull/176)）。harness 把这一新档位打通到了各处：`max` 现在是 Web 拾取器里可选的思考等级、`run_subagent` 合法的 `thinking_level`，以及一切存储或传输档位处都接受的取值。

## 网关心跳

架在模型 API 前面的网关——one-api 一类的代理、OpenRouter——会在长时间生成期间发送心跳。在 0.4.2 上，这类事件会落到未知事件的兜底分支并抛错，harness 把这次抛错判定为可重试的请求失败，而重试又会撞上下一个心跳：经由这类网关的长生成会一直重连到放弃，在 Web App 里表现为无休止的「正在重连」。

- Responses 协议的 client（`gpt-5.6`、`openai-responses`、`minimax-m3`）把 `keepalive` 视为已知的空操作；Chat Completions 系的 client（`openai-chat`、`deepseek-v4`、`glm-5.3`、`kimi-k3`）只在 `choices` 字段确实有值时才读取它；Anthropic 协议的 client（`claude-5`、`ant-messages`）接受 `ping`。真正未知的事件仍然照旧报错。
- 0.4.4 又把 Gemini 这一侧的判断做得更通用：`gemini3_7` 不再靠「分块既无 candidates 也无 usage」来反推心跳，而是在一个分块里什么都没读出来时——没有内容项、没有 usage、没有 finish reason——直接标记为 `unused`。对于本就不带 usage 的流，两种做法表现一致。

## max 档位

- `ThinkingLevelName` 新增 `"max"`，`mapThinkingLevel` 把它映射到 AgentHub 的 `ThinkingLevel.MAX`。各 client 会把该档位映射到对应厂商能接受的最深 effort，厂商没有这一档时静默降级——Gemini 与 MiniMax M3 止步于各自的 `high`——因此选它不会失败。
- `max` 是**可选**档位，而不只是一个能被接受的已存值。拾取器之所以排除 `none`，是因为多数模型无法关闭思考；`max` 没有这层顾虑，所以它与 `low` / `medium` / `high` / `xhigh` 一同进入 `SELECTABLE_THINKING_LEVELS`、`DEFAULT_CHAT_THINKING_LEVELS`（Project 的 `[default_chat]` 兜底档位），以及 `SUBAGENT_THINKING_LEVELS`——即 `run_subagent` 的 `thinking_level` 接受的档位集合。
- `POST /api/sessions/:id/tasks` 的逐轮 `thinkingLevel` 与 Agent 配置的 `model.thinking_level` 都接受 `max`；其他取值仍然返回 400。
- 两个语种此前都把 `xhigh` 描述为扩展推理的「最高」档，新档位使这句话不再成立。现在它的描述改为「在 `high` 之上再进一步」，最高级的说法交给 `max`——AgentHub 也对自己的 playground 选择器做了同样的改写。harness 里没有任何地方对档位做序数比较或收敛，因此不存在其他把 `xhigh` 当作天花板的地方。

## DeepSeek effort 重新映射

DeepSeek 的 `reasoning_effort` 只接受 `low` / `high` / `max`，服务端会把 `medium` 与 `xhigh` 都折算成 `high`。0.4.4 让 client 与这套取值对齐，于是在 DeepSeek 模型上，两个既有档位实际发送的值发生了变化：

| 档位 | 此前发送（0.4.3） | 现在发送（0.4.4） |
| --- | --- | --- |
| `LOW` | `high` | `low` |
| `XHIGH` | `max` | `high` |
| `MAX` | — | `max` |

因此，停在 `low` 的 DeepSeek 会话思考更浅、花费也更少；停在 `xhigh` 的会话思考深度有所下降。

## 思考等级标签标注实际取值

每个档位现在都以它真正发送的取值来标注：中文标签在括号里补上该取值（`极高 (xhigh)`、`最高 (max)`），英文标签则直接就是该取值——是 `xhigh`，不是 `Extreme High`。所有读取这份共享名称表的界面都随之更新：对话态拾取器、会话中途切换的确认框与其提示、以及 Project 聊天默认值对话框。Agent 设置中的行本就显示原始取值。

## 兼容性

- **此前依赖 `xhigh` 的 DeepSeek 用户请改选 `max`**，以保留该档位原先发送的 effort。停在 `low` 的会话无需处理，除非确实想要原先（深得多）的行为，那么最接近的选择是 `high`。
- 加宽 `run_subagent` 的 `thinking_level` 枚举改变了默认工具条目，因此 `KERNEL_VERSION` 推进到 `2026-08-19` 这一代，其中唯一变化的叶子是 `tools.builtin.run_subagent`。所有既有 Agent 都会执行一次内核更新；用户改过的条目保持不动，用户删掉的条目也不会被重新加回，无需任何手工操作。
- 携带任何旧档位的已存配置与 Trace 均照常工作——阶梯只在顶端变长，harness 中没有任何既有取值改变了含义。
- `pnpm-workspace.yaml` 中 `minimumReleaseAgeExclude` 的条目现在只列 0.4.4；按该文件自身注释的要求，移除了 0.4.3 的条目。
- 已逐个比对两个已发布版本的 client，确认 0.4.3 到 0.4.4 之间没有任何 base URL 或端点构造上的改动，因此模型目录与协议路径提示不受影响；`protocol-path.ts` 的校验注释也已改为标注 0.4.4 这一复核版本。
