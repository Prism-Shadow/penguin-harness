# 这台部署实际在跑的插件，以及命令执行时的封禁策略

- **Date:** 2026-09-01
- **Type:** feature
- **Scope:** `server`, `web`

[English](2026-09-01-installed-plugins-and-sandbox.md)

插件页原本只列出可安装的目录，却完全没说这台部署自己装了什么；而沙盒——Agent 每次执行命令时的封禁策略——只能靠编辑寄存文档来配置。现在两者都有了界面。

## 已安装的插件

插件页标题旁的图标打开 **已安装的插件**：`<root>/plugins.json` 列出的内容，以及其中哪些正在被当前进程运行——这是两件不同的事实，刻意分开呈现。插件在每个进程里只加载一次，且由 runtime 加载，所以新增的条目在服务器重启前不会生效，移除的条目在此之前也会继续服务；对话框直接这么说，而不是假装运行中的进程已经变了。管理员在这里增删条目，即写入该文件；插件页每一行也带同样的控件，可以在读到它的地方直接安装，之后该行会显示它对这台部署意味着什么——等待重启，还是正在运行。

哪个已加载模块属于哪个插件，是从**文件**得出的，而不是问宿主：包在自己的 `package.json#penguin` 里声明模块名，因此当一个已列出的插件所声明的模块全部在场时，它就是运行中的。无法解析、或解析到的不是插件包的 specifier，会带着原因显示，而不是被算作"待重启"。`GET /api/plugins/installed`（成员即可）与 `PUT /api/plugins/installed { plugins }`（管理员）。

## 沙盒设置

设置里新增 **沙盒** 页（管理员）：封禁模式（关闭 / 仅工作区可写 / 只读）、是否断开网络、以及对被封禁命令屏蔽的路径。`GET|PUT /api/admin/sandbox`；改动对下一次命令启动生效，无需重启，且设置随平台寄存，热更新后依然有效。

真正实施封禁的是插件提供的后端（bwrap、Seatbelt、MXC、DSH）。页面会列出已挂载的后端及各自实现的隔离维度；一个都没有时会明说——没有后端时选择模式不会产生任何约束，而一个让人误以为有保护的安全控件，比没有这个控件更糟。
