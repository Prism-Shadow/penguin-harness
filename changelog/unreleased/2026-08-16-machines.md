# Machines: point the window at another machine's server over SSH

The **login page** opens with a server picker: it is the account chooser, and which machine's server to sign into comes first — machine, then account, then password. Pick a host from `~/.ssh/config` and the whole app becomes that machine's PenguinHarness — agents, shells, file tools, workspaces and previews all run in the server process, so pointing the app at a remote server IS running remotely. The way there is the bottom-left **Switch account** (which already lands on the login page); this supersedes the short-lived desktop-app "Install Server on Remote Host" menu — no separate install entry, no install UI in the shell at all.

**The window never leaves the local origin.** Switching servers flips an ACTIVE SERVER state and reloads the document (the same shape as switching accounts); every `/api/…` call and SSE subscription is then rewritten to `/server/<id>/api/…`, which the local platform forwards through that machine's tunnel — streaming both ways (verified: SSE chunks arrive as sent). The frontend is always served locally and remote pages are never proxied. Each remote's cookies live under the local origin renamed per machine (`penguin_s_<hex(id)>_…`), so every server's session and parked-account jar coexist with no collisions, and local cookies never leak to a remote. One practical consequence: **no shell change is needed at all** — desktop builds that predate this feature run it fully the moment the platform is pushed to them.

**Built for a big config.** A config can declare hundreds of hosts, so the list is the config text alone — no `ssh -G` per alias; the picked alias resolves once, at connect time. The block shows a handful of rows (live tunnels first, then most recently connected — the server's order), and a search box reaches the rest; a counter names how many the current view leaves out.

**Who may use it:** on the desktop app's embedded server, the login page itself (no session exists there yet; the human at the loopback keyboard is the owner). On a multi-user server, an admin session — its login page shows no machine list. The connect POST additionally requires `content-type: application/json`: the desktop-mode exemption would otherwise be reachable by any website firing a text/plain request at `http://localhost:7376`, and the seam runs before the runtime's json-only middleware, so the rule is enforced in the route.

## Where it lives — the layer, deliberately

The whole capability is **platform code** (`packages/server/src/platform/machines/`), served through the HTTP seam as `/api/machines`: reading `~/.ssh/config` (never writing it), `ssh -G` resolution, the identity probe, packing this build and installing it over there, starting the remote server, the tunnel, the per-machine port memory. Every piece of it ships and changes by hot push, per the layer rule in `packages/server/src/hmr/README.md`.

The whole capability now includes the `/server/<id>/api/…` proxy (machines/proxy.ts), also on the seam. The shell contributes nothing: no machine list, no ssh, no install code, and — since the window stays on its own origin — not even a navigation-policy change. (The loopback navigation gate shipped earlier remains as a harmless mechanism; nothing depends on it.)

The seam runs before the runtime's auth middleware, so the routes gate themselves: the request's cookies are exchanged for an identity against the server's own `/api/me` — connected to 127.0.0.1 (the address the server's lock is probed on) with the Host header forced to the canonical app host, never to a name that could resolve to some other server's listener.

## What a connect does

Probe the host → **install or update this build there automatically** if absent or different (the pushed image is what this server actually runs, in order of truth: the **hot-pushed version in its own store** — the self-contained CLI bundle plus the in-memory web dist, sha-stamped `0.0.0-hmr.<cli>.<web>`, so every new push re-syncs remotes on the next connect — then the tarball tree, then the desktop app's staged payload; a remote *newer* than this build is a downgrade and the job log says which way it went) → make sure its server runs (`nohup`-detached, found again through its own `server.lock`, never supervised) → open the `ssh -N -L` tunnel → set it as the active server and reload onto this same login page, now speaking to that server through the proxy. No token rides the tunnel: signing in over there is a password the first time and the parked-session jar afterwards. Connecting to the machine and account this server already runs on is refused (fingerprint comparison — machine-id or hostname, plus the account): you are already here, and the port-conflict path could kill the server serving the request.

A connect is a job of four numbered steps — probe, install, server, tunnel — and every log line carries its step (`[2/4] …`), so the wait has a visible shape; a step that turns out unnecessary says so and passes. A fresh install's seeded admin password is read back from the remote's own initial-password store and shown in a dialog before switching — without it the first sign-in is a locked door. `POST /api/machines/connect` starts the job, the web polls `GET /api/machines` and narrates the log. A port conflict (the remote server's port is taken locally, and tunnel ports must match on both ends — preview URLs are built from the server's own bound port) stops for explicit consent, because resolving it restarts the remote server.

## Ports, memory, adoption

Tunnel ports shift forward from 7376 and are remembered per machine in `<data root>/machines-state.json`. The local port still MUST equal the remote port: Workspace preview URLs are built from the remote server's own bound port on `127.0.0.1`, and they bypass the proxy — the tunnel is what makes them reachable. The tunnel's pid is remembered too: a hot-swapped platform (or restarted server) **adopts** a still-live tunnel instead of duplicating it (green dot in the picker; switching there is instant), and the proxy finds a machine's port through the same state.

Coming back is a picker row that clears the active server — same origin, nothing to remember across origins.

## Boundaries

- Windows remotes: install works, connect refuses for now — starting a detached server from a cmd.exe ssh session is a different mechanism.
- A dev-checkout server has no pushable image and says so; connect from an installed build.
- `~/.ssh/config` stays read-only; nothing on the remote is touched outside `~/.local/share/penguin`, `~/.local/bin/penguin` and `~/.penguin/data/server.log`.
