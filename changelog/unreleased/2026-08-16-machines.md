# Machines: point the window at another machine's server over SSH

The account menu in the bottom-left corner gains a **Machines** section (admins only): pick a host from `~/.ssh/config` and the window becomes that machine's PenguinHarness — agents, shells, file tools, workspaces and previews all run in the server process, so pointing the window at a remote server IS running remotely. This supersedes the short-lived desktop-app "Install Server on Remote Host" menu: there is no separate install entry, and no install UI in the shell at all.

## Where it lives — the layer, deliberately

The whole capability is **platform code** (`packages/server/src/platform/machines/`), served through the HTTP seam as `/api/machines`: reading `~/.ssh/config` (never writing it), `ssh -G` resolution, the identity probe, packing this build and installing it over there, starting the remote server, the tunnel, the per-machine port memory. Every piece of it ships and changes by hot push, per the layer rule in `packages/server/src/hmr/README.md`.

The shell's entire contribution is one mechanism: the window may navigate between loopback penguin origins (`http://localhost:<any port>`), and the preview/window-open policy follows the origin the window is on. That is a one-time navigation-policy primitive; the shell has no machine list, no ssh, no install code.

The seam runs before the runtime's auth middleware, so the routes gate themselves: the request's cookies are exchanged for an identity against the server's own `/api/me` — connected to 127.0.0.1 (the address the server's lock is probed on) with the Host header forced to the canonical app host, never to a name that could resolve to some other server's listener.

## What a connect does

Probe the host → **install or update this build there automatically** if absent or different (the pushed image is the running install itself — the tarball tree, or the desktop app's staged payload — so the two ends match by construction; a remote *newer* than this build is a downgrade and the job log says which way it went) → make sure its server runs (`nohup`-detached, found again through its own `server.lock`, never supervised) → open the `ssh -N -L` tunnel → land on that server's own login page. No token rides the tunnel: signing in over there is a password the first time and the parked-session jar afterwards.

A connect is a job: `POST /api/machines/connect` starts it, the web polls `GET /api/machines` and narrates the log. A port conflict (the remote server's port is taken locally, and tunnel ports must match on both ends — preview URLs are built from the server's own bound port) stops for explicit consent, because resolving it restarts the remote server.

## Ports, memory, adoption

Tunnel ports shift forward from 7376 and are remembered per machine in `<data root>/machines-state.json` — the port is the origin, and the origin buckets localStorage, cookies and the parked-session jar. The tunnel's pid is remembered too: a hot-swapped platform (or restarted server) **adopts** a still-live tunnel instead of duplicating it, shown in the menu as a green dot — switching to an adopted machine is instant.

Coming back: a switch navigates with `?penguinHome=<origin>`, and the destination stores it and offers a "Back to …" row — the one entry its own server's list could never contain.

## Boundaries

- Windows remotes: install works, connect refuses for now — starting a detached server from a cmd.exe ssh session is a different mechanism.
- A dev-checkout server has no pushable image and says so; connect from an installed build.
- `~/.ssh/config` stays read-only; nothing on the remote is touched outside `~/.local/share/penguin`, `~/.local/bin/penguin` and `~/.penguin/data/server.log`.
