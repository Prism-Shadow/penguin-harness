# Machines 页面：使用一台机器、停用它，并在它上面打开工作区

- **Date:** 2026-09-09
- **Type:** feature
- **Scope:** `web`, `server`
- **PR:** [#448](https://github.com/Prism-Shadow/penguin-harness/pull/448)

[English](2026-09-09-machines-page.md)

驱动这一切的页面。机器是这个 Project 用来跑 agent 的东西：**使用**一台，本服务端就安装程序、启动它、连接、下发 Model 配置并保持连接；**停用**它，机器就被放开。机器也可以在工作区选择器里被选中，因此可以在另一台机器的某个目录下开一个 Session。

**暂时还进不去。** 侧边栏入口、路由与选择器里的机器一行被刻意留住，等功能稳定之后由一个单独的改动一次性放开。这里落地的是页面本身。

## 窗口不会整个搬走

点名了某台机器的调用会被改写成 `/server/<machineId>/api/…`，由本地服务端转发过去。这里刻意**没有整窗口的「当前服务器」模式**。它一度存在过，后来被移除了：把整个窗口指向另一台机器，会让每一个页面都落到隧道后面，`/api/me` 也不例外——于是隧道一断，应用连「有没有人登录」都答不上来，而用来退出这个状态的控件，恰恰渲染在那个永远没能挂载的布局里面。藏在故障物后面的逃生门不是逃生门。

改为在真正与那台机器有关的调用上点名它，就不会这样失败：隧道死了，坏掉的正好是需要它的那个请求，而且它会说出来。一条字符串规则同时管住 `fetch` 与 SSE 订阅。

## 两个动作，每台机器一句话

**使用**一次做完让机器能跑 agent 所需的全部事情——安装或更新程序、启动对端服务、连接、下发 Model 配置——作为一个任务；**停用**则放开它。每张卡片用人话说明这台机器在哪一步（「已连接，随时可用」「对端服务未运行——点『使用』即可启动」），凡是提到问题的句子，都由同一个按钮解决。安装、更新、重启、连接、断开不是需要人手动排顺序的各自独立的控件。

- 每台机器一张卡片，本服务端排第一，按名字排序，因此更新或探测不会挪动任何一张。静止时一张卡片只有两行：名字，以及状态和它旁边唯一要紧的那个信息——上次检查时间、落后于本服务端时它所装的版本、失败时对端的原话。卡片边缘的圆点：蓝色表示连接在线，琥珀色和红色表示需要人处理，灰色表示已安定。
- 选择即卡片：点一下即选中。全选、全不选、**使用**（插头）和**停用**（拔下的插头）是纯图标，放在标题和卡片之间一条高度固定的操作条里，因此选择出现或消失时卡片不会移动；文字保留为 tooltip 与无障碍名称。批量操作在服务端同时处理多台，其余排队等候。
- 排队或处理中的卡片在名字下方长出一条分段进度条，每段对应流程的一步（检查、安装、交接、重启、连接、下发配置），由服务端报告的当前步骤驱动。
- 卡片右侧的箭头展开详情：版本、安装时间、对端服务状态和端口、上次检查、机器 ID、那台机器上的**服务端根目录**（`PENGUIN_HOME`——由 profile 决定，dev 实例访问的是机器上的 dev 安装，绝不会碰旁边的 release 安装）、任务的完整输出，以及任务给出时的强制安装。「强制安装并重启」出现在每一次失败的安装或连接上，只有两种情况除外：这次运行本身就是那次安装，以及安装也无法弥补的那一种失败——本服务端自己没有可发送的构建；它仍会提示这会打断正在使用那台机器的人。
- 尚未使用的机器放在「添加机器…」后面，在服务端的 ssh 配置里搜索：先列前几个匹配，其余折叠在后，选中后才出现确认。多选后确认即一起使用。
- 机器连上之后，保持连接是服务端的事：断开且未自行恢复的机器会以逐步拉长的间隔重试——从一分钟到十五分钟——直到重新连上或有人停用它。重启服务端后，不再需要有人打开页面机器才会重新连接。
- 标题栏显示本服务端的版本；当有在用的机器落后于它时，出现「全部更新」，一次把它们全部更新并重新连接。
- 服务端提供 `POST /api/projects/:projectId/machines/use`，请求体 `{ machines: [...] }`（同时处理多台、其余排队，返回 `202`；无需 ssh 即可判定的拒绝按 id 返回），以及 `POST .../machines/stop-using`。列表带有 `jobs`：每台机器排队中、运行中和最近一次完成的任务，以及各自所处的流程步骤（`phase`）。原有的按机器安装、连接、重启、释放、断开路由保留。

## 在页内声明 ssh 主机

还没写进服务端 ssh 配置的机器，可以直接在页面里声明。「添加机器…」面板底部的 **+** 打开一个简短的表单——别名、地址，以及可选的用户、端口和密钥文件——服务端会把对应的 `Host` 块追加到它自己的 `~/.ssh/config`。之后这台主机就和其他主机一样出现在「添加机器…」里。

- 写入的是 ssh 自己的语法，开头一行注释标明由 PenguinHarness 于何时写入，方便日后翻看配置的人分辨哪些行不是自己写的。目录和文件不存在时，按 ssh 要求的权限创建。
- 每个值必须是一个词且不含 `#`，别名不能是通配模式，端口必须是 1 到 65535 之间的整数。表单会在发送前就在字段下方说明。配置里已有的别名会被拒绝：ssh 只认先出现的那一块，新块会被静默忽略。
- 由本应用写入的主机可以再配置：卡片详情里的齿轮会把那一段读回来，在同一个表单里打开，保存即原地改写。手写的那一段只展示不保存——它可能带有表单不认识的选项——表单会提示直接改文件。
- 服务端提供 `POST /api/projects/:projectId/machines/ssh-hosts`，返回机器列表（`201`）、指明字段的 `400 ssh_host_invalid`，或 `409 ssh_host_exists`；`GET …/ssh-hosts/:alias` 读回一段并说明能否改写，`PUT …/ssh-hosts/:alias` 改写本应用写入的一段（`404` 不存在，`409 ssh_host_foreign` 为手写）。与该路由组其余部分一样仅管理员可用。

## 在机器上选工作区

工作区是某台机器**上**的一个目录，所以只有此刻文件系统可达的机器才能被浏览：本机永远可以，其余需要一条持有的连接。每一台在用的机器都**照样列出**，不可达的置灰并在行上写明原因——一个悄悄略去答案的列表，和一个坏掉的功能无法区分。

机器以自身的 id 标识、以 ssh 别名显示，因此改了名的主机仍然保得住它的工作区。

## 早于迁移的 machines 表

一个数据根目录若在 machines 线发布之前就跑过它，其 machines 各表会按原有的列被接管——迁移 4 用 `IF NOT EXISTS` 创建它们——于是连接在「Opening the connection…」处失败，报 `table machines has no column named session_pid`。迁移 5 `machines-columns` 为缺少 `session_pid` 和 `platform` 的 machines 表补上这两列，已有的表原样保留。纯增量且可在热推送时应用；它的回退什么也不做，因为迁移 4 声明的正是同样的列。

## 范围

机器从头到尾都是管理员能力：页面、该路由组的每一条路由，以及通往机器 API 的代理。
