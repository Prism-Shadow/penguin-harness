# Switching accounts without signing out

The bottom-left account menu can switch accounts, and an account you have already signed into on this browser is one click away — no password, because its session is parked server-side rather than destroyed.

## Switch account

The account menu's bottom block reads Change password → … → the accounts already signed in → Switch account → Sign out. Switching parks the current session and hands over the login page; the parked account keeps working and is listed on the way back.

Unlike Sign out, the entry is present in desktop mode as well: the desktop window is where reaching for another account actually happens, and the way back needs no password — every launch of the shell starts its server with a fresh one-shot token and points the window at `/api/auth/desktop-login`, so quitting and reopening the app signs the desktop admin straight back in.

Switching ends the session before it goes: parking keeps it alive for a passwordless return, and a server that cannot park it — an older build has no such endpoint — falls back to a plain sign-out. Landing on the login page with a live session would simply be bounced back by the route guard, which looks exactly like a menu entry that does nothing.

Switching loads the app as a new document rather than navigating within it, so every per-account store the tab was holding — Project / Agent / Session state, model lists, the draft caches' in-memory mirrors — goes away with the reload instead of living on under the next account.

## The session jar

Sessions are now a small jar instead of a single cookie. The active account's token stays in `penguin_session`, the only cookie the auth middleware reads; the tokens of other accounts signed in on this browser sit parked in `penguin_parked_sessions`. Both are HttpOnly, so the stashed credential is never readable by script — the reason the stash is a cookie and not `localStorage`.

- `GET /api/auth/sessions` lists the accounts in the jar, active first, pruning expired ones as it reads.
- `POST /api/auth/switch` activates a parked account. It grants nothing new: it can only turn on a token the browser already holds, which the middleware would have accepted as the active one anyway.
- `POST /api/auth/park` moves the current session into the jar and signs this browser out of it — the "sign in as someone else" path, with the previous account still one click away.
- Signing in as a second account parks the first instead of dropping it. At most one session per account is kept, five parked beside the active one; anything evicted is deleted server-side, not merely forgotten.
- `POST /api/auth/logout` is deliberately total: every session in the jar is destroyed and both cookies are cleared, so Sign out leaves nothing on the machine that can be re-entered without a password.

## Remembered accounts

Accounts with no live session are still remembered by id so the login page can prefill them: clicking one fills the username and puts the cursor in the password box; the row's ✕ makes the browser forget it. The login page shows the two tiers separately — parked sessions enter with one click, remembered ids ask for a password. The list is capped at eight entries.

An entry is a `(machine, userId)` pair rather than a bare id, where `machine` is the SSH identity of the server — `root@localhost`, Linux account included, since each account has its own `~/.penguin` and therefore its own server and user table — and `userId` is an account inside that server. Neither implies the other.

An id alone is not an identity, and `localStorage` is bucketed per origin: once the shell can open a penguin server on another machine over an SSH tunnel, every target is `http://localhost:<port>`, so two of them handed the same local port share one bucket — untagged, one server's account ids would be offered on another server's login page. The identity comes from the shell as `window.__PENGUIN_MACHINE__`, falling back to the origin's host for a browser talking to a server directly.

Only ids are stored in `localStorage` — no passwords, no tokens, nothing beyond what watching someone sign in would reveal.
