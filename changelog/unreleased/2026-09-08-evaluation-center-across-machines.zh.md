# 评估中心会读遍这个 Agent 跑过的每台机器

- **Date:** 2026-09-08
- **Type:** fix
- **Scope:** `web`
- **PR:** [#450](https://github.com/Prism-Shadow/penguin-harness/pull/450)

[English](2026-09-08-evaluation-center-across-machines.md)

Agent 在它运行过的机器之间是**同一个身份**——本项目的 `default_agent` 在这台和在某台机器上是同一个 Agent，不是两个。它的 `benchmarks/` 目录却不是：评测在哪台机器上真正跑起来，就写在哪台机器上，于是同一个 Agent 的用例库与记分板被摊在它被评测过的所有磁盘上。而评估中心只读它自己所在的那块磁盘：在机器上建的 Benchmark 根本不会出现在列表里；两边都评测过的 Benchmark，则会显示一段缺了在别处跑过那几轮的历史——一张有洞的曲线，而且屏幕上没有任何东西说明这一点。

现在列表会同时问本机与本机持有连接的每台机器，并按 benchmark id 归并：一个 Benchmark 一条记录，其下是一段完整历史。机器作为**归属信息**而非分组维度出现——当某个 Benchmark 在不止一处被评测过时，评测行会点名记录它的那块记分板所在的机器（`[SSH: prod-1]`）；只存在于某台机器上的 Benchmark，则以那台机器命名。

顺序只有一种定法。记分板的追加顺序**就是**评测序列，页面信任它胜过信任时间戳——但两块磁盘上的两份记分板之间根本不存在共同的追加顺序，因此合并出来的历史按时间排序，而只来自单台机器的 Benchmark 则原样保留其文件里的顺序。

左侧的树本身也是并集。Agent 属于 Project，但它的状态目录是在它运行过的那台机器上创建的——因此只在某台机器上跑过的 Agent 就只存在于那里，而按本机 Agent 列表构建的树根本没有一行可以挂它的 Benchmark。现在各机器的 Agent 会一并归入，本机也有的由本机描述，只存在于某一台机器上的 Agent 以那台机器命名。

Benchmark 的用例取这些机器所持有的并集，用例文件从其列表来源的那台机器读取——它们是同一个用例的两份副本，读其中一份就是读这个用例。答不上来的机器会被排除在归并之外，这正是「读不到它」的含义：本机持有的内容照常渲染，只有当没有任何来源作答时才报错。
