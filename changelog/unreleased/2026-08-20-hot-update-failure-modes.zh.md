# 热更新这条路补齐了自己的三种失败模式

- **Date:** 2026-08-20
- **Type:** fix
- **Scope:** `core`, `server`

推送 platform（[热更新](../0.2.3/2026-08-18-hot-update.zh.md)）有三种出错方式的结局不是「推送失败」：
目标跑不了的 bundle 只落地半个版本、交换之后旧 App 的工作还在新 App 背后跑、启动失败的 bundle
会让业务面一直半死到重启。现在每一种都有确定的结局。

## 目标跑不了的 bundle

把当前的 bundle 推到 runtime 早于资源接口握手的机器上，会让它用**新**前端去打**旧** API——打开
「上传限制」时浏览器报 `Cannot read properties of undefined (reading 'attachmentLimitMinMb')`，
因为 `/api/me` 仍然是上一个版本的。推送是原子的，但它送过去的 platform 必须先**认领** runtime
发布的业务能力才能服务业务 API，而过旧的 runtime 发布不出这些能力，认领失败。platform 当时的
处理是降级成一个只有终端的 App：它拒绝了所有业务路由，seam 把这些请求交还回去，更旧的 runtime
就用自己内建的路由回答了它们。于是一次原子推送悄悄地只落地了半个版本，还报告为成功。

现在认领不到业务能力的 platform 会拒绝启动，升级按任何一次启动失败的方式整体回滚——正在运行的
版本继续服务，web dist 不提交，什么都不持久化——推送方拿到的是原因：需要更新的是这台机器的安装
本身，因为推送替换的是 platform，从来不是 runtime。已经处在半个版本状态的机器同样需要这次更新：
它已提交的 bundle 早于这项检查，重启只会把它原样降级恢复；更新安装后，同一个 bundle 就能认领
成功、完整服务（或者删掉 `<数据根>/hmr/harness.json`，退回打包自带的版本）。

真的没有业务 runtime 的宿主，会在每个宿主用来自我描述的那份接口描述符里把这件事说出来，照旧得到
只有终端的 platform。「答不上来」不再被当成「只要终端」。

## 两代之间的交接

替换 platform 以前停旧 App 停得很松：调度器停了、agent 运行中止了，但中止是发完即忘，于是新 App
可能已经在服务，旧 App 的运行还在收尾。资源也跟着漏了——会话里启动的 dev server 一直跑着，继任者
既看不见也停不掉；旧 App 的 pty 回收定时器和退出监听会从一个已死的世代里继续触发，dispose 的会话、
移除的注册表条目却已经归新 App 所有。

App 创建的每一个资源都被列进一份成文清单，三种命运之一，交换按清单执行：

- **交付**——pty 通过资源注册表跨代存活，由继任者接管；runtime 自己的单例由每代重新认领。
- **暂停**——调度器停止，运行中止，每个会话的环境被 dispose，杀掉它拥有的后台命令；继任者全部
  重新构建。
- **脱钩**——旧 App 注销自己的 pty 退出监听，已死的世代不再对新世代拥有的对象做任何动作。

这份清单是契约，而不是对当下存在的服务的描述：新增自带状态的服务要自己选一条列表，否则交换就会
漏掉它。

dispose 是同步的，所以异步的剩余部分——等被中止的运行真正结束——由 App 暴露出来，内核在 dispose
旧树与启动新树之间等待它。继任者因此绝不会与前任并行。

## 启动失败的 bundle

内核的交换是先校验、后交换：旧 App 先被 dispose，新 App 才能接管它交付的资源。此前如果新 platform
的启动随后抛错，就没有回头路了——错误以异常抛出、park 状态丢在异常里，进程陷入半死：被 dispose 的
App 的路由还靠闭包应答，但它的 manager 已关闭（新任务一律 503），直到有人重启服务器。

现在内核以返回值报告这次失败——`status: "failed"`，携带启动错误和 park 文档——而不是抛出，host 用
它把之前运行的那个版本从这份 park 文档重新启动。上面那份清单正是让恢复变成一次普通 load 的东西：
被 dispose 的 App 已经完成了暂停与脱钩，恢复的 App 接管交付的资源、重启被暂停的机器，和任何继任者
一样。推送方仍然拿到错误，因为推送确实失败了，但那台机器继续工作，活状态原样延续。二次故障只会
告警：`/api/hmr` 归 runtime 所有、始终可达，后续推送仍能修复，重启则无论如何都会恢复已提交的版本。
