# 一个 Project 一份插件清单，不重启即生效，并在它的机器上保持一致

- **Date:** 2026-09-06
- **Type:** feature
- **Scope:** `core`, `server`, `web`
- **PR:** [#383](https://github.com/Prism-Shadow/penguin-harness/pull/383)
- **Breaking:** 数据根的 `plugins.json` 不再被读取

[English](2026-09-06-plugin-fleet-parity.md)

插件原本是一份部署级的文件，且只在进程启动时生效。有了机队，这两条都不成立：机器是按 Project 借出的，而产品里根本没有「登进每台机器的服务端各启用一遍」这条路。见 PRFC-0010。

## 清单属于 Project，进程跑的是闭包

一个 Project 的插件写在它自己的配置里——`.project_config.toml` 的 `[plugins]` 表，包名 → 要求，形状同 Cargo 的 `[dependencies]`（`"@scope/name" = "*"` 表示部署自带的那个，或版本字符串，或 `{ version = "…" }`，后续字段就放在这里）——与它的模型并列——因为机器是按 Project 借出的，所以 Project 的清单才是「插件要抵达哪些机器」的依据。但加载是按进程的：模块树只有一棵。所以部署跑的是**闭包**，即它各 Project 的并集，插件贡献的东西对所有 Project 可见。插件页上的一行因此是两个事实的合并：这个 Project 要了它，以及这个进程有它。

路由移到 `/api/projects/:projectId/plugins/installed`。只有当没有任何 Project 还要它时，包才从磁盘上移除。

## 不重启即生效

写入之后会让 App 自行重组：平台用 kernel 自带的 `upgrade` 把内层的树再启动一次——同一个 bundle、同一份寄存文档，热推送本来就在做的那次交换——所以 pty 与机器连接像跨越一次推送那样跨过去。不重启进程，HMR 层也一字未动：运行时自始至终握着同一个外层实例，因此在任何运行时上都生效，旧的也一样。启动失败就恢复到上一棵树，并报告「未生效」。

重组是平台自己的事：它用 kernel 自带的 `upgrade` 把内层的树再启动一次——同一个 bundle、同一份寄存文档，正是热推送做的那次替换——HMR 层一字未动，运行时自始至终握着同一个外层实例，因此在任何运行时上都生效，旧的也一样。启动失败就恢复到上一棵树，并报告「未生效」。

## 一个 Project 的机器上保持同一份清单

Project 的清单会被交给它使用的机器，走的是它的模型凭据本来就在走的那趟，时机也一样：清单变动时，以及每次连接时。一致是**严格**的——以 Project 的清单为准，机器上多出来的被移除。

代价需要知道：分平台的沙盒后端不在另一平台的清单里，因此会被拿走。想保住就把它列进整支机队的清单；解析不到它的那台会显示一条惰性的错误行，而不是丢掉自己能用的那个。同步按机器汇报：加了什么、移除了什么、哪些它列了却解析不到（多半是那台需要先更新），以及它是否仍需重启。

## 兼容性

**数据根的 `plugins.json` 不再被读取，也不做任何迁移。** 原本装着插件的部署会以**没有任何插件**的状态启动：沙盒后端、语法、会话表面都不在树里，直到各 Project 在插件页重新勾选。旧文件原样留在盘上，因此回滚到更早的平台时它还在。

这个键在发布前短暂有过的列表形式（`plugins = ["…"]`）同样不再读取：这样的 Project 视为不要求任何插件，直到在插件页重新写入它的表。

没有任何兼容代码要背，也就没有以后要清理的东西——这正是选它而不是迁移或双读的理由。
