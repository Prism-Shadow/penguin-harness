# 一个 Project 一份插件清单，不重启即生效，并在它的机器上保持一致

- **Date:** 2026-09-06
- **Type:** feature
- **Scope:** `core`, `server`, `web`
- **PR:** [#627](https://github.com/Prism-Shadow/penguin-harness/pull/627)
- **Breaking:** 数据根的 `plugins.json` 不再被读取

[English](2026-09-06-plugin-fleet-parity.md)

插件原本是一份部署级的文件，且只在进程启动时生效。有了机队，这两条都不成立：机器是按 Project 借出的，而产品里根本没有「登进每台机器的服务端各启用一遍」这条路。见 PRFC-0010。

## 清单属于 Project，进程跑的是闭包

一个 Project 的插件写在它自己的配置里（`.project_config.toml` 的 `plugins`），与它的模型并列——因为机器是按 Project 借出的，所以 Project 的清单才是「插件要抵达哪些机器」的依据。但加载是按进程的：模块树只有一棵。所以部署跑的是**闭包**，即它各 Project 的并集，插件贡献的东西对所有 Project 可见。插件页上的一行因此是两个事实的合并：这个 Project 要了它，以及这个进程有它。

路由移到 `/api/projects/:projectId/plugins/installed`。只有当没有任何 Project 还要它时，包才从磁盘上移除。

## 不重启即生效

写入之后会重新读出闭包、建一份新的插件宿主，并请运行时以同一个 bundle 重新装配 App——热推送本来就在做的那次交换，所以 pty 与机器连接像跨越一次推送那样跨过去。不重启进程。

`Hmr.reload` 是可选**字段**而不是方法，这一点是承重的：签名校验容忍运行时没有声明的可选字段，却会拒绝一个必需方法缺失的平台。比它旧的运行时照常接收推送，只是报告「等待重启」，也就是此前每个运行时的行为。

页面也改成同一个说法：Installed plugins 对话框不再提数据根下的 `plugins.json`，也不再说要等重启；目录页的提示改为指向该行自己的「安装」控件。唯一还提到重启的地方，是那种无法重新装配的运行时——也正是会产生它的情形。

## 一个 Project 的机器上保持同一份清单

Project 的清单会被交给它使用的机器，走的是它的模型凭据本来就在走的那趟，时机也一样：清单变动时，以及每次连接时。一致是**严格**的——以 Project 的清单为准，机器上多出来的被移除。

代价需要知道：分平台的沙盒后端不在另一平台的清单里，因此会被拿走。想保住就把它列进整支机队的清单；解析不到它的那台会显示一条惰性的错误行，而不是丢掉自己能用的那个。同步按机器汇报：加了什么、移除了什么、哪些它列了却解析不到（多半是那台需要先更新），以及它是否仍需重启。

## 兼容性

**数据根的 `plugins.json` 不再被读取，也不做任何迁移。** 原本装着插件的部署会以**没有任何插件**的状态启动：沙盒后端、语法、会话表面都不在树里，直到各 Project 在插件页重新勾选。旧文件原样留在盘上，因此回滚到更早的平台时它还在。

没有任何兼容代码要背，也就没有以后要清理的东西——这正是选它而不是迁移或双读的理由。
