# The Windows sandbox runs commands as a dedicated account

- **Date:** 2026-09-16
- **Type:** feat
- **Scope:** plugins, server
- **PR:** [#771](https://github.com/Prism-Shadow/penguin-harness/pull/771)

[中文](2026-09-16-windows-account-sandbox.zh.md)

Confinement on Windows no longer goes through a container, because no container available there can run the shell the harness spawns. `penguin-winuser` confines by identity instead: each agent command runs as a dedicated local account that owns nothing, and what it may touch is what the setup granted.

- **A new backend, `sandbox-winuser`**, implementing all three dimensions. The Workspace is opened to a local group — Modify under `workspace-write`, Read and Execute under `read-only`; `network: "none"` picks the one of two accounts whose outbound traffic three firewall rules block, loopback included; `mask-paths` becomes an explicit Deny, which outranks the Workspace's own grant. Everything else is already out of reach: one local user cannot read another's profile.
- **Setup is elevated, once, and it is a script a person runs** (`setup/penguin-sandbox-setup.ps1`) — creating local accounts and firewall rules is not something a server should do behind anyone's back. It leaves a group, two accounts with random passwords, three firewall rules and one state file naming them; `-Remove` takes all of it away. The passwords are protected by that file's permissions: Administrators, SYSTEM and the account the harness runs as. Until it has run, the backend declines to load and the fail-closed message carries the command, rather than letting the first agent command fail.
- **A confined command is invisible and cheap.** It runs without loading the sandbox account's user profile — that would mount and unmount a registry hive per command, build a profile directory, and tell the shell about a logon, which a person at the machine sees as the harness's own window dropping to the taskbar. The console Windows gives a process in another logon session is hidden through the startup info, since the secondary logon service ignores `CREATE_NO_WINDOW`. And the command runs in the directory the harness asked for, not the Workspace root.
- **The confinement seam can now carry environment for the runner.** A backend's `ConfinedArgv` (and the platform's `SpawnConfiner`) may name entries laid over the command's environment at spawn. The Windows backend needs it: its launcher is a script run by the server's own interpreter, and in the desktop app that interpreter is the app binary, which runs a script only under `ELECTRON_RUN_AS_NODE`. Without the switch every confined command opened a second instance of the app — which handed off to the running one, whose window came to the front, and exited with nothing on its streams — so the agent saw an empty result in a third of a second and the person saw the window jump. The launcher strips the switch again before the command inherits the environment.
- **The command's identity never reaches its command line.** The provider rewrites a confined command into a launcher carrying the policy; the launcher reads the credentials from the state file, because every process on a machine can read another's arguments.
- **Verified on a Windows 11 host**, driving the backend directly: Git Bash runs as the sandbox account, a write inside the Workspace succeeds and one outside is denied, `read-only` denies the Workspace too, a cut network fails to connect while an open one reaches the internet, and `git init` works. Two holes the run exposed are closed: a confined command inherited the harness's `http_proxy`, and Windows does not filter loopback, so "no network" fetched the internet through a local proxy — those variables are now stripped when the network is cut; and grants ACCUMULATED, so a Workspace opened for writing stayed writable when the mode later said read-only — the group's entries are now replaced rather than added to.
