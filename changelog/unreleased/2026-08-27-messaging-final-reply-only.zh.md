# 消息绑定可以只转发一次运行的最终回复

- **Date:** 2026-08-27
- **Type:** feature
- **Scope:** `server`, `web`, `docs`
- **PR:** [#512](https://github.com/Prism-Shadow/penguin-harness/pull/512)

[English](2026-08-27-messaging-final-reply-only.md)

此前一次运行中每条完成的助手消息都会在完成的那一刻转发到聊天，因此在工具调用之间写下过程记录
的运行，会把每条记录都作为一条消息发出去。现在每份绑定多了一个选项，可以把这些消息扣下，只在运
行结束时发出该次运行**最后**完成的那段助手文本——只要结论，不要过程。默认关闭，关闭时的行为与此
前逐字节一致。

## 细节

- 该选项存为 `messaging_bindings.final_reply_only` 列，与 `enabled`、`line_per_message` 并列，理
  由和后者当初一样：`config_json` 是渠道自己的凭据文档、由其连接器拥有，而这个选项在每个渠道上
  含义相同。它是 `INTEGER NOT NULL DEFAULT 0`，由既有的 `ensureColumn` 清单在打开存量数据库时
  ALTER 补上——即[向后兼容](2026-08-27-backward-compatibility.zh.md)中记述的新增列惯例，用户无需
  做任何事：默认值复现了每份存量绑定原本的送达方式。
- `finalReplyOnly` 加入 `FeishuBindingInfo` / `TelegramBindingInfo` / `QQBindingInfo` 与三个 PUT
  请求体，与 `linePerMessage` 并列、口径相同——随 Save 生效的普通表单字段，没有独立路由，省略则
  保持已存值，新建的绑定默认关闭。
- 扣下的始终只有一条：每条完成的助手文本覆盖该次运行此前扣下的那条，留到最后的那条在运行的
  `task_state` → `idle` 边沿发出，走的是每条转发消息都走的同一条路径。长度分段、按行拆分、发送
  节奏、群聊中唯一的一次回复引用、发送链的顺序，都沿用现有的那一套。
- 被扣下的回复发往**提问所在的那个会话**，而不是聊天此后移动到的那个。会话引用与首段所引用的那条入
  站消息，都在该次运行的 `task_state` → `running` 边沿取下：只有这一条消息是在运行的另一端才发出
  的，否则期间在另一个 Telegram 论坛话题里发言的第二个人，会收到一份自己从未提过的问题的完整回答，
  还被引用在他自己的消息上。跟随这条回复的文件发往同一处。完成即转发的消息不受影响——它仍然发往行上
  当时记录的会话，那里才是对话正在进行的地方。
- 两个送达选项按一个方向叠加：`finalReplyOnly` 决定发哪一段文本，`linePerMessage` 决定这段文本
  怎么拆，因此同时开启时，最终回复按行逐条发出。
- 随回复发送的文件，跟随**真正到达聊天的那些文字**。选项开启时就是那条最终消息：只在被扣下的过程
  记录中提到的文件，在聊天里找不到任何一句话解释它为何出现，而「被提及」正是这个功能判断哪个产
  物才是交付物的全部依据。
- 在 QQ 上该选项有利有弊：它把一次运行对该平台被动回复额度的消耗压到最低——只发一条；但被动回复
  只在为其提供额度的入站消息之后几分钟内被接受，而把回复扣到运行结束才发，等于把这个窗口花在了运
  行本身上：运行时长超过窗口时什么都送不出去，而逐条转发至少能把窗口之内完成的部分发出去。
  这与另外两个渠道是不同的结果，而不是同一件事的程度差别——那边的代价是安静，这边是输出丢失——所以在
  QQ 上这句提醒说了两遍，而不是只留在这份记录里：既附在该选项的说明中供正在做决定的人读到，也在开关
  真正打开时以警示条的形式立在该行下面。「每行一条消息」不需要类似的提醒：QQ 会把拆分收敛到自己的额
  度内，回复仍然会到达。
- `approval_request` 提醒不属于助手消息，不受影响——运行卡在审批上，恰恰是聊天必须听到动静的时
  候。其余固定提示与测试消息同理不受影响；压缩输出仍在这一切之前就被跳过；中途接入的连接依旧不
  转发该次运行的任何内容。
- 扣着回复却始终没等到运行结束的绑定——进程结束，或运行中途的启用开关、凭证保存重建了连接——扣下
  的内容不会发出。逐条转发的路径在同样的情况下只损失该次运行的剩余部分。
- 绑定编辑器中，两个选项以一对 `Switch` 行收尾表单，三个渠道完全一致，由既有的 Save 保存，各自的
  说明放在标签旁的「?」之后。两行按生效顺序排列：先决定发哪些消息，再决定每条怎么拆。
