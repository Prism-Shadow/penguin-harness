# A server's terminals and Agent commands run its own `penguin`, against that server

- **Date:** 2026-10-11
- **Type:** fix
- **Scope:** `server`, `cli`, `scripts`, `docs`
- **PR:** [#1037](https://github.com/Prism-Shadow/penguin-harness/pull/1037)

[中文版](2026-10-11-dev-terminal-cli.zh.md)

In a development instance started with `pnpm dev` or `pnpm desktop`, `penguin` typed in a terminal could run the installed CLI, or this checkout's CLI talking to the installed server. The `<root>/bin/penguin` launcher, the terminal's environment and its shell hooks were changed so that a server's terminals and Agent commands run that server's own CLI against that server.

## Details

- The launcher sets `PENGUIN_HOME` to its server's data root for the CLI it starts, unless the caller has set it, together with `PENGUIN_WEB_DB`, as an absolute path, when the server's database is not `<root>/web.db`; `--root`, `--server` and `PENGUIN_API_URL` still take precedence. Nothing is exported into the shell that runs it.
- A terminal no longer inherits the server process's `PENGUIN_*`, `PORT` and `HOST` variables, which core already removed from Agent commands. An inherited `PENGUIN_API_URL` or `PENGUIN_HOME` had pointed `penguin` at another server, an inherited `PENGUIN_CLI_ENTRY` had retargeted a server started from the terminal, and an inherited `PENGUIN_HOME` or `PORT` had made `pnpm dev` typed there collide with the running instance. Variables the user's own startup files export are still set, and so are the user's own settings among the `PENGUIN_*` ones, whatever set them: `PENGUIN_LANG`, `PENGUIN_UPDATE_CHECK`, `PENGUIN_NO_LOGIN_SHELL_ENV`, `PENGUIN_SHELL`, `PENGUIN_INSTALL_DIR`, the download and update source variables, and `PENGUIN_GO_API_KEY` / `PENGUIN_GO_BASE_URL`. A Windows user variable set with `setx`, as `penguin config lang` suggests there, reaches the desktop app's terminals only that way. Where no launcher names the data root (a server with no CLI to offer, a missing launcher, or a pushed platform on an older runtime), the terminal keeps `PENGUIN_HOME` and `PENGUIN_WEB_DB` as before.
- bash, zsh and fish run the PATH statement as their last prompt hook (`PROMPT_COMMAND`, `precmd_functions`, the `fish_prompt` event) as well as after the startup files, so a prompt hook that puts another `penguin` first no longer wins from the first prompt on. The hook stays last: when a hook added after startup (a plugin loader's) comes after it, it moves back behind that hook before the next prompt, keeping before the last hooks powerlevel10k and bash-preexec keep for themselves, and without growing `PROMPT_COMMAND` or `precmd_functions`. The hook leaves the last command's exit status as it was and never fails itself, so a `set -e` shell and an ERR or ZERR trap behave as they did without it; the entry it adds to an exported `PROMPT_COMMAND` does nothing in a bash started inside the terminal. On bash before 5.1, a `PROMPT_COMMAND` array gets the hook in its first element. A full path, or an alias or function named `penguin`, still runs another `penguin` there.
- A server running from TypeScript source (`pnpm dev`) offers the checkout's CLI source through the checkout's own tsx, so CLI edits and pulls apply without a restart. A built server (`pnpm desktop`, `node packages/server/dist/index.js`) offers the checkout's built CLI; each falls back to the other, and Electron uses the build only.
- A server running from a checkout whose CLI can run neither way writes a launcher that prints the reason and exits 1, instead of removing the launcher and leaving `penguin` to whatever else is on PATH. The server log says so.
- Each terminal of a server running from a checkout opens with one line naming the CLI `penguin` runs and the data root it targets, or why it cannot run; terminals of an installation show no such line. On either, a terminal whose launcher is missing opens with a line saying that `penguin` there is whatever PATH finds.
- In bash, zsh, fish, sh and PowerShell, the shell prints that line itself at its first prompt, after the user's startup files have run. When they export `PENGUIN_API_URL`, or a `PENGUIN_HOME` naming another data root, the line says so instead: `Your shell sets PENGUIN_HOME=…, so penguin here talks to that server, not this instance (data root …).` zsh prints it once an instant prompt (powerlevel10k's) has handed the terminal back. cmd and other shells get the plain line from the server, as before.
- The dev entry points `pnpm dev`, `pnpm desktop` and `pnpm penguin` clear an inherited `PENGUIN_CLI_ENTRY`, such as one a terminal of the installed app hands on, and always offer the checkout's own CLI. They do it with a new `--unset=VAR` of `scripts/run-with-env.mjs`, which names what it cleared on stderr. A packaged or installed launch still honours the variable.
- The `penguin chat` and `penguin run` banners show the build identity that `penguin --version` prints, which names a source build's commit, and the server they talk to, with its data root when that is how it was found.
- The CLI reference and the configuration and CLI quickstart pages describe the launcher's data root, the terminal's environment and first line, how to run another `penguin` in a terminal, and the dev entry points' `PENGUIN_CLI_ENTRY`.
