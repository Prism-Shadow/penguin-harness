# Windows 沙盒保留真实的用户目录，完全访问也能断网

- **Date:** 2026-09-16
- **Type:** fix
- **Scope:** core, server, plugins
- **PR:** [#771](https://github.com/Prism-Shadow/penguin-harness/pull/771)

[English](2026-09-16-windows-home-and-full-access.md)

Windows 账户沙盒有两处不合理，现已修复。

- **被封禁命令的用户目录被改写**到了 `C:\ProgramData\penguin\sandbox-home`，于是 `~/.gitconfig`、`~/.ssh`、工具缓存以及本平台自身的配置全都不可见，「写你的 home」这类测试写进了一个假目录还报告成功。现在用户目录就是真实的那个。写入限制本来就不需要用户目录：命令以一个一无所有的账户运行，因此它在任何地方本就被拒绝，启动器只在**工作区**上授予它写权限——目录小，所以很快。安装脚本新增的是对一组**精选配置路径**的读取权（用户目录根、根下的各个 dotfile，以及 `.config`、`.aws`、`.gnupg`、`.docker`、`.kube`、`.azure`），这样 `~/.gitconfig` 之类才解析得到。`~/.ssh` 不在其中，而且安装脚本每次运行（包括 `-Remove`）都会把沙盒账户从它上面移除——无论早先的构建是直接授予、经继承授予，还是授予给了一个已被删除的账户：OpenSSH 拒绝其他账户可读的配置文件或私钥，这样的授权会让你自己的 ssh 失效，而被封禁的 ssh 本来也用不了这些文件。根目录下的文件中，注册表配置单元（`NTUSER.DAT` 及其日志）会被跳过。刻意不是整个用户目录：开发者的用户目录里有数以百万计的文件（缓存、`node_modules`、`AppData\Local`），逐个打标记既耗时漫长，又平白把浏览器数据交给沙盒。完全访问的两个账户在同一组路径上获得**修改**权。唯一仍被重定向的是临时目录，指向一个共享的可写目录，且仅在「临时目录可写」开启时。
- **完全访问与断网无法同时成立。** `danger-full-access` 在读取网络设置之前就短路为「不封禁」，于是「完全访问」悄悄丢掉了「断网」。完全访问且网络放行（且无屏蔽路径）时仍是真正的不封禁；完全访问且**断网或屏蔽路径**时，现在会走到一个后端去执行这一维度，同时不限制文件系统。这是对沙盒契约的小幅放宽：provider 现在可能收到 `danger-full-access`，此时它必须放开文件、但仍要断网或隐藏路径。bwrap 把根目录以读写方式绑定并仍 `--unshare-net`；seatbelt 不拒绝任何写入但仍 `(deny network*)`；Windows 后端以一个被防火墙挡住、且 home 可写的账户运行命令。
- **Windows 后端现在有四个账户**——网络轴（放行 / 阻断）与文件系统轴（home 只读 / 可写）的交叉——因此每个账户的可达范围在安装时一次性授予，没有命令需要再去重排你用户目录的权限（目录较大时那会花上几分钟）。

## 兼容性

这改变了 Windows 安装脚本留下的东西（四个账户、一处用户目录授权、一个共享临时目录）以及状态文件的形态，因此早前版本留下的状态会被读作「未安装」。请重新运行一次安装：在管理员 PowerShell 中执行 `setup\penguin-sandbox-setup.ps1`。在重新运行之前，Windows 沙盒拒绝加载，封禁模式会 fail-closed 而不是不封禁地运行；新脚本的 `-Remove` 也会一并清除旧的账户、组与规则。重新运行很快：它只授予那组精选配置路径，绝不遍历整个用户目录。此前的构建在用户目录根上加过一条可继承的授权，根下每个文件都继承了它——某台主机上的 `ssh` 对 `~/.ssh/config` 报 `Bad permissions`，就是它留下的。现在安装脚本每次运行都会从根上撤掉这条授权（Windows 随即从根下每个文件撤掉，用户目录很大时要花几分钟，且只在确有这条授权时才发生），并清退那个构建的账户、组、防火墙规则与假用户目录，于是早先布局的任何东西都不会在一次运行后残留；`-RemoveLegacyProfileGrant` 会再遍历整个用户目录，处理那个构建逐个文件打上的条目，缺省仍不执行。等到不再有 Windows 主机持有双账户状态文件时，本条即可移除。
