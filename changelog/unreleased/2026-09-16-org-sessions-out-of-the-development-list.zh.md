# 公司模式的会话不再进入开发模式的会话列表

- **Date:** 2026-09-16
- **Type:** fix
- **Scope:** `server`, `web`, `docs`
- **PR:** [#751](https://github.com/Prism-Shadow/penguin-harness/pull/751)

[English](2026-09-16-org-sessions-out-of-the-development-list.md)

组织运转期间，它的会话可能冒进开发模式的会话列表。一个员工的会话数一旦超过列表每页加载的数量，
服务端的统计仍把尚未加载的工位会话与工单会话计在内，列表便把它们的 Workspace 画成一个分组——由
刚打开的那个会话把它顶到最上面——附带一行什么都展开不出来的「展开其余」；员工派生出的子会话则完全
不带组织标记，像普通对话一样列在「子智能体」文件夹下。现在列表只向服务端请求用户自己的行，子会话
也继承其父会话的标记。

## 细节

- `GET /api/projects/:projectId/agents/:agentId/sessions` 接受 `excludeOrg=1`：组织拥有的行——
  工位会话、工单会话及其派生的子会话，依据持久的 `client: "org"` 标记或组织缓存判定——同时从分页、
  `counts=1` 的统计、按 Workspace 的分项与 Workspace 时间戳中剔除，分页沿过滤后的流推进。不带该
  参数时路由照旧列出所有行，无论由哪个客户端创建。服务端 API 参考的中英两份文档都记录了该参数。
- 在标记为 `client: "org"` 的会话下注册的子会话，插入时带上同一标记；在其他会话下注册的子会话保持
  原有的空标记。
- Web App 的会话列表 store 每次请求都带上 `excludeOrg`，不再在客户端修正服务端统计；仍经聊天页深链
  自愈进入的行在渲染时被丢弃、不改动统计，并在列表重新加载后保留，于是聊天页打开的工位或工单会话仍能
  收到审批模式、思考级别、标题与状态的更新。
- store 记住用户频道报告的每一次运行状态（`session_state`），不论已加载的分页是否持有该行；公司模式的
  工位行、组织架构图与总览读取的正是这份记录——于是一个排在员工会话流第一页之外的工位，也能看到运行结束。
  收到 `resync_required` 时这份记录被清空，公司模式重新读取组织的会话接口、组织列表与当前打开的组织
  架构，运行结束的事件即便在丢失之列，工位也不会一直显示运行中。
- `GET /api/projects/:projectId/organizations/:orgId/sessions` 为启用了消息渠道绑定的工位会话带上
  `messagingChannel`，与该 Session 自身列表行的读法一致。公司模式侧栏的工位行据此绘制消息渠道标记——
  覆盖每个已绑定的工位，而此前标记只来自开发模式列表恰好持有的那些工位——在工位行菜单里绑定或解绑后，
  该行标记随即更新。
- 两处标记共用同一个渠道判定，覆盖飞书、Telegram、QQ 与微信，并以 `MessagingChannel` 为键，
  漏掉任何一个渠道都无法通过类型检查。
