# 图片可以发进来，生成的文件可以发出去

- **Date:** 2026-08-26
- **Type:** feature
- **Scope:** `server`, `docs`
- **PR:** [#496](https://github.com/Prism-Shadow/penguin-harness/pull/496)

[English](2026-08-26-messaging-media.md)

粘贴进飞书或 Telegram 的图片现在会真正送达智能体，而不再只收到「仅支持文本」提示；一次运行结束后，回复中点名的文件也会跟着发进会话。两个方向都走既有的渠道连接器接缝，第三个渠道按同样的方式实现即可。

## 入站图片

- 入站图片会转成与网页输入框完全相同的输入：图片说明文字（渠道有的话）作为用户文本，随后每张图片一个 `image_url` 部分，内容为 base64 `data:` URL。不支持视觉的模型会像处理粘贴图片那样把它们折叠成 Scratchpad 文件。
- 飞书通过消息的 `image_key` 调用 `im.v1.messageResource.get` 取图；Telegram 取 `message.photo` 中最大的一档，经 `getFile` 与文件端点下载，并把 `message.caption` 作为该消息的文本。
- 连接器接缝携带的是**延迟拉取的句柄**而非字节：被重复投递的消息在任何下载发生之前就被丢弃；上限也随拉取一起传入——超限的传输在越界的那个字节上就被拒绝，而不是先缓冲下来再测量。
- 上限沿用服务端既有的内联图片上限（`INLINE_IMAGE_MAX_BYTES`，20MB）：这些图片与输入框粘贴的图片一样进入对话和 Trace；该数值也正好等于 Telegram 对机器人下载的 20MB 限制。
- 图片超过上限与渠道拒绝下载分别回复**不同的**双语提示，两种情况都不启动 Task——让模型去回答一张它根本没收到的图片，只会得到一本正经的胡说。拒绝下载的提示会带上渠道自身给出的原因，并记入错误记录：飞书上最常见的原因是应用未获授「读取消息中的资源文件」权限，那是需要去后台授予的权限，代码修不了。
- 「暂不支持」提示改为点明现在支持什么。表情、语音、视频与文件仍收到该提示；入站文件不在本次范围内。

## 出站文件

- 一次运行结束时，回复中**提及**的文件会跟在文本之后发进会话：回复中形如路径、能解析到 Workspace 之内且确实存在的片段，出现在回复的任何位置皆可——于是送达的是智能体指出的产物，而不是这次运行顺手写下的全部文件。「确实存在」正是宽松匹配的安全边界；Web 端「文件卡片」只认行内代码，用在会话里过于严格——把文件名写在普通句子里的回复将一个文件都发不出来。
- 图片（`.png/.jpg/.jpeg/.gif/.webp`）按图片发送，图表因此能在会话里直接显示；其余按文件发送。飞书先上传 `im.v1.image.create` / `im.v1.file.create`，再用返回的 key 发消息；Telegram 以 multipart 调用 `sendPhoto` / `sendDocument`。
- 路径解析、越界检查与存在性判断都取自 Files 面板所用的同一个 `WorkspaceFilesService`——离开 Workspace 的路径（无论经由 `..` 还是符号链接）在那里被拒绝，而不是由桥接层里另一份规则副本来判断。
- 上限：每次运行最多 5 个文件，单张图片最大 10MB、单个文件最大 30MB——取两个渠道各自限制中更紧的一个（飞书图片 10MB / 文件 30MB，Telegram `sendPhoto` 10MB / `sendDocument` 50MB）。被上限拦下的文件会在会话中点名；因数量上限截断时会说明还剩多少个未发送。
- 发送与文本共用同一条按绑定串行的队列，因此文件排在点名它们的那条回复之后，且顺序与回复中出现的顺序一致；上传失败记入错误记录，不会中断其后的文件。
