# 群消息以用户实际写下的内容抵达模型，而不是提及占位符

- **Date:** 2026-08-26
- **Type:** fix
- **Scope:** `server`
- **PR:** [#497](https://github.com/Prism-Shadow/penguin-harness/pull/497)

[English](2026-08-26-messaging-inbound-mentions.md)

在群里对机器人说话就意味着要提及它，因此绑定收到的群消息几乎每一条都带着一个 `@`。两个渠道此前都
没有把它交成模型可用的形式：飞书写入的是模型无法解析的占位符，Telegram 则把机器人自己的 handle 留
在句首。一个由飞书群驱动的 Session 因此答道「我看到你发的是 `@_user_1 你好`，但我不太确定
`_user_1` 指的是谁或什么」——整整一轮花在一个从来不属于该消息的 token 上。

## 飞书：占位符变成名字

飞书的 `im.message.receive_v1` 在 content JSON 的 `text` 里放的是 `@_user_1`，真实身份放在连接器
未曾读取的并列 `mentions` 数组中。该数组现在随 `FeishuInboundEvent` 一同传递，每个占位符在文本抵达
Session 之前都会被替换为被提及者的名字。

替换是对原文的一次从左到右扫描，键名按从长到短排列。这是两个问题共同要求的。飞书的占位符从 1 开始
编号，因此 `@_user_1` 是 `@_user_10` 的字面前缀。而逐个键各扫一遍，后面的扫描会重新扫到前几遍刚写
下的内容，于是一个读起来像占位符的显示名会被替换第二次。每个键只在**首次**出现处被替换——飞书对每
个键只发出一个占位符，因此再往后出现的同名 token 是用户亲手敲出来的文字，会原样抵达模型。

机器人身份来自每次连接一次的 `/open-apis/bot/v3/info` 查询，而这次查询已被移出连接路径，交给一个后
台 promise。每个已启用的绑定都在服务器启动、HTTP 监听尚未绑定之前建立连接；一个接受了 TCP 却永远不
作答的飞书端点——卡住的代理、黑洞防火墙——原本会让整台服务器被一次尽力而为的显示名查询拖住。在答案
落地之前，以及应用根本无法给出身份时，本机器人的提及与其他人一样被命名。

## Telegram：剥掉机器人自己的 handle

机器人的 `@username` 本就来自轮询循环在每段连通期之前所做的 `getMe`。属于它自己的开头 `mention` 实
体（大小写不敏感匹配）或 `text_mention` 实体（按用户 id 匹配）会从文本开头剪除，剩下的部分做一次
trim——与飞书侧对自己占位符所用的空白处理策略相同。实体偏移以 UTF-16 码元计数，而这正是 JavaScript
字符串下标本身的单位，因此 handle 之前的 emoji、或被链接的显示名内部的 emoji，都不会让剪除位置错位。

## 只有开头的称呼会被丢掉

只有当消息以某个提及开头时，它才算称呼。本机器人出现在句子中间时——「@thisbot 的状态是什么？」「总
结一下 @thisbot 昨天说了什么」，以及飞书中位于句中的占位符——那是用户自己选择的文字，于是它被保留下
来：在 Telegram 上保留为用户敲出的 handle，在飞书上则显示为本机器人的名字，与其他任何人的提及一样。
剪掉它们会给模型留下一个带窟窿的句子（「 的状态是什么？」），那比让它看出消息来自哪个渠道更糟。

## 没有实际内容的消息不再发起 Task

只剩提及的消息——有人 `@` 了机器人却没有写别的——现在走与表情包相同的分支，以「仅支持文本消息」的
提示作答，而不是拿一个裸占位符发起一轮运行。在飞书侧，这一「是否为空」的判断是在移除**全部**占位符
（而不只是本机器人的）之后做出的，因此无论机器人身份是否解析成功都成立。
