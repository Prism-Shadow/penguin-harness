# Web App: drag files onto the window to attach them to the composer

Attachments used to have exactly two entry points — the "+" menu's pickers and image paste. Dragging a file onto the page did the worst possible third thing: the browser navigated to the file, replacing the running app. Now the drag is a first-class entry into the same attachment pipeline (#311).

- Dragging OS files anywhere over the window — chat page or draft page, and while a Task is running just the same — shows a full-window "Drop files to attach" overlay; releasing attaches the whole batch to the composer. Images join the pasted-image pipeline (`image_url` parts, vision-less models keep the scratchpad-path fallback), everything else becomes a file attachment (scratchpad + `[attached file: <path>]` line), with the same validation and the same errors as the "+" menu — an oversize file is refused before it is read, with the existing toast.
- The overlay tracks the drag honestly: it hides when the drag leaves the window (a depth counter absorbs the dragenter/dragleave churn of internal element boundaries, and drop/dragend reset it outright so a missed dragleave cannot strand it), and non-file drags — text selections, dragged links or page images, the sidebar's session reorder — never trigger it. Goal mode takes dropped images but refuses files with a toast, the same reason the "+" menu grays its file entry out there.
- An app-shell guard cancels the browser's navigate-to-file default for any file drop no drop zone claimed — on every page, with a no-drop cursor while such a drag hovers — while leaving non-file drags to their native behavior, so dropping selected text into the composer still inserts it.
- The decision logic (file-drag detection, drag depth, batch splitting, the shell guard) lives in `lib/file-drop.ts` and is unit-tested; docs (web-app page, en/zh) describe the flow.
