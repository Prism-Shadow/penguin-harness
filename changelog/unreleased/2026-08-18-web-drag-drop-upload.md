# Web App: drag files onto the chat area to attach them to the composer

Attachments used to have exactly two entry points — the "+" menu's pickers and image paste. Dragging a file onto the page did the worst possible third thing: the browser navigated to the file, replacing the running app. Now the drag is a first-class entry into the same attachment pipeline (#311).

- Dragging OS files over the **chat area** — the conversation and the composer, on the chat page or the draft page, and while a Task is running just the same — shows a "Drop files to attach" overlay bounded to that region; releasing attaches the whole batch to the composer. Images join the pasted-image pipeline (`image_url` parts, vision-less models keep the scratchpad-path fallback), everything else becomes a file attachment (scratchpad + `[attached file: <path>]` line), with the same validation and the same errors as the "+" menu — an oversize file is refused before it is read, with the existing toast.
- Only the chat area reacts. The sidebar, the top bar, the conversation toolbar, the docked Files and Subagents panels and every page without a composer are outside it: no overlay lights up there and nothing is attached. Non-file drags — text selections, dragged links or page images, the sidebar's session reorder — are ignored everywhere, so dropping selected text into the composer still inserts it natively. Goal mode takes dropped images but refuses files with a toast, the same reason the "+" menu grays its file entry out there.
- Outside the chat area a file drop is inert rather than destructive: an app-shell guard silently cancels the browser's navigate-to-file default — which would otherwise replace the running app and any unsent draft with a file viewer — and shows a no-drop cursor while such a drag hovers. It attaches nothing and says nothing; it exists only so that dropping a file on the sidebar does nothing at all.
- The overlay is derived from the drag's current position rather than accumulated from enter/leave counts, so it cannot be stranded on screen by a drag that ends outside the browser (which fires neither `drop` nor `dragend`). The decision logic (file-drag detection, the region decision, batch splitting, the shell guard) lives in `lib/file-drop.ts` and is unit-tested; docs (web-app page, en/zh) describe the flow.
