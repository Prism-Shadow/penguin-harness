# 每台机器都有自己的 id，也能被问出状态

- **Date:** 2026-09-01
- **Type:** feature
- **Scope:** `server`, `cli`, `docs`

[English](2026-09-01-machines-identity.md)

机器现在会说明自己是谁、服务是否在跑。列表以**本机**开头，每台已安装的机器带着最近一次探测到的状态，而 `penguin server status` 就是控制端通过 ssh 去问的那一条命令。

## 哪台机器是哪台

每台机器都由运行在其上的服务铸出自己的 id——16 个 base64url 字符，本机也不例外——此后一直保持不变。用 base64url 是因为这个 id 会出现在路径、查询串和文件名里，而 `+` 与 `/` 在那些地方活不下来；取 96 位是因为这些 id 由互不协调的机器各自铸出，标准应当是生日界。

ssh 别名担不起这个职责：别名只是某一台机器配置文件里的一行，所以同一台主机在这边叫 `build-box`、在那边叫 `bb`，而同一台主机的两个别名就是一台机器的两个名字。别名仍然是给人**读**的；id 才是它们背后的身份，也是一切存储下来的引用所指向的东西。

它搭乘状态探测本来就要走的那一趟往返，因此获知它不额外花钱，并且与安装记录一起被记住。服务从未启动过的机器还没有 id——没有任何东西铸出过它——于是它如实说没有，而不是被塞一个编造的。别名被改指到另一台主机后会答出不同的 id，且以新答案为准：id 对一台机器永不改变，所以 id 变了就意味着机器换了。

## 本机，以及其他机器是否在跑

列表以**本机**开头——服务所在的主机，用它的 hostname 命名，带着它运行的版本与正在服务的端口。它是直接读出来的而非探测得来（两个事实都在本地），它始终存在，且永远不是安装目标：服务不会在自己正运行的程序目录上覆盖推送本次构建，因此对它 `POST …/install` 会得到 `409 self_install`。

随后每台已安装的机器带着它服务的状态：running 并附端口、stopped，或 unreachable 并附上 OpenSSH 自己的诊断。这里刻意没有单独的「ssh」状态——ssh 是传输方式，因此 ssh 到不了的机器读作一件事，而不是要读者自行合并的两件。

状态每台要花一次 ssh 往返，因此**绝不在列表时获取**，也绝不对整个 ssh config 获取——只针对本 Project 确实安装过的机器，并发 5，且仅当 `POST …/machines/probe` 来问时。

## `penguin server status`

```bash
penguin server status
# {"running":true,"port":7364,"pid":41233,"machineId":"LNrJdHAZJ91G58i0"}
```

它刻意是面向机器的。这个问题过去是用 shell 问的——`cat` 锁文件、`sed` 出 pid、`kill -0`、再 `cat` 第二个文件取 id——这意味着本侧要为一个无人定义的格式写解析器，而且 Windows 远端根本给不出答案，`kill -0` 在 cmd.exe 里没有对应物。改为询问机器自己的 CLI，把这两个问题都挪到了有 Node 的那一侧。

`running` 为真要求记录的 pid 存活**且**其端口可建立连接，这是 shell 版本做不到的：它只有 `kill -0`，而被回收复用的 pid 会被读成一个活着的服务。

读取 id 绝不会铸出一个，而状态探测以只读方式打开数据库——控制端询问一台机器「你是什么」时，不得在那台机器正运行的服务底下改动它的 schema，也不得在从未有过数据根目录的机器上留下一个。

完全不含答案的输出会被报告为 **unreachable** 而非 stopped：版本过旧、没有该子命令的构建会打印一条错误，把它读作一个格式良好的「否」，会让每一台这样的机器都变成静默错误的机器。
