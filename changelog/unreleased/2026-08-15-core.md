# Core: a thinking-mode request the provider rejects for missing `reasoning_content` no longer kills the Session

## What happened

Reasoning models reached over an OpenAI-compatible API — DeepSeek and the relays in front of it — require every assistant turn in the replayed history to bring its `reasoning_content` back when the request runs in thinking mode, and reject the whole request otherwise:

```
status_code=400 [invalid_request_error] The `reasoning_content` in the thinking mode
must be passed back to the API.
```

The thinking level is a **per-turn** parameter while the model history is shared by the whole context, so a context can legitimately hold assistant turns that carry no reasoning at all:

- a turn run at `none` (per-turn level, or an Agent config that had it off), with a later turn asking for thinking;
- a Session **resumed** at a level its recorded turns never ran with — `session_meta` deliberately records no thinking level, so resume reads the Agent's current config;
- a provider that returned no reasoning for one turn.

From that point every request in the context carried the same history and was rejected identically. The rejection is a 400, which classifies as `failed` and retries — so the run burned its whole reconnect budget on a deterministic failure and the Session was left dead, with no path back short of a new conversation.

## The fix

`GenerativeModel` now recognizes the rejection (new exported `isThinkingReplayRejection`, matched on the provider's message text across the error's `cause` chain and both parsed-body shapes, in English or Chinese) and reads it as a verdict on the **context** rather than on the turn:

- thinking goes off the wire for the rest of that model context — an explicit `none`, which outranks both the per-request override and the construction default, and is sent even where no level was configured at all, since an absent level leaves a provider default that is thinking-on for exactly these models;
- the attempt is still reported as `failed` with the provider's own message, so the engine's existing retry re-issues the identical input with thinking disabled — which the unchanged history is always valid for — and the run continues;
- the switch is announced once on stderr, so a session that quietly stopped thinking is diagnosable from the log;
- committed history is **not** rewritten to synthesize the missing reasoning: that would forge model output and invalidate the provider's prompt cache for everything after it (the same reason compaction corrects forward instead of rewriting a bad attempt, issue #84). Turning the request parameter down is the one lever that fixes the request without touching what the model actually said.

The state is per-object and dies with the history it describes: a new context — after a compaction, or in a new session — starts from the configured level again.

Guarded against neighbouring verdicts: a rejection saying `reasoning_content` is *unsupported* (which disabling thinking would not fix) is not matched, and an attempt that already ran with thinking explicitly off never absorbs the verdict as "thinking disabled". Docs (`models`, `interfaces`, both locales) updated.
