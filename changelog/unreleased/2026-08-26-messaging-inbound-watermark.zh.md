# 重投的聊天消息跨越服务端重启也不会被运行两次

- **Date:** 2026-08-26
- **Type:** fix
- **Scope:** `server`

[English](2026-08-26-messaging-inbound-watermark.md)

消息桥会丢弃绑定已经处理过的入站消息，使渠道重投同一事件时不再重新发起一次 Task。此前这份记忆只
存在于进程内：桌面端重启或运行时热替换会将其清空，而渠道跨重启的重投——连接一打开渠道就会这么做
——会让该消息第二次运行。于是同一个 Session 在聊天中与网页端各答复了两次。

## 绑定行上的水位

`messaging_bindings` 新增 `last_inbound_message_id`：最近一条被处理的入站消息的渠道 id。它由本就
在执行的那条 `UPDATE`（把消息所在会话记为该绑定的回复目标）一并写入，对每条入站消息都执行，因此
代价是一个绑定参数，而不是一条额外语句。

连接打开时、事件流尚未投递任何内容之前，`MessagingBridge` 会把存储的 id 折回该绑定的内存环。二者
是同一份记忆而非两道防线：环在进程存续期间保留最近 64 个 id，行在绑定存续期间保留最后一个。

行只记住一个 id，因此渠道跨重启重投一整批事件时，只能保证其中最近的一条被识别。连接器在处理完每
个事件后即予确认，因此进程结束时最多只有正在处理的那一条尚未确认。

把绑定改存到**另一个**机器人账号时，水位会与记住的会话一同清除——另一个账号的消息 id 对新账号毫无
意义。

## 去重记忆不再按时间过期

内存环此前同时按数量和十分钟的时限来限定自身。时限是为了容忍会复用消息 id 的渠道；而两个渠道都不
复用——飞书的 `om_*` 全局唯一，Telegram 的键是 `chatId:message_id`，其计数只增不减。既然没有复用
需要防范，过期就只会遗忘仍然欠着的重投，而渠道在长时间中断后恢复事件流时，会重投它未曾见到确认的
消息，无论那已经过去多久。数量上限保留，并由它来约束这份记忆的大小。

## 兼容性

新增的列由本批的[向后兼容条目](2026-08-26-backward-compatibility.zh.md)统一说明。用户无需任何操
作。
