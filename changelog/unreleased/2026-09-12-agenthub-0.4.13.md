# AgentHub 0.4.13: a DeepSeek tool chain survives the turns the model thought nothing on

- **Date:** 2026-09-12
- **Type:** fix
- **Scope:** `core`, `cli`
- **PR:** [#703](https://github.com/Prism-Shadow/penguin-harness/pull/703)

[中文版](2026-09-12-agenthub-0.4.13.zh.md)

`@prismshadow/agenthub` moved from 0.4.12 to 0.4.13 (agenthub [#212](https://github.com/Prism-Shadow/agenthub/pull/212)). A task run against DeepSeek over the `openai-chat` protocol no longer dies part-way through with `400 The reasoning_content in the thinking mode must be passed back to the API. (invalid_request_error)`. The client attached the reasoning field only when an assistant turn had thinking text, so a turn that made tool calls and thought nothing went back with the field absent; it now sends that field as an empty string on such a turn.

## Details

- DeepSeek requires the chain of thought back only when it cannot recover it from a `tool_call` id it issued itself, so the rejection appears on an endpoint that reissues ids — a relay, or a custom OpenAI-compatible entry in front of DeepSeek — and not on a direct `provider = "deepseek"` row. The turns it applies to are DeepSeek's own doing: past the first few steps of a long tool chain it answers with a bare tool call and no reasoning at all.
- The engine classified the rejection as a provider 4xx, which is `fatal` and never retried, so the Task stopped where it stood and every automatic continuation reproduced it.
- The fix lives in AgentHub's `openai_chat` client, so every row pinned to `openai-chat` and the vLLM rows that subclass it are covered. `claude5`, `ant_messages`, `gpt6`, `openai_responses`, `glm5_3`, `kimi_k3`, `minimax_m3` and `gemini3_8` were probed against their own endpoints and need no equivalent change.
- `pnpm-workspace.yaml`'s `minimumReleaseAgeExclude` entry names 0.4.13 in place of 0.4.12.
