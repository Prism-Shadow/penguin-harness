# AgentHub 0.4.13：DeepSeek 的工具链不再死在「模型没思考」的那一轮上

- **Date:** 2026-09-12
- **Type:** fix
- **Scope:** `core`, `cli`
- **PR:** [#703](https://github.com/Prism-Shadow/penguin-harness/pull/703)

[English](2026-09-12-agenthub-0.4.13.md)

`@prismshadow/agenthub` 从 0.4.12 升至 0.4.13（agenthub [#212](https://github.com/Prism-Shadow/agenthub/pull/212)）。经 `openai-chat` 协议访问 DeepSeek 的任务不再跑到一半以 `400 The reasoning_content in the thinking mode must be passed back to the API. (invalid_request_error)` 中断。client 此前只在 assistant 轮带思考文本时才附上 reasoning 字段，于是「有工具调用但没产出思考」的那一轮整个不带该字段；现在这种轮次会以空字符串发出该字段。

## 详情

- DeepSeek 只在无法从自己签发的 `tool_call` id 复原思考内容时才要求回传，因此这个拒绝只出现在会重签 id 的端点上——中转站，或架在 DeepSeek 前面的自定义 OpenAI 兼容条目——直连的 `provider = "deepseek"` 条目不会遇到。而触发它的那些轮次正是 DeepSeek 自己造的：长工具链跑过头几步之后，它会直接给出工具调用、一点 reasoning 都不带。
- 引擎把这个拒绝归类为 provider 4xx，即 `fatal`、从不重试，于是 Task 当场停住，之后每一次自动续跑都会复现同一个错误。
- 修复在 AgentHub 的 `openai_chat` 客户端，因此所有钉在 `openai-chat` 的行、以及继承它的 vLLM 行都被覆盖。`claude5`、`ant_messages`、`gpt6`、`openai_responses`、`glm5_3`、`kimi_k3`、`minimax_m3` 与 `gemini3_8` 均已对各自端点实测，无需同样的改动。
- `pnpm-workspace.yaml` 的 `minimumReleaseAgeExclude` 条目改为 0.4.13，替换 0.4.12。
