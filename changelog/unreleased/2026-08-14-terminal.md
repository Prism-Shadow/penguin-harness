# Server-side terminals: an integrated dock and a standalone page

A real shell now runs **in the server**, not in the browser tab that shows it (#285). Every
pty byte is fed into a headless xterm inside the daemon, so the server — not any client —
owns the screen. Views can come and go: a reload, a moved panel, a second device or a
detached window all repaint the exact screen the shell already had, scrollback and cursor
included, while the shell itself never restarts and whatever it was running keeps running.

## Server: `/api/terminals`

- **Control plane, JSON over HTTP.** `GET /api/terminals` lists the caller's terminals,
  `POST` creates one (`cwd`, `~`-expanded and absolute-only; optional `name`, `cols`/`rows`
  and a `shell` override), `GET /:id` reads one, `DELETE /:id` kills it,
  `GET /:id/capture` returns the screen as plain text (line ranges, negative indices count
  from the end), and `POST /:id/keys` drives it with literal text or key tokens (`Enter`,
  `C-c`, `Up`, …). The last two exist so anything that is not a rendering client — a test,
  later an agent — can run a command and read the result.
- **Naming and numbering.** An unnamed terminal takes its directory's name and
  auto-increments per user (`tmp`, `tmp 2`, …), and every terminal carries a stable per-user
  sequence number assigned at creation (smallest free among live ones). The number stays
  with the terminal for life — ending one frees its number for the next create, but
  survivors are never renumbered, so UI numbering can never shift under a reorder.
- **Data plane, binary WebSocket** at `/api/terminals/:id/stream`: frames are
  `[opcode, slot, payload]`, and output is coalesced into ~5 ms windows with an immediate
  leading flush, so a keystroke echo pays no added latency while a noisy build still
  collapses into few frames.
- **Attach is a repaint, not a replay.** The attaching client's geometry resizes the pty
  first, then one Restore frame re-renders the current grid as a self-contained ANSI stream
  (scrollback, colours, cursor position, and the DEC input modes a program had turned on —
  bracketed paste, application cursor keys — so a reattached client sends the right bytes).
  Output produced while the snapshot is being rendered is buffered and delivered after it,
  so no line is lost in the seam.
- **Size ownership.** A pty has one size but many possible viewers, so geometry has a single
  claimant: focusing or attaching claims it, later changes from that same connection apply,
  and updates from any other connection are ignored — a background tab can no longer squash
  the viewport being typed into. Ownership is released when the owner disconnects.
- **Lifetime.** A session is independent of any connection: closing the view leaves the
  shell (and its work) running. An exited session stays readable for a grace period, so a
  reload right after `exit` shows the final screen instead of an empty box, and each user is
  capped at 12 live shells. Server shutdown ends them properly — SIGHUP escalating to
  SIGKILL, since a server started under `nohup` has HUP ignored and its children inherit
  that.
- **Slow viewers resync instead of dropping.** Past a 1 MiB socket backlog a viewer stops
  receiving live output; once its socket drains below 64 KiB it gets one fresh Restore frame
  — the same repaint an attach uses — and the live stream resumes. The connection is never
  closed, and nothing is lost, because the server's emulator holds every byte regardless.

## Security

- A terminal is **a shell as the OS account running the server**, i.e. the most privileged
  thing the API hands out, and it is deliberately not Project-scoped. It is visible only to
  the account that created it: someone else's terminal id answers 404, not 403, so the id
  space cannot be probed. Do not enable terminals for accounts you would not give SSH.
- The stream upgrade authenticates with the same session cookie as the REST API **plus a
  strict `Origin` check** (exact `host:port`, `http`/`https` only) — a WebSocket handshake is
  not subject to CORS, so without it any page the user visits could open a shell on the
  machine. A malformed cookie escape answers 401 rather than throwing in the upgrade
  handler.

## Web App: the terminal dock

`` Ctrl+` `` toggles an integrated terminal, available on every page. The dock is a set of
panes — at most one per edge of the content area — and hiding it never loses the
arrangement.

- **Tabs.** Each pane has a strip of its terminals, labelled `N: title` from the stable
  sequence number and the shell's live window title (the `user@host` marker shells prepend
  is dropped for display). Tabs drag sideways to reorder; when crowded they squeeze
  browser-style until only the number is readable, and the strip scrolls with the mouse
  wheel. The `×` on a tab ends that shell; killing the last one closes the pane rather than
  spawning a replacement nobody asked for.
- **Split by dragging a tab out.** Pulling a tab out of its strip switches the gesture from
  reorder to move: the edge overlay appears — 45 % edge bands plus a drop-target widget —
  with a preview covering the exact region the panel will occupy, and releasing moves that
  terminal to the chosen edge, creating a pane there if none exists. Dragging a pane's
  header moves the whole pane the same way, merging into an existing pane on the target
  edge.
- **Layout changes never reconnect.** The xterm views live in a pool keyed by terminal id
  and are handed to panes as DOM, so moving a terminal between panes, moving a pane to
  another edge or splitting a tab out keeps the same emulator and the same WebSocket — the
  only thing that happens is a refit, exactly as if the window had been resized.
- **Resizing.** The boundary with the main content is a drag handle (double-click resets).
  Sizes are stored as ratios per edge rather than pixels, so a resized panel keeps its
  proportion across repositioning and window resizes, with minimums and an 85 % ceiling that
  keep both the terminal and the main content usable.
- **Detach** hands one terminal to its own `/terminal?id=…` window; the shell stays live and
  listed (the stream supports several attached clients), and the dock moves on to its
  remaining tabs.
- **Opening always lands on a live shell**: the terminal shown last if it is still alive,
  else the newest live one — wherever it was created, including the API — and only then a
  fresh one. Panes, sizes, tab order, terminal assignments and each pane's shown terminal
  all persist across reloads.

## Web App: the `/terminal` page

A full-window terminal outside the app shell, and a deep link: `?id=` attaches an existing
terminal (this is what detach hands off), while `?cwd=` and `?name=` parameterize a new one.
The attached id is written back into the address bar, so a reload — or the URL pasted into
another window — reattaches to the same shell instead of starting over.

## Web App: the chat toolbar's panel switcher

The chat toolbar's panel actions became an icon-only switcher: triggers for the pinned
panels, plus a **Create** menu that opens on hover and lists every panel (Agents panel,
Terminal, Workspace) with a pin toggle per row, so which panels get their own toolbar icon
is up to the user (Agents and Workspace pinned by default; the terminal is opt-in and
persists per browser). The terminal carries a live count of running shells — on its own icon
when pinned, on the Create trigger otherwise, hidden at zero, and updated the moment the
user creates or closes one rather than at the next poll. Hovering the pinned terminal icon
lists the live terminals; picking one brings it on screen in its pane.

## Terminal interaction

- **Copy**: `Ctrl+Shift+C`, `Ctrl+Insert`, or plain `Ctrl+C` while a selection exists —
  with nothing selected `Ctrl+C` is still SIGINT. **Paste**: `Ctrl+V`, `Ctrl+Shift+V` or
  `Shift+Insert`, all riding the browser's native paste event, so pasting needs no
  clipboard-read permission.
- **Mouse**: right-click copies the selection, or pastes when there is none, and never shows
  the page's context menu; middle-click pastes. Both step aside while a full-screen program
  (vim, htop) has mouse tracking on, since the escape codes belong to it then. Clicking
  anywhere in the view — padding included — focuses the shell.
- Controls that appear on hover (a tab's `×`, the menu's pin toggles) also appear on
  keyboard focus.
