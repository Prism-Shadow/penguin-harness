# 文件可以发进来，作为输入框附件

- **Date:** 2026-08-27
- **Type:** feature
- **Scope:** `server`, `docs`
- **PR:** [#513](https://github.com/Prism-Shadow/penguin-harness/pull/513)

[English](2026-08-27-messaging-inbound-files.md)

在飞书或 Telegram 里发给机器人的文件现在会真正送达智能体，而不再只收到「暂不支持」提示。它以网页输入框自己的文件附件形态到达——写进该 Session 的 Scratchpad，并以 `[attached file: <path>]` 行交给模型——走的是入站图片所用的同一条连接器接缝，第三个渠道按同样的方式实现即可。

## 入站文件

- 连接器接缝新增 `MessagingInboundMessage.files`：与图片句柄并列的延迟拉取句柄，携带发送者的原始文件名，理由与图片那一侧完全相同——被重复投递的消息在任何下载发生之前就被丢弃；上限随拉取一起传入，超限的附件在越界的那个字节上就被拒绝，而不是先缓冲下来再测量。该字段是可选的，不投递文件的渠道根本不必填写。
- 文件走的是输入框的附件路径，而不是对话：`attachFilesToInput` 把它写进 `<agent>/scratchpad/<sessionId>/`，文件名经过面向文件系统的净化，消息文本则每个文件追加一行 `[attached file: <绝对路径>]`，由模型用它常规的文件工具打开。下游没有任何环节随文件大小增长，这正是那个大得多的上限得以成立的前提。
- 上限沿用服务端自己的附件限制——管理员可设的单个文件上限（默认 100MB）与单条消息总量上限（120MB），与经过鉴权的输入框上传是同一组数值——按消息逐次读取而非启动时快照，并再取渠道自身更紧的那个上限。同一条消息中后面的文件，其上限收敛为该消息总量的剩余部分，因此一批文件也无法累加越界。
- 这里没有图片那样的「每绑定滚动窗口预算」：该预算所要防的代价在这条路径上并不存在。内联图片会写入 Trace，并在每次翻阅历史、每次恢复 Session 时被整体读回；文件只是磁盘上的字节，没有任何环节会重读，且随 Session 一同删除。
- 文件超过单个上限、一批文件超过单条消息总量、机器人缺少权限、传输失败，分别回复**四种不同的**双语提示，每一种都点名具体文件。四种情况都不启动 Task——让模型去回答一份它根本没收到的文档，只会得到一本正经的胡说——也都不会在 Scratchpad 里留下写了一半的批次。因大小被拒不是任何人的过错，不进错误日志；传输失败则以 `messaging_file_fetch_failed` 记录，并带上渠道自己的原因，其归类与入站图片下载一致——应用从未获授的权限记为 `expected`，因为修复方式已经交到会话里了；只有没人被告知的失败才算缺陷。
- 因大小被拒时，提示点名的是**真正拦下它的那个上限**，未必是服务端请求的那一个：`MessagingMediaTooLargeError` 现在携带 `maxBytes`，于是收紧了传输上限的渠道报出的是自己的数值，而不是把发送者打发去对着一个根本不挡路的限制压缩文件。
- 说明文字即该消息的文本（图片消息本来就是如此），因此文本、图片与文件可以组成同一份输入。附件**不会**被送达的那些消息，其说明文字仍然归一化为 null。

## 飞书

- 支持 `file` 消息类型，经 `im.v1.messageResource.get` 以 `type: "file"` 下载——与图片同一个资源端点，差别仅在这个查询参数，权限也是同一项：被拒绝下载图片的应用会被同一个 `99991672` 拒绝下载文件，并得到同样点名权限与授权链接的提示。
- 事件本身携带文件名，因此发送者原始的名字直达模型。事件未携带文件名时使用占位名 `file`，而不是编造一个扩展名。
- `audio`（语音）与 `media`（视频）同样带有 `file_key`，但有意不纳入：它们为播放而被重新编码，名字并非发送者所选，且下游没有任何环节能解码或转写。两者仍收到「暂不支持」提示。

## Telegram

- 支持 `document` 字段——发送者主动**以文件形式**发出的那一个，也是 Bot API 各媒体字段中唯一携带发送者原始文件名的。以「原图」拖入的图片同样是 `document`，现在会作为附件到达，而这正是发送者以原始字节发送时所要的。
- `audio`、`video`、`voice` 与 `video_note` 出于与飞书同样的理由不在范围内，并如实说明而非假装支持。`voice` 是一段无名的 opus 数据；把它以 `[attached file: …]` 路径交出去，等于承诺一项并不存在的能力。
- 传输上限取 Telegram 自身对机器人的 20MB 下载上限（`TELEGRAM_MAX_DOWNLOAD_BYTES`），而不是交由 Bot API 去拒绝。超过之后 `getFile` 回的是一个 400，其唯一信号是 Telegram 随时可改写的散文，于是一件发送者本可处理的「文件太大」，会以「下载莫名失败」的面目抵达他们。

## 提示语

- 「暂不支持」提示改为点明现在支持什么，因此改为「目前仅支持文本、图片和文件消息。」，其常量名为 `MESSAGING_UNSUPPORTED_NOTICE`。
