# 在另一台机器上运行 Agent——它的 Session、工作区、Agent、Benchmark、插件与终端都在这个窗口里

- **Date:** 2026-09-09
- **Type:** feature
- **Scope:** `core`, `server`, `web`
- **PR:** [#450](https://github.com/Prism-Shadow/penguin-harness/pull/450)

[English](2026-09-09-machines-run-agent.md)

选一个位于另一台机器上的工作区，对话就在那台机器上运行：由那台机器的服务端驱动 Agent、保存消息、写入 trace、提供终端。窗口不会移动——它始终留在本服务端上，只在与那台机器相关的调用里点名它。机器需要处于已连接状态，而连接是服务端的事：持有的连接不会因空闲而关闭，断了会自行重建，服务端重启或热推之后也会恢复——所以一台机器在「机器」页面连接过一次之后，每个窗口都能一直到达它。

## Session 的调用跟着拥有它的机器走

一个 Session 活在其工作区所在文件系统的那台服务端上，所以关于它的**每一个**调用都必须到达那台机器，而这样的端点有二十多个。与其给它们全部加一个机器参数，路由是一条基于路径的规则：对 `/api/sessions/<id>/…` 的请求去往 `<id>` 最后一次被看到的地方。调用点原样不动，Session 所在的机器只在两处被记录——列表交回一条时，以及创建一条时。输出流遵循同一规则。

有两类地址逃过了基于路径的规则，需要自己带上机器：Trace 端点，它把 Session 放在 Agent 级路径里；以及工作区文件的内容 URL 和消息附件的 scratchpad 图片，它们是地址而不是调用。没有这一层，位于机器上的 Session 的每一个预览、图片、PDF 和下载都会向本服务端索要一个它没有的文件。

刻意收窄：项目级的 `…/agents/:a/sessions` 列表**不是** Session 级的。它问的是某台服务端有哪些 Session，让另一台机器来回答，就是那台机器在替这一台回答关于自己的问题。

## 编辑器跟着机器走

Agent 是按服务端划分的，所以编辑器提供的是所选工作区所在机器上存在的 Agent——而不是本服务端的，那会点名一个目标机器跑不了的 Agent。询问期间先给出那台机器上次被看到在跑的 Agent；若无法到达，这份列表仍然可选，并在行里说明原因。从工作区分组新建对话时保留该分组的机器，因为不带机器的工作区路径在每台主机上指向的都是不同的目录。

切换模型同样留在那台机器上。切换会为同一个 Agent 以所选模型开一个新 Session，并沿用原 Session 的工作区，好让对话引用的文件仍然可达——而这个工作区是那台机器上的目录，所以新 Session 在那里创建，它的第一个任务（`[model_switch_from]` 源信息块加用户的文字）发往那里，模型为取上下文而读的轨迹也就在它被服务的那块磁盘上。

## 一个列表，几台机器

侧边栏的 Session 列表是所有已连接机器的合并：每台服务端用自己的偏移量分页自己的行，所以合并从每台各取一页再排在一起，而不是共用一个游标去向一台机器要只有另一台才翻到过的行。文件夹计数按应答了的服务端求和。

无法询问的机器会被如实记录，它上次持有的内容会从缓存显示，直到它再次应答。这正是「本服务端没有那个 Session」与「可能持有它的人都没有应答」之间的区别——于是一台不可达机器上的 Session 读作不可达而非消失，正在打开的对话也不会因为它所在机器暂时不在而被丢掉。打开这样一个对话会说明它在等哪台机器，连接恢复后自动打开。

## 工作区是某台机器上的目录

本机的 `/srv/app` 与机器上的 `/srv/app` 是两个不同的目录，所以侧边栏的工作区分组按「机器 + 路径」建键——一台机器一个文件夹，并以所在机器命名：`app [SSH: prod-1]`，同样的写法用于它的悬浮提示，以及 Session 详情面板里的工作区一行。本机自己的分组写法照旧——不加后缀，键也不变——因此折叠状态、置顶与分组顺序原样保留。每个文件夹的「+」在它自己的机器上创建，计数只采信那台机器的回答，翻页也只问它所在的那台机器。

手工添加的工作区同样按这一对来匹配：加载项目时同一路径在两台机器上的条目都保留，重命名或删除只作用于那台机器的条目，并保留其机器。机器没有可用名称时（机器列表仅管理员可读，主机也可能从 `~/.ssh/config` 里消失），回退为它自己的 id，而不是编一个名字出来。

## 列表不用刷新也保持真实

在任何地方创建的 Session——CLI、另一个标签页、定时任务、Agent 派生的子 Session——都会在用户通道上被宣告，列表去取那一行而不是凭空造一行。通过 API 设置的标题以同样方式宣告。

对于机器上的 Session，列表通过代理监听每台已连接机器自己的事件流：那边的 Session 在**那台**机器的服务端上改变状态，其他人都不知道。机器自己的 `web_updated` 会被忽略，因为那是它的 web，不是这个窗口正在跑的。

## 智能体页面列出每台机器上的 Agent

Agent 属于 Project，但它的状态目录是在它运行过的那台机器上创建的，所以只在某台机器上跑过的 Agent 就只存在于那里。智能体页面会同时问本机与本机持有连接的每台机器，并按 agent id 归并：本机也有的 Agent 由本机描述；只存在于某一台机器上的，以那台机器命名——名字旁边是 `[SSH: prod-1]`，别名保持它自己的大小写。

这样一张卡片能做什么，取决于那台机器能回答什么。**新建对话**会以那台机器为目标打开草稿，临时工作区也建在它上面，于是对话就从 Agent 的状态所在之处开始。设置及其统计快捷入口、用量、删除读写的都是本机没有的状态目录，因此置为不可用，把原因放在悬停提示里，而不是让你点完之后收到一个 404。

## 评估中心会读遍本服务器持有的每台机器

Benchmark 属于 Project，而 Project 在它借给的每台机器上都是同一个。它的 `benchmarks/` 目录却不是：Benchmark 在哪台机器上创建或评测，就写在哪台机器上，于是同一个 Benchmark 的题目与记分板被摊在它跑过的所有磁盘上。卡片列表与 Benchmark 自己的页面会同时问本机与每台已连接的机器，并按 benchmark id 归并：一个 Benchmark 一张卡片，其下是一段完整历史。机器作为**归属信息**而非分组维度出现——当某个 Benchmark 存在于不止一处时，评测行会点名记录它的那块记分板所在的机器（`[SSH: prod-1]`）；只存在于某台机器上的 Benchmark 以那台机器命名；它评测过的 Agent 取所有记分板的并集。

记分板的追加顺序**就是**评测序列，页面信任它胜过信任时间戳——但两块磁盘上的两份记分板之间根本不存在共同的追加顺序，因此合并出来的历史按时间排序，而只来自单台机器的 Benchmark 则原样保留其文件里的顺序。Benchmark 的题目取持有它的机器的并集，题目文件从其列表来源的那台机器读取。答不上来的机器会被排除在归并之外：本机持有的内容照常渲染，只有当没有任何来源作答时才报错。创建与删除仍只作用于本机：只有本机持有的 Benchmark 才提供删除，删除的也是本机这一份。

## 终端，以及它背后的文件

终端在其工作区所在的机器上打开——包括回退到家目录的情形，那也是*那台机器上*的家目录——并且在本应用重启后仍然存在：shell 活在那台机器的服务端上，需要恢复的只是标签。恢复它的列表由所有已连接机器汇成，只有在每个来源都应答之后才修剪对话里保存的标签。打开终端时优先接管对话自己机器上已经在跑的 shell，而不是在旁边再开一个。流始终是本服务端自己的：远端 pty 在终端 id 里以 `<terminalId>@<machineId>@<userId>` 命名，由平台经持有的连接中继套接字。

## 插件，按机器运行

Project 的插件清单新增按机器的子表：列给某几台机器的插件，只在那几台运行，也只在那几台下载。插件页与设置弹窗中的插件设置各自新增机器选择器，用来逐台查看和编辑。

### 配置

- **`[plugins.<machineId>]`** 位于 `.project_config.toml` 的共享 `[plugins]` 表之下，列出某台机器在共享表之外还要运行的插件；两表同名时，以该机器的条目为准。键是机器自己的 16 位 ID（由该机器的服务端首次启动时生成），不用 ssh alias；本机同样使用自己的 ID。
- **加载**时，本机读取自己的有效清单，即共享表加上本机子表。只列给其他机器的插件，本机既不安装也不加载；移除时，一旦没有任何 Project 要求本机运行它，它的包就从本机磁盘删除。

### API

- `POST /api/projects/:projectId/plugins/installed` 接受 `machineId`，将包列入该机器的子表。本机只在自己要运行时才用 npm 安装。
- `DELETE …?specifier=…&machineId=…` 只从该机器的子表中移除；不带 `machineId` 时从所有表中移除。
- 不改变本机运行内容的改动直接写盘，不重新装配本机 App。
- `GET` 的每行带 `everywhere`、`machines`、`here`，响应带本机 `machineId`。

### 机队同步

- 发给一台机器的是共享表加上它自己的子表；到了对端，清单落为该 Project 的共享表。
- 对端缺少、且其构建不自带的包，经对端自己的 `POST` 安装，带上固定的版本。没有列给某台机器的插件从不发往那台，也就从不在那边下载。
- 安装失败的条目在连接日志中汇报，并从本次同步中略去；其余插件照常送达。

### 插件页

- **机器选择器。** 设置按钮旁新增选择器，可在「**所有机器**」「**本机**」与该 Project 连接的每台机器之间切换；只要除本机外还有机器，它就会出现。
- **「所有机器」**列出全部插件；只列给部分机器的插件，标注这些机器的名字。
- **某台机器的视角**列出那台机器要运行的插件，状态由那台机器自己报告。在此安装只对那台机器启用。共享表中的插件在这里不能移除，行上会注明原因。

### 插件设置

设置弹窗的「插件」页在 Project 连接了其他机器时显示机器选择器。选中某台机器后，读取、保存与执行动作都经 `/server/<machineId>/api/admin/plugin-config` 作用于那台机器自己的插件设置。每台服务端把设置存在自己的数据库里，机器之间不互相复制。无法应答的机器显示空页面，并注明原因。

## 范围

机器从头到尾都是管理员能力：「机器」页面、通往机器 API 的代理，因此这里的一切也是。非管理员的列表就是本服务端的 Session，与从前完全一样。
