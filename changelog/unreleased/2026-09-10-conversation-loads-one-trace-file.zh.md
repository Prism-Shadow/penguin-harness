# 对话打开只加载最新一个 Trace 文件，更早的按需载入

- **Date:** 2026-09-10
- **Type:** feature
- **Scope:** `server`, `web`, `docs`

[English](2026-09-10-conversation-loads-one-trace-file.md)

此前在 Web App 中打开一个对话会拉取 200 个 Task 的尾部窗口，而对几乎所有真实 Session 而言，这意味着一次读入并渲染全部 Trace 文件。现在改为一次只加载一个 Trace 文件：打开时只读最新一个（一个文件就是一段模型上下文，也就是模型自己仍看得见的那部分），更早的由消息流顶部的按钮逐个载入。

## 细节

- 对话页打开时只加载最新一个 Trace 文件，因此跨月的 Session 与新会话一样快。消息流顶部是「加载更早的对话」按钮，剩余不止一个文件时附上「（还有 N 段）」；每点一次恰好向前载入一个文件，并在插入过程中保持阅读位置不动。不再随滚动自动加载——一个文件可能装着整段上下文的工具输出，是否为它买单由读者决定。载到开头显示「已是对话开头」，失败则显示点击重试行。
- `GET /api/sessions/:sessionId/messages` 在既有的 `tailLimit=n` 与 `before=<文件序号>:<记录序号>&limit=n` 两种窗口形式之外新增 `unit=task|file`：`task`（缺省）沿用按 Task 边界的切分，`file` 则以整个 Trace 文件为单位——窗口从该文件自己的 `session_meta` 头开始，`before` 游标恒为 `<文件序号>:0`，`before` 不带 `limit` 时缺省为一个文件。响应的 `page` 新增 `earlierFiles`：窗口之前开始的 Trace 文件数，也就是按钮上的那个数字。
- Task 运行中途触发的压缩会切换文件，新文件从 `[context_summary]` 注入与下一次 Request 续行，没有自己的用户提问。服务端把切点处未结束 Task 的用时、API 时间与工具时间折入该窗口的 `prior`，前端归约器则在续行部分的首条记录处开启一轮，使它有自己的统计页脚。被切开的 Task 因此每个文件渲染为一轮、两轮之间隔着压缩横幅，Session 累计与整段加载完全一致。
- 长时间断连后的 resync：仅当重新拉取的最新文件起始游标未变时才保留已载入的更早文件——在压缩切换文件之前一直成立。文件已切换时只采用最新的那个文件，丢弃已载入的更早文件（点一下即可重新载入），而不是重新拉取整段历史。
- 无参数的完整读取未变，CLI（`logs`、`--resume`）与其他依赖完整历史的调用方拿到的响应照旧。
- 服务端 API 与 Web App 文档补充说明窗口形式、`page` 字段与对话页按文件加载的行为。
