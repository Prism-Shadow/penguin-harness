# AgentHub 0.4.14: a DeepSeek tool chain survives a strict Responses relay and the turns the model thought nothing on

- **Date:** 2026-09-12
- **Type:** fix
- **Scope:** `core`, `cli`
- **PR:** [#703](https://github.com/Prism-Shadow/penguin-harness/pull/703)

[中文版](2026-09-12-agenthub-0.4.14.zh.md)

`@prismshadow/agenthub` moved from 0.4.12 to 0.4.14 (agenthub [#212](https://github.com/Prism-Shadow/agenthub/pull/212) in 0.4.13, agenthub [#215](https://github.com/Prism-Shadow/agenthub/pull/215) in 0.4.14). Two DeepSeek failures end with it. A row pinned to `deepseek-v4` — the direct `deepseek-flash` preset, or a relay entry with `client_type = "deepseek-v4"` — no longer dies on the request after its first tool call with `400 {"code":"invalid_json"}` behind a strictly validating Responses endpoint: the client sends a text-only tool result as a plain string and keeps the content-part list only for a result that carries images. And a task run against DeepSeek over the `openai-chat` protocol no longer dies part-way through with `400 The reasoning_content in the thinking mode must be passed back to the API. (invalid_request_error)`: the client sends the reasoning field as an empty string on a tool-calling turn the model thought nothing on.

## Details

- 0.4.14: the `deepseek_v4` and `gpt6` clients wrapped every tool result in a one-part content list, the multimodal form; a strict DeepSeek Responses endpoint rejected it, and the engine classified the rejection as a provider 4xx, `fatal`, so the Task stopped where it stood. Both clients now take the form the generic `openai-responses` client has used since 0.4.11, so every Responses and Chat Completions client AgentHub ships sends a text-only tool result as a plain string. `deepseek_v4` keeps refusing images on the ids whose model reads none.
- 0.4.13: DeepSeek requires the chain of thought back only when it cannot recover it from a `tool_call` id it issued itself, so the rejection appears on an endpoint that reissues ids — a relay, or a custom OpenAI-compatible entry in front of DeepSeek — and not on a direct `provider = "deepseek"` row. The turns it applies to are DeepSeek's own doing: past the first few steps of a long tool chain it answers with a bare tool call and no reasoning at all. The fix lives in AgentHub's `openai_chat` client, so every row pinned to `openai-chat` and the vLLM rows that subclass it are covered.
- `pnpm-workspace.yaml`'s `minimumReleaseAgeExclude` entry names 0.4.14 in place of 0.4.12.
