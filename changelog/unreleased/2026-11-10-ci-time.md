# Shorter CI runs: a lockfile change checks only the packages it reaches, and the longest jobs build and run less

- **Date:** 2026-11-10
- **Type:** process
- **Scope:** `ci`, `server`
- **PR:** [#1526](https://github.com/Prism-Shadow/penguin-harness/pull/1526)

[中文版](2026-11-10-ci-time.zh.md)

CI's planner stopped turning ordinary pull requests into full three-platform runs, and the longest jobs were split or given less to build. Every suite still runs where it ran before.

## Planning

- A `pnpm-lock.yaml` change selects the packages whose own lockfile entry changed, or whose resolved dependencies reach an entry that changed, and their dependents (`scripts/ci-lockfile.mjs`). A plugin among them also selects the packages that read the plugins, as a change to its files does; a lockfile change still walks the npm packaging job, and packs the desktop app when the desktop's own dependencies changed. A change to the root's toolchain, the lockfile's settings or overrides, or a lockfile the planner cannot read still validates the whole workspace. Before, every lockfile change did.
- `rfcs/` is documentation and selects no package job. The planner's and the gate's own tests, which the style job runs in every run, select nothing more; `scripts/release-npm.sh` selects the npm packaging job, which walks it.
- No test shard builds the Web App's bundle or the UI package's build any more. The desktop's tests read only the desktop's own build, and the gallery's build reads the web's sources; browser-smoke and the runtime job, which packs the desktop app, still build the bundle.

## Jobs

- The server suite runs in two Linux jobs (`test (server-1)`, `test (server-2)`), dealt by the same measured weights as the Windows shards, each uploading the coverage of its half.
- The job that runs the gallery's layout checks installs Chromium while it builds, through a new `alongside` input of the shared setup action, and runs the checks against the gallery it has just built (`GALLERY_SERVE=build`, `vite preview`) rather than the dev server.
- `packages/server/test/shard-weights.json` was refreshed from eight recent runs: the suite had grown from 873 to 1349 Windows test-seconds since the table was made, and the old table left one Windows shard about a sixth heavier than the others.
