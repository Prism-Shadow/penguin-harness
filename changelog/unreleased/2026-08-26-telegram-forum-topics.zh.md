# 回复留在被提问的那个 Telegram 话题里

- **Date:** 2026-08-26
- **Type:** fix
- **Scope:** `server`
- **PR:** [#507](https://github.com/Prism-Shadow/penguin-harness/pull/507)

[English](2026-08-26-telegram-forum-topics.md)

论坛型超级群把一个会话拆成若干话题，每条消息都带着它被写在哪个话题里。此前只有一轮运行的第一条回
复留在原处——Telegram 会从被引用的消息推断回复所属话题——其余的都走出了对话、落进 **General**：本轮
后续完成的消息、长回复第一段之后的每一段、工具审批提示，以及测试消息。答案的一半到了该到的地方，
另一半出现在别处。

## 话题搭在 chat id 上

话题被打包进 `messaging_bindings.last_chat_id`，形如 `<chat id>:<话题 id>`；写在话题之外的消息仍
留裸 chat id。`MessagingInboundMessage.chatId` 本就对消息桥不透明，与 `messageId` 同理——由连接器
铸造、也由连接器在 `sendText` 中消费——因此话题抵达了每一条出站路径，而渠道中立的接口、仓储与
schema 都不必知道「论坛话题」是什么；它也随着本就存储会话的那一列一起跨过了重启。

绑定拿到的是**最近一个**话题，与它此前对会话本身的处理一致：用户换到新话题，回复就跟到新话题。

回复引用（reply ref）也获得了同样的可选分量，因为 `allow_sending_without_reply` 会在被引用消息消
失时退化为普通发送，那会把话题一并丢掉。

此前写入的行无需任何处理——见[向后兼容](2026-08-27-backward-compatibility.zh.md)。

## 只记住真正的论坛话题

Telegram 也会在普通的回复链上设置消息的 `message_thread_id`——私聊里如此，非论坛的超级群里也如此
——而 `sendMessage` 的同名参数只接受论坛型超级群，其余一律以
`Bad Request: message thread not found` 拒绝。因此只有当消息所在会话报告 `is_forum`、且该消息自身
报告 `is_topic_message` 时，才会铸造出话题。其他任何地方，引用都仍是裸 chat id 与消息 id，出站消息
也仍是它一贯的那一次请求。

## 话题被删除时退化，而不是丢失回复

Bot API 没有与回复标志对应的 `allow_sending_without_thread`，因此向一个已被删除或关闭的话题发送会
以 `400` 失败。这类发送会不带话题重试一次，于是消息落在 General。只有 `400` 会重试，且只在本次发送
带了话题时重试：限流等待会被一次毫无间隔的重发拉得更长，而传输层失败根本没有拿到 Telegram 的任何答
复，它要发的那条消息可能已经送达。不带话题的发送绝不重试，真正的失败仍会以 `messaging_send_failed`
呈现。以这种方式落进 General 的回复会被记入日志，每次退化记一条，而不是每条消息记一条。

## 一条回复，一个地方

一条回复的两半——它要去的会话，以及第一段所引用的入站消息——在第一次发送之前被一起快照下来，而不再
由其中一半在每一段时重新读取。此前，投递途中到来的、写在另一个话题里的消息，能够把这两半分开，从而
把一条回复劈到两个话题里。
