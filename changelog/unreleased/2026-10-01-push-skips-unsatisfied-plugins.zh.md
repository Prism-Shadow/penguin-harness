# 推送遇到无法满足的已装插件时先询问

- Date: 2026-10-01
- Type: fix
- Scope: server, web

热推送替换平台，但已安装的插件原样保留。此前，若某个已装插件向推送来的平台所没有的槽位贡献、或依赖它所没有的模块与接口，整棵模块树会被拒绝，推送失败，推送的人没有选择。

- **询问推送的人。** 这样的推送会以 `409` `plugins_unsatisfied` 被拒绝，逐个写明是哪个插件、它会被停用还是只少一部分、原因为何；运行中的版本保持不变。带上请求头 `x-penguin-unsatisfied-plugins: leave-out` 重发，推送照常完成，应答里列出被略过的插件。`scripts/deploy.mjs` 会打印清单，在终端里询问；非交互运行时停下并提示使用 `--force`。
- **确认之后平台怎么做。** 向构建没有声明的槽位所做的贡献被丢弃，插件其余部分照常运行；其他不匹配让整个插件退出这一代。插件仍保持安装，之后具备其所需的构建会重新运行它。无法归因到插件的拒绝仍会使推送失败。
- **没有人等待回答的启动不询问。** 冷启动、插件变更后的重新装配、推送失败后的恢复、从版本历史回滚，以及把构建交接给机器，都直接略过这些插件启动。
- **在哪里能看到。** 每个这样的插件都会写入日志，在成本中心记为一条来源为 `plugin` 的意外错误，并在插件页标出：「此构建上已停用」及原因，或仍在运行并注明哪一部分未生效。`GET /api/projects/:projectId/plugins/installed` 以 `unsatisfied: {disabled, reason}` 给出，这样的插件不再计入 `restartPending`。
- **用 AI 修复。** 管理员可以在插件所在的行把它交给 Agent：确认之后，打开一个使用临时 Workspace 的新对话，输入框里已写好修复提示词；在用户发送之前不会执行任何操作。

把这项改动送到一台服务器上的第一次推送，由改动之前的平台接收，它不会询问：这一次推送直接略过无法满足的插件启动，并按上面的方式报告。
