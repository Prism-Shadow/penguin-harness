# 在另一台机器上运行 Agent，并在一个列表里看到它的 Session

- **Date:** 2026-09-04
- **Type:** feature
- **Scope:** `server`, `web`

[English](2026-09-04-machines-run-agent.md)

选一个位于另一台机器上的工作区，对话就在那台机器上运行：由那台机器的服务端驱动 Agent、保存消息、写入 trace、提供终端。窗口不会移动——它始终留在本服务端上，只在与那台机器相关的调用里点名它。机器需要处于已连接状态，而连接是服务端的事：持有的连接不会因空闲而关闭，断了会自行重建，服务端重启或热推之后也会恢复——所以一台机器在「机器」页面连接过一次之后，每个窗口都能一直到达它。

## Session 的调用跟着拥有它的机器走

一个 Session 活在其工作区所在文件系统的那台服务端上，所以关于它的**每一个**调用都必须到达那台机器，而这样的端点有二十多个。与其给它们全部加一个机器参数，路由是一条基于路径的规则：对 `/api/sessions/<id>/…` 的请求去往 `<id>` 最后一次被看到的地方。调用点原样不动，Session 所在的机器只在两处被记录——列表交回一条时，以及创建一条时。输出流遵循同一规则。

有两类地址逃过了基于路径的规则，需要自己带上机器：Trace 端点，它把 Session 放在 Agent 级路径里；以及工作区文件的内容 URL 和消息附件的 scratchpad 图片，它们是地址而不是调用。没有这一层，位于机器上的 Session 的每一个预览、图片、PDF 和下载都会向本服务端索要一个它没有的文件。

刻意收窄：项目级的 `…/agents/:a/sessions` 列表**不是** Session 级的。它问的是某台服务端有哪些 Session，让另一台机器来回答，就是那台机器在替这一台回答关于自己的问题。

## 编辑器跟着机器走

Agent 是按服务端划分的，所以编辑器提供的是所选工作区所在机器上存在的 Agent——而不是本服务端的，那会点名一个目标机器跑不了的 Agent。询问期间先给出那台机器上次被看到在跑的 Agent；若无法到达，这份列表仍然可选，并在行里说明原因。从工作区分组新建对话时保留该分组的机器，因为不带机器的工作区路径在每台主机上指向的都是不同的目录。

## 一个列表，几台机器

侧边栏的 Session 列表是所有已连接机器的合并：每台服务端用自己的偏移量分页自己的行，所以合并从每台各取一页再排在一起，而不是共用一个游标去向一台机器要只有另一台才翻到过的行。文件夹计数按应答了的服务端求和。

无法询问的机器会被如实记录，它上次持有的内容会从缓存显示，直到它再次应答。这正是「本服务端没有那个 Session」与「可能持有它的人都没有应答」之间的区别——于是一台不可达机器上的 Session 读作不可达而非消失，正在打开的对话也不会因为它所在机器暂时不在而被丢掉。

## 列表不用刷新也保持真实

在任何地方创建的 Session——CLI、另一个标签页、定时任务、Agent 派生的子 Session——都会在用户通道上被宣告，列表去取那一行而不是凭空造一行。通过 API 设置的标题以同样方式宣告。

对于机器上的 Session，列表通过代理监听每台已连接机器自己的事件流：那边的 Session 在**那台**机器的服务端上改变状态，其他人都不知道。机器自己的 `web_updated` 会被忽略，因为那是它的 web，不是这个窗口正在跑的。

## 终端，以及它背后的文件

终端在其工作区所在的机器上打开——包括回退到家目录的情形，那也是*那台机器上*的家目录——并且在本应用重启后仍然存在：shell 活在那台机器的服务端上，需要恢复的只是标签。恢复它的列表由所有已连接机器汇成，只有在每个来源都应答之后才修剪对话里保存的标签。打开终端时优先接管对话自己机器上已经在跑的 shell，而不是在旁边再开一个。流始终是本服务端自己的：远端 pty 在终端 id 里以 `<terminalId>@<machineId>@<userId>` 命名，由平台经持有的连接中继套接字。

## 范围

机器从头到尾都是管理员能力：「机器」页面、通往机器 API 的代理，因此这里的一切也是。非管理员的列表就是本服务端的 Session，与从前完全一样。
