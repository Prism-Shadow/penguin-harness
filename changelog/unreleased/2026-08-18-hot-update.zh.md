# 热更新：经 HTTP 替换运行中 Harness 的代码，无需重启

- **Date:** 2026-08-18
- **Type:** feature
- **Scope:** `server`, `cli`, `web`, `tooling`
- **PR:** [#298](https://github.com/Prism-Shadow/penguin-harness/pull/298)

[English](2026-08-18-hot-update.md)

一个正在运行的 PenguinHarness——包括桌面应用——现在可以就地更新：一次 HTTP 推送即可把后端平台、CLI 的命令实现与 Web App 一并替换，耗时数秒，无需重启服务端、也无需重新安装任何东西。存活状态能挺过这次替换——在更新之前启动的终端进程，在更新之后仍在运行，其输出完好无损。

## 一次推送，一个版本

`POST /api/hmr/upgrade` 接受单个 gzip 载荷，其中携带三份产物——平台包、CLI 包与构建好的 web dist——并把它们作为一个原子版本施加。新的平台必须能启动、web dist 必须校验通过，然后才会提交任何东西；两者中任一失败都会让此前的版本原封不动地继续运行。重启会把最后一次提交的版本作为一个整体恢复，而受损的存储会回退到随包发布的默认值，而不是一个半成品更新。该存储保留当前版本外加一个可回滚的候选版本。

部署是一条命令：`PENGUIN_ADMIN_PASSWORD=… node scripts/deploy.mjs <port|url>` 会构建并推送全部内容，经由 ssh 隧道推送到远程机器同样有效。

## 被推送的代码拥有自己的 API

运行时不再拥有路由表。每一个请求都会先交给正在运行的平台，因此一次推送可以新增一个端点、替换一个端点，或改变某个既有端点的行为——无需重新构建，也无需发布新的服务端版本。只有 `/api/hmr/*` 这条升级通道是保留的：一个损坏的平台正是要靠它被替换掉，因此任何推送都不能把它拿走。

## CLI 随推送一同更新

`penguin` 运行的是最近一次推送到该机器上的 CLI 实现，直接取自更新存储；没有推送过任何东西时才回退到内置于二进制中的那一份——因此命令层面的修复可以与它们所对话的服务端代码在同一次推送中发布，无需重装二进制文件。`penguin-hmr` 是它的严格版本：拿不到被推送的 CLI 就报错而不回退，用来确认某次推送确实到位了。被推送的 bundle 加载失败只会打印一行警告而不是失败，而 `PENGUIN_NO_HMR=1` 会跳过查找、直接运行内置实现。

## 访问控制

这些热更新 API 要求管理员会话（与浏览器相同的登录），并且除非经 HTTPS 提供，否则仅限环回访问——这里刻意不提供落盘的令牌，也不提供不安全网络的绕过开关：一份文件凭证会被以同一用户身份运行的一切读到，包括某个 Agent 自己的 shell。
