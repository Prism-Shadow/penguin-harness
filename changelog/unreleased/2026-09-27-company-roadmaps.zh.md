# 公司路线图：一场讨论落成一份路线图，并委托出它的提案

- **Date:** 2026-09-27
- **Type:** feature
- **Scope:** `server`, `web`, `plugins`

[English](2026-09-27-company-roadmaps.md)

公司模式新增**路线图**：几名员工的一场讨论最终落成的东西——一份以论文形式写成的 body，以及由它引出的提案（各有 brief 与负责人，彼此叠成栈）和子路线图。它以一个缺省不启用的模块插件交付：`@prismshadow/penguin-plugin-company-roadmaps`（`plugins/company-roadmaps`），依赖 company-proposals（[2026-09-21-company-proposals.zh.md](2026-09-21-company-proposals.zh.md)）：委托出去的提案由负责人在那里创建。

## Details

- **讨论室是一个别人看不见的频道。** 开一份路线图就会开出它的讨论室：一个组织频道 `roadmap_<n>`，成员是开路线图的人和选中的员工（第一名主持）。它由组织网关新增的 `OrgGateway.openRoom` 建出，并标成**不列出**——`channel.toml` 里新增一个可选的 `unlisted = true`，频道列表（侧栏、`GET …/channels`、`penguin org channel ls`）会跳过它。进入它要从路线图走：路线图页把讨论室和路线图并排摆着（见下），应用自己的频道页从那里点一下就到；其余一切——读、发言、邀请与移出成员、提及、归档——都是频道本来的功能，凭 id 使用。组织运行在另一台机器上时，这里拒绝 `openRoom`（409 `org_runs_elsewhere`，与组织路由拒绝在那里写入一样）：本服务器持有的只是它的镜像，下一次从那台机器拷贝会把讨论室删掉——在这样的服务器上开出的讨论室，就是这样落成了「Channel does not exist: roadmap_1」。插件只从磁盘读讨论室的成员与消息，从不写它。通过 API 仍可以在一个已有频道上开路线图（`channelId`）；`unlisted` 出现之前写下的频道一律按列出处理。
- **员工的工位为讨论室克隆一份。** 插件经组织网关为讨论室里的每名员工开一条该员工 Agent 的会话，第一条输入就是这个讨论室：有谁、谁主持、最近 20 条消息、怎么在里面发言。之后讨论室里的每条消息都经会话运行时投进其他成员的讨论室会话（忙时排在进行中的 Task 之后），从不落到工位上。这些会话在开路线图时、应答之前就开好；由人开的讨论室里，主持人的会话被告知先发言、先对那个人说（`@user:<id>`）——都有谁、议题是什么、他想从这份路线图里得到什么——其余员工的会话被告知在这两位之一对他说话之前先不作答。开路线图时，每名员工的工位收到一行：在哪个讨论室、谁主持、哪条讨论室会话替它参加（工位上无需做事）；投递不了的记一条并作为提示返回。被邀请进来的员工在下一轮（每 `pollSeconds` 秒，缺省 5）得到一条讨论室会话；被移出的员工，他的会话会被关掉；被删掉的会话会重开一条。讨论室会话发出的消息在组织里恒为 hop 1，所以插件自己记深度：人的消息为 0，回复比它所回应的那条多 1，到达 `relayDepth`（缺省 3）的消息不再转给任何人。组织暂停时不转发。
- **被插件认领的频道不叫醒工位。** 组织运行时新增一个接缝 `OrganizationModule.channelClaims`（类型写在组织网关旁，为 `OrgGatewaySlots`）：每一轮把某个频道的提及投到工位之前，先问一遍插件贡献的认领；只要有一个认领回答 `true`，这个频道的消息照常记录、发布、可读，但其中的提及不再叫醒任何工位。认领抛错时记一条错误（`org_channel_claim_failed`），按不认领处理。company-roadmaps 只认领讨论中的路线图的讨论室（已确立或已搁置的不认领）：认领由插件里一个单独的节点做，它读账本文件作答，并立即把这条消息转进讨论室会话。
- **手册下面的入口。** 公司模式的侧栏在组织自己的页面之后多一行**路线图**（Roadmaps），排在「提案」之上，打开 `/org/<project>/<org>/roadmaps`：一个由 company-roadmaps 自己服务的页面（`GET /api/company-roadmaps/page`，以 iframe 嵌入），列出各份路线图的状态、讨论室、条目与负责人，也能看一份路线图的 record 和 body，语言跟随应用。这个页面不会是一块空白：文档送出时就写着自己是什么，发请求前先写明在请求什么，被拒时写出 HTTP 状态码和服务器的原话，15 秒没有应答时单独写一句；列表上方（无论空不空）有一个**开一份路线图**按钮，展开一份表单：名称、组织里的一到多名员工（取自组织图；先选的那位主持）。提交走 `POST …/roadmaps`，然后直接进入新开的路线图；被拒时表单留着，写出 HTTP 状态码和服务器的原话。对话框只画一次：勾选员工只挪动「主持」标记，别的都不动，所以名单保持滚动位置，对话框里没有东西被重画或重放动画。一份路线图就是**讨论室与详情并排**：左边是讨论室——消息取自频道自己的 `GET …/channels/<id>/messages`，每 4 秒再读一次，下面是一个用 `POST …/messages` 发言的输入框（Enter 发送，Shift+Enter 换行）——右边是 record、body 和条目；窄于 900 px 时上下叠放，讨论室在上。组织运行在另一台机器上时，页面像应用一样去问那台机器：先读一次 Project 的组织列表，之后每个请求都经 `/server/<machine>/…` 发出，所以那台机器上也得装这个插件（那边回一个光秃秃的 404 时页面会这么说）。为此没有新增任何接口。页面穿的是应用自己的样子：链接应用给嵌入页的样式表（`/workflow-ui.css`），从外层窗口拷贝应用已经解析好的主题值（深浅、灰阶、强调色、字体与根字号），外层一变就跟着变；版式也照应用的公司模式页面：页头右侧是主操作，列表是带边框的行、状态用药丸并带「进入讨论室」（打开那份路线图：讨论室与详情），空态居中，开路线图用对话框（Esc、点遮罩或「取消」都能关，没填全时「开」按钮不可点），整行都能点开那份路线图，读取失败时有「重试」。网页端会给「它有文案和图标的那个 key」（`roadmaps`）的 iframe 页画出侧栏一行，并按自己那张表排这些被贡献的行，而不是按贡献次序（它跟随 Project 的 `[plugins]` 清单）；页面贡献的形状没有变。
- **草案。** 主持人或人写 record、body 和条目（`PUT …/roadmaps/:n/draft`）；条目只有 brief，讨论期间不创建任何东西。人可以开一份派生自另一份的路线图（`parent`），到另一个讨论室里继续讨论；员工不能直接开路线图。
- **确立**（`POST …/:n/establish`，主持人或人）要求 body 非空、至少一个条目、每个条目的 cites 都对应 body 里的一个标题（否则 400 `cite_unknown`）。确立后路线图归档、停止转发，并立即委托全部条目：提案条目是往负责人工位上投的一行，写明 brief、叠在哪一条之上（缺省叠在前一个提案条目上，`stackedOn` 可另指），并给出用 `penguin org proposal create` 建提案、再回挂编号（`POST …/:n/items/:key/link`）的命令；回挂后，叠在它上面的负责人会收到这个编号。路线图条目变成一份派生路线图，当场开好自己的讨论室、直接进入讨论，并告诉它的主持人讨论室已经开好；只有讨论室开不出来时，它才等待讨论室，由插件请主持人开一个频道并绑定（`POST …/:n/room`）。投递失败时记一条 `notify_failed`，并作为提示返回。重开后再次确立时，只重新委托负责人或 brief 有变化的条目。
- **重开**（`POST …/:n/reopen { reason }`，负责人、讨论室里的员工或人）把路线图放回讨论中，并把理由投进每一条讨论室会话。路线图可以改名，讨论可以搁置（归档）再取回（`archive` / `unarchive`）。
- **边界。** 讨论室会话的花费不计入组织预算，这与任何经组织网关开的会话一样。频道页本身不显示草案（路线图页把两者并排显示）；频道页可以读 `GET …/roadmaps?channel=<id>`。开路线图时工位收到的那一行只是请求：工位若仍在讨论室里发言，不会被拦下。
- 账本是 `<orgDir>/roadmaps.jsonl`，只追加，首次使用时重放；`<orgDir>/roadmaps-relay.json` 记着每个讨论室的游标和转发深度。
