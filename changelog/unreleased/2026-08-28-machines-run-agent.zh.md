# 在另一台机器上跑 agent，并在一个列表里看到它的 Session

- **Date:** 2026-08-28
- **Type:** feature
- **Scope:** `web`
- **PR:** [#450](https://github.com/Prism-Shadow/penguin-harness/pull/450)

[English](2026-08-28-machines-run-agent.md)

选一个位于另一台机器上的工作区，对话就在那里运行：那台机器的服务端驱动 agent、保存消息、写 trace。窗口始终不移动——它留在本服务端，只在真正相关的调用上指明机器。

## 一个 Session 的调用跟着拥有它的机器走

Session 存在于其工作区所在文件系统的那台服务端上，因此关于它的**每一个**调用都必须抵达那台机器——而这样的端点有二十多个。与其把机器参数穿过所有端点，路由改为一条基于路径的规则：发往 `/api/sessions/<id>/…` 的请求，去往 `<id>` 最后一次被看到的地方。调用点全部不变，一个 Session 的机器只在两处被记录——列表交回它时，以及它被创建时。输出流走同一条规则。

这份映射存在内存里：它由展示这些 Session 的那个列表本身重建，而一条跨过刷新存活下来的记录，会把调用发往一台可能已经不再拥有、甚至不再持有该 Session 的机器。

刻意收窄：项目作用域的 `…/agents/:a/sessions` 列表**不是** session 作用域的。它问的是某台服务端「你有哪些 Session」，由另一台机器来回答，就成了那台机器在回答关于这一台的问题。

## 输入区跟着机器走

Agent 是按服务端存在的，因此输入区提供的是所选工作区所在机器上存在的 Agent，而不是本服务端的——后者会给出一个目标机器根本跑不了的名字。从工作区分组发起对话时保留该分组的机器，因为一个不带机器的工作区路径，在每台主机上都指向不同的目录。

## 一个列表，多台机器

侧栏的 Session 列表是所有机器的合并结果：每台服务端用自己的 offset 分自己的页，所以合并是从每台各取一页再一起排序，而不是共用一个游标——那会向一台机器索要只有另一台才走到的行。

问不到的机器会被单独记下。这正是「本服务端没有这个 Session」与「可能持有它的没有一个回答」之间的区别——于是一台宕机机器上的 Session 读作「够不着」而不是「没了」，而一台时断时续的机器也不会把列表清空。

## 可达性

机器是一项自上而下的管理员能力：Machines 页面、通往机器 API 的代理，因而也包括这里的一切。非管理员看到的列表就是本服务端的 Session，与从前完全一致。
