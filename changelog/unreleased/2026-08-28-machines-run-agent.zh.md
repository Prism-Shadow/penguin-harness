# 在另一台机器上跑 agent，并在一个列表里看到它的 Session

- **Date:** 2026-08-28
- **Type:** feature
- **Scope:** `server`, `web`
- **PR:** [#450](https://github.com/Prism-Shadow/penguin-harness/pull/450)

[English](2026-08-28-machines-run-agent.md)

选一个位于另一台机器上的工作区，对话就在那里运行：那台机器的服务端驱动 agent、保存消息、写 trace。窗口始终不移动——它留在本服务端，只在真正相关的调用上指明机器。

## 一个 Session 的调用跟着拥有它的机器走

Session 存在于其工作区所在文件系统的那台服务端上，因此关于它的**每一个**调用都必须抵达那台机器——而这样的端点有二十多个。与其把机器参数穿过所有端点，路由改为一条基于路径的规则：发往 `/api/sessions/<id>/…` 的请求，去往 `<id>` 最后一次被看到的地方。调用点全部不变，一个 Session 的机器只在两处被记录——列表交回它时，以及它被创建时。输出流走同一条规则。

这份映射存在内存里：它由展示这些 Session 的那个列表本身重建，而一条跨过刷新存活下来的记录，会把调用发往一台可能已经不再拥有、甚至不再持有该 Session 的机器。

刻意收窄：项目作用域的 `…/agents/:a/sessions` 列表**不是** session 作用域的。它问的是某台服务端「你有哪些 Session」，由另一台机器来回答，就成了那台机器在回答关于这一台的问题。

## 输入区跟着机器走

Agent 是按服务端存在的，因此输入区提供的是所选工作区所在机器上存在的 Agent，而不是本服务端的——后者会给出一个目标机器根本跑不了的名字。从工作区分组发起对话时保留该分组的机器，因为一个不带机器的工作区路径，在每台主机上都指向不同的目录。

## 一个列表，多台机器

侧栏的 Session 列表是所有机器的合并结果：每台服务端用自己的 offset 分自己的页，所以合并是从每台各取一页再一起排序，而不是共用一个游标——那会向一台机器索要只有另一台才走到的行。

问不到的机器会被单独记下。这正是「本服务端没有这个 Session」与「可能持有它的没有一个回答」之间的区别——于是一台宕机机器上的 Session 读作「够不着」而不是「没了」，而一台时断时续的机器也不会把列表清空。

## 首次需要时自动连接，连接后自动更新

选中一台已安装机器上的工作区，页面会自行连上那台机器：输入区向它索要 Agent 列表，而一台没有活动转发的机器会被拉起，而不是被报告为不可用。尝试按翻倍的节奏重试——2 秒、4 秒、……64 秒——之后放弃，每次页面加载对每台机器只尝试一轮；输入区会说明当下处于三种状态中的哪一种（连接中、可访问、够不着），此后由人在 Machines 页面接手。一台机器一连上，Session 列表就重新询问哪些机器能应答，因此它的 Session 无需刷新即可进入列表。

连接时还会把本服务端的构建交给携带不同版本的机器——通过刚拉起的转发，在同步模型配置之前。只有热通道是自动的：一次热替换只需数秒，不会停掉任何东西。机器不肯接收的交接会作为连接任务的失败报告出来，并把重装作为下一步提供；转发保持打开，因为无论如何机器已经连上了。那一步仍由人来做，因为它会重启一台别人可能正在使用的服务端。

## 终端，以及它背后的文件

终端在其 Workspace 所在的机器上打开，并能活过本应用的重启：shell 活在那台机器的 server 上，被恢复的是标签。恢复它的列表由每台可达机器汇总而成，且只有在**每个来源都应答之后**才修剪会话存下来的标签——刚打开的页面只够到本 server,对别处活着的 shell 一无所知。开终端时会先认领该对话自己机器上已在运行的 shell,而不是在旁边再起一个。

Workspace 文件的地址同样跟随 Session。内容 URL 与消息附件的 scratchpad URL 是地址而非调用，上面那条路由规则从不经过它们，于是每一次预览、图片、PDF 与下载都在向本 server 要另一台机器上的文件。它们现在自己携带机器信息。(仍有一处缺口：隔离 HTML 预览的"新标签页打开"是跳转到预览源，而代理有意丢弃 `Location`;应用内的预览不受影响。)

## 列表无需刷新即为真

在任何地方创建的 Session——CLI、另一个标签页、定时任务、agent 派生的子 Session——都会在用户频道上被通告，列表随即去取那一行，而不是凭空造出它。通过 API 设置的标题以同样方式通告。

对机器上的 Session,列表通过代理监听每台可达机器自己的事件流：那里的 Session 在**那台**机器的 server 上变化状态，别处无从得知。事件流跟随可达集合——机器掉线即关闭、上线即打开——而机器自己的 `web_updated` 被忽略，因为那是它的 web,不是这个窗口的。

## 连接是被确认的，不是被假定的

只有机器本身应答过，一次尝试才算连接成功，而不是机器列表报了一条 forward:forward 是本侧的 ssh 子进程，能活过对侧的 server,所以信它就会对着一台死机器宣告成功——而由于成功有意不被记住，下一次需要又发起新的尝试，永无止境。永不应答的机器现在会走 connect 任务(那正是启动已停 server 的东西),然后走完递增的重试计划，落到被记住的放弃。

## 可达性

机器是一项自上而下的管理员能力：Machines 页面、通往机器 API 的代理，因而也包括这里的一切。非管理员看到的列表就是本服务端的 Session，与从前完全一致。
