# The Web App's page carries a Content-Security-Policy for fonts, stylesheets, plugins and `<base>`

- **Date:** 2026-11-10
- **Type:** feature
- **Scope:** `server`, `web`
- **PR:** [#1532](https://github.com/Prism-Shadow/penguin-harness/pull/1532)

[中文版](2026-11-10-page-csp.zh.md)

The server now sends `Content-Security-Policy: font-src 'self' data:; style-src 'self' 'unsafe-inline'; object-src 'none'; base-uri 'self'` with the Web App's page: `index.html`, every SPA-fallback answer, and the 304 that revalidates either. Fonts load only from the server's own origin or `data:` URIs, and stylesheets only from the server's own origin or inline. The page loads no plugin content, and a `<base>` element cannot point its relative URLs at another host. This is defence in depth for imported theme packs and for any injected stylesheet; the theme-pack validator stays the gate. `img-src` is not restricted, because the chat shows remote images. There is no script policy yet: no `script-src`, no `default-src`.

## Scope

- The desktop app loads the server's own address, so its window gets the same policy.
- The development server (`pnpm dev`) sends the same header, so a violation shows up during development.
- Scripts, stylesheets, fonts and API answers are served without the header, as before.
- Workbench pages, plugin pages and Workspace previews are separate documents with their own responses, so the policy does not reach them. A Workbench page can still load stylesheets and fonts from anywhere.
- A frame with no response of its own takes the page's policy, as browsers require. One such frame is the Files panel's `srcdoc` view of an HTML file, used for a Workspace directory and when the server has no separate preview origin. A stylesheet or font from another host in that view is now blocked.
