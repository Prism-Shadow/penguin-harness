[终端在移动网络下不再假死](2026-09-07-terminal-on-a-slow-link.zh.md) 给终端流新增了两个 opcode——`Ping`（0x07）与 `Pong`（0x08）——而这条流的两端都可能比本次发布更旧。磁盘上的东西不受影响：没有 schema、没有配置、没有已存 Trace。受影响的是**此刻正开着的 socket**。

## 两端都可能不认识这个 opcode

热更新会替换平台与 Web App，**但不会重新加载已经打开的标签页**。所以更新后的几分钟里，最常见的情形就是「更新前的页面」对着「更新后的服务端」。反向也存在：本 Web App 会接入机器上的终端（`<terminalId>@<machineId>@<userId>`），而那些机器跑的是各自最后一次安装的版本。

未知 opcode 本身在两个方向上都无害——各端忽略自己解不出来的帧，这正是这套线格式的设计意图。真正的风险是各端**从沉默里得出的结论**：

- 服务端会发现旧页面从不应答探测，判定 socket 已死并关闭它。而旧页面也没有重连，于是面板每 75 秒死一次。
- 本页面会发现旧服务端从不应答，而空闲终端本来就不会有输出，于是大约每分钟重新接入一次，每次都用快照重绘整屏。

采用的方案：**两端共用一条规则，不做版本协商**——只有**应答过**探测的对端，才会因沉默被判定。从未发过 `Pong` 的对端就是发不出 `Pong` 的对端，它的安静说明不了任何事。旧对端的其余行为一概不变：接入、重绘、改尺寸、输入与退出仍是原来的那些帧。

用户不需要做任何操作。旧页面在下次刷新时自然获得新行为，旧机器在其服务端更新后获得。

## 何时移除

这条规则的代价是每条 socket 上的一个布尔量（`server/src/terminal/stream.ts` 与 `web/src/features/terminal/terminal-connection.ts` 中的 `answersProbes`）。当不再预期有早于本次发布的页面或机器接入时即可移除——实践上是本版本发布后的下一个版本，由下一个改动心跳的人清理。在那之前，它同时也是「非浏览器客户端（测试、CLI 接入）不会因为安静而被回收」的依据，删除前值得先读一遍。
