# Install a server on another machine, from the Machines page

- **Date:** 2026-08-24
- **Type:** feature
- **Scope:** `server`, `web`, `desktop`, `cli`, `tooling`, `docs`
- **PR:** [#447](https://github.com/Prism-Shadow/penguin-harness/pull/447)

[中文版](2026-08-24-machines.zh.md)

**Machines**, a new page under Models, lists the hosts in the server's own `~/.ssh/config` and installs this build of PenguinHarness on the one you pick. It replaces the desktop app's **Install Server on Remote Host** menu entry, which shipped only inside the Electron shell.

## Picking a host

Targets come from `~/.ssh/config` and nowhere else — the config text, read once, with no `ssh -G` and no network. `Host *` patterns are skipped and `Include` globs expand the way OpenSSH expands them; the file is never written. An alias is resolved to a user, hostname and port only when it is installed to, and that resolution is `ssh -G`'s job, so `Match` and wildcard inheritance behave exactly as ssh says.

Because a config routinely declares hundreds of entries, the hosts are a searchable picker rather than a list. The query matches as a **subsequence** (`gpu1` finds `gpu-01`), the matched characters are highlighted, and a counter names how many the view leaves out.

Admin only: the install spawns ssh with the **server account's** keys and writes a program directory on another machine. Connections run `BatchMode=yes` — nothing here has a terminal for a password prompt — and OpenSSH's own diagnostic is shown verbatim when a key does not work.

## What gets installed

The release this server stands on, installed by the ordinary installer: the remote runs `install.sh` / `install.ps1` online, pinned to this server's own base version, and downloads the standard artifact — launchers, libs, web assets, bundled runtime — from the release sources over its own network (GitHub, or the OSS mirror the installer speed-picks). The ssh channel carries only the installer script.

When this server itself runs a hot-pushed version, that state travels too: `hmr/harness.json` and the store are streamed across (local tar → ssh), and the remote's next boot runs the same pushed platform, web and CLI. The Machines page then shows the combined version, `<base>+hmr.<sha>`.

A matching base skips the download; matching base and pushed state does nothing. The remote is left with what an ordinary install plus a push leaves — the program directory, on POSIX the `~/.local/bin/penguin` symlink, and the data root's `hmr/` state. No sudo, no systemd unit, no profile edits, and the rest of the data root is never touched.

## Which machine is which

Every machine has an id of its own: a UUID at `<data root>/machine-id`, minted by the server that runs there — this one included — and stable ever after. It is what anything stored points at. An ssh alias cannot do that job: an alias is a line in one machine's config file, so the same host is `build-box` here and `bb` there, and two aliases for one host are two names for one machine. Aliases stay what you READ; the UUID is the identity behind them.

It rides the same round trip the status probe already makes, so learning it costs nothing extra, and it is remembered beside the install record so it survives a restart without asking again. A machine whose server has never started has no id yet — nothing has minted one — and says so rather than being given a made-up one. An alias repointed at a different host answers a different id, and the newer answer wins: an id never changes for a machine, so a change of id is a change of machine.

## This machine, and whether the others are up

The list opens with **This machine** — the host the server is running on, named by its hostname, with the version it runs and the port it is serving on. It is read directly rather than probed (both facts are right here), it is always present, and it is never an install target: a server does not push this build over its own program directory while running from it, so it is absent from the picker and `POST …/install` on it answers `409 self_install`.

Every installed machine then carries its server's state: **Running** with the port, **Not running** (the program is there, nothing is serving), or **Unreachable** with OpenSSH's own diagnostic behind it. There is deliberately no separate "ssh" status — ssh is the transport, so a machine it cannot reach reads as one thing rather than two a reader has to combine.

Status costs an ssh round trip per machine, so it is never taken at list time and never for the whole ssh config — only for the machines something was actually installed on, five at a time. The page re-probes on a widening schedule: 15s, 30s, 45s, a minute, two, three… up to ten, and back to 15s the moment any answer actually changes. The schedule lives in the page, not the server, so nothing spawns ssh once the last tab is closed; a **Refresh** control covers the case where you already know something moved.

## Watching it, and what stays

An install takes minutes in the bad case, so it is a job: the page starts it and polls, showing the far side's own words. One runs at a time, and the panel follows the job rather than the current selection. The job lives in server memory; re-running is the recovery, since every step is idempotent and the installer stages, smoke-tests and swaps, restoring the previous installation if anything fails after the swap begins.

Which hosts carry this program is recorded in `<data root>/machines-installs.json` and listed under **Installed machines** with the version and time. It is what this server did, not a survey: a machine wiped by hand reads as installed until the next install corrects the record.

## Details

- New API, admin only: `GET /api/machines` and `POST /api/machines/:machineId/install`.
- The capability moved from `packages/desktop/src/remote/` to `packages/server/src/machines/`, which is what makes it reachable from a browser, available to a tarball install, and shippable by hot push.
- The far side runs the ordinary installers online — no payload is assembled or transferred, and staging, smoke test, swap, rollback and the PATH plumbing are the one implementation every release install runs. The trade: the remote must be able to reach GitHub or the OSS mirror for its first install and for base upgrades.
- One payload layout, spelled once. `bin/penguin` and `bin/penguin.cmd` were written in four places — as shell heredocs in the release workflow and as strings inside three JavaScript modules — and the copies had drifted about where `web/` and the bundled runtime sat. They are now two ordinary files under `scripts/launchers/`, copied verbatim into each release package: readable, diffable, and runnable on their own.
- The desktop app no longer stages a ~190 MB install image into its resources. Nothing read it: the app forks the server as one bundled file, so the lookup that was supposed to find that image never matched a packaged app at all — which also means the Machines page never worked there. A packaged app now names its release from its own manifest, and carries the ~4 KB installer scripts instead of an image: the far side downloads the release itself.
- `install.ps1`'s fallback launcher — written only when a payload arrives without one — named a CLI entry (`lib\dist\index.js`) that has never existed.
