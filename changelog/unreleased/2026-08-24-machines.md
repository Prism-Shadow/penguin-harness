# Install a server on another machine, from the Machines page

- **Date:** 2026-08-24
- **Type:** feature
- **Scope:** `server`, `web`, `desktop`, `cli`, `tooling`, `docs`
- **PR:** [#447](https://github.com/Prism-Shadow/penguin-harness/pull/447)
- **Breaking:** yes — the program tree moves out of `~/.penguin` (migrated automatically)

[中文版](2026-08-24-machines.zh.md)

**Machines**, a new page under Models, lists the hosts in the server's own `~/.ssh/config` and installs this build of PenguinHarness on the one you pick. It replaces the desktop app's **Install Server on Remote Host** menu entry, which shipped only inside the Electron shell.

## Picking a host

Targets come from `~/.ssh/config` and nowhere else — the config text, read once, with no `ssh -G` and no network. `Host *` patterns are skipped and `Include` globs expand the way OpenSSH expands them; the file is never written. An alias is resolved to a user, hostname and port only when it is installed to, and that resolution is `ssh -G`'s job, so `Match` and wildcard inheritance behave exactly as ssh says.

Because a config routinely declares hundreds of entries, the hosts are a searchable picker rather than a list. The query matches as a **subsequence** (`gpu1` finds `gpu-01`), the matched characters are highlighted, and a counter names how many the view leaves out.

Admin only: the install spawns ssh with the **server account's** keys and writes a program directory on another machine. Connections run `BatchMode=yes` — nothing here has a terminal for a password prompt — and OpenSSH's own diagnostic is shown verbatim when a key does not work.

## What gets installed

What this server runs, found rather than configured: the hot-pushed version in the hmr store, a tarball install's program directory, or the desktop app's staged payload, probed in that order. The far side receives the bytes this side is running.

The machine is asked what it is first. Its own Node is reused from 22 up — the common case, costing no download — with `--experimental-sqlite` baked into the launchers below 24, where `node:sqlite` lives behind that flag. Otherwise the official build for that platform and arch is fetched from nodejs.org and verified against the release's `SHASUMS256.txt` before anything is sent, then installed as `lib/runtime`.

Nothing installed installs; a different version replaces; the same version does nothing. The remote is left with what an ordinary install leaves — the program directory, the runtime inside it, and on POSIX the `~/.local/bin/penguin` symlink. No sudo, no systemd unit, no profile edits, and the data directory is never touched.

## Watching it, and what stays

An install takes minutes in the bad case, so it is a job: the page starts it and polls, showing the far side's own words. One runs at a time, and the panel follows the job rather than the current selection. The job lives in server memory; re-running is the recovery, since every step is idempotent and the remote installer stages, smoke-tests and swaps, restoring the previous installation if anything fails after the swap begins.

Which hosts carry this program is recorded in `<data root>/machines-installs.json` and listed under **Installed machines** with the version and time. It is what this server did, not a survey: a machine wiped by hand reads as installed until the next install corrects the record.

## Details

- New API, admin only: `GET /api/machines` and `POST /api/machines/:machineId/install`.
- The capability moved from `packages/desktop/src/remote/` to `packages/server/src/machines/`, which is what makes it reachable from a browser, available to a tarball install, and shippable by hot push.
- `pnpm --filter @prismshadow/penguin-desktop build:install-image` writes the portable image the push sends: the CLI package deployed at `lib/`, web assets at `web/`, launchers that run on plain Node, and no Electron.
- One payload layout, spelled once. `bin/penguin` and `bin/penguin.cmd` are generated from `packages/server/src/machines/launcher.cjs` for all three trees that have them — the release packages, the install image and a pushed install — which previously carried a copy each. The copies had drifted: two of them looked for the web assets and the bundled runtime in places the third did not put them, so a server installed from a release tarball pushed its own machine's Node to the remote and left that remote pointing at a web directory that was not there. Both are fixed by the trees agreeing: `lib/dist/penguin.js`, `web/`, and an optional `node/`.
- `install.ps1`'s fallback launcher — written only when a payload arrives without one — named a CLI entry (`lib\dist\index.js`) that has never existed.

## Compatibility

Installs put the program tree in the platform data directory (`~/.local/share/penguin`, or `%LOCALAPPDATA%\penguin`) instead of `~/.penguin`. **Data does not move**: the data root stays `~/.penguin/data`, which is what `PENGUIN_HOME` defaults to.

Re-running the installer — or `penguin update`, which runs it — migrates an existing install: the new tree is installed and smoke-tested first, and only then are the legacy program directories (`bin`, `lib`, `web`, `node`, and `git` on Windows) removed from `~/.penguin`. `data/` is never touched, `~/.penguin` is removed only if nothing else is left in it, and a failure to clear the old copy is a warning rather than a failed install.

`PENGUIN_INSTALL_DIR` (or `-InstallDir`) opts out entirely. For the same reason `penguin update` no longer passes the old default back to the installer, which would have frozen every existing install on the old layout.
