# Install a server on another machine, from the Machines page

- **Date:** 2026-08-24
- **Type:** feature
- **Scope:** `server`, `web`, `desktop`, `docs`

[中文版](2026-08-24-machines.zh.md)

**Machines**, a new page under Models in the sidebar, lists the hosts declared in the server's own `~/.ssh/config` and installs this build of PenguinHarness on the one you pick. It replaces the desktop app's **Install Server on Remote Host** menu entry, which could only ship by redistributing the app and existed only in the Electron shell.

## The list

Targets come from `~/.ssh/config` and nowhere else. The list is the config text and nothing more — aliases only, no `ssh -G`, no processes, no network — so a config declaring hundreds of hosts costs one file read. Pattern entries like `Host *` are skipped, since they configure other hosts rather than naming one, and `Include` globs are expanded the way OpenSSH expands them. The file is never written. An alias is resolved to a user, hostname and port only when it is actually installed to, and that resolution is `ssh -G`'s job, so `Match`, `Include` and wildcard inheritance behave exactly as ssh says they do.

Admin only, on a personal server as much as a multi-user one: the install spawns ssh with the **server account's** keys and writes a program directory on another machine. For anyone else the page's sidebar row is not rendered at all.

## Picking one

The hosts are a picker, not a rendered list, because an ssh config routinely declares hundreds of entries. The panel shows the first few with a search box above them, and a counter names how many the current view leaves out — a silent truncation would read as "that host is not in my config". The query is a **subsequence** match rather than a substring one, since aliases are punctuated and the letters you remember are rarely the separators you do not: `gpu1` finds `gpu-01`. Matches rank contiguous runs above word-start hits above scattered ones, with the config's own order as the tiebreak, and the characters the query actually hit are highlighted in each row — with subsequence matching, an unmarked row looks like a wrong result.

## What gets installed

What this server runs, found rather than configured. Three shapes are probed in order: the hot-pushed version in the hmr store (assembled from the pushed CLI bundle, the web artifact and the skill library, stamped `0.0.0-hmr.<cli>.<web>`), a tarball install's own program directory, and the desktop app's staged payload. "The two ends match" therefore holds by construction — the far side receives the bytes this side is running — and each new hot push gives the remote a new version to be brought up to. Only a development checkout that has never been pushed to has no image; the page says so up front instead of letting every install fail at the same step.

The machine is asked what it is before anything is sent. Its own `node -v` is reused from Node 22 up — so the common case costs no download, no ~30 MB transfer and no second runtime on a machine that already has one — with `--experimental-sqlite` baked into the launchers below Node 24, where the server's `node:sqlite` lives behind that flag. Otherwise the official build for that platform and arch is fetched from nodejs.org, verified against the release's own `SHASUMS256.txt`, and installed as `lib/runtime`; an unverified download never leaves this machine, and runtimes are cached per shape so the second host of a kind costs nothing either.

The decision is: nothing installed → install; a different version → replace it; the same version → nothing to do. What the remote is left with is what an ordinary install leaves — the program directory (`~/.local/share/penguin`, `%LOCALAPPDATA%\penguin`) with the runtime inside it and, on POSIX, the `~/.local/bin/penguin` symlink. No sudo, no systemd unit, no profile edits, and the data directory is never touched.

## What stays installed

Which hosts already carry this program is remembered on the server, in `<data root>/machines-installs.json`. The page lists them under **Installed machines**, most recently installed first, each with the version it got and when — a standing answer to "what have I already done", which a picker that has to be opened one row at a time cannot give; the picker marks them too, with the version, for while you are choosing. Clicking a listed machine selects it, so a reinstall is one more click. It has to be written down rather than derived from the running job: the job is one slot, so an installed machine would stop looking installed the moment anything else was installed, and would be forgotten entirely on the next restart or hot push. A machine that already carries the program offers **Reinstall** instead of Install.

The record is what this server did, not a survey of the far side. A machine wiped by hand still reads as installed until the next install probes it and corrects the record — asking the remote instead would cost an ssh round trip per host at page load, which is the price the config-text list exists to avoid. A failed install records nothing, and a damaged file reads as "nothing remembered" rather than breaking the list.

## Watching it happen

An install takes minutes in the bad case, so it is a job: the page starts it and then polls, and the progress lines it shows are the far side's own words wherever there are any — ssh's diagnostics and the remote installer's output say more about a refused key or an unusable Node than a reworded version would. One install runs at a time; while one does, the button refuses. The job panel follows the JOB and names the host it belongs to, not the current selection — picking a second host mid-install must not hide the install that is running. The job lives in the server's memory and does not survive a hot push or a restart, and re-running is the recovery: every step is idempotent, and the installer on the far side stages, smoke-tests and swaps, restoring the previous installation if anything fails after the swap began.

## Authentication

Connections run with `BatchMode=yes`: nothing here has a terminal, so an ssh that decided to ask for a password would hang with nothing to type into. Key or agent authentication must already work for the host; when it does not, OpenSSH's own diagnostic is shown verbatim.

## Details

- New API, admin only: `GET /api/machines` and `POST /api/machines/:machineId/install` (see the [server API reference](../../packages/docs/content/server-api.en.md)).
- The capability moved from `packages/desktop/src/remote/` to `packages/server/src/machines/`, which is what makes it reachable from a browser, available to a tarball install, and shippable by hot push. The desktop app still stages the install image into its resources, since a packaged app is one of the three image shapes.
- The installer that runs on the far side is now embedded in the server bundle as text rather than read from a file, because a hot-pushed bundle lives in the hmr store where no sibling file resolves.
