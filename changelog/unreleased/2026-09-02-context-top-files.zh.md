# 上下文圆环改按压缩阈值计量，阈值成为可拖动的切刀，面板在工具排行旁加上文件排行

- **Date:** 2026-09-02
- **Type:** feature
- **Scope:** `web`, `server`, `core`
- **PR:** [#584](https://github.com/Prism-Shadow/penguin-harness/pull/584)

[English](2026-09-02-context-top-files.md)

输入区的上下文圆环改以「压缩触发的那个点」为标尺，不再以模型的上下文窗口为标尺——大窗口模型上一段
已经压缩过半的上下文，此前会被画成几乎空的圆环。面板条形仍以模型窗口为标尺，并用一道虚线切刀标出
那个触发点——切刀同时也是移动它的控件：拖动切刀、确认数值，这个 Agent 的压缩阈值立刻改变，正在看的
这段对话也立刻生效。这份「立刻」来自内核的改动：压缩配置离开严格层，改为在每个压缩检查点重读。构成
面板另多了第二份 Top 5：`read_file` / `edit_file` / `write_file` 的流量在当前上下文里占得最多的文件，
与原有的工具排行并列。列表上方的「工具 / 文件」开关切换视图，面板在本页签会话内记住上次的选择。

## 圆环以压缩阈值为标尺

- 圆环、面板表头的比值与面板条形统一用一个标尺：压缩阈值的**生效值**——`min(Agent 的
  compaction.max_context_length, 模型 context_window − 压缩余量)`，与 Agent 实际压缩所用的推导
  同一份；Agent 未配置阈值时按缺省阈值、模型条目未声明窗口时按假定的 128000 推导。1M 窗口模型上
  128k 阈值、64k 占用现在显示 50%，此前显示 6%。>80% 转琥珀、>95% 转红同样按该标尺计。
- 窗口并未从视野中消失：窗口大于阈值时，面板表头在比值下方淡显窗口值。
- 面板**条形**仍以模型窗口为标尺，因为两者回答的是不同的问题：圆环答「离压缩还有多远」，条形答
  「这个模型还有多少地方、触发点落在其中何处」。面板打开期间优先采用服务端回报的
  `compactionThreshold`——两者是同一套算术，只是服务端那份刚从磁盘读出——因此改过 Agent 配置后
  无需刷新页面。
- 两处回退保证圆环不编造数字：压缩关闭（`<= 0`），以及没有 Session 级 Agent 配置可依据的子智能体
  输入区，二者仍以模型窗口为标尺。
- 对话页在切换 Agent 与页签重新获得焦点时重新读取 Agent 配置，因此在设置页调低阈值后返回即可看到。

## 模型窗口装不下 Agent 阈值时给出提示

- 所选模型的 `context_window` 小于 Agent **配置的** `compaction.max_context_length` 时，输入区上方
  给出一条可关闭的琥珀色提示——这正是压缩会在窗口边缘悄悄触发、而不是在用户设定的那个数触发的情形。
  提示点名两个数值，说明压缩因此会在窗口边缘触发，并指出把阈值调到窗口以下的两条路径——面板里的
  切刀，或 Agent 设置——两者都立即生效；提示另附直达该 Agent 设置页的入口。
- 判据取配置值而非生效值——生效值已被窗口钳住，用它永远不会成立。提示随所选模型的切换与 Agent 配置
  的重新读取复算；关闭按 Session + 模型记住，仅在本页签会话内有效。

## 新增模型的上下文窗口缺省为 1000000

- Web 的模型弹窗在自定义 / 自建分组模型留空上下文窗口时按 1000000 写入（此前为 128000），字段提示
  同步改写。手动新增的是已知模型，而今天手动新增的多是大窗口模型：猜小会白白损失容量，猜大只需
  用户改一次。
- 核心对**根本没有** `context_window` 的条目的假定仍是 128000——那是「窗口未知」的安全缺省，与本项
  是两个问题的两个数。`penguin config model add` 省略 `--context-window` 时仍不写入任何缺省值。

## 压缩阈值成为可拖动的切刀

- 面板条形上的虚线切刀落在压缩阈值的生效值上，悬停即报出该值。拖动它提出一个新阈值：按最近的
  1,000 token 取整、在条形自身的两端之间钳住，拖动期间在旁浮出待定值。
- 切刀是 `role="slider"`，也接受键盘：`←` / `→` 每次 1,000，配合 `Shift` 每次 10,000，`Enter`
  确认、`Esc` 放弃本次调节。
- 松手（或 `Enter`）弹出确认卡片：点名 Agent 与被替换的阈值，并带一个**以待定值预填、仍可编辑的
  数字输入框**——这样粗的手势不该独自写入一项配置。输入框接受任意大于 0 的整数；填入超过模型窗口
  的值是允许的，此时提示行报出实际会生效的那个阈值。取消或 `Esc` 则切刀弹回。
- 确认后经 Agent 设置页所用的同一接口写入 `compaction.max_context_length`（只发送压缩这一项改动），
  随后重读对话页持有的 Agent 配置——圆环、切刀与窗口过小提示一并更新——并以 toast 告知已生效。
- 只要压缩是开着的就画切刀。模型窗口够不到的阈值把切刀钉在条形右端，而不是让它消失：切刀正是调低
  这类阈值的手段，阈值不合适的时候它最不该是消失的那一个。

## 压缩配置立即生效，包括进行中的对话

- `compaction.max_context_length`、`max_session_turns`、`mode`、`prompt` 离开严格层。引擎在每个
  压缩检查点——每次请求回报 token 用量之后，以及手动 `/compact`——从该 Agent 的 `system_config.yaml`
  重读该节，因此保存到 Agent 的修改被已在运行的 Session 采纳，不必等一次压缩轮换上下文。压缩配置
  本就不属于请求前缀：它决定的是上下文何时结束，不是上下文长什么样。
- 为此 `ContextEngineDeps` 新增可选的 `readCompaction` 提供者。它只刷新既有基线、从不凭空造出一个，
  因此「压缩是否配置过」仍是 Session 的常量；只提供 `compaction` 的 SDK 宿主保持原有的「每上下文
  固定」行为，轮换时 `openNextContext` 的 `compaction` 依旧替换基线。读盘抛错时沿用已在生效的设置
  并只警告一次——一份一时读不出来的配置文件不该终结一次运行。
- `Agent` 为每个 Session 提供该读取器：只取 `compaction` 一节，并按配置文件在磁盘上的身份缓存，
  文件未变时每个检查点只花一次 `stat`。文件里的其余部分仍属严格层，仍归属于当初据以装配的那个上下文。
- Agent 设置页的保存反馈随之区分：**只**改动了压缩字段的保存改口为「立即生效（包括进行中的对话）」，
  其余运行参数保持原有措辞。

## 面板在工具排行旁加上文件排行

- `GET /api/sessions/:sessionId/context` 新增 `topFiles`：至多五条 `{ path, tokens, ops: { read, edit, write } }`，
  按每个文件的文件工具调用与其结果所占上下文排序——与 `topTools` 用同一套字符启发式、同一套调用与结果
  的配对，因此两份排行是同一份估算的占比。调用按其 `file_path` 解析到的文件归并，解析方式与文件工具
  对 Workspace 的解析一致，所以 `a.ts`、`./a.ts` 与绝对路径写法是同一行。`file_path` 缺失或无效的调用
  不进文件排行（工具本身也会拒绝这样的调用），但仍计入工具流量。
- Session 的 Workspace 内的文件按相对路径显示；其余文件为绝对路径，home 目录缩写为 `~`。
- 文件视图每行加粗显示文件名、淡显目录、悬停给出完整路径，其后是读取、编辑、写入各自的次数，字形沿用
  文件摘要卡与记忆更新卡已有的文件、铅笔与加号页；token 与占比两列与工具视图同为占整个上下文的份额。
  工具没有碰过任何文件的上下文显示「本轮上下文没有文件读写」。
- 六个分项、`contextClosed` 与 `compactionThreshold` 不变。

## 核心

- `DEFAULT_MAX_CONTEXT_LENGTH` 从 `state/default-config.ts` 移到 `llm/context-limits.ts`，与钳制它
  的那段推导放在一起；core 另新增 `@prismshadow/penguin-core/context-limits` 子路径导出。阈值规则的
  两半由此经同一个不依赖 Node 的模块进入浏览器打包，Web 端用 core 的算术推导圆环标尺，而不是另抄
  一份。该常量仍从包根导出，既有导入方无需改动。
