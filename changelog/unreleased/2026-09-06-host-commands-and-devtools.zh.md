# 宿主命令移到热接缝之下、自带文案，并新增 DevTools 入口

- **Date:** 2026-09-06
- **Type:** feature
- **Scope:** `desktop`, `server`, `web`

[English](2026-09-06-host-commands-and-devtools.md)

## 命令离开 runtime

`/api/command` 原先挂在平台 HTTP 接缝**之上**，这让它成了 runtime 代码：它的形状只能靠重建并重新分发每一个安装来改变。而这正是 runtime 层不该承担的——runtime 只装机制，「宿主命令是什么、叫什么、谁能运行」是策略。

现在它由平台提供，因此和其他业务 API 一样靠推送发布。留在 runtime 的是消息端口本身：宿主发来的最后一帧以 `platform.shellFrames` 发布出来，原样不解析，由平台解释。这一帧必须由 runtime 发布而不能由平台自己保存，因为宿主每次接线只宣告一次——平台把它存在自己内存里，下一次推送就会丢失，而且不会再被告知。

另一条兼容路径同样在可推送的那一半：比该状态袋更旧的 runtime 改从它自己的 service 读。runtime 不保留自己的路由副本——一个旧到不肯接受 `/api/command` 前缀的平台，就是没有宿主命令路由。

## 命令自带文案

命令面板会向宿主询问「你能做什么」。此前的回答只是一串 id，页面再拿每个 id 去查自己内置的表——于是它能显示的永远只有自己早已带着的那几条。宿主提供别的东西没有任何意义；而页面没听说过的 id 会在构建动作列表时抛错，整个 App 变成空白页。

现在宿主把文案随命令一起发过来：`GET /api/command` 返回 `offers`，每条是一个 id 加两种语言的标签，页面照单渲染。服务端与页面都不再拿 id 去比对自己的清单，两边唯一要问的是「宿主是否提供了它」。

这件事之所以重要，是因为三个程序各走各的发布节奏——桌面 shell 经安装包抵达用户，服务端与页面经热推送抵达——所以「shell 比它所服务的页面新」是常态，不是边角情况。

页面**认识**的命令仍用页面自己的文案：它们翻译得更准、带搜索关键词，而且改动只需一次推送而不是一个安装包。宿主的文案是兜底，不是命令。比 `offers` 更旧的页面读的是收窄后的 `commands` 字段，其中只有它查得到的 id。

## 从命令面板与 F12 打开开发者工具

桌面端的命令面板（默认 ⌥⌘P / Ctrl+Alt+P）新增「打开开发者工具」一项，与安装 `penguin` 命令、检查更新并列。**F12** 同样能打开，Ctrl+Shift+I 也能。

View 菜单一直带着开发者工具，但 Windows 与 Linux 上菜单栏是隐藏的，想看一条控制台报错就只剩一个没人告诉过你的按键；而菜单自身的快捷键并不可靠——Chromium 会先把按键交给页面，页面消费掉 Ctrl+Shift+I 它就到不了菜单。现在 shell 在 `before-input-event` 上先于页面接住 F12 与 Ctrl+Shift+I，与 F10 唤出菜单栏是同一条路径；命令面板那一项则让同一个动作不靠按键也能找到。

它以独立窗口而非停靠面板的形式打开：读取报错时页面不会被重新排版；已经打开时再次执行只是把那个窗口聚焦。

该入口只在桌面端出现：打开开发者工具的是宿主进程，走的是其他 shell 动作共用的 `/api/command` 通道，而普通服务端不提供任何宿主命令。在浏览器里，浏览器自带的开发者工具就是答案。
