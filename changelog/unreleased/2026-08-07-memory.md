# Memory: what an agent keeps between Sessions

An agent now has a long-term store it maintains itself: Markdown notes under `agent_state/memory/`, kept in two scopes — one for the user and one per Workspace — each with its own `MEMORY.md` index that enters the context, topic bodies read on demand. It covers what a later Session cannot re-derive from the Workspace — who the user is and their standing preferences, project decisions with their reasons, conventions, entry points into external systems.

Memory is not context compaction. Compaction preserves one Session's short-term working state; Memory is what survives the Session ending.

## Scope and layout

There are two scopes, both belonging to one agent and never shared with another:

- **User scope** (`memory/user/`) — what stays true wherever the agent works: who the user is, their standing preferences (`type: user`), reference material not tied to one codebase. Every session reads it.
- **Workspace scope** (`memory/<workspace_key>/`) — facts about one Workspace (`type: feedback | project | reference`). Sessions of one agent in one Workspace share it; different Workspaces keep their topic files apart.

Each scope carries its own `MEMORY.md` index — one line per memory, `- [Title](file.md) — hook`, links relative to the scope directory — and different agents never share Memory even in the same Workspace.

```text
agent_state/memory/
├── user/                         # user scope (created with the agent)
│   ├── MEMORY.md                 # this scope's index
│   └── prefers-pnpm.md
└── my-app-a81f32c4/              # created on the first Session in that Workspace
    ├── .workspace                # the Workspace path this key stands for
    ├── MEMORY.md
    └── testing-conventions.md
```

`user` is safe to reserve because every generated workspace key is `<base>-<8 hex>` and so always carries a hyphen — a hyphen-free name can never be produced.

The workspace key is `<safe-basename>-<8 hex of the real path's sha256>`. Identity is the directory itself, with no dependence on Git: two symlinks to one directory resolve to a single key, and moving or renaming a directory makes it a new Workspace — the old Memory stays on disk under the old key rather than following a path that no longer exists.

A **temporary** Workspace gets no Workspace scope. One is allocated per session, so no later session would ever run there to read it back — memory keyed off it would be write-only storage. Such a session still gets the user scope, which is where anything it learns belongs anyway. The test is the directory's location — anything under an agent's `workspaces/` — rather than whether the caller passed a Workspace explicitly, because a subagent inherits its parent's Workspace as an explicit argument, temporary ones included.

A topic file is a semantic subject, not one per Task, Session or date, and declares `name` (kebab-case, matching the file name) / `description` (one line used to decide relevance during recall) / `type` / `updated_at` in frontmatter; in the body, `[[name]]` links related memories and `feedback` / `project` topics carry **Why:** and **How to apply:** lines. Never saved: credentials, task progress, unconfirmed guesses, or facts the code and Git history already state.

## What reaches the model

Only the indexes, through the `# Memory` section of the system prompt template — ordinary visible template text with the same status as the # Vault / # Skills statements, ending in a `## Workspace memory` subsection. Four placeholders carry the dynamic parts (`{{MEMORY_USER_DIR}}` / `{{MEMORY_USER_INDEX}}` / `{{MEMORY_DIR}}` / `{{MEMORY_INDEX}}`); injected index content is fenced by `[user_memory_index]` / `[workspace_memory_index]` marker pairs, a blank index injects an explicit "nothing saved yet" note, and injection is capped at 200 lines per scope — past the cap a truncation note tells the model to open the full `MEMORY.md` itself.

Rendering only ever removes, never invents: `memory.enabled: false` drops the whole `# Memory` section at render time, and a Session in a temporary Workspace drops the `## Workspace memory` subsection — so such a Session is never told about a directory it does not have. The stored template is never rewritten and the assembled prompt is recorded in `session_meta`. An agent created before Memory has no section and injects nothing; the Memory tab offers inserting the default section as an explicit one-click action.

Reading, writing and deduplicating are the model's own work through the ordinary file tools — the Harness decides where Memory lives and keeps writes inside it, nothing more.

## Managing it in the Web App

Agent settings gain a **Memory** tab between Prompt and Runtime: the switch on top (written immediately, not joining the tab's Save, so turning Memory off never drags an unrelated half-finished edit along), then every memory grouped by scope — user memory first, then one group per Workspace, labeled by its `.workspace` path, newest activity first. Rows show a type badge, the memory's name, description and date.

Rows are deliberately read-only. **View** opens the rendered body in a drawer; **Delete** confirms, removes the file and mechanically drops its `](<file>)` lines from that scope's `MEMORY.md`, so the index never lists a file that is gone; **Edit** jumps to a new chat with this agent — the same draft-cache route the skill import flow uses — prefilled with the memory's file path and an instruction to keep the index and `updated_at` in step, with the requirement line left trailing for the user to complete. A Workspace memory's edit chat also pins that Workspace, so the editing Session is injected with the very index it is about to change.

Turning Memory off keeps every file and leaves the tab fully usable; it only stops Memory from entering the context and from preparing directories for new Sessions.

The API is under `/api/projects/:p/agents/:a/memory` — overview, per-scope file listing, file read, file delete, and the idempotent template-section insert; deliberately no content write or rename, since content changes go through chat. It never accepts a path: a file is addressed by agent, scope key and a name inside that scope, each validated and then re-checked for containment after resolution.
