# A plugin's manifest is its package.json, and an agent can port a foreign plugin into one

- **Date:** 2026-10-10
- **Type:** feature
- **Scope:** `core`, `server`, `web`, `cli`, `skills`
- **PR:** [#1024](https://github.com/Prism-Shadow/penguin-harness/pull/1024)
- **Breaking:** yes — `plugin.json` is no longer read; a plugin describes itself in its `package.json`

[中文版](2026-10-10-plugin-package-json.zh.md)

A plugin's `package.json` became its only manifest: npm's own fields plus a `penguin` block for everything that is PenguinHarness's, every field but the name and the version optional, and a missing field shown as missing. An agent can now port a plugin written for another tool — a Codex or Claude Code plugin, a skills repository, a folder in a GitHub repository — into such a package and install it on the server, from where any agent gets it with **Manage installs**. A plugin can also carry MCP servers, which **Manage installs** adds to an agent's configuration, their secrets read from the agent's vault.

## The manifest

- The npm fields keep their npm meaning: `name` (required; the part after the scope is the plugin name), `version` (required, semver), `description`, `keywords` (`penguin-plugin` is the discovery keyword), `author`, `license`, `homepage` and `repository`.
- The `penguin` block holds `title` / `title_zh` (a display name), `description_zh`, `short_description` / `short_description_zh`, `category`, `icon` (an SVG path in the package; `icon.svg` at the root when absent), `preinstall`, `quick_start` and `hooks` (the hook package, with its date `version`). Skills, hooks and server modules are still found by their directories.
- Core reads every package through one reader, `parsePluginPackage`. A package without a valid name or release version is refused; any other field of the wrong type is dropped with a warning naming the key. For a package the build ships, any such warning fails the library; for one an admin installed, the warning goes to the server log once and the package lists with the field missing.
- Missing fields are shown as missing: no description reads "No description" (「暂无描述」) in muted ink, no title shows the plugin name, no icon the puzzle piece, no category the Other group, no quick start pre-selects the first Skill.
- An icon is inlined only when it stays inside the package, weighs at most 64 KiB and holds no script, event handler, link or external reference; otherwise it is dropped, for a package an admin installed as well as for the index rows of server modules on this machine. An XML declaration before `<svg>` is left out of what is sent, so such an icon still shows.
- In a package an admin installed, a Skill without a date version reads as unversioned and is never offered an update, and `hooks/` without `penguin.hooks.version` lists the Skills and no hook package. A skill directory whose name is not a skill name is left out with a warning, since no agent could install it. A file in a skill directory that is not UTF-8 text, such as an image, is left out instead of being installed garbled.
- The 19 shipped packages moved their `plugin.json` fields into `package.json`, gained `keywords` with `penguin-plugin`, and dropped `plugin.json` from their `files`. `scripts/check-plugin-versions.mjs` reads the hook declaration from `penguin.hooks`, and from the base commit's `plugin.json` while the base still has one.
- The plugin's details show the title with the package name beneath it, and a line with the author, the license and links to the homepage and the repository, each only when the package carries it. The search box matches the title too. `PluginItem` gained `title`, `titleZh`, `author`, `license`, `homepage` and `repository`.

## Importing a foreign plugin

- The `skill-porting` plugin gained a second Skill, `plugin-porting`: the package format, how to fetch a source at a pinned commit, how to recognise a Codex or Claude Code plugin, the field-by-field mapping into `package.json` (`reference/foreign-plugins.md`), a script that reduces each ported Skill's frontmatter to `name`, `description` and a date `version` and removes images and another tool's display metadata (`scripts/normalize-skills.mjs`), the review duties and the install. Commands that only point at a Skill, subagents, another tool's hooks, hosted apps and images are not carried, and the package's README lists them; MCP servers are carried, as the next section describes.
- `penguin plugin install <directory>` installs a local package directory: the CLI reads it with the plugin library's reader (a package the library would refuse is reported and nothing is sent), zips it without `node_modules`, `.git` and `.npmrc`, and uploads it through the zip route. `--overwrite` replaces another version on the server.
- The import dialog's link tab refuses a link to a folder or a file inside a GitHub repository and offers **Ask an agent**, which carries the link to the agent tab; the server refuses the same links before npm runs. The agent tab's prompt names the package format and sends anything that is not a package yet through `plugin-porting`.

## MCP servers travel with a plugin

- A plugin's `package.json` gained `penguin.mcp_servers`: entries in the `tools.mcpServers` shape of `system_config.yaml`, each with an optional `setup` list of the vault keys a user sets before the server can connect (`key`, `label`, `label_zh`, `help`); a key the config references counts even without an entry. A package that carries MCP servers alone is a plugin of the library, so a Codex plugin such as Gmail, one remote server and no Skills, now ports and installs instead of being refused as not a plugin.
- `${KEY}` in any string value of a server's `config` is read from the agent's vault when the server connects. The configuration, the config API and the Trace carry only the reference, and the rest of the vault still never reaches an MCP server. `${PLUGIN_ROOT}` is replaced with the package's directory when the plugin is installed on an agent, and `config.oauth` marks a server that signs in with OAuth.
- Installing a plugin on an agent appends its servers to the agent's `tools.mcpServers`, each with `plugin: <plugin name>`, keeping the file's comments; reinstalling replaces exactly those entries and uninstalling removes them. A server name the agent already has from elsewhere refuses the whole install with 409 `mcp_server_name_taken`, and nothing is written. A plugin counts as installed once each of its servers is there too; MCP entries carry no version and never raise an update. Restoring an agent's default configuration drops them, and **Manage installs** puts them back.
- `GET /api/projects/:projectId/agents/:agentId/mcp-servers` lists an agent's servers with their target, plugin, missing keys and sign-in state, never a header or `env` value, and `DELETE …/mcp-servers/:name` removes one (404 `unknown_mcp_server`). The install answer and the `GET /api/plugins` items gained `mcpServers`. `POST …/config/mcp-test` fills in references from the vault first, and answers "needs setup" without connecting when a key is missing.
- A server whose references the vault cannot fill is skipped as needs setup, with `mcp_needs_setup` and the missing key names, never a value, in its connect result. One with `config.oauth` and no `Authorization` header is skipped as sign-in required (`mcp_sign_in_required`): OAuth sign-in is not supported yet. The plugin's details, **Manage installs** and the agent's **Tools** tab mark both with icons, the chat's MCP connect row shows such a server as waiting rather than failed, and the Project owner fills in the keys with **Set up** in **Manage installs** or on the **Vault** tab. In the agent's settings, a server a plugin installed carries a puzzle mark naming the plugin.
- `plugin-porting` carries MCP servers: its `scripts/port-mcp.mjs` turns a Codex `.mcp.json` or a Claude Code `mcpServers` map into `penguin.mcp_servers`. Placeholders such as `<GMAIL_PUBLIC_CLIENT_ID>` and forwarded environment variables become `${KEY}` references with setup keys, a client secret published upstream becomes a key to set up instead of being carried, and a stdio command inside the plugin is rooted at `${PLUGIN_ROOT}`. Hosted apps (`.app.json`) stay out: they are ChatGPT connector ids.
- What a package brings is disclosed. The import dialog says a plugin may carry MCP servers, a stdio one being a command the server runs when an agent session starts; the details show each server's transport and target; installing a plugin with a stdio server on an agent asks first and shows the command; and `penguin plugin install <directory>` prints each server's name, transport and target.
- `${KEY}` now reads as a vault reference in every `tools.mcpServers` entry, hand-written ones included, so an existing entry with a literal `${…}` in a value is skipped as needs setup until the vault holds that key.

## Compatibility

The shipped plugins carry their fields in `package.json` now, and a plugin name the build ships is always read from the build, so nothing a release installed changes: an older `@penguinharness/*` package in a server's prefix stays unlisted, as before. A plugin written for the documented `plugin.json` format has to move its fields into the `penguin` block of its `package.json`. Until it does, it lists by its directories: its English description, icon, version and Skills show, while its Chinese and short descriptions, category, quick start and hook package are missing. Skills and hook packages already installed on agents are untouched.
