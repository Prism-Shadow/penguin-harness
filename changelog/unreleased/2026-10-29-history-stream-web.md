# A remote conversation's history loads newest first, with progress

- **Date:** 2026-10-29
- **Type:** fix
- **Scope:** `web`, `ui`, `ui-gallery`
- **PR:** [#1393](https://github.com/Prism-Shadow/penguin-harness/pull/1393)

[中文版](2026-10-29-history-stream-web.zh.md)

A long conversation on a remote machine no longer failed with "Failed to load history" and a network error on a slow link. The chat read its history over the `history` stream instead of one call with a 20-second deadline. The first read asked for the newest Tasks that fit 64 KiB of records, so the latest messages showed within seconds even at 10 KB/s. Older windows then followed until the conversation's newest 20 Q&A pairs were on screen, each one added above the transcript without moving the reading position. A prompt with images counted as one pair: each window's page said how many Tasks it held. A background subagent of an older Task that spoke, or whose approval was sent again, before that Task's window had loaded kept its history, and no stray subagent card appeared in the newest Task. A dropped link was resumed by the socket from the last event, and no record arrived twice. A reconnect that had to read the history again kept the earlier windows on screen: when new Tasks had arrived meanwhile, the windows between were read behind the transcript and joined at the exact record where the old ones began. Leaving the conversation closed every read it had opened.

Conversations on this server changed too: their history came over the same stream, opened on the newest Tasks and filled up to 20 pairs, and carried the same folded values. A conversation that fit its first window looked as before, with no beginning-of-conversation marker; the marker showed only after the reader scrolled up past the pairs the conversation opened on.

While a conversation on a machine was still loading after one second, the skeleton gave way to a transfer row that named the machine and showed the amount received against the total, in one unit and at one width. The row waited for the machine list, so the machine's name never popped into a row already on screen. When the server was retrying the machine, the retry showed under the row with Retry now, in words that told a lost connection (reconnecting) from a connected machine that had stopped answering (asking again); the machine's own retry row showed while the machine was away. Once the newest messages were on screen, one muted line at the top of the transcript showed the rest of the conversation syncing to this server, and it went away when the sync finished. An older window that was still being fetched showed its own progress in the same place; the automatic fill-up to 20 pairs was one line from its first window to its last, and like the skeleton, the line said nothing during its first second. While the server waited for the machine, the same line said so: an hourglass, the waiting words in the same muted ink, and the amount and bar as they stood. A machine that was connected but had sent no new data for a minute was said as such, with no attempt number, countdown or Retry now, since nothing was being retried; a waiting reason this build did not know was said in neutral words.

A link to a conversation that the list did not hold no longer said "This conversation does not exist or was deleted" while a machine that could hold it had not answered. This server's "no such Session" counted as an answer only once every machine had answered: until then the page waited, said that this server did not have the conversation and named the silent machines it might be on (up to three), and asked again when they answered. The hub's `machine_no_answer` named the machines it could not ask, and a Session this page had seen on this server was settled by this server's answer alone.

A tool output, a long tool argument or a thinking block that the history carried folded showed its head and tail around an ellipsis; inside a call's arguments the ellipsis sat in the folded string itself. Opening the row fetched the whole value and showed it in place of the preview. A fetch that failed said why on the same line, with a retry. A pending approval always showed the whole call it asked about: the server's re-sent request replaced the folded copy from the history. A value already fetched stayed whole through a reconnect and was not fetched again, an unfold under way when the transcript was rebuilt finished on the rebuilt row, and the amount fetched never went backwards when the stream started over.

The Trace panel brought a machine's Trace file to this server with the same progress row before reading its analysis, instead of forwarding a minutes-long read. It asked for that one file only, and a file on this server answered at once. The panel kept one loading state until the analysis arrived, instead of returning to the skeleton between the transfer row and the file.

The UI package gained `TransferProgress`: one sentence of plain text, the amount and a thin progress bar. The tool call card and the thinking block gained a `bodyNote` slot that is mounted only while the row is open. The gallery showed the transfer row in each place it appears, and its mocked API answered the history and trace-body streams.
