# The Windows sandbox keeps your real home, and full access can cut the network

- **Date:** 2026-09-16
- **Type:** fix
- **Scope:** core, server, plugins
- **PR:** [#771](https://github.com/Prism-Shadow/penguin-harness/pull/771)

[中文](2026-09-16-windows-home-and-full-access.zh.md)

Two things about the Windows account sandbox were wrong, and both are fixed.

- **A confined command's home was remapped** to `C:\ProgramData\penguin\sandbox-home`, so `~/.gitconfig`, `~/.ssh`, tool caches and the harness's own config were all invisible, and a "write your home" test wrote to a decoy and reported success. The home is now the real one. Write-confinement never needed the home at all: a command runs as an account that owns nothing, so it is already denied everywhere, and the launcher grants it write on the **Workspace alone** — small, and fast. What the setup adds is READ on a **curated set of config paths** (the profile root, its own dotfiles, and `.config`, `.aws`, `.gnupg`, `.docker`, `.kube`, `.azure`), so `~/.gitconfig` and friends resolve. `~/.ssh` is not among them, and every run of the setup — `-Remove` included — takes any sandbox account off it, whether an earlier build granted it directly, through inheritance, or for an account since deleted: OpenSSH refuses a config or a private key another account can read, so such a grant breaks ssh for you, and a sandboxed ssh could not use those files anyway. The registry hive (`NTUSER.DAT` and its logs) is skipped among the root files. Deliberately not the whole profile: a developer's profile holds millions of files in caches, `node_modules` and `AppData\Local`, and stamping every one would take an age and hand the sandbox their browser data for nothing. The full-access accounts get **modify** on that same set. The one thing still redirected is the temp directory, to a shared writable folder, and only when "temp writable" is on.
- **Full access and a network cut could not both hold.** `danger-full-access` short-circuited to unconfined before the network setting was read, so "full access" silently dropped "no network". Full access with the network open (and no masked paths) is still genuinely unconfined. Full access that **cuts the network or masks a path** now reaches a backend that enforces that while leaving the filesystem unrestricted. This is a small widening of the sandbox contract: a provider may now be handed `danger-full-access`, and must leave files alone while still cutting the network or hiding a path. bwrap binds the root read-write and still `--unshare-net`s; seatbelt denies no writes and still `(deny network*)`s; the Windows backend runs the command as a network-blocked account whose home is writable.
- **The Windows backend now has four accounts** — the network axis (open / blocked) crossed with the filesystem axis (home read-only / writable) — so each account's reach is granted once at setup and no command re-permissions your profile, which on a large one would take minutes.

## 兼容性

This changes what the Windows setup script leaves behind (four accounts, a profile grant, a shared temp folder) and the shape of its state file, so the state from an earlier build reads as "not set up". Re-run the setup once: run `setup\penguin-sandbox-setup.ps1` from an elevated PowerShell. Until it is re-run, the Windows sandbox declines to load and confining modes fail closed rather than running unconfined; `-Remove` on the new script also takes the old accounts, group and rules away. The re-run is quick: it grants only the curated config paths, never the whole profile. A build before this one granted the whole profile with an inheritable entry on its root, which every file below inherited — a host where `ssh` reports `Bad permissions` on `~/.ssh/config` was left that way by it. Every run of the setup now withdraws that entry from the root (Windows then withdraws it from every file below, which takes minutes on a large profile, and only when the entry is there) and retires that build's accounts, group, firewall rules and decoy home, so nothing of the earlier layout survives a run; `-RemoveLegacyProfileGrant` additionally walks the profile for entries that build stamped on individual files, and stays off by default. This note can go once no Windows host still holds a two-account state file.
