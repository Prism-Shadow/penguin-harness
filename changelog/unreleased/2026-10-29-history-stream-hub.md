# The hub keeps a copy of its machines' Trace lines and streams a remote conversation's history from it

- **Date:** 2026-10-29
- **Type:** feature
- **Scope:** `server`
- **PR:** [#1392](https://github.com/Prism-Shadow/penguin-harness/pull/1392)

[中文版](2026-10-29-history-stream-hub.zh.md)

A server that connects machines kept a copy of the Trace lines each machine sent it, under `<data root>/machines/traces/`, and answered a remote conversation's history from that copy as a stream with progress. A conversation opened again asked the machine only for the lines it did not hold yet, and a machine on an older build still loaded its history.

## Details

- `GET /api/sessions/:id/history` streamed a window as whole-record lines with its bulky values elided, under the same query as `/messages` (`tailLimit`, `before` and `limit`, none for the whole transcript) plus `budget` and `fill=1`. Each event carried `<windowId>:<offset>` as its id, and a stream issued again with that id within two minutes continued the same window, for the same Session, user and query only. Every failure ended the stream with an `error` event, and an HTTP stream ended when its user was signed out. A local Session was answered from its own Trace.
- For a machine's Session, the hub asked the machine's `history-lines` route over the API socket, committed whole lines into a byte-exact copy, and assembled the window from it. One sync job per conversation ran one machine stream at a time: a window or a body went first and the background fill gave way to it, and a fill ended once nobody stayed for it. A stream was cut only once nothing at all had come from the machine for 15 s, on the socket or on any request proxied beside it over the same ssh session, so a stream waiting behind a large answer on a slow link was not told the machine had stopped answering; the API socket itself was dropped only after 40 s of that same silence, and while the hub still heard the link it pinged the machine; one that moved was reopened from the copy at once; one that did not, and a machine that was away, were retried from 1 s doubling to 30 s with the wait reported as `progress.waiting`. The last reader leaving cancelled the machine stream at once, and a replaced server generation ended its streams without an error so their readers asked again. Every generation used the same copy of a directory.
- Each file's `have` named every run held and a line held in part, and a conversation's whole `have` stayed within the machine's limit, its own files first. A copy that could not be written did not stop a read: the window was assembled from the stream itself.
- The copy was checked on every open: a file that the machine had rewritten or replaced started over, told by its inode and by its birth time where both sides knew one, never by its device. A file the machine no longer listed in a window or a fill was dropped; fetching one value never dropped anything. A window whose copy did not read back was read again for its own ranges only. Lines past the size the machine gave their file were never kept. A conversation the machine deleted dropped its copy, on the machine's `session_not_found` or its `session_deleted` event. Its directories were named by hashes of the ids. It was capped at 1 GiB, counting each file up to its highest offset held and evicting the least recently read conversations first. A machine's copy was dropped when the machine was uninstalled with its data, and at the next start once the machine was no longer in this server's list; nothing was dropped at start while the ssh config could not be read.
- `GET /api/sessions/:id/trace-body?ref=` sent one elided value whole, from the copy or after fetching its line, with one progress total. Images by reference were answered from the copy too, and so were the Trace panel's events, live file included, for every record held from the file's start. Its analysis was computed on the hub from the copy, priced with the conversation's Project. A Project-scoped Trace path for another Project found nothing. Everything else was forwarded to the machine as before.
- A read the copy answered alone (an image, the Trace panel's events and analysis, a held value) was answered at once and asked the machine behind it, at most once every 30 seconds, whether the conversation was still there: one deleted over there without this server hearing of it lost its copy, and the reads after it answered `404`. While the machine was away, silent or unclear, the copy kept answering and the machine was not asked again for 30 seconds. A machine that would not show this server a conversation (`403` `session_forbidden`) ended the read with that error and kept the copy. Dropping a deleted conversation's copy kept a subagent copy that a fork still named, and an analysis for a Project this server has no config for was left to the machine. A machine stream that carried only its beats for a minute told its reader the machine was slow (`waiting.reason` `slow`) instead of saying nothing, and a socket whose own channel stayed silent longer than the rest of the link could queue ahead of it (2 MiB at the link's rate, never under twice its period) was dropped however busy the link was; a hub slow to write what it received was not reported as a slow machine.
- A Session-level request for a Session this server does not hold answered `503` `machine_no_answer`, naming the machine in `details`, when a machine that could hold the Session did not answer in time, and `403` `session_forbidden` when the machine holding it would not show it; a `404` `session_not_found` came only once every machine asked had said it did not hold it.
- A machine without `history-lines`, or one this server held no API socket to, had its window read from its `/messages` over HTTP inside the same stream, with the bytes counted as they arrived and nothing cached; the hub counted the window's Tasks (`units`) itself. A machine that turned this server's session away ended the stream with `machine_refused`, one being upgraded was waited for, and one no longer in this server's list ended it with `machine_not_found`.
