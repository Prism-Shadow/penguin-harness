# 压缩行在压缩结果旁流式呈现压缩请求的思考

- **Date:** 2026-09-02
- **Type:** feature
- **Scope:** `core`, `web`, `cli`, `docs`
- **PR:** [#582](https://github.com/Prism-Shadow/penguin-harness/pull/582)

[English](2026-09-02-compaction-banner-thinking.md)

Web App 的压缩行改为按运行中的工作分组的形态呈现：组头写明模式并带 wall time；压缩运行期间该行展开、其中两节仍折叠——压缩请求的思考与它产出的摘要——两节各带自己的 wall time，请求运行期间都流式写出。压缩结束后该行自行收起。

## 细节

- Core 在成对压缩事件之间把压缩请求的思考推上输出流，方式与此前推送摘要文本相同：`partial_thinking` 片段原样转发，没有片段承载内容时改推完整的 `thinking`，二者绝不同时出现。压缩请求沿用模型上下文既有的思考等级，不会为它单独开启思考。Trace 不变。
- Web 端的 reducer 把这段思考累积到进行中的压缩条目上（`thinkingText`，并以 `thinkingStreaming` 记录片段是否仍打开），与摘要并列；历史重建从压缩区间已记录的思考读回同一内容；未完成的压缩把两份草稿一并丢弃。
- 压缩行的正文改为两条上下堆叠的折叠行：**思考**（有思考抵达后才出现）与**压缩结果**，都用思考块的正文样式与流式渲染器。两节各在思考块原有的位置带上自己的状态图标与 wall time，因此压缩的一节、思考块、以及它们上方的那一行读起来完全一致。
- 步骤行（压缩、首次 MCP 连接）改用工作分组的展开策略：运行期间该行展开，正文里的行随产生逐条出现在屏幕上；结束后该行自行收起，而正文里的行始终不随之展开。手动切换会把该行钉住，读者展开的已完成行保持展开。工作分组自身的策略也从「是否为最后一段」改为组头的运行中/运行完毕状态，因此以该分组收尾的一轮同样会收起。组头从 summarize 压缩开始就带折叠箭头，请求运行期间在详情位显示「生成中」提示，实时计时的 wall time 在结束后定格为与运行结束统计行相同的格式。失败的压缩保留一行原因，`discard` 行仍不带折叠箭头。
- 每一节的计时范围恰好是它显示自己「运行中」的那段窗口：思考从第一段思考内容起、到收束其片段的 stop 止；压缩结果从第一段摘要文本起、到压缩自身结束止。历史重建以上一条消息的时间近似各自的起点，沿用普通思考块既有的约定。重试的压缩会把各次尝试拼成一份草稿，因此起点只记录一次、之后的 stop 只延长它——wall time 覆盖产出屏幕上这段文字的整段时间，而不是只算最后一次尝试。
- CLI 不打印流式思考，一如它此前不打印流式摘要。
- agent-loop 与 Web App 文档描述了压缩行的新形态。
