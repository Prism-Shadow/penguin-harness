# 微信成为第四个消息渠道，通过扫码完成绑定

- **Date:** 2026-08-28
- **Type:** feature
- **Scope:** `server`, `web`, `docs`

[English](2026-08-28-messaging-wechat.md)

Session 多了第四个可绑定的渠道：微信官方的 claw 机器人，接在前三个渠道早已使用的同一套连接器
接口后面。绑定它只有一条路——用微信扫码授权，没有任何可以复制凭据的后台，因此扫码在这里不是
更省事的那条路，而是唯一的一条。入站消息走长轮询，绑定它不需要任何公网回调地址；而且它能双向
传输文字、图片与文件，这是另外三个渠道都做不到的。

## 细节

- 传输层落在 `wechat-api.ts`：请求信封与其请求头、带不透明游标的 `getupdates` 长轮询、单条
  消息项的发送，以及双向的 CDN 媒体链路——出站是把按文件随机生成密钥的 AES-128-ECB 密文上传到
  预签名地址，入站是与之对应的解密。它以可注入的工厂形式落地，因此测试是对着假实现跑的，不碰
  网络。协议来自腾讯自己以 MIT 协议开源的 OpenClaw 插件，以及由它衍生的独立 SDK；两者都没有被
  当作依赖引入，因为它们都要接管进程的消息循环、只承载单个账号，并把登录二维码画在终端里。
- 渠道策略落在 `wechat-connector.ts`。轮询循环失败后按退避重试，且每次故障只上报一次；它的
  **第一次**响应是一次清空：空游标意味着「从头开始」，因此一个搁置了一周才启用的绑定只是确认
  掉这一周，而不是把它重放成一堆 Task。
- **扫码连接就是这个渠道的全部凭据表单。** `wechat-scan.ts` 只在内存中持有进行中的二维码与
  平台的轮询句柄——也就是能换取 Bot Token 的那个——按发起的 Session 隔离，并按 Session 设上限。
  浏览器拿到的是服务端另行签发的句柄，外加要渲染的 URL 和一个状态。相比 QQ，这套流程要上报更多
  状态，因为微信本身就更多：已扫码但未确认、手机上显示、需要在面板里输入的配对码、因多次输错而
  作废的二维码，以及「该机器人已连接过本服务」——最后一种结束流程但不是失败。IDC 重定向会在流程
  中途切换轮询主机，而不作为一个独立状态暴露出去。
- `/wechat` 路由子树带来了其他渠道同样的动词集合，以及两处因「没有可填写的凭据」而产生的差异：
  它的 PUT 只保存投递偏好、且拒绝凭空创建绑定（400 `wechat_token_required`），它的凭据探测则
  完全不接受请求体——没有草稿可探，只能探已存绑定。扫码得到的 bot id 就是账号身份，因此
  「一个账号同时只由一个 Session 持有连接」的规则对微信机器人与对飞书应用完全一致。
- **只支持单聊。** 这个渠道不接收群消息：在群里发给机器人的消息根本不会到达，因此面板把这一点
  写在控件下方，而不是留在折叠的说明里。
- 媒体是双向的。回复中的图片与附件会被上传，并以真正的图片和文件到达；入站的图片、文件与视频
  以惰性句柄的形式到达，只有在 bridge 判定这条消息值得处理之后才真正下载。语音消息按微信**自带**
  的语音转文字结果转发，因此一句说出来的问题会被回答而不是被拒绝；微信没能转写的语音则以共用的
  「不支持」提示回到聊天。
- `wechat-markdown.ts` 面向的是一个本身就读 Markdown 的客户端，因此它做的是删减而不是翻译：
  标题、粗体、删除线、列表、引用、分割线、链接、行内代码、代码块与表格都按原样发出——四个渠道
  里最全的一份——而客户端不渲染的部分只去掉标记、保留文字（五级以下的标题、中文两侧的斜体，以及
  行内图片，后者改为链接）。
- 三个投递偏好在这里原样适用，且没有一个在本渠道有不同的代价：它既没有回复额度，也没有会过期的
  回复窗口，因此它的绑定类型不重复声明任何字段。
- 绑定编辑器的渠道选择器多了第四个选项，微信也在两份词典里带来了自己的扫码面板、配置步骤、媒体
  说明与排查条目。
- Session 行的消息动作及其对话框现在标注为**远程控制**（英文 `Remote control`）。只改了文案，
  路由、键名与各类标识符都没有变。
