# socket 上没有回音的请求会被放弃，并说明原因

- **Date:** 2026-09-23
- **Type:** fix
- **Scope:** `web`, `server`
- **PR:** [#832](https://github.com/Prism-Shadow/penguin-harness/pull/832)

[English](2026-09-23-socket-silent-hangs.md)

对话可能一直空白，直到刷新页面为止，而且什么线索都没有：界面无报错、控制台无日志、网络面板里也没有失败的
请求。所有 API 调用都走同一条 socket（PRFC-0011），而 socket 客户端此前会无限等待——握手既不成功也不失败、
调用服务端始终不应答、流服务端始终不打开——同时服务端的心跳又让连接看上去一切正常。同样的沉默也会把
Session 列表卡在骨架屏上：一次 reload 里本服务器对所有请求都没有作答时，不会有任何东西再问一次，只能等某个
事件碰巧触发。

这些警告随后指出了原因：热推之后，在旧 App 上打开的 socket 会继续把请求派发给它。socket 的 `fetch` 在握手时绑定
的是那个 App 的路由，而被 dispose 的树已把机器会话交给了后继者——于是所有经过机器的调用（`/server/<machine>/…`，
组织的工位与频道都在那里）永远没有回音，本服务器自己的路由却仍在应答，心跳也让 socket 看起来一切正常。socket
从未关闭，浏览器自然不会重连。

## Details

- API socket 改由平台 shell 服务，其上的每次调用都进入当时的 App：插件变更在开着的 socket 底下重组 App，不再把它
  搁浅。推送替换的是 shell 本身，因此开着的 socket 交给后继者，由后继者在启动完成两秒后关闭（关闭码 1012，「the
  harness was updated; reconnect」）——此时运行时已把自己的树指向新 App，而这个窗口内的握手此前读到的是已 dispose
  的树。浏览器的 socket 客户端随后重连，并按各流的 last event id 重新发起。带上这个改动的第一次推送仍由旧平台完成
  换出，当时开着的窗口需要刷新一次；之后的每次推送都会自动重连。

- 握手 10 s 内仍未打开的，由客户端主动关闭并重试；连续三次即放弃 socket，改用 EventSource 与 fetch，与被拒绝
  的握手处理一致。
- 单次调用 20 s 内无应答的即放弃，并以 `console.warn` 报出调用名与 socket 状态（是否打开、上一帧是多久前）。
  读请求（`GET`/`HEAD`）改走 HTTP 重发；写请求报为网络错误，因为它可能已经生效。
- 流 20 s 内未打开的，取消后重新发起，附同样的警告。
- 本服务器对所有请求都未作答的 Session 列表 reload，按退避（2 s 起，翻倍至 30 s）重试，并以警告列出各请求
  得到的回答。
- 对话历史 15 s 后仍在加载的，记录这次调用去了哪里（本服务器还是哪台机器）以及 socket 正在做什么，下次报告
  就能直接说出原因。
