# The Web App holds one socket to its server, and every stream is a call on it

- **Date:** 2026-09-07
- **Type:** feature
- **Scope:** `server`, `web`
- **PR:** [#642](https://github.com/Prism-Shadow/penguin-harness/pull/642)

[中文版](2026-09-07-single-socket.zh.md)

The Web App opened one never-ending HTTP response per long-lived subscription — this server's `/api/events`, one `/server/<id>/api/events` per connected machine, and one Session stream per open chat — and browsers allow six HTTP/1.1 connections per host, so a few machines and one chat left the page's own requests queued behind them, and a proxied stream that died half-way never gave its slot back. Now a tab holds one WebSocket to its server and everything long-lived is a call on it; the server holds one socket per connected machine and relays their streams over it. Design: PRFC-0011.

## Details

- The socket is a second transport of the same API: each text frame is a call to an existing endpoint — method, path, a whitelisted header (`last-event-id`, `accept`, `content-type`), a JSON body — entering the same routes HTTP requests enter, so authorization, validation and error shapes are the endpoint's own. A `text/event-stream` response comes back as a `stream` frame, one frame per event, then `end`; a `cancel` frame releases it. The socket pings on the SSE heartbeat's cadence and terminates a peer silent for two beats; a client lagging past the send watermark has its stream ended with reason `lagging` rather than buffered without bound. The runtime-owned prefixes (`/api/auth`, `/api/hmr`, `/api/desktop`) answer `421 not_on_socket` and are made over HTTP.
- It is opened on the terminal-stream upgrade path under a reserved id naming the signed-in user, `GET /api/terminals/api-socket@<userId>/stream`, which the terminal manager's lookup answers with a reference the platform serves the socket protocol for. The handshake is the terminal stream's — session cookie, same origin, the id's owner held to the signed-in user — and the platform enters its routes as that user (`Http.fetchAs`). Everything lives in the platform: a shipped shell serves the socket once the platform carrying it is pushed, with no change to the runtime.
- The machines proxy relays a stream request (`accept: text/event-stream`) over one socket it holds to that machine (dialled through the machine's ssh session as its admin), turning the frames back into a `text/event-stream` response. Streams never fall back to an HTTP forward, which would hold one channel per stream per machine: when no socket carries a stream — the machine refuses the handshake (a build without it, remembered for a minute), the dial does not complete within 10 s, or the machine does not open the stream within 8 s (the socket is then torn down) — the stream is answered `502`/`504` with the reason (`machine_socket_refused`, `machine_socket_unavailable`, `machine_stream_not_opened`). A socket is reused only within the ssh session it was dialled through; when the transport reopens the session, the old socket is closed and the next stream dials anew.
- The web's `apiFetch` sends a call over the socket when it is open and fetches otherwise, through one code path; a response the socket declines to carry (415 `unsupported_transport`) is fetched. Streams (`openUserEvents`, `openSessionStream`) are calls on the socket that survive every interruption — a reconnect, a server-side end, a 5xx while a machine has no socket — by being re-issued with their last event id, each on its own backoff (1 s doubling to 30 s, reset when it opens) with a console warning naming the server's reason; a 401/403/404 stops them. When the handshake keeps failing the page falls back to `EventSource` and fetch.
- The two SSE endpoints and the `/server/<id>/api/…` proxy are unchanged; the CLI keeps consuming SSE over HTTP.
