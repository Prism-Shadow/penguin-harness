# 压缩：先执行工具再压缩、中途退出即判失败、摘要默认折叠流式呈现

- **Date:** 2026-08-18
- **Type:** fix
- **Scope:** `core`, `server`, `web`, `cli`
- **PR:** [#329](https://github.com/Prism-Shadow/penguin-harness/pull/329)
- **Issue:** [#288](https://github.com/Prism-Shadow/penguin-harness/issues/288), [#290](https://github.com/Prism-Shadow/penguin-harness/issues/290)

[English](2026-08-18-compaction-continuity-and-streaming.md)

修复了两个压缩缺陷，并让压缩行以默认折叠的方式实时呈现摘要。工具调用之后触发的压缩，现在先把工具执行完，再带着工具结果开始压缩，全程不合成任何东西；用户中途退出程序导致没写完的压缩，会在会话下次加载时以失败收束、并丢弃写了一半的草稿，因此压缩之后发出的消息不再因刷新而消失，过期的 `(unknown tool)` 卡片也随之消失；摘要则在写出的同时抵达 Web App，并且像思考块一样默认折叠。

## 工具调用之后触发的压缩，先把工具执行完

引擎只有在 `runTurn` 返回之后才会走到压缩检查点，而 `runTurn` 要等本轮全部工具调用执行完毕才返回——所以在以工具调用收尾的一轮上触发的压缩，绝不会抢在工具前面。

- 本轮所有工具结果都随压缩请求本身发出，排在压缩 Prompt 之前、保持原始调用顺序，无论它们承载的是正常结果、`[tool error]` 还是被拒绝的回执。
- 需要审批或耗时数分钟的工具只是让压缩延后：压缩请求尚未发出，也就没有任何计时在跑。
- 全程不插入任何合成消息去闭合待决的交换，`LLMInterface` 保持不变。
- 手动 `/compact` 保留自己的语义：它没有待决的轮次，因此只发出 Prompt（以及它折叠进来的打断 carry-over）。

## 用户中途退出导致的压缩，就是一次压缩失败

压缩进行到一半时退出程序，会在分片里留下一个没有对应结束事件的 `compaction_begin`。核心的重放能够容忍它，并把后续对话继续追加到同一个文件，但每一个读取方都会把这一对事件之间的消息当作压缩内部内容，于是压缩之后发出的一切都会在重新加载时消失；等到后来某个 `compaction_end` 在 Task 中途把状态解开，工具输出便会因为其调用被吞掉而渲染成 `(unknown tool)` 卡片。

- `resumeTrace` 会报告这个未配对的 begin，`resumeSession` 则在任何新记录落盘之前以 `failed` 收束该区间，使文件对此后每一个读取方都是良构的。该处理是幂等的，健康的 Trace 会被跳过。
- 这次压缩写了一半的摘要会被**直接丢弃**，绝不重建：不注入任何 `[context_summary]`，原上下文照旧，阈值依然超标、压缩留待下次触发时补做。
- Web 侧的 reducer 会丢掉任何未完成压缩的半成品草稿，绝不把截断的摘要摆成像是已被采纳的样子。
- 本 PR 早先加入的读取方侧「过期区间」启发式规则，连同扫描器缓存版本的提升一并移除：在加载时收束区间已经足够，读取方因此保持简单。

## 被放弃的压缩结束本次运行、留待补做

Task 中途的压缩一旦失败，此前的循环会陷入一个说不清的状态：整个运行要么在压缩之后空手而归地结束，要么只带着几条光秃秃的 `[tool error]` 修复输出继续，而模型并没有收到任何据以行动的指示。

- Task 中途的压缩失败或被中止时，现在按普通打断的同一套流程收场：本轮尚未了结的状态按既有的「是否已提交」规则转入 carry-over（[#85](https://github.com/Prism-Shadow/penguin-harness/issues/85)），以 `abort` 事件结束本次运行（失败一路的原因为 `compaction failed`），下一条消息把 carry-over 与用户输入合并重发——阈值依然超标，压缩在那里再次触发。
- Task 边界上的压缩失败一如既往：保留原上下文，直接结束本次运行。

## 压缩摘要实时流式呈现

压缩请求的原始消息仍然只存在于 Trace 中，唯一的例外是正在生成的摘要：它以普通的 `partial_text`（不产出流式消息的 LLM 实现则为完整 `text`）在成对的压缩事件之间上行。整个过程不涉及新的协议类型，Trace 的内容也没有变化。

- Web App 的压缩行**默认折叠，与思考块完全一致**：summarize 压缩一开始就带上折叠箭头，摘要在折叠的正文内流式写出（沿用思考块的 `md-body` 样式与同一个流式渲染器），读者展开即可实时观看或事后阅读。标签由核心所用的同一个宽松抽取器剥掉，因此仍在流式过程中的摘要读起来就是正文。历史重建从压缩区间已记录的助手输出读回同一段文本，因此重新加载后看到的与实时观看者看到的一致。
- 由于这段文本就是普通的流式消息，服务端的实时尾巴（live tail）也会记录它：在压缩过程中加入或刷新页面，能接上此前已生成的摘要前缀，而不是从空白开始。
- CLI 保留它那一行压缩进度提示，不打印流式摘要的任何内容。
