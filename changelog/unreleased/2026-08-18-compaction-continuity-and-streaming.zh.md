# 压缩：悬空区间的修复、按打断流程收场的失败与流式摘要

- **Date:** 2026-08-18
- **Type:** fix
- **Scope:** `core`, `server`, `web`, `cli`
- **PR:** [#329](https://github.com/Prism-Shadow/penguin-harness/pull/329)
- **Issue:** [#288](https://github.com/Prism-Shadow/penguin-harness/issues/288), [#290](https://github.com/Prism-Shadow/penguin-harness/issues/290)

[English](2026-08-18-compaction-continuity-and-streaming.md)

修复了两个压缩缺陷，并让压缩横幅显示实时的摘要文本。被进程意外终止留下的悬空压缩区间会在会话恢复时得到修复，压缩之后发出的消息不再因刷新而消失，过期的 `(unknown tool)` 卡片也随之消失；被放弃的压缩现在按普通的打断流程结束本次运行，并在下次触发时补做；摘要则由压缩区间自己的文本消息承载，在写出的同时抵达 Web App，不引入新的事件类型。

## 悬空的压缩区间在恢复时自愈

压缩进行到一半时进程死亡，会在分片里留下一个没有对应结束事件的 `compaction_begin`。核心的重放能够容忍这个悬空事件，并把后续对话继续追加到同一个文件，但每一个无状态读取方都会把这一对事件之间的消息当作压缩内部内容，于是压缩之后发出的一切都会在重新加载时消失；等到后来某个 `compaction_end` 在 Task 中途把状态解开，工具输出便会因为其调用被吞掉而渲染成 `(unknown tool)` 卡片。

- `resumeTrace` 会报告这个未配对的 begin，`resumeSession` 则在任何新记录落盘之前追加一条合成的、标记为 aborted 的 `compaction_end`，使文件对此后每一个读取方都是良构的。修复是幂等的，健康的 Trace 会被跳过。
- 各读取方另外还会在几个无歧义的信号上自行关闭过期区间——另一个 `compaction_begin`（区间从不嵌套）、一个 `abort` 事件（引擎总是先关闭这一对），以及轮转产生的 `session_meta`——Web 侧的 reducer、服务端的窗口扫描器与 Trace 分析流程都是如此，让在修复之前就已受损的 Trace 仍然可读。
- 服务端扫描器的缓存版本随之提升（`CACHE_VERSION` 2），已缓存的 `page_stats` 记录会按新的边界规则重新计算。

## 被放弃的压缩结束本次运行、留待补做

Task 中途的压缩一旦失败，此前的循环会陷入一个说不清的状态：整个运行要么在压缩之后空手而归地结束，要么只带着几条光秃秃的 `[tool error]` 修复输出继续，而模型并没有收到任何据以行动的指示。

- Task 中途的压缩失败或被中止时，现在按普通打断的同一套流程收场：本轮尚未了结的状态按既有的「是否已提交」规则转入 carry-over（[#85](https://github.com/Prism-Shadow/penguin-harness/issues/85)），以 `abort` 事件结束本次运行（失败一路的原因为 `compaction failed`），下一条消息把 carry-over 与用户输入合并重发——阈值依然超标，压缩在那里再次触发。
- Task 边界上的压缩失败一如既往：保留原上下文，直接结束本次运行。

## 压缩摘要实时流式呈现

压缩请求的原始消息仍然只存在于 Trace 中，唯一的例外是正在生成的摘要：它以普通的 `partial_text`（不产出流式消息的 LLM 实现则为完整 `text`）在成对的压缩事件之间上行。整个过程不涉及新的协议类型，Trace 的内容也没有变化。

- Web App 的压缩横幅会在标题下方展示正在写出的摘要，尾部截断，并用核心所用的同一个宽松抽取器剥掉标签；压缩尘埃落定之后，完整文本会折叠进一个可展开的正文区域。历史重建从压缩区间已记录的助手输出读回同一段文本，因此重新加载后看到的与实时观看者看到的一致。
- 由于这段文本就是普通的流式消息，服务端的实时尾巴（live tail）也会记录它：在压缩过程中加入或刷新页面，能接上此前已生成的摘要前缀，而不是从空白开始。
- CLI 保留它那一行压缩进度提示，不打印流式摘要的任何内容。
