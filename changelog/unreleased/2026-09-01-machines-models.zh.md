# 机器拿到它的 Agent 所需的模型凭据

- **Date:** 2026-09-01
- **Type:** feature
- **Scope:** `server`
- **PR:** [#575](https://github.com/Prism-Shadow/penguin-harness/pull/575)

[English](2026-09-01-machines-models.md)

在一台机器上运行的 Agent，是**从那边**去调模型端点的，依据的是**那台机器的**配置。因此一台没有凭据的机器是连上了却用不了：在这边选好模型、到那边开 Session，会以「Model is not in the Project config」失败。现在连接一台机器时，会把使用它的那些 Project 的模型配置一并交过去。

## 交给哪些 Project，以及路由为何归属于 Project

只交给本服务端上确实把该机器列入自己名下的 Project。机器是共享的——一台主机、一份程序，谁想用谁纳入——但凭据不是：它属于持有它的那个 Project。正是这个不对称，决定了 machines 路由为什么要放在 Project 之下。

在这边编辑模型时也会向外同步，同步到所有本应拥有它的机器——整表保存、项目设置里切换默认模型、通过提供商登录铸造的密钥，三条路径都汇入同一个后续动作，所以无论改动从哪条路来，机器都会知道。这个过程不被等待：编辑一把密钥的人，不该是等一组 ssh 隧道的人。同步进行中到达的改动不会被丢掉：本次结束后再跑一次收尾同步，读的是那一刻的配置。

## 是合并，不是覆盖

机器那侧的 `PUT /models` 是整表替换，因此只存在于对面的条目会被原样回送——但**不带** `apiKey`，因为省略它就保留已存的值，而 GET 读回的密钥本就是打码的。发生冲突时以本侧为准。有人手工配过的机器保住它原有的东西，不会悄悄丢掉一把本服务端从未见过的密钥。

只发送值得携带的条目：带内联密钥或自有 base URL 的条目是机器不可能已经有的，而裸的目录条目是每台服务端自己都会播种的预设。

## 走隧道，以那台机器的管理员身份

密钥在转发内部送达机器自己那个需要鉴权的 `PUT /models`，由它写入 `.project_config.toml`，权限 0600——能做这件事的人本就有到那台机器的 ssh，也就本就能读那个文件。用一次普通的 API 调用而不是一段远端脚本，是因为校验、让缓存的运行时失效、通知已打开的标签页，都是那个端点在做的事。

机器拒绝的项目——id 不合它自己的规则、表它不接受——会被报告并跳过，后面的项目照常写入；只有机器不可达才会让整次同步失败。同步失败**如实报告，但从不致命**：连接日志里写的是机器自己说的话，机器仍然保持连接。不会因为后面一步没做成，就让已经在它上面的东西变成错的。
