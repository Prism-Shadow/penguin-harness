# 图片可以发进来，生成的文件可以发出去

- **Date:** 2026-08-26
- **Type:** feature
- **Scope:** `server`, `docs`
- **PR:** [#496](https://github.com/Prism-Shadow/penguin-harness/pull/496)

[English](2026-08-26-messaging-media.md)

粘贴进飞书或 Telegram 的图片现在会真正送达智能体，而不再只收到「仅支持文本」提示；一次运行结束后，回复中点名的文件也会跟着发进会话。两个方向都走既有的渠道连接器接缝，第三个渠道按同样的方式实现即可。

## 入站图片

- 入站图片会转成与网页输入框完全相同的输入：图片说明文字（渠道有的话）作为用户文本，随后每张图片一个 `image_url` 部分，内容为 base64 `data:` URL。不支持视觉的模型会像处理粘贴图片那样把它们折叠成 Scratchpad 文件。
- 只有**图片**消息的说明文字才算作该消息的文本。Telegram 的文件、视频、音频同样带说明文字，而它们的字节并不会送达——把图片以「原图」拖进来就会变成 `document`——仅凭说明文字运行只会让模型对一个它从未收到的文件侃侃而谈。这些类型仍然收到「暂不支持」提示。群聊中图片说明文字里的 `@` 机器人前缀，与文本消息同样会被剥离。
- 飞书通过消息的 `image_key` 调用 `im.v1.messageResource.get` 取图；Telegram 取 `message.photo` 中最大的一档，经 `getFile` 与文件端点下载，并把 `message.caption` 作为该消息的文本。
- 连接器接缝携带的是**延迟拉取的句柄**而非字节：被重复投递的消息在任何下载发生之前就被丢弃；上限也随拉取一起传入——超限的传输在越界的那个字节上就被拒绝，而不是先缓冲下来再测量。
- 上限沿用服务端既有的内联图片上限（`INLINE_IMAGE_MAX_BYTES`，20MB）：这些图片与输入框粘贴的图片一样进入对话和 Trace；该数值也正好等于 Telegram 对机器人下载的 20MB 限制。
- 总量上另有一道约束：每个绑定一个滚动窗口的字节预算（十分钟两张满额图片）。单张上限一直都在，但没有总量预算时，任何能私聊机器人的人都可以往一个 Session 的 Trace 里写进几百 MB base64，而该文件在每次翻阅历史、每次恢复 Session 时都会被整体读进单个字符串。网页输入框要达到同一个天花板还得先通过鉴权，这条路径则完全没有鉴权。超出预算的那张有自己的提示语——图片本身没问题，只是短时间内太多了。
- 图片超过单张上限、超出窗口预算与渠道拒绝下载分别回复**三种不同的**双语提示，三种情况都不启动 Task——让模型去回答一张它根本没收到的图片，只会得到一本正经的胡说。因机器人自身权限被拒时，提示会点名所需权限并带上渠道给出的授权链接，于是这件事是十秒钟的操作，而不是一段要去翻的日志：在飞书上，「接收消息」与「读取消息中的资源文件」是两项独立权限，应用完全可能只有前者。
- 「暂不支持」提示改为点明现在支持什么。表情、语音、视频与文件仍收到该提示；入站文件不在本次范围内。

## 出站文件

- 一次运行结束时，回复中**提及且由本次运行产出**的文件会跟在文本之后发进会话：回复中形如路径、能解析到 Workspace 之内、确实存在、且修改时间不早于本次运行开始的片段，出现在回复的任何位置皆可——于是送达的是智能体指出的产物，而不是这次运行顺手写下的全部文件。Web 端「文件卡片」只认行内代码，用在会话里过于严格——把文件名写在普通句子里的回复将一个文件都发不出来。
- 「修改时间」这一条不是锦上添花，而是宽松匹配得以成立的前提。回复的内容可以被会话里的任何人引导，仅凭「提及」判断的话，群成员问一句「secrets.json 里是什么？」，那句「我不会把 secrets.json 贴在这里」本身就会把文件传上去——拒绝即泄露。而且「本次运行写下的文件」本来就是这个功能一直宣称的含义。
- `./chart.png` 与 `.eslintrc.json` 现在能被识别了。此前边缘标点的裁剪把开头的点和结尾的点一并去掉，于是前者变成了 Workspace 之外的绝对路径，后者变成了一个并不存在的文件——而「已保存到 ./out/report.pdf」正是回复交付文件时再普通不过的写法。
- 图片（`.png/.jpg/.jpeg/.gif/.webp`）按图片发送，图表因此能在会话里直接显示；其余按文件发送。类型由**读取时实际拿到的文件名**决定，而不是回复中写下的那个名字：Workspace 内一个 `report.png -> report.pdf` 的符号链接（再常见不过的「最新版」写法）否则会被当作图片发到图片端点，却带着 `report.pdf` 的文件名，Telegram 直接拒收。飞书先上传 `im.v1.image.create` / `im.v1.file.create`，再用返回的 key 发消息；Telegram 以 multipart 调用 `sendPhoto` / `sendDocument`。
- 路径解析、越界检查与存在性判断都取自 Files 面板所用的同一个 `WorkspaceFilesService`——离开 Workspace 的路径（无论经由 `..` 还是符号链接）在那里被拒绝，而不是由桥接层里另一份规则副本来判断。
- 上限：每次运行最多 5 个文件，单张图片最大 10MB、单个文件最大 30MB——取两个渠道各自限制中更紧的一个（飞书图片 10MB / 文件 30MB，Telegram `sendPhoto` 10MB / `sendDocument` 50MB）。被上限拦下的文件会在会话中点名；因数量上限截断时会说明还剩多少个未发送。
- 被提及的文件凡是没送到，现在都会在会话中说明：超过单个上限、超出数量上限、Workspace 内没有该文件、渠道拒绝上传——最后一种此前只写进 `error_records`，而那是会话里的人打不开的地方，于是这个功能看上去就是「不管用」。唯一有意保持沉默的是「本次运行没有写过的文件」：回复里提到自己读过的配置文件属于常态，逐一播报只会把真正要紧的提示淹掉。
- 发送与文本共用同一条按绑定串行的队列，因此文件排在点名它们的那条回复之后，且顺序与回复中出现的顺序一致；上传失败记入错误记录，不会中断其后的文件。

## Telegram 的文件为何一个也没发出去

- `sendPhoto` / `sendDocument` 实际发出的是 17 个字节的字符串 `[object FormData]`，`content-type` 为 `text/plain`，于是 Bot API 回答「there is no document in the request」。启动入口会把 `globalThis.fetch` 换成 **undici 的**，好让出站流量走代理调度器；而 undici 的 fetch 会用**它自己那份** FormData 类去做品牌检查，`new FormData()` 拿到的却是 Node 内置的那一个——两个不同的类。检查失败，请求体便退化成了 `String(body)`。
- 现在 `fetch` 与 `FormData` 都从 undici 导入，成对出现，并在构造处留了注释说明原因：只把 `FormData` 换成 undici 的、却仍调用 `globalThis.fetch`，会原封不动地把同一个 bug 反过来再犯一遍。代理不受影响——undici 的 fetch 每次调用都会解析全局调度器，这正是 `net/proxy.ts` 所依赖的契约。`Blob` 无需改动：`globalThis.Blob` 就是 node:buffer 的 Blob，undici 的 FormData 接受它。
- 这个故障在生产环境 100% 复现、在 CI 中 0% 复现，因为 `installGlobalProxyDispatcher()` 只在真实的服务端入口里执行——测试中 `globalThis.fetch` 仍是运行时自带的那个，而那种搭配恰好能工作。因此这次的防线是一个**按生产方式构造传输层**的测试：把 undici 的全局调度器指向本地 `http.createServer`，然后断言实际到达的字节——`multipart/form-data`、`document` 分段、文件名与文件内容。两种搭配错配都会让它变红。

## 两个飞书适配器此前报不出来的故障

- **流式**请求被拒时，原因藏在没人读过的响应流里：`im.v1.messageResource.get` 以流的方式发起，出错时 axios 交还的是响应流而非解析好的 `{code, msg}`，直接从错误对象上读只能得到「Request failed with status code 400」——恰恰是用户无法据以行动的那一句，把他们能行动的那一句盖住了。现在会把响应体读完并解析，像普通调用一样报出 `code`、`msg` 与 `log_id`。
- 该适配器发出的每一次调用现在都有超时。Lark SDK 默认的传输层是一个不带 `timeout` 的裸 `axios.create()`，而一个 Session 的全部出站消息共用一条串行队列——于是一个被服务端接受却永不作答的请求，会把该 Session 之后的每一条回复、审批提示与文件全部无声地卡住，既没有错误记录也没有状态变化，直到绑定被重新开关或服务器重启为止。Telegram 侧从落地起两个方向就都有超时。
