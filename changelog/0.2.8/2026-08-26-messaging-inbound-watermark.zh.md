# 重投的聊天消息跨越服务端重启也不会被运行两次

- **Date:** 2026-08-26
- **Type:** fix
- **Scope:** `server`
- **PR:** [#493](https://github.com/Prism-Shadow/penguin-harness/pull/493)

[English](2026-08-26-messaging-inbound-watermark.md)

消息桥会丢弃绑定已经处理过的入站消息，使渠道重投同一事件时不再重新发起一次 Task。此前这份记忆只
存在于进程内：桌面端重启或运行时热替换会将其清空，而渠道跨重启的重投——连接一打开渠道就会这么做
——会让该消息第二次运行。于是同一个 Session 在聊天中与网页端各答复了两次。

## 绑定行上的水位

`messaging_bindings` 新增了 `last_inbound_message_id`：最近一条被处理的入站消息的渠道 id。连接打
开时、事件流尚未投递任何内容之前，`MessagingBridge` 会把存储的 id 折回该绑定的内存环。二者是同一
份记忆而非两道防线：环在进程存续期间保留最近 64 个 id，行在绑定存续期间保留最后一个。

水位由一条独立的 `UPDATE` 推进，且只在消息已经变成 Task——或者已被「仅支持文本」的提示答复——之后
才执行。把消息所在会话记为该绑定回复目标的那条写入仍然排在最前，因为出站转发要读取这个会话；水位
则无法与它同行：忙碌 Session 排队的后续输入只存在于内存中，因此抢在工作之前落盘的 id，会在进程恰
好死于这段间隙时比它所代表的工作活得更久，上面那段折回又会让渠道的重投彻底空转——消息永远不会运
行，也永远不会有任何答复。而发起失败时这个 id 根本不会被写入，重投于是会把这条消息真正跑起来。

行只记住一个 id，而这正是飞书长连接所需要的全部：该事件流会重投它未曾见到确认的事件，而 SDK 只在
消息桥的处理函数返回之后才确认每一条，因此进程结束时最多只有正在处理的那一条尚未确认。Telegram 跨
重启则不重投任何东西——它的轮询在把更新交给处理函数之前就已推进偏移量，而新连接会把无人连接期间到
达的内容一并排空——所以在这个渠道上，这一行只是被带着走，从不会被查阅。

把绑定改存到**另一个**机器人账号时，水位会与记住的会话一同清除——另一个账号的消息 id 对新账号毫无
意义。

## 去重记忆不再按时间过期

内存环此前同时按数量和十分钟的时限来限定自身。时限是为了容忍会复用消息 id 的渠道；而两个渠道都不
复用——飞书的 `om_*` 全局唯一，Telegram 的键是 `chatId:message_id`，其计数只增不减。既然没有复用
需要防范，过期就只会遗忘仍然欠着的重投，而渠道在长时间中断后恢复事件流时，会重投它未曾见到确认的
消息，无论那已经过去多久。数量上限保留，并由它来约束这份记忆的大小。
