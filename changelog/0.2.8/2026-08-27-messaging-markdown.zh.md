# 转发的回复以排版到达，而不是 Markdown 源码

- **Date:** 2026-08-27
- **Type:** feature
- **Scope:** `server`, `web`, `docs`
- **PR:** [#519](https://github.com/Prism-Shadow/penguin-harness/pull/519)
- **Breaking:** yes — 升级后存量绑定即开始渲染 Markdown，每条转发消息的样子都会改变；新增的按绑定开关可将其关闭

[English](2026-08-27-messaging-markdown.md)

消息桥此前在所有渠道上都以纯文本转发助手回复——Telegram 的 `sendMessage` 不带 `parse_mode`，飞书用
`msg_type: "text"`，QQ 用 `msg_type: 0`——因此模型写的 Markdown 到达聊天时就是字面的 `**bold**`、
`## heading` 和裸代码围栏。新增的按绑定偏好 `renderMarkdown` 会将其按各渠道自身的标记语言渲染。它
**默认开启**：被修正的正是原先的行为，所以修正后的行为才是默认值。

## 细节

- 该选项存为 `messaging_bindings.render_markdown`，与 `enabled` 及另外两个送达偏好并列成列，而不是
  放进 `config_json`。`renderMarkdown` 同时加入 `FeishuBindingInfo` / `TelegramBindingInfo` /
  `QQBindingInfo` 与三个 PUT 请求体；省略该字段保持已存值，未表态创建的绑定即为开启。
- 「把回复读成 Markdown」与「决定长回复可以从哪里切开」是共享的（`runtime/messaging/markdown.ts`，
  与 `media.ts` 并列）：一条回复包含哪些构件是文本本身的事实，而切穿构件在每个渠道上都会损失它。
  解析器是 `unified` 之上的 `remark-parse` + `remark-gfm`，即 `packages/web` 本就用来渲染 Markdown
  的那套，因此同一条回复在网页记录与聊天里读法一致。
- 渲染则按渠道各自实现，因为三个平台在两种标记语言、三套转义规则之上接受三个不同的子集：
  - **Telegram**（`telegram-html.ts`）使用 `parse_mode: "HTML"`。粗体、斜体、删除线、链接、行内
    代码、带语言的代码块与引用均可渲染。它没有标题、列表和表格标签，因此标题渲染为一行粗体，列表
    符号作为文本保留（`• `、`1. `，每层缩进两个空格，任务项用 `☐`/`☑`），表格改用 `<pre>` 块承载
    其各行。
  - **飞书**（`feishu-card.ts`）使用 `msg_type: "interactive"`，承载 JSON 2.0 卡片的
    `{"tag": "markdown"}` 组件，可渲染 1–6 级标题、粗体、斜体、删除线、行内代码与代码块、嵌套
    列表、引用、分割线、链接和表格。该组件每张表最多显示 5 行数据、每条消息最多 4 张表，因此超限的
    表格改以代码块发出，而不是静默丢行。
  - **QQ**（`qq-markdown.ts`）使用 `msg_type: 2` 自定义 markdown，单聊与群聊场景已对全部机器人开放。
    标题、粗体、斜体、删除线、列表、引用、分割线和链接均可渲染；行内代码、代码块和表格则完全没有
    对应语法，因此代码块按转义后的普通文本行到达，表格按其行到达。
- 只是「看起来像标记」的文本在每个渠道上都作为文本到达：`5 < 6` 与 `a & b` 在 Telegram 和飞书上转为
  实体、在 QQ 上加反斜杠转义，代码块里的 `<script>` 仍然是代码块里的 `<script>`，模型自己写下的裸
  HTML 只展示、不转发。链接的协议若非聊天可打开的，则保留其文字、仅失去可点击性。
- **渠道拒绝的格式化发送会退回为同一条消息的纯文本发送。** Telegram 对它无法解析的 HTML 返回 400，
  飞书与 QQ 各自返回自己的拒绝码；每个连接器都会用模型自己的 Markdown 源码重试一次，因此该设置只
  可能损失排版，绝不会损失回复。只有「被拒绝」才重试——超时或连接中断有可能其实已经送达，重发会让
  回复在聊天里出现两次。在 QQ 上，该重试还会额外占用一条入站消息所提供的四条被动回复之一，因为重复
  的 `(msg_id, msg_seq)` 组合会被拒绝而非去重；与消息体无关的拒绝则根本不重试。
- 分段改为随格式变化。超过 `MESSAGING_TEXT_CHUNK_CHARS` 的回复先在顶层块之间切分，再在那个自身过长
  的块内部切分——在段落的行内片段之间、沿引用或列表自身的行——而跨消息的代码块会在每一片里重新加上
  带语言的开合围栏。`linePerMessage` 通过保持「逐字面」与之共存：每一行各自转换，因此不构成完整
  构件的一行就按它本身的文本到达。
- 在既有的 `TelegramApiError` 之外新增了 `FeishuApiError` 与 `QQApiError`，使三个适配器都能区分
  「平台答复的拒绝」与「从未完成的请求」——这正是退回机制所依赖的区分。
- 消息桥发送链的每一步现在都会先确认自己的条目仍持有该 Session 的连接，与 `observe` 一贯的做法一致。
  一次运行的最后几条消息及其随附文件都排在这条链上，而硬停止会在它们还在排队时丢弃条目并关闭数据库。
- 在绑定编辑器中，该选项是另外两项之下的第三个 `DeliveryOptionRow`，其说明按渠道分别置于标签旁的
  「?」之后——某个渠道能显示什么，正是读者做决定所需要知道的全部。

## 兼容性

新增列在升级与降级时的表现见[向后兼容](2026-08-27-backward-compatibility.zh.md)。

升级后第一次打开时，所有存量绑定即开始渲染 Markdown。用户无需做任何事，也没有任何数据被改写，但这是
每条转发消息都可见的变化：原先以 `**bold**` 到达的回复现在会真的加粗，标题按渠道渲染为一行粗体或真正
的标题，代码块在 Telegram 与飞书上以等宽呈现、在 QQ 上作为普通文本行到达。在绑定编辑器中关闭该开关，
即可完全恢复原先的纯文本转发。
