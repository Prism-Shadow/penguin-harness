# 消息绑定会说出它实际看到了什么

- **Date:** 2026-08-26
- **Type:** feature
- **Scope:** `server`, `web`
- **PR:** [#505](https://github.com/Prism-Shadow/penguin-harness/pull/505)

[English](2026-08-26-messaging-delivery-observability.md)

「给机器人发了消息，什么也没发生」有三种完全不同的成因，却只有一种表象。可能渠道根本没有把消息投
递过来；可能消息到了而 Task 没能开始，被消息桥吞进了一条错误记录；也可能 Task 跑完了而回复没能发
出。三者在聊天里都表现为沉默，而绑定面板在每一种情况下都只显示 `connected`，再说不出别的。

## 运行时状态拿到了流量，而不只是连接

`MessagingRuntimeStatus` 新增三个字段，都由活跃连接填写：

- `lastInboundAt`——该绑定最近一次接受入站消息的时间。尚未收到过时该字段缺席，而这正是值得补上的读
  数：**已连接、无报错、什么也没收到**，恰恰就是渠道扣着消息不投递时的样子，而此前产品里没有任何地
  方能说出这一点。
- `lastDeliveryError`——最近一次**在消息被接受之后**发生的失败，形如 `{at, stage, detail}`。
  `stage: "inbound"` 表示消息到了而 Task 没能开始；`stage: "send"` 表示 Task 跑完而回复没能发出。
  两者指向不同的排查方向，因此明确报出阶段，而不是揉成一句话。后续的成功不会把它清掉——否则一次时
  有时无的失败会被下一条普通消息抹去——所以面板那一行带上了失败自身的时间，过期的记录读起来就是过
  期的。
- `lastConnectionError`——最近一次连接失败，形如 `{at, detail}`，且**在连接恢复之后依然保留**。
  `lastError` 属于 `error` 状态，状态一离开就被抹掉；于是一个反复断连又恢复的连接器——两个程序在同
  一个 Bot Token 上轮流占用时就是这样——在任何一次快照里都读作 `connected`，只给读者留下症状而没有
  原因。

三者都只存在于进程内，且作用域是一条**连接**，而不是一次服务端运行：每次（重新）建立连接都从空开
始，重新启用连接或保存一次凭证都会开启一条新的。文案是按这个作用域写的——空的到达行写作「本次连接
建立以来还没有收到过消息」，而不是断言消息从未到达过；下面那条常见问题也只把它当作「读到它之后再发
的那条消息」的证据。

绑定面板把三者都收到了连接开关下方，与既有的连接错误行并列，双语。到达行刻意没有限定在 `connected`
才显示：它报的是流量而不是连接本身，而 `connecting`（机器人正在握手）与 `error`（Token 反复被抢）
恰恰是读者最需要知道这个机器人到底有没有收到过东西的时候。

## 消息类错误归属到所属 Project

`MessagingBridge` 此前记录每一次失败时只带 `sessionId`。而 `GET /api/projects/:id/usage/errors`
是按 project 过滤的，没有 project 的记录属于**未归属**——只对管理员提供。于是普通成员在产品的任何
地方都看不到自己绑定的失败。现在每条记录都带上了该 Session 的 `projectId` 与 `agentId`，取自消息桥
本就持有的 sessions 索引。

## 新增一条「群里还是收不到」的 Telegram 常见问题

紧挨着 Group Privacy 那一条：先讲怎么读到达行，再讲读对之后该查什么。它写明这一行只覆盖当前这条连
接，所以复测意味着重新发一条消息，而不是去信一行刚被重新启用清零过的字；如果重新发的这条仍然什么也
没显示，那就是 Telegram 没有投递，本地再做什么也无济于事。该条目写清了要检查什么——机器人是否仍在
群里、改动 Group Privacy 之后必须把机器人移出再重新拉入（已有的群不会自动生效）、以及是否有别的东
西在用同一个 Token 轮询——并说明 Telegram **频道**（channel）贴文不受支持，本连接只处理群聊与私聊。

「一个 Token 只能被一个程序使用」那一条则补上了排查这类问题时最费时间的陷阱：**手动执行的
`getUpdates` 也算那个「另一个程序」。** 跑它之前必须先停用连接；而且手动查看积压也可能把它丢掉——任何带
`offset` 的调用都会确认它之前的全部更新，连接器自己的下一次连接也会清空积压——因此复测需要重新发一
条新消息。
