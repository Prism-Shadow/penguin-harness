# QQ 成为继飞书、Telegram 之后的第三个消息渠道

- **Date:** 2026-08-27
- **Type:** feature
- **Scope:** `server`, `web`, `docs`
- **PR:** [#501](https://github.com/Prism-Shadow/penguin-harness/pull/501)

[English](2026-08-27-messaging-qq.md)

Session 多了第三个可绑定的渠道：QQ 机器人，接在飞书与 Telegram 早已使用的同一套连接器接口
后面。凭据是 QQ 开放平台的 App ID 与 App Secret，入站消息走平台的 WebSocket 网关，因此绑定
它不需要任何公网回调地址。这个渠道没有照抄前两个，因为 QQ 不允许机器人自由发言：它发出的每
一条消息都是对用户几分钟内发来的某条消息的回复，下面每一条送达规则都由此而来。

## 细节

- 传输层落在 `qq-api.ts`：带提前刷新的 app access token 交换（无论一次涌入多少发送，只换一
  次），两个发送接口，以及网关会话——以 `GROUP_AND_C2C_EVENT` intent 鉴权、心跳、断线续传，
  以及决定「续传还是重新鉴权」的关闭码。会话若不再承载流量却也没有关闭——握手迟迟不来，或者
  心跳不再被确认——会被断开并按退避重连，而不是停在 `connected` 上什么也收不到。它以可注入的
  工厂形式落地，因此测试是对着假实现跑的，不碰网络。
- 渠道策略落在 `qq-connector.ts`。`C2C_MESSAGE_CREATE`（单聊）与 `GROUP_AT_MESSAGE_CREATE`
  （群聊 @ 机器人）都归一到 bridge 的入站结构；同一 intent 携带的「群内全部消息」事件被丢弃。
- **被动回复额度。** 一条入站消息在单聊中最多支撑 4 条回复、群聊 5 条，且只在数分钟的窗口内
  有效。一次运行中前 `budget - 1` 条完成的助手消息随完成即时发出，其余的暂存并合并为最后一条
  发出——长回复是被合并，而不是被截断。审批提醒与之共享额度，在即时槽位用尽时占用预留的最后一
  条：停在审批上的运行不会走到「结束」，因此等待运行结束的提醒将永远等不到。
- 这套记账按会话（聊天）分别持有，且活不过开启它的那条连接：把绑定关掉、或把它改指到另一组
  凭据，都会把它忘掉，因此暂存的内容不会送进一个 Session 已经不再应答的聊天里。被重复投递的
  `msg_id`——平台为保证送达而有意重发——不算新额度；而被平台拒收的一次回复会把文本留给下一条
  入站消息的额度，而不是丢掉。
- QQ 上的 `linePerMessage` 收敛到该回复额度，而不是渠道无关的上限 20；实现方式是连接器接口上
  新增的可选 `replyBudget`。飞书与 Telegram 不声明该字段，行为未变。
- **不做任何主动推送。** 没有可回复对象的发送——在网页端发起的对话，或窗口关闭之后的回复——会
  带着可读的原因被拒绝，而不是改用主动消息：后者被限频、需单独审批，且任何用户都能自行关闭。
  面板把这条规则直接写在界面上而非折叠区里——不知道这条规则的人会把该渠道读成「坏了」。
- 该渠道拒绝外发文件并给出原因：平台的富媒体接口要求为文件提供公网可达地址，这与当初排除
  webhook 模式的是同一个约束。入站媒体暂不读取。
- `/qq` 路由子树带着与其他渠道一致的动词集合落地（GET / PUT / state / DELETE / test /
  test-message）。账号身份是 App ID，因此「一个账号同时只能被一个 Session 启用」对 QQ 机器人
  的适用方式与飞书应用完全相同——启用时如此，把一条已启用的连接改指到别人的机器人上的保存
  同样如此。
- 绑定编辑器的渠道选择器多了第三项，QQ 带着自己的表单区、创建步骤、回复额度说明与常见问题条目
  落地，中英词典成对补齐。
