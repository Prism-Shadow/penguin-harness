# 消息回复可以每行一条送达

- **Date:** 2026-08-26
- **Type:** feature
- **Scope:** `server`, `web`, `docs`
- **PR:** [#494](https://github.com/Prism-Shadow/penguin-harness/pull/494)

[English](2026-08-26-messaging-line-per-message.md)

转发的助手回复此前无论怎么写都以一条消息抵达聊天。现在每份绑定多了一个选项，可以改为每个非
空行各自一条消息——写成多句台词的角色扮演回复本该以这种形态到达。默认关闭，关闭时的行为与此
前逐字节一致。

## 细节

- 该选项存为 `messaging_bindings.line_per_message` 列，与 `enabled` 并列，而不是塞进
  `config_json`：后者是渠道自己的凭据文档、由其连接器拥有，而这个选项对每个渠道的含义完全
  相同。
- `linePerMessage` 加入 `FeishuBindingInfo` / `TelegramBindingInfo` 与两个 PUT 请求体。它是随
  Save 生效的普通表单字段，没有独立路由；省略则保持已存值，新建的绑定默认关闭。
- 拆分刻意保持字面：每个非空行成为一条消息，代码围栏之内同样如此；空行与行尾空白一并丢弃，行
  首缩进保留——缩进的代码块到达时仍然可运行。拆出的每条消息仍走渠道的长度分段，因此超长的单行
  会被分段而不是被拒绝。
- 一条回复最多拆成 `MESSAGING_MAX_LINE_MESSAGES`（20）条消息，这个数取自最紧的渠道的单聊突发
  额度——Telegram 对同一会话每分钟约 20 条以上就会返回 429。这份额度按真正发出的消息计，含长度
  分段在内，而不是按行计，长回复因此无法绕过它；超出额度的行合并为最后一条，而不是被丢弃。这样
  一条回复的各条消息之间相隔一秒发出，正是同一份额度描述的速率。
- 送达的顺序与失败都有兜底：审批提醒排在已在发送的内容之后，不会插进一条回复的两行之间；被渠道
  拒绝的那条消息只损失它自己——错误会被记录，回复的其余部分照常送达。
- 群聊规则不变：一次运行的第一条外发消息回复到入站消息，其余为普通发送，因此多行不会变成多个
  引用头。该选项只作用于转发的助手回复——审批提醒、「仅支持文本」提示与测试消息都不受影响。
- 绑定编辑器中，该选项以 `Switch` 收尾表单，两个渠道通用，由既有的 Save 保存，说明放在标签旁
  的「?」之后。
