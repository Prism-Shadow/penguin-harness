# Session 接入消息软件机器人（飞书、Telegram）

- **Date:** 2026-08-25
- **Type:** feature
- **Scope:** `server`, `web`, `docs`
- **PR:** [#464](https://github.com/Prism-Shadow/penguin-harness/pull/464)

[English](2026-08-25-feishu-session-bridge.md)

新增消息渠道接入，飞书（Lark）与 Telegram 为首批两个渠道：Session 接入自建飞书应用或 Telegram 机器人后，发给机器人的消息以普通用户输入进入该 Session，AI 完成的回复再转发回对应会话。一个 Session 每个渠道至多保存一份配置（两份可并存），其中至多一个处于启用状态——启用的那个持有在线连接。

## 细节

- 两处管理入口共用同一个渠道感知的绑定编辑器：会话行菜单的「消息软件绑定…」对话框，与对话页右侧面板栏新增的「消息软件」停靠面板（排在轨迹面板之后，管理当前会话的接入配置）。渠道选择器在两个渠道的表单之间自由切换，两份配置各自独立保存、各自显示自己的已存 / 启用状态——飞书填 App ID / App Secret / API 域名，Telegram 只有一条 Bot Token。表单以连接控件开头——「启用连接」开关与实时连接状态、两个探测按钮，其后是说明开关为何置灰的提示——凭据字段排在它们下方，两个渠道的字段数量不同也不改变控件的纵向位置；该渠道的「前往开发者后台」链接挂在凭据字段右上角（与模型库「获取 API key」同口径），保存区下方是默认收起的折叠说明：建机器人步骤（末尾附该渠道的「前往教程」）、绑定后会发生什么、常见问题。
- 已存密钥按模型库管理 API key 的口径管理：字段始终留空，已保存的值只以全站统一掩码显示在下方一行，掩码旁的「清除已存」勾选在保存时生效（新输入的密钥优先于已勾选的清除）。渠道连接启用期间拒绝清除——勾选框置灰并在界面上写出原因，服务端返回 409 `messaging_disable_before_clear`——在线连接因此永远不会跑在存储已经没有的凭据上。没有解绑按钮：移除凭据就是清除。
- 保存与启用拆分为两件事：「保存」只保存凭据、从不建立或断开连接（唯一例外——已启用配置在保存新凭据时用新凭据重启连接器，存储配置与在线连接永不背离）；独立的「启用连接」开关用已存凭据即时建立或断开连接。启用在同一 Session 内互斥：另一渠道已启用时开关置灰并提示先停用它，服务端以 409 `another_channel_enabled` 拒绝。新配置默认停用；服务端启动只连接已启用的配置；会话行以一枚纸飞机标记启用中的连接（所有渠道共用同一图形，渠道名写在该标记的悬浮提示与读屏文本里），仅保存不标。
- 侧栏会话行的悬停按钮改形：归档保留为直接按钮，删除按钮换成实心三圆点「更多」按钮——点击即在按钮处打开该行的完整右键菜单（菜单新增了仅靠右键难以发现的配置类操作），删除移入菜单（仍为危险样式）。
- 服务端以带渠道判别列的 `messaging_bindings` 表存储配置，主键为 `(session_id, channel)`，跨 Session 唯一性按渠道内机器人账号计（409 `feishu_app_in_use` / `telegram_bot_in_use`），`enabled` 为存储的连接意图；并经渠道连接器接缝运行消息桥，持有已启用配置的那条入站事件连接：飞书走 SDK 的 WebSocket 长连接，Telegram 走基于 offset 的 `getUpdates` 长轮询（建立连接时先清空停用期间的积压；轮询瞬时失败按指数退避、每次故障只上报一次、恢复后自动回连）——两者都无需公网地址。入站文本以 `queueIfBusy` 按普通输入框口径发起 Task（无标记块、无特殊 sender，模型不知道消息来自消息软件）；其他消息类型收到双语「仅支持文本」回复；每条完成的助手消息在完成的当下各自镜像回最近的会话——一次运行中先写工具调用之间的进展、再给出答案，聊天里就按同样的顺序逐条收到，而不是结束时收到一整块；同一 Session 的发送串行排队，到达顺序与完成顺序一致，并按渠道文本上限分段（不超过 Telegram 的 4096 字符硬上限）；群聊中只有该次运行的第一条消息回复到原消息，其余为普通发送。有工具调用等待审批时发送一行指向 Web 界面的提醒。
- `/api/sessions/:sessionId/messaging` 下新增接口：渠道无关的 GET 列出该 Session 每一份已保存的渠道配置（以 `channel` 判别，逐行给出 `enabled` 与连接状态），加上每个渠道相同的动词集——`/feishu` 与 `/telegram` 各有 get / put / state / delete / test / test-message。PUT 携带该渠道的清除标记；密钥被清除过的配置在 state 开关处得到 400 `feishu_secret_required` / `telegram_token_required`。DELETE 整体删除某渠道的配置，仅为 API 完整性保留——Web 界面的移除入口是清除标记。Telegram 的机器人身份取 Token 冒号前的数字 id，换发 Token 不丢配置，清除密钥也保留这份身份。密钥在所有响应中掩码、留空重存时保持原值，读取与测试对任意 Project 成员开放、写入仅限所有者。删除 Session 连带删除其全部渠道配置。
