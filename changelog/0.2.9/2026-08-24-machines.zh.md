# 在 Machines 页面上，把服务端装到另一台机器

- **Date:** 2026-08-24
- **Type:** feature
- **Scope:** `server`, `web`, `desktop`, `cli`, `tooling`, `docs`
- **PR:** [#447](https://github.com/Prism-Shadow/penguin-harness/pull/447)

[English](2026-08-24-machines.md)

**Machines** 是 Models 之下的新页面：列出服务端自己 `~/.ssh/config` 里的主机，把当前这份 PenguinHarness 装到你选中的那台上。它取代了桌面端的 **Install Server on Remote Host** 菜单项——那一项只存在于 Electron 外壳里。

## 选一台主机

目标只来自 `~/.ssh/config`：读一次配置文本，不跑 `ssh -G`，不碰网络。`Host *` 这类模式条目会跳过，`Include` 的通配按 OpenSSH 的方式展开；文件永不被写。别名只在真正安装时才解析成用户、主机名和端口，而那一步交给 `ssh -G`，所以 `Match` 与通配继承的行为和 ssh 说的完全一致。

一份配置动辄声明上百条，所以主机是可搜索的选择器而不是列表。查询按**子序列**匹配（`gpu1` 能找到 `gpu-01`），命中的字符会高亮，计数会说明当前视图漏掉了多少条。

仅管理员可见：安装会用**服务端账号**的密钥拉起 ssh，并在另一台机器上写程序目录。连接带 `BatchMode=yes`——这里没有终端可供输入密码——密钥不通时原样展示 OpenSSH 自己的诊断信息。

## 装上去的是什么

这台服务端立足的那个 release，由常规安装器安装：远端在线运行 `install.sh` / `install.ps1`，钉在本机自己的底座版本上，经它自己的网络从 release 源（GitHub，或安装器测速选中的 OSS 镜像）下载标准产物——启动脚本、依赖库、Web 资源、内置运行时。ssh 通道只携带安装脚本本身。

若本机正在跑热推的版本，这份状态也一并过去：`hmr/harness.json` 和 store 以流的方式复制（本地 tar → ssh），远端下次启动就运行同一份推送的 platform、web 与 CLI。Machines 页面随之显示合成版本 `<base>+hmr.<sha>`。

底座相同则跳过下载；底座与推送状态都相同则什么都不做。远端最后拿到的和"普通安装 + 一次推送"留下的一样——程序目录、POSIX 上的 `~/.local/bin/penguin` 软链、数据根下的 `hmr/` 状态。不用 sudo，不写 systemd unit，不改 profile，数据根的其余部分从不被碰。

## 机器的身份

每台机器都有属于自己的 id：位于 `<数据根目录>/machine-id` 的 16 个字符（12 个随机字节的 base64url 编码），由运行在那台机器上的服务端铸造（包括本机），此后保持不变。选 base64url 是因为这个 id 会出现在路径、查询串与文件名中，而 `+` 与 `/` 在那些位置活不下来；取 96 位是因为各机器互不协调地各自铸造，衡量标准是生日界，即便一百万台机器发生碰撞的概率也在 1e-17 量级。凡是要被存下来的引用都应当指向它。ssh 别名做不了这件事：别名只是某一台机器配置文件里的一行，同一台主机在这里叫 `build-box`、在那里叫 `bb`，而同一主机的两个别名不过是一台机器的两个名字。别名仍然是**给人读**的；这个 id 才是它们背后的身份。

它搭乘状态探测已经在做的那一次往返，因此获取它不额外花费任何代价；同时它被记录在安装记录旁边，所以重启后无需再问一次。服务端从未启动过的机器还没有 id——没有任何东西为它铸造过——此时如实报告为空，而不是编一个出来。别名被改指到另一台主机时会返回不同的 id，并以较新的答案为准：一台机器的 id 永不改变，因此 id 变了就意味着机器换了。

## 本机，以及其他机器是否在运行

列表开头是**本机**——服务端自己所在的主机，以主机名标识，并显示它运行的版本与正在监听的端口。这两项都是就地读取而非探测（答案就在手边）；本机始终存在，且永远不是安装目标：服务端不会在自己正运行的程序目录上覆盖安装，因此它不出现在选择器里，对它 `POST …/install` 会返回 `409 self_install`。

其余每台已安装的机器都带有其服务端状态：**运行中**并附端口、**未运行**（程序在那里，但没有进程在服务）、或**连不上**并在背后保留 OpenSSH 自己的诊断信息。这里刻意没有单独的「ssh」状态——ssh 是传输方式，因此连不上的机器只呈现为一件事，而不是两个需要读者自行拼合的状态。

状态的代价是每台机器一次 ssh 往返，所以它从不在列表时获取，也从不针对整个 ssh config——只针对真正安装过的机器，且一次最多并发五台。页面按逐步拉长的节奏重探：15 秒、30 秒、45 秒、1 分钟、2 分钟、3 分钟……直到 10 分钟为止；一旦任何答案真的发生变化，立即回到 15 秒。该节奏位于页面而非服务端，因此最后一个标签页关闭后不会再有任何 ssh 被派生；另有**刷新**按钮，用于你已经知道情况有变、不想等的时候。

## 触达另一台机器

已安装的机器可以被**连接**：服务端经 ssh 把对端的 `penguin server` 拉起来，并持有一条 `ssh -N -L` 隧道。这让那台机器的文件系统与 API 从此处可达——工作区选择器可以浏览它的目录，其他任何指明了机器的调用也走同一条隧道，由本地服务端改写为 `/server/<machineId>/api/…`。

窗口始终不移动。这里没有「切换到该机器」这种模式，而且是刻意没有：它曾短暂存在过，随后被移除。把整个窗口指向另一台机器，意味着每一个请求都要经过隧道，`/api/me` 也不例外——于是隧道一断，应用连「当前有没有人登录」都答不上来，而返回的入口恰恰渲染在那个永远挂载不起来的布局里面。藏在故障物背后的逃生口不是逃生口。改为在真正需要的调用上指明机器，就不会有这种失效方式：隧道断了，坏掉的正是那一个需要它的请求，并且会明说。

寻址用机器自身的 id，而非 ssh 别名。正因如此，主机被改名——甚至从 `~/.ssh/config` 中整条删除——都不会让仍在转发的通道失联。只有一个身份：本服务端的管理员就是那台机器的管理员，因为授权两者的都是当初装上程序的那份 ssh 权限——所以不会再要求第二次登录，浏览器的 cookie 不会过去，且只有 `/api` 会被代理：前端永远是本地那一份。

**断开**只拆除隧道，远端服务端继续运行。那是那台机器自己的服务端，上面可能还有别人。

## 过程与留存

最坏情况下一次安装要几分钟，所以它是一个 job：页面发起后轮询，显示对端自己的输出。同一时刻只跑一个，面板跟随 job 而不是当前选中项。job 存在服务端内存里；重跑就是恢复手段——每一步都幂等，安装器会先暂存、冒烟测试再切换，切换开始后若失败则恢复上一份安装。

哪些主机装过这份程序记在 `web.db` 里，在 **Installed machines** 下按版本和时间列出。它记录的是这台服务端做过什么，不是对远端的普查：被手工清掉的机器仍显示为已安装，直到下一次安装纠正这条记录。

## 细节

- 新增 API，仅管理员：`GET /api/machines` 与 `POST /api/machines/:machineId/install`。
- 该能力从 `packages/desktop/src/remote/` 移到 `packages/server/src/machines/`，因此它能从浏览器触达、对 tarball 安装可用、并可随热推分发。
- 对端跑的就是常规安装器的在线模式——不再组装或传输任何载荷；暂存、冒烟测试、切换、回滚和 PATH 处理就是每次 release 安装跑的那一份实现。交换条件：远端首装与底座升级时必须能访问 GitHub 或 OSS 镜像。
- 载荷布局只写一遍。`bin/penguin` 与 `bin/penguin.cmd` 此前写在四处——release 工作流里的 shell heredoc，以及三个 JavaScript 模块里的字符串——副本已就 `web/` 和内置运行时的位置发生漂移。现在它们是 `scripts/launchers/` 下的两个普通文件，原样复制进每个 release 包：可读、可 diff、可直接运行。
- 桌面端不再往 resources 里塞约 190 MB 的安装镜像。没有任何东西读它：桌面端把 server 打成单文件运行，本该找到该镜像的那段查找在打包后的应用里从来没有匹配成功过——这也意味着 Machines 页在桌面端一直不可用。打包后的应用现在从自己的清单读出所属 release，并改为携带约 4 KB 的安装脚本而非整份镜像：对端自己下载 release。
- `install.ps1` 的兜底启动脚本——只在载荷未自带时写出——指向了一个从未存在过的 CLI 入口（`lib\dist\index.js`）。
