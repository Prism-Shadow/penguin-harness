# 消息通道的 HTTP 层不再写三遍

- **Date:** 2026-08-27
- **Type:** refactor
- **Scope:** `server`
- **PR:** [#525](https://github.com/Prism-Shadow/penguin-harness/pull/525)

[English](2026-08-27-messaging-channel-spec.md)

`runtime/messaging/connector.ts` 早已为运行时提供了渠道接缝：连接器自己拥有线路协议，交给桥接的是与渠道无关的视图。HTTP 层没有这样一层，于是它的六个端点每个渠道各写一遍，每新增一个保存字段就再多写三遍——同一个版本里到来的三个投递偏好，合起来花掉了九处声明、九处读取和九处展开。

现在由 `MessagingChannelSpec` 承载渠道之间真正的差异，而除此之外别无不同的端点只写一次。

## 细节

- `http/routes/messaging-channels.ts` 承载该 spec 以及路由共用的部件：绑定线路形状中与渠道无关的那一半、脱敏后的密钥投影、从 PUT body 读出的投递偏好补丁，以及 `resolveSecret`——三个渠道共同攀爬的那道凭据阶梯。它的四步（键入的凭据优先、启用状态下拒绝清除、否则沿用已存、首次绑定无凭据则 400）此前被陈述了三遍，本可以各自漂移。
- 每个渠道的四个端点——读取、状态开关、删除、测试消息——改为从 spec 表注册。这十二份副本之间的差异只有渠道字面量和 `<channel>_` 错误码前缀，因此 spec 携带一个展示名，错误码由它推导。
- PUT 与凭据测试**刻意**保留为每渠道手写。它们的骨架是共享的，现在也走同一道阶梯，但输入的校验顺序、以及账号身份如何从凭据中得出，确实各不相同——Telegram 的 bot id 就是从 token 本身推导的——用一张表会把这个差异藏起来，而不是消除它。
- 线路类型这一侧由 `MessagingBindingCommon` 与 `MessagingDeliveryPatch` 做同样的事。QQ 重新声明了那三个偏好字段（类型不变），因为它们在该平台上各自的代价不同，而被动回复额度正是设置它们的人需要知道的；编译器保证重新声明只能增加文档、不能改变契约。
- 该 spec 不与连接器的配置解析合并：两者方向相反——连接器读取**已存文档**来构造客户端，而这里读取**请求**来决定存什么。它们只共享对文档形状的认知，仅此而已。

端点、状态码、错误码与响应体均无变化：整套消息测试未经修改即全部通过。
