# 观点文章：vibe coding 时如何立住规矩

- **Date:** 2026-10-19
- **Type:** process
- **Scope:** `landing`
- **PR:** [#1234](https://github.com/Prism-Shadow/penguin-harness/pull/1234)

[English](2026-10-19-blog-rules-for-vibe-coding.md)

博客新增一篇观点文章，中英文各一份，按一篇完整的议论文来写：Agent 必须遵守的规矩应当放进仓库，让每个 Session 都能读到（代码即记忆），并排成一座金字塔。塔尖是按 RFC 方式逐条写的规矩，中层是核心接口，塔基是可复用组件；越靠上内容越少、越需要人的注意力，越靠下内容越多、越不需要人逐行看。其中的硬约束由代码和测试守住，而不是靠提示词。

## 细节

- 文章先写中文，整篇一次写成，再整篇翻译成英文。每一节论证一个观点，并回应最有力的反对意见；每一层都说明它装了多少内容、需要多少人的注意力（0.2.16 中 25 条编号规矩、3 个核心接口、1489 个源文件）；过渡单独做了一轮，只改小标题前后的句子。
- 五张插图以内联 SVG 绘制，使用共享的插图样式。三层结构图重画成金字塔：上窄的塔尖是规矩，中层是接口，宽的塔基是可复用组件，每层写明数量、由谁来看和一个例子（Trace 只追加；Agent State 的边界、审批走 Human 接口；热更新复用终端交接），一侧标出人的注意力向上递增，另一侧标出内容量向下递增。其余四张（一条硬规矩落到测试断言的路径、Agent State 目录树、`context_engine` 周围的边界、复用优先的判断流程）沿用已发布的版本。
- 文章用编号脚注标注来源：每段最多一处，每个来源只引用一次，中英文引用同一组 9 个来源。
- 文章开头是三条要点的 TL;DR，导语和每一节各加粗一句关键句。
