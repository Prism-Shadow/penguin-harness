# 从源码检出运行时也能使用机器管理，能装到不同系统与架构的机器上，启用后自动保持连接，并以工具栏管理机器

- **Date:** 2026-10-10
- **Type:** fix
- **Scope:** `server`, `web`, `tooling`, `ci`, `docs`
- **PR:** [#1023](https://github.com/Prism-Shadow/penguin-harness/pull/1023)

[English](2026-10-10-machines-dev-image.md)

从源码检出运行的服务端（`pnpm dev`、`pnpm desktop`）在每次安装或启用机器时，自行构建安装镜像。此前这样的服务端没有任何镜像：机器管理页禁用了「添加机器…」与「启用」，每次安装都返回 `409` `no_install_image`，提示语还说镜像会在「第一次热推后」获得，而热推从未带来镜像。安装现在也能到达与服务端系统或架构不同的机器、连不上发布版下载源的机器，以及从页面上添加的主机；途中每一种失败都说明它的含义。添加机器改用对话框；机器启用后由服务端自动保持连接；各处读同一份实时的机器状态，任务的步骤随进展实时推进，新建对话页也不再把已连接的机器说成未连接。在 `pnpm dev` 下，页面可以访问机器的 API；只有当机器运行着那里安装的构建时，才会收到本服务端的模型配置。

## 细节

- 镜像用与热推送相同的打包器构建。`scripts/deploy.mjs --out <file>` 打包的正是一次推送会发送的版本（web 产物、平台与 CLI 两个 bundle、node-pty、TypeScript、安装脚本、内置插件与插件库），把 gzip 压缩的升级请求体写入文件而不推送。这一用法不需要推送目标，也不需要凭据；web 产物构建在该文件旁边的独立目录里：`pnpm desktop` 与开发服务端正以 `packages/web/dist` 托管使用中的页面，因此镜像从不原地重建它。推送仍照旧原地构建。
- 服务端把请求体落成一份 hmr store，放在 `<root>/machines/checkout-image/<id>/hmr`，从不写进自己的 `<root>/hmr`；安装方式与热推送过的服务端相同：远端自行下载检出的 `VERSION` 所指的发布版，store 经 ssh 复制过去。镜像按内容命名；每次构建保留它所替换的那一份，以及仍有任务在安装的镜像，其余删除。
- 版本为 `<VERSION>+hmr.<平台 bundle 哈希>`，与热推送过的服务端报告的形式相同。未改动的工作区重建出同一份镜像，已装上它的机器不会被重装；平台代码改动之后，装着上一份镜像的机器显示为落后。
- 一批任务共用一次构建，构建进行中开始的任务直接加入它。服务端启动和页面列出机器时都不构建。构建超过 20 分钟即连同它启动的一切（pnpm、vite、插件安装）一并终止；服务端退出时仍在进行的构建同样如此：开发终端里按 Ctrl-C、开发服务端重启、桌面端退出。
- `GET /api/projects/:projectId/machines` 新增 `checkoutImage`（`unbuilt`、`building`、`built`，或 `failed` 并附构建输出的最后几行），只在源码检出时出现。`imageVersion` 报告检出最近一次构建的镜像，第一次构建之前仍为 `null`。
- 构建失败时，任务停在 `build the install image` 这一步，附构建输出的最后几行，不提供强制安装；机器管理页在提示区显示同样的内容，直到某次构建成功。
- 经机器更新通道的移交（安装时，以及服务端启动时的那轮同步）发送的是正在安装的那份计划的构建，因此源码检出移交的是它的镜像。
- 现在只有既不是安装版、也不是本仓库源码检出的服务端才会返回 `no_install_image`，其报错信息与页面提示都照此说明。作为依赖装进其他 pnpm 工作区的服务端不算源码检出，也从不运行那个工作区的 `scripts/deploy.mjs`。
- 推送或安装镜像记录的来源（`source.repo`，接收它的机器经 `GET /api/version` 与 harness 历史展示）所写的 origin 远端地址，不再带有 https 克隆可能携带的用户名与密码。
- `deploy.mjs` 在 Windows 上经 shell 调用 `pnpm`，因为那里的 `pnpm` 是一个 `.cmd` 包装脚本。

## 不同系统与架构的机器

- 推送到机器上的平台在打开终端时，先用那台机器上已安装发布版自带的 node-pty（按那台机器发布），再用推送带去的那份（在推送它的机器上构建）。Mac 构建的推送只带 node-pty 的 darwin 与 win32 二进制，Linux 机器上的每个终端因此都以「Failed to load native module: pty.node」失败。修复 spawn-helper 执行权限的步骤跟随实际加载的那一份；哪一份都加载不了的机器，用一句话说明原因；二进制在、却被拒绝加载时（比如 glibc 比构建它时的旧），附上动态链接器的原话，而不是 node-pty 最后一次查找落空的信息。
- 发布版程序包带上 node-pty 的 linux-arm64 二进制（`prebuilds/linux-arm64/pty.node`），由发布流程在 QEMU 下构建一次。此前没有任何发布版带这份二进制，arm64 Linux 机器上的终端全部失败。
- 安装时复制的 hmr 状态改在进程内打包（可移植的 tar），不再调用服务端所在机器的 `tar`。macOS 的 `bsdtar` 会为每个带扩展属性的文件加一个 AppleDouble `._<name>` 成员，机器随后把 `archives/._node-pty.tgz` 当作归档解包。平台自己解包时也跳过 `._*` 文件。
- 连不上 GitHub 与 OSS 镜像、或者没有 `curl` 的机器，改由服务端为它取发布包：从镜像或 GitHub 下载一次，核对发布时附带的校验和，存放在 `<root>/machines/releases/v<version>/`，经 ssh 会话发过去，再以 `--archive` 安装。两个下载源都没有的发布版，安装停在 `download the release` 这一步。
- 复制 store 的传输时限按慢速上行链路估算，不再固定为十分钟。
- 比较两份构建时，看 `harness.json` 指向的文件，而不是它的全文，因此经更新通道接收了构建的机器，会被视为已带着这份构建。已在镜像版本上的机器再次启用时，若 web、CLI 或附带资源有变化，仍会移交新构建。

## 用平实的话说明失败

- ssh 那些固定的诊断信息，前面先加一句话说明含义和下一步：主机密钥未知或已变化、密钥被拒绝、私钥文件不可用、主机名解析不了、端口拒绝连接或无响应、登录前连接被断开、ssh 配置有错误。随后附上 ssh 的原话。这类失败不再改用第二条 Windows 连接重试，也不再提供强制安装；任务会在构建镜像之前先检查 ssh。失败的任务带上原因（`sshReason`），页面据此用界面语言说明，下方附 ssh 的原话；一开始就被 ssh 拒绝的任务，失败在第一步。
- 页面写入的 Host 段以 `StrictHostKeyChecking accept-new` 结尾：这里的连接都以 BatchMode 运行，无法回答 ssh 首次连接时的确认问题，因此从页面添加的主机此前一律以「Host key verification failed」失败。
- 只有连接被保持时，机器才显示为已连接。安装或连接检查打开的 ssh 会话会一直开着、直到空闲超时，此前会让刚刚安装失败的机器在这段时间里显示为已连接。
- 一行 `Include` 可以列出多个文件。
- 服务启动时因端口被其他程序占用而退出，会直接说明，并且不提供强制安装；崩溃的调用栈只保留它的错误行。
- 安装脚本的进度条不再写进任务日志；安装失败时，引用它输出的 `error:` 行；若它指向上方的错误，先引用程序自己的报错。
- `POST /api/projects/:projectId/machines/:machineId/diagnose` 在不改动机器的前提下检查它：ssh 登录、系统（glibc 低于发布版 Node 所需或是 musl 时，会点明原因；低于终端所需时给出提醒）、安装脚本要用的工具、能否下载发布版、可用磁盘，以及它的服务将使用的端口。它不再是按钮：任务失败在它能解释的步骤之后、保持连接的机器连续 3 次连不回来之后，服务端会自动运行它，机器对话框逐项显示结果，作为失败的说明。

## 添加机器

- 「添加机器…」下拉框改为「添加机器」对话框：一句话说明会发生什么；一个标签页从 ssh 配置中选择主机（搜索框，每台主机一行可勾选，并显示它的配置段如何连接）；另一个标签页手动填写新主机（名称、主机地址、用户名、端口（默认 22）、私钥文件）；页脚是「取消」「添加」，以及默认勾选的「添加后立即安装并连接」。页头按钮改为主按钮样式，放在标题行末，与智能体页、插件页一致。
- `POST /api/projects/:projectId/machines/add` 把机器加入 Project 的列表而不安装任何东西，`MachineInfo.member` 标明哪些机器在列表中。`GET /api/projects/:projectId/machines/ssh-hosts` 列出每台主机，以及它自己的配置段写明的用户、主机地址与端口。
- 机器从被要求添加的那一刻起就在列表中，因此卡片会显示进行中的安装，首次安装失败时也会保留卡片和「重试」。删除它会同时移除卡片和失败的任务。只添加、未安装的机器显示「未安装」，它的对话框提供「启用」。
- 添加对话框按设置控件的提交口径是一张表单：勾选的主机、手动填写的内容与「添加后立即安装并连接」都是它的草稿。勾选了主机、或手动填写的内容完整且没有不合法的值之前，「添加」不可用；不合法的值（含 ssh 配置里已有的名称）随输入写在字段下；回车不提交。有改动时关闭对话框先询问，「添加」的请求返回前关闭不响应。「配置 SSH」对话框遵循同样的口径。

## 保持连接

- 启用（或启动服务）过的机器由服务端保持连接（`MachineInfo.keepConnected`），直到被停止、删除或断开。它的 ssh 会话断开、服务停止或重启、本服务端重启时，服务端都会自己把它连回来：探测机器，服务没在运行就启动它，重新持有连接并下发模型配置。每次失败后的等待是上一次的两倍，从 5 秒起、封顶 5 分钟；有任务在处理这台机器时等任务结束。其间机器带 `reconnect`（`since`、`attempts`、`nextAt`、`lastError`、`sshReason`、`diagnosis`），卡片与对话框显示「重新连接中…」，超过一分钟时注明已持续多久；连续失败 3 次后自动运行连接检查，对话框显示检查结果。
- 经机器会话的 SOCKS 拨号在机器拒绝该通道时立即失败。ssh 关闭这种连接时不发 SOCKS 应答，拨号此前会一直等下去：发往服务已死的机器的请求挂住而不失败，服务死掉也没有人发现。

## 页面只持有一条事件流

- 服务端经各已连接机器的 ssh 会话订阅它的 `GET /api/events`，把每个事件包成 `machine_event`（`{machineId, event}`）重新发布到自己的用户事件流上，只发给管理员。此前页面经 `/server/<id>` 代理为每台已连接的机器各开一条流，而浏览器对同一来源只允许 6 条 HTTP/1.1 连接：连上 5 台机器后，页面的其余请求都排在这些流后面永远发不出去——机器管理页卡死，「添加」也到不了服务端。
- 机器列表的每次变化——任务排队、开始、进入下一步、输出一行日志、结束，连接建立或断开，重连进行中，机器加入或离开 Project——都以 `machines_changed` 告诉管理员，每秒至多几次；页面据此重新读取列表，不再每 1.5 秒轮询。
- 机器管理页、新建对话页、会话列表与终端读同一份机器状态（`state/machines.tsx`）。新建对话页此前只在选定工作区时向那台机器要一次 Agent 列表，并一直沿用这次的回答：选定时机器还在连接中，草稿开着多久就显示多久「那台机器尚未连接」，而机器管理页早已显示已连接。现在机器每次连上都会重新询问，连不上时说明原因——正在重新连接、服务已停止、不在本 Project 的列表里，或那台机器自己答复的失败。
- 新建对话页上，草稿原本在本机的临时工作区时，改选某台机器上的「从临时工作区开始」，会话仍建在本服务器上：两次的路径都为空，发送沿用了之前的机器。现在会话建在那台机器上，与在那里选定文件夹时一样。

## 任务步骤

- 每个任务带自己的 `steps`，`phase` 只前进不后退。源码检出构建镜像成为独立的一步「构建安装镜像」；它此前记在「检查机器」名下，步骤条在构建的几分钟里一直停在第一步；安装之后的连接也不再把步骤条退回第一步。
- 每台机器同一时刻只运行一个任务，几台机器可以同时处理：一台机器上的操作不再因为另一台机器有任务在运行而被拒绝。

## 机器管理页

- 卡片带上智能体页式的快捷按钮：「使用」在这台机器的临时工作区新建对话，「设置」打开机器对话框，「删除」在确认后把机器移出本 Project——确认框写明连接会断开，程序、数据与 ssh 主机都保留。「使用」不可用时，卡片以淡色一行写明原因：重新连接中、服务已停止、尚未安装、上次任务失败。
- 机器对话框的操作改为头部下方的一条工具栏：「更新」（只在机器装着另一个构建时出现；未安装时为「启用」）、「停止服务」或「启动服务」、「重启服务」、「配置 SSH」、「卸载」；置灰按钮的原因在工具栏下方用一句淡色的话说明。「停用」「断开」「移出 Project」「检查连接」「重新连接」以及每个操作旁的说明文字都已去掉。
- `POST /api/projects/:projectId/machines/:machineId/stop` 停止机器的服务并不再保持连接，机器显示「已停止」，直到再次启动；`POST …/uninstall` 停止服务后删除程序，带 `{removeData: true}` 时连同数据目录，确认框写明程序目录，并以缺省不勾选的复选框询问是否删除数据目录。两者都是带步骤与日志的任务，连不上机器时不做任何改动。
- 任务日志带复制按钮，与代码块相同。


## 模型配置与 `pnpm dev`

- 在 `pnpm dev` 下，页面经由 Vite 访问机器，而 Vite 原先只转发 `/api`。发往机器的每个请求（`/server/<machineId>/api/…`）都由 Vite 自己答复：GET 拿到的是页面自己的 `index.html`，其他请求拿到空的 `404`，于是在已连接的机器上选择 Agent 时显示「那台机器没有答复：请求失败，请稍后重试」。现在 Vite 也把这些请求转发给开发服务端。
- 不是服务端发出的答复（没有 JSON 正文）现在会说明是谁答复的，而不再显示「请求失败，请稍后重试」：一个网页（中间的开发服务器或反向代理没有转发这个请求）、一个代理（网关状态码，或带有代理自己的响应头），或者其他情况下的状态码与类型。这样的答复即使是 `401` 也不再让窗口退出登录。
- 向一台机器下发模型配置之前（启用、启动服务，或服务端把保持连接的机器连回来时），服务端先问那台机器的服务在运行什么（`GET /api/version`）。服务没有在运行那里安装的构建（例如在那个数据目录上启动的正式版自带的服务），就把它重启到这个构建上；服务运行的构建与本服务端的镜像不同，就先通过它的更新通道把镜像交给它。两样都做不到时，任务停在 `sync`，说明那台机器在运行什么、需要先更新，什么都不下发。把本服务端以 MMSP 客户端类型命名的配置交给 0.2.13 的服务，会让那里的每个 Session 都报「deepseek-official is not supported」；重启到已安装的构建也会修好已经处于这种状态的机器。问不到的机器照常连接，但不下发，任务日志写明原因。
- 修改模型时，只有运行本服务端镜像的已连接机器会收到；运行其他构建的机器保留原有配置，直到它被更新。

## 同步 Project 配置

- 交给机器的是使用它的每个 Project 的完整配置，而不只是模型：分组连接、默认模型与视觉模型、Project 名称（这里重命名，那里也随之改名）、沙箱命令策略（对端的 `PUT …/command-policy`）、新对话默认值（对端的 `PUT …/chat-defaults`），以及插件列表。新对话默认值里的工作区是本服务端上的目录，在那台机器上没有意义，保留它自己的；那台机器没有我们的默认 Agent 时，也保留它自己的。某个 Project 的某一部分被拒绝时写进日志，其余照常下发。
- 对端按名拒绝的模型条目会被跳过，表中其余条目照常写入：`PUT /models` 是整表替换，此前分组只承载内置模型时，一个手动添加的模型（`model_not_addable`）就让整个 Project 的模型都同步不过去。指向被跳过条目的默认模型或视觉模型不下发。`model_not_addable` 与 `model_not_routable` 现在在 `details.provider` 与 `details.modelId` 中给出该条目。
- 本服务端每次写入 Project 配置之后——模型、默认模型、命令策略、新对话默认值、重命名、插件列表——都会下发给运行本服务端镜像的已连接机器，与此前修改模型时一样。
- 「同步配置」立即把配置下发给一台已连接的机器：卡片快捷按钮最前的一个图标按钮，以及机器详情弹窗工具栏里的一个操作，都只在机器已连接、且与本服务端同构建时出现（构建不同的机器提供「更新」，重连时一并同步）。`POST /api/projects/:projectId/machines/:machineId/sync` 是带 `check`、`sync` 两步的任务；检查不做任何改动，运行其他构建的机器以指向「更新」的那句话失败。未连接的机器返回 `409` `not_connected`。
- 模型条目取自本服务端环境变量的值——条目与分组都没有的 Key，或没有 base URL 的条目所用的 `*_BASE_URL`——不在配置里，无法下发。同步日志按 core 的凭据规则逐条写明。
- 每台机器带上最近一次同步的结果 `configSync`（`{at, ok, detail?, envOnly, skipped}`，只存内存）。机器详情弹窗在工具栏下方用淡色一行说明：「配置已同步 · 3 分钟前」或失败原因；环境变量来源的模型与对端拒绝的模型，合在一条 attention 色的提示里列出。
- 机器详情弹窗的工具栏去掉了上下两条分隔线，只靠间距与上下内容分开。
- ssh 主机表单（「添加机器」对话框的「手动填写」与「配置 SSH」）的占位文字不再是示例值：选填字段写明留空时生效的值——用户名为本服务端账户的用户名，端口为 22，私钥为 ssh 的默认密钥——必填字段写明要填什么；与之重复的提示随之去掉。

## 密码登录

- 主机可以用密码代替密钥登录。「添加机器」对话框的「手动填写」与「配置 SSH」多了「登录方式」：「密钥」（缺省，下接私钥文件）或「密码」。已保存的密码从不回显：密码框显示「已保存，留空保持不变」，填写即替换，改选「密钥」保存时删除。手写的配置段保留原样，登录方式仍可设置。
- 密码保存在本服务端，每个别名一个 0600 文件，位于 `<root>/machines/ssh-passwords/`，不写进 ssh 配置、数据库、日志、任务日志、API 应答或命令行。本服务端对那台机器的每次 ssh——保持的会话及其 SOCKS 转发、一次性命令、Windows 机器的 scp——都经 `SSH_ASKPASS` 用它登录：`<root>/machines/ssh-askpass/` 下的辅助脚本从那一个 ssh 进程的环境变量里打印密码。这样的机器不提供密钥，每种方式只问一次。低于 8.4 的 OpenSSH 在 Linux 与 macOS 上照常可用；在 Windows 服务端上，保存密码时即被拒绝并写明版本。
- ssh 拒绝了的密码不再重试，以免把账户锁住。机器显示「登录被拒」与「那台机器拒绝了保存的密码——请在机器的 SSH 设置里重新填写。」，服务端停止重连它（`reconnect.waitsForPassword`），任务与连接检查直接以 `sshReason: "password-rejected"` 失败（主机不接受密码时为 `"password-not-offered"`），直到为它重新保存或删除密码。把机器从最后一个使用它的 Project 中删除时，它的密码一并删除。
