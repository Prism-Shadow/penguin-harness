# 被重复投递的聊天消息只启动一个 Task

- **Date:** 2026-08-27
- **Type:** fix
- **Scope:** `server`
- **PR:** [#484](https://github.com/Prism-Shadow/penguin-harness/pull/484)

[English](2026-08-27-messaging-inbound-dedupe.md)

被渠道投递两次的消息会排入两个 Task 并都执行，于是在聊天中出现两次，在 Web App 中也出现两次。桥接层现在会丢弃该绑定已经处理过的消息。

## 细节

- 去重按绑定进行，键取渠道自身的消息标识——飞书的 `message_id`、Telegram 的 `chatId:message_id`。绝不按文本去重：同一个问题问两遍是两条消息，仍然会执行两次。
- 重复消息是彻底的空操作，不仅不启动 Task，也在记录会话与「仅支持文本」回复之前就返回，因此被重播的表情消息不会再回两次提示。
- 记忆在两个维度上都有上界——每个绑定保留最近 64 个消息 id，时间窗口十分钟——且归属于绑定而非某一条连接，因此重新保存一个已启用的绑定（会重启其连接器）不会重播已处理过的消息。绑定或其会话被移除时该记忆一并丢弃。
- 该记忆只存在于进程内：服务端重启即遗忘，因此跨重启仍然到达的重复投递依然会重复执行。
- 两个界面都出现重复，是因为排队的后续输入会发布到会话通道。同一个用户可见症状的另一端由 [Telegram 轮询冲突修复](2026-08-27-telegram-conflict-recovery.zh.md)处理，它消除了重复投递的一个常见来源。
