PenguinHarness 0.2.7 — a fix release for what 0.2.6 shipped: the messaging bindings it introduced now work from the desktop app, survive a Telegram poller conflict and run a redelivered message once; the desktop app puts its bundled `penguin` command on PATH by itself and repairs it at every launch; and a command whose Workspace has gone, or whose machine has no `bash`, says so instead of reporting a missing shell.

## Install

**Desktop app**: grab your platform's installer from [penguin.ooo/download](https://penguin.ooo/download) — the page measures both sources on every visit and keeps GitHub unless the OSS mirror is measurably faster, with a manual selector beside the result. The macOS builds are Developer ID signed and notarized and the Windows installers are Authenticode-signed, so neither platform needs a first-launch unblock.

CLI / server (Linux, macOS; bundled Node runtime):

```sh
curl -fsSL https://penguin.ooo/install.sh | sh
penguin web
```

Windows (PowerShell):

```powershell
irm https://penguin.ooo/install.ps1 | iex
penguin web
```

Or via npm (needs Node >= 24):

```sh
npm install -g @prismshadow/penguin-cli
```

## Highlights

**Feishu connects from the desktop app.** Binding a Feishu app from the desktop shell failed at the credential test and at connect with `__dirname is not defined`, so the messaging integration 0.2.6 introduced could not be used there at all. Only the desktop app was affected: an npm or CLI install resolves `@larksuiteoapi/node-sdk` from `node_modules`, where it runs as CommonJS and is handed its own `__dirname`, while the desktop app bundles the server and the CLI into one self-contained ESM file each and absorbs the SDK along with them. Those bundles carried a banner declaring `require` for exactly this reason, but not `__filename` or `__dirname`, so the SDK's read of its own `package.json` — which it uses to put a version into its User-Agent header — hit an undeclared identifier and failed the whole connect attempt. The banner now declares all three, from one shared definition used by both bundling sites, and declares them with `var` so a bundled module that derives the same names from `import.meta.url` redeclares them instead of colliding. Telegram was never affected; it calls the Bot API with `fetch` and loads no SDK.

**Telegram connections come back from a poller conflict.** A binding that hit Telegram's one-poller-per-token rule parked at "connection error" and never delivered another message. Recovery was gated on a `getMe` probe, and `getMe` never conflicts — so the failure counter cleared on every cycle, the exponential backoff never left its first step, and the connector re-polled once a second indefinitely while the status flapped between `connected` and `error` faster than the panel reads it. Readiness is now proven by a `getUpdates` and nothing else: one outage reports once and backs off to the documented 60-second ceiling, and the recovery poll returns immediately rather than parking for the long-poll window, so the end of an outage is seen at once. A webhook registered on the bot — mutually exclusive with polling on the Bot API — is now found by a read-only probe that names the URL blocking the poll, and leaves it alone: that registration belongs to whatever service the user pointed it at. Removing it there needs no re-enable; the connection comes back on its own. The panel gives a failure its own row instead of a truncated share of the row carrying the switch, the label and the status word.

**A redelivered chat message starts one Task, not two.** A message a channel handed the bridge twice queued two Tasks and ran both, appearing twice in the chat and twice in the Web App. The bridge now drops a message its binding has already processed, keyed on the channel's own message identity — Feishu's `message_id`, Telegram's `chatId:message_id` — and never on the text, so the same question asked twice is two messages and still runs twice. A duplicate is a complete no-op, ahead of the chat record and the text-only reply as well as the Task start, so a replayed sticker no longer answers with the notice twice. The memory is bounded on both axes, the last 64 ids per binding within a ten-minute window, and belongs to the binding rather than to one connection, so re-saving an enabled binding does not replay what it already processed. It is in-process: a server restart forgets, so a redelivery that outlives a restart still duplicates.

**The desktop app installs the `penguin` command itself.** Only the deb package did this before; macOS, Windows and the AppImage offered it once, in a first-launch dialog, and never again. The shell now installs and repairs the command at every launch without asking — the app and the CLI it carries come from the same build, so installing it from the app is also what keeps the two in step across an update. Running every launch is what makes it *repair* and not merely create: a dangling link left by a moved or updated app, and a wrapper naming an AppImage that has moved, are rewritten. Two refusals are enforced in the decision code itself rather than left to a caller: a `penguin` this app did not write is never touched — ownership means a symlink into the packaged layout or the launcher marker every generated launcher has carried since 0.2.2, and everything else is skipped with the reason recorded, so where `install.sh` has put its own symlink at the same path, this app gives way; and an install is never made from a location that will not persist, so running from a mounted dmg or from Gatekeeper's translocation directory defers to the next launch from `/Applications`. On macOS the unprivileged write is tried first and an administrator prompt appears only where it is actually refused; on Windows the app's `bin` directory is appended to the user PATH idempotently.

**A command says what is actually wrong.** Two failures used to arrive as the same misleading string. `exec_command` answered `[spawn error: spawn bash ENOENT]` when the Session's Workspace had been deleted or moved — Node reports an unusable working directory using the *command's* name, not the directory's, which sent every reader hunting for a `bash` that was there all along. The working directory is now checked before the spawn and the message names the path; it is still never auto-created, so a typo cannot silently start work in the wrong place. Separately, the shell resolver gained on POSIX the fallback chain the Windows branch already had: it used to return a bare `bash` with no existence check and no alternative, so a machine whose `PATH` has no bash failed every command before it ran — which a desktop app launched from a GUI can meet, since it inherits the desktop session's `PATH` rather than a login shell's. Resolution is now `PENGUIN_SHELL`, then `bash` on `PATH` (still spawned as the bare name, so the common case is unchanged), then the usual absolute bash paths, then `$SHELL` when it names a POSIX shell that exists, then `sh`. A service account's `/usr/sbin/nologin` or `/bin/false` is skipped rather than handed `-lc`, and a shell resolved through a non-bash step is reported to the model under its own name, because that is the syntax it has to write.

## Notable in this release

- **Breaking (a "Not Now" to the old `penguin` offer is not carried forward).** Desktop releases 0.2.2 through 0.2.6 wrote an empty `cli-install-offered` marker under `userData` and skipped the offer whenever it existed. It was written **before** the dialog appeared, so it records that the question was asked and not what was answered — an install, a "Not Now" and a dialog that was never answered all leave the same file. It cannot be read as a decline, and reading it as one would deny the command to the entire existing install base, so it is ignored and removed on the first new state write. The consequence: a user who answered "Not Now" gets the command installed on their next launch. Nothing installed by another route is moved or replaced.
- **A queued follow-up is recallable however it was queued.** A message sent to a busy Session from a bound chat channel joined the follow-up queue without the content a recall hands back, so the Web App drew its queued line empty and its recall button answered "this message already went out" while the message was still waiting. Every queued entry now carries that content whichever path queued it, and the two recall endpoints stopped sharing one error code: a follow-up that already became a task of its own answers `follow_up_started`, while a steering message the model has already received keeps `not_pending` — they are different sentences to a user.
- **The landing site and both READMEs were corrected where the copy had stopped being true.** The download page's first-launch FAQ was still telling visitors that builds were unsigned and walking them through `sudo xattr -rd` and Windows SmartScreen; macOS has been signed and notarized since 0.2.2 and Windows Authenticode-signed since 0.2.4, so both items are gone and the Linux AppImage execute bit is the one that remains. The built-in Skill lists gained the five Skills that had joined the library since they were written, and the supported-model table was re-derived from the catalog. The Skill lists are now pinned by tests against the shipped library — membership and grouping, in both dictionaries and all three READMEs — since nothing had been guarding the surfaces that rotted.
- **The bundled `penguin` command is checked in CI.** `verify-packed-cli.mjs` inspects the tree `electron-builder --dir` produces and runs the packed launcher on all three runners, and unit tests pin the packaging configuration the launchers depend on.
- **Both `web.db` upgrade directions are pinned by tests.** A database formed before `messaging_bindings` existed gets the table and its uniqueness index on open with its Sessions intact, and a database written by a newer build survives an open by this one untouched. Where that tolerance stops is pinned beside it: a `NOT NULL` column with no default, or a new unique index over columns this build already writes, leaves the open succeeding and the first write failing.
- **Landing copy and the RAG demo poster.** Three proof points reworded, and the demo's finished-app poster replaced with locale- and theme-matched screenshots of PenguinHarness building the app.

## Requirements

Linux or macOS (x64 / arm64), or Windows 10+ (x64). The desktop app and the CLI installers bundle their own runtime; installing from npm needs Node >= 24. All data stays under `~/.penguin/data`.
