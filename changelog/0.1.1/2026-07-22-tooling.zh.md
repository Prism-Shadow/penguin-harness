# 工具链与加固：原地升级、请求校验与 core 测试覆盖

- **Date:** 2026-07-22
- **Type:** feature
- **Scope:** `cli`, `server`, `core`
- **PR:** [#9](https://github.com/Prism-Shadow/penguin-harness/pull/9), [#10](https://github.com/Prism-Shadow/penguin-harness/pull/10), [#44](https://github.com/Prism-Shadow/penguin-harness/pull/44)

[English](2026-07-22-tooling.md)

- **`penguin update` 原地升级已有安装。** `penguin update [--check] [--release <tag>] [-y|--yes]` 从 GitHub Releases API 解析最新版本（与 `install.sh` 解析 `releases/latest/download` 所用的是同一数据源），并按安装实际所采用的机制升级——该机制是从运行中 CLI 的真实路径检测出来的，而不是猜的：tarball 安装会重新运行官方安装脚本，保留其安装目录以及是否自带 Node 运行时；全局 npm/pnpm/yarn/bun 安装会调用对应管理器的全局安装命令，当无法识别管理器时则打印命令而不是瞎猜；源码检出会被拒绝，并提示改用 `git pull` 加重新构建。不带 `-y` 时它会打印机制、目标版本与安装目录并请求确认；stdin 非 TTY 时要求显式 `--yes`，而不是就此阻塞。数据根目录永不被触碰——只有 `bin`、`lib`、`web` 与 `node` 会被替换。目标版本的参数名是 `--release` 而非 `--version`，因为 CLI 自身的 `-v, --version` 优先级高于同名的子命令选项。
- 服务端现在会校验 `positiveIntParam` 与 `optionalDateParam` 输入，而不再信任查询字符串——畸形的分页/日期参数会干净地返回 400，而不是渗进 SQL 或算术运算。
- Core 新增了针对 `CappedTextBuffer` 与 `ToolCallIdAllocator` 的专门单元测试，这两个小型纯模块此前没有直接覆盖。
