## 除被拒绝的凭证之外，所有失败现在都会重试

引擎此前只在 `timeout` 与 `malformed` 时重连。`failed`——也就是「分类器没有判定它是瞬时的」这个兜底桶——会直接终结该轮。

麻烦在于那个分类器是什么：一份已知错误码、HTTP 状态与消息词汇的允许清单。一个用自己的措辞描述瞬时故障的网关（比如 `Upstream HTTP/2 stream failed`）会径直穿过它，落进 `failed`。对一个真正永久的错误做重试，代价不过是走完退避阶梯然后以同样方式结束；而中止一个瞬时错误则会毁掉这一轮。于是策略放宽了：**`failed` 也重试，而 `auth` 是唯一会终止运行的 LLM 状态**——被拒绝的凭证不可能靠重试变得可用。这改变的是策略，不是分类法：一个 `failed` 请求在它的 `request_end` 上以及在成本中心里仍然报告为 `failed`，不会被改称超时。

重试是可见的，因为用户看不见的重试就是一个没有解释、也没有出路的卡死会话：`failed` 的渲染与另外两者完全一致——Web App 的倒计时带「立即重试」与「放弃」，CLI 的 `[retry]` 行——而尝试次数在混合阶梯上持续累加，而不是从 #1 重新开始。

压缩重试同一组状态。它此前在 `failed` 时停止，而轮次循环却会重试它，这个取舍恰好反了——一次放弃的压缩会保留完整上下文，于是下一个请求会以更小的余量再次撞上同一堵墙。仍然更窄的是预算：压缩跑在自己更短的上限上（3 次重试），而不是轮次循环的 5 次。

可观测性跟随策略。被阶梯恢复过来的 `failed` 不再被归档为面向运维的事故——它作为预期情况记录在 `llm_failed_retried` 之下，而耗尽阶梯的情况仍作为非预期记录在 `llm_failed` 之下。认证失败迁到自己的 `llm_auth` 错误码：它们此前与 `llm_failed` 共用去重桶，因此一次紧跟在已恢复抖动之后的真实凭证失败会被直接丢弃。Trace 分段此前保有旧规则的第二份副本，把一次被重试的 `failed` 读作轮次边界，从而把一轮的 Token、时长与 TPS 抹到了两个 Task 上；它现在跟随引擎的循环。

## 忽略 Stop 的 Provider 不再能把 Session 卡死

在请求中途按下停止，可能会让一个 Session 永远处于运行状态——发不出消息、也压缩不了，而再按一次停止毫无作用。除了重启，这个 Session 就算完了。该问题是针对 Kimi 报告的。

请求循环本已防住了其中一半。在循环挂起于某个 `yield` 时打断——这是常见情况，此时引擎正阻塞着等待工具审批——会被它在再次从上游拉取之前所做的中止检查捕获。而在循环**阻塞于拉取本身之内**时打断则未被覆盖：Provider 的流 Promise 永远不会敲定，于是什么都没回来供检查。空闲计时器也救不了它，因为到那时该请求内部的 AbortController 早已中止，而计时器自己的中止是一次空操作。没有任何东西还能结束这次运行。

现在这次拉取会与一个「在该 controller 中止的那一刻即敲定」的 Promise 竞速——无论触发者是用户还是空闲计时器——因此无论上游怎么表现，请求总能收尾。被遗弃的流会被尽力而为地请求关闭，且刻意不去等待它：一个连自己的中止信号都忽略的流，很可能也会忽略这个。终态由哪一个触发器先触发来分类，因此停止仍然把运行结束为「被打断」，而空闲停滞仍然把它结束为一次会重连的超时。

这一点刻意做成与 Provider 无关。「请求在其信号触发时是否终止」是 Harness 自己要守住的保证，而不是从底下碰巧是哪个 SDK 那里继承来的东西。
