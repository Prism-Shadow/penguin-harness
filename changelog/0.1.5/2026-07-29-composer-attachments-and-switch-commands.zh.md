# Web App：输入区的文件附件，以及用 `/agent` 取代 `@` 提及

- **Date:** 2026-07-29
- **Type:** feature
- **Scope:** `web`, `server`, `core`
- **PR:** [#121](https://github.com/Prism-Shadow/penguin-harness/pull/121), [#122](https://github.com/Prism-Shadow/penguin-harness/pull/122)

[English](2026-07-29-composer-attachments-and-switch-commands.md)

输入区新增第二个上传入口，并去掉了它的 `@` 触发。一条消息现在可以像此前携带粘贴图片那样携带任意文件；而那两个会把对话搬到别处的命令——`/agent` 与 `/model`——现在把选择暂存为一个芯片而不是立即执行，因此开启新对话的那条消息，正是用户本意要写的那条。

## 文件附件

「+」菜单在图片上传正下方放了一个回形针条目：任意文件类型，每条消息至多 20 个文件、单个 10MB、解码后合计 12MB（超限的选择会在浏览器中读取之前就被拒绝，因此不会为了换来一次拒绝而先上传；对于绕过这一层的情况，服务端回以 413 `file_too_large` / `too_many_files`）。选中的文件以可移除的芯片显示在图片缩略图旁边，顺序即选取顺序；而且——与图片一样——一条只有附件、没有文字的消息是可以发送的。目标模式会清空并阻止它们，因为服务端只接受纯文本的目标输入。

这些限制所依附的请求体上限现在是实测而非读取得来的：它此前比较的是 `content-length`，而分块传输的请求压根不带这个头，于是任意大小的请求体都能通过。它改为从流上计数字节。

这里没有上传端点：一个仍处于草稿状态的聊天没有可上传的 Session，因此文件是作为 base64 `data:` URL 搭乘任务请求本身的，与粘贴的图片完全一样。`TaskInputPart` 新增一个 `{type: "file", fileName, dataUrl}` 变体；服务端在不触碰文件系统的情况下校验它，然后把字节写入 Session 草稿区——它随 Session 一起删除，因此清理是免费的——并在消息文本上追加一行 `[attached file: <绝对路径>]`。模型用它平常的文件工具打开该文件；字节从不进入对话。

那一行是追加在用户文本**之后**，而不是作为 `[tag]…[/tag]` 区块前置的：`[use_skills]` 与来源区块是在消息开头解析的，第二个位于开头的区块会打断那条链。追加也有它自己的一条规则，出于同样的原因——`[handoff_from]` 与 `[model_switch_from]` 只有在构成**整条**消息时才被识别，因此一条除了这类区块别无他物的消息会被跳过，那些追加行则自成一条消息。没有这一条，一次携带附件而无文字的交接会把它自己的来源区块变成无法解析的文本，于是新对话开场时在用户气泡里露出的是原始标记，而不是一条横幅。

那一行的写法存放在一个与既有 `[attached image: …]` 产出方共享的 core 模块中，因此两种约定不会各自漂移；Web 渲染器会把两者从正文中重新提取出来，图片变成图像、文件变成一条「附件」提示——并且与图片行一样，只有当该路径确实解析进本 Session 的草稿区时才如此，因此手工敲出来的一行仍是普通文本，而不会渲染进系统外观之中。

附件保留它被赋予的名字。只有 `[A-Za-z0-9._-]` 之外的 ASCII 会被改写——路径中的空格或 shell 元字符，一旦被模型粘进命令里就是货真价实的陷阱——而 ASCII 以上的一切都得以保留，只除去 Unicode 的 C 类（不可见控制符，以及文件名欺骗背后的双向覆盖符）：`报告 2026.pdf` 会落成 `报告-2026.pdf`，而不是一个匿名的 `file.pdf`。Windows 卫生处理随之而来——去掉结尾的点与空格，为设备名加前缀（`con.txt` → `_con.txt`）——而主干部分按 UTF-8 **字节**在字符边界处截断，因为一个 CJK 字符要占三个字节，按字符计数会让中文名撑爆文件系统的真实上限。

草稿区的读取端点也随之改变：它的穿越防护原本是一份字符白名单，非 ASCII 的文件名根本过不去。它现在做结构性检查（不含分隔符、不含控制字符、不是相对标记），并通过解析该路径、要求其父目录恰好是该 Session 的目录来加以确认——这严格强于原先的字符集检查，因为它同时拒绝了字符类会漏掉的那些形态，例如 Windows 的驱动器相对路径 `C:evil.png`。该端点的响应现在携带 `X-Content-Type-Options: nosniff`，因为这是从应用自身的源提供用户上传的任意字节。

## `/agent`，以及两个切换都暂存到发送时

输入 `@` 不再打开 Agent 拾取器，随之消失的还有发送时对开头 `@` 的解析。同样的交接现在经 `/agent` 到达，它会消耗掉自己的斜杠 token，并打开一个与 `/model` 同款构造的拾取器——一个匹配 Agent id 与显示名的搜索框、带头像的行、键盘导航、Escape 或点击外部关闭。两个拾取器共用同一个面板组件，而不是各存一份副本。与 `/model` 一样，`/agent` 只在活跃会话中提供：草稿没有可交接的对话，它在草稿页自己的选择器中挑选 Agent。

两个切换命令都是暂存而非立即执行。选中一个 Agent 或一个模型不会发送任何东西：它在文本区上方钉住一个芯片，用户继续打字，回车（或发送）才执行切换——交接进该 Agent 的新聊天，或把本次对话分叉到所选模型上。只有输入区为空时才回退到默认的自动消息；已选中的 Skill 仍以 `[use_skills]` 区块一同搭乘。两个芯片彼此互斥，也与目标模式互斥；用它们的 × 或在文本开头按退格都能丢弃；而且它们与所属的草稿文本一同缓存——因此切换会话或刷新之后，恢复的是完整的意图，而不是留下没有芯片的孤零零文本。

已暂存的模型分叉还会额外等待会话空闲，并在输入区上方说明这一点：它要从一个运行或压缩仍在追加的 Trace 上分出新会话，因此在运行途中触发会让新模型指向一份被截断的对话。每一条发送路径都把已暂存的模型切换按它早已对待交接目标的方式来处理：仅凭它就足以让输入区可发送、它让那个唯一的操作按钮保持在「发送」而非「停止」，并且它会阻止运行中转向——一个已暂存的切换不是发给正在此处运行的 Agent 的消息。

`[handoff_from]` 来源区块此前告诉接收方模型说它是被「@ 提及」的。该标签及其字段行属于旧 Trace 仍在解析的持久化格式，因此只改了散文部分：它现在与触发方式无关，能在输入区改变交接发起方式之后继续成立。
