# CLI：向聊天中粘贴中日韩文字或 emoji 不再在分块边界处损坏字符

- **Date:** 2026-07-30
- **Type:** fix
- **Scope:** `cli`
- **PR:** [#127](https://github.com/Prism-Shadow/penguin-harness/pull/127)

[English](2026-07-30-paste-filter-utf8.md)

`penguin chat` 此前对每个 stdin 分块单独解码，因此被终端切分到两次读取中的多字节字符会在两半里同时被毁掉。粘贴几千个汉字就足以丢掉一个。

`PasteFilter` 位于原始模式 stdin 与 readline 之间，而原始模式的分块在终端缓冲区结束的地方结束——经常正好在字符中间，因为粘贴是以固定大小的块交付的，与字符边界毫无关系。孤立地解码一个分块，会立刻把它末尾不完整的字节变成 U+FFFD，又把下一个分块开头的字节变成更多的 U+FFFD：一个 3 字节的字符出来变成三个替换字符而不是一个，因此文本还会悄悄变长。粘贴约 1400 个汉字——大致就是一个 4KB 的终端块——就已经足以触发，而且这种丢失在模型开始回答用户从未发送过的文本之前是不可见的。

解码现在经 `StringDecoder` 跨分块进行，它会把不完整的尾部字节序列保留到下一个分块将其补全为止。对 Agent 所运行命令的输出，`setEncoding("utf8")` 早已是这么做的；输入路径是唯一一处手写解码的地方。既有的 `leftover` 机制——用于重组被分块切开的括号粘贴标记——保持不变：它作用于已解码的文本，因此它能看到的字符本就是完整的。

测试喂入的是字节切片而非字符串，因为一个字符串分块按定义就是整数个字符，压根表达不出这个缺陷：一个被从中切断的 CJK 字符、一个在第二个字节处被切断的 emoji、一个逐字节交付的字符，以及一个标记与一个字符在同一批分块边界上同时被撕开。
