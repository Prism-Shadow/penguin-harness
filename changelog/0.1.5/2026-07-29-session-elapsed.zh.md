# Web App：Session 的已用时间取自 Trace 时间戳，因此刷新不再让它重新计时

- **Date:** 2026-07-29
- **Type:** fix
- **Scope:** `web`
- **PR:** [#124](https://github.com/Prism-Shadow/penguin-harness/pull/124)

[English](2026-07-29-session-elapsed.md)

聊天头部的已用时间芯片，在重新加载一个运行中的 Session 时会从零重新开始，而它最终稳定在的数字又取决于浏览器时钟。两者同出一源：运行中的那个 Task 是这个数字里唯一不由 Trace 推导出来的部分。

## 运行中途刷新会续上芯片，而不是重新开始

该芯片渲染的是已结算的跨 Task 总量，加上运行中 Task 至今的墙钟，而后半部分是从一个本地时钟锚点开始跳动的。历史重建会给每条被重放的消息喂入同一个「现在」，因此这个锚点被打上了页面加载那一瞬间的时间戳：一个已经跑了五分钟的 Task 被当作刚刚开始，于是芯片跌回已结算总量并再次从零往上爬。

现在这个锚点会在重放结束后，按该 Task 身后已经过去的时间做回溯校正，因此跳动的数值会从它离开的地方续上。那段已过时间完全以服务端时间测量，之后才施加到本地时钟上，这既把客户端/服务端的时钟偏差排除在结果之外，又让芯片能平滑地继续跳动。实时流不受影响：它一次推送一条消息、用的是真实的当前时钟，而 Task 打开时那里的已过时间仍然是零。

它是针对服务端自己的时钟、在读取时刻测量的，取自消息响应的 HTTP `Date` 头，而不是针对 Trace 的最后一条记录。这个区别正是让「仍在进行中的事件」也被计入的原因：当一个工具正在执行、一个 Request 正在流式输出，或一次压缩正在进行时，自它开始以来 Trace 上并没有追加任何内容，因此只测量 Trace 所记录内容的刷新，会完全看不到该事件已经花掉的时间。Trace 自身的跨度仍是下限——当没有返回 `Date` 头时它就是回退值；而一个被缓存或被改写的头只可能比真实当下更旧，因此它只会少报、绝不会超报。该头携带整秒，这已经比一个按整秒跳动的芯片所能显示的更细。

## 一个已结算的轮次，实时看与重放看读数一致

一个轮次的时长，是从它的第一条消息到它最后一个非压缩 `request_end` 之间的跨度。有一种情况逃出了这条规则：一个压根没有 `request_end` 的轮次——在它的第一个 Request 甚至还没运行时就被打断了——在恰好被实时观看时是用本地时钟测量的，而在稍后被重放时则是用消息跨度测量的。于是同一个轮次在刷新前显示一个数字、刷新后显示另一个，而前者还把空闲检测与中途加入的时延一并折了进去。它现在在两条路径上都结算为其消息跨度，而这个跨度仍由那次打断性中止自身的时间戳来界定。

本地时钟现在只在恰好一个地方进入已用时间的计算——为进行中的 Task 做动画——而绝不进入任何已结算的数值。该统计量的含义未变：仍是每个 Task 墙钟之和。压缩的处理也未变，轮次中途的压缩计入跨度内、轮次之后的压缩计入跨度外，而聊天页与 Trace 页的总量之间那处刻意的差异也保持原样。
