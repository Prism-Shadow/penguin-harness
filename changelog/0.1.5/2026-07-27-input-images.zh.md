# 图片抵达每一个输入通道：运行中转向、目标陈述，以及不再有失效的操作按钮

- **Date:** 2026-07-27
- **Type:** feature
- **Scope:** `core`, `server`, `web`
- **PR:** [#71](https://github.com/Prism-Shadow/penguin-harness/pull/71)

[English](2026-07-27-input-images.md)

转向——即你发给一个已经在运行的 Agent 的消息，在轮次之间以 `[user_steering]` 用户消息投递——此前只能是文本。那是通道的限制，而不是模型的限制：图片最有用的时刻恰恰是在运行途中，此时 Agent 刚刚产出了错误的布局，而最快的纠正就是一张截图。转向现在像提示词一样携带图片，而一张没有说明文字的图片本身就是一条完整的转向消息。

Core 把图片与文本一同排队——`session.steer(input)` 接受一个 OmniMessage 列表，与 `session.run` 接受提示词的形状相同——并把它们作为普通的用户图片消息，紧跟在 `[user_steering]` 区块之后投递；这与提示词所用的形状一致，因此 LLM 客户端、Trace 与重放本就知道该拿它们怎么办。在不支持视觉的模型上，它们会折叠成 `[attached image: <path>]` 行，且是折叠在该区块**内部**，与提示词的图片折叠方式完全一致——因为该区块必须仍然是整条文本：追加在闭合标签之后的一行会让该消息丢失其转向身份，于是每一层渲染都会把它读作一个新的 Task。无法写入的草稿区会终结本次运行——图片通常正是*因为*这次运行走偏了才送来的，因此不带着它继续，只会把这个任务余下的时间花在继续走偏上。

各渲染层沿用它们本就对提示词图片施加的分组规则——直到下一条非图片消息为止的所有内容，都归属于它前面那条消息。在 Web 应用中，图片落在转向芯片内部而不是变成各自独立的气泡，聊天流与 Trace 时间线都不会为它们开启新的 Task；而稍后发送的一条纯图片提示词，仍然是一个货真价实的新轮次。

## 目标可以用一张图片来陈述

「把这个页面做得和这张设计稿一样」是一个目标，而一张截图比一段文字陈述得更好——但目标陈述此前直接拒绝图片。它现在接受图片，只有一处与其他所有输入刻意不同：**无论模型是否支持视觉**，它们都会被折叠为草稿区路径。目标陈述会作为每一轮 `[goal]` 区块的文本被重新注入，因此图片不可能以图片的形式一路搭乘。只在第 1 轮发送它，会让此后的每一轮都指向一个压缩早已移除的东西——这是一种无声的失败，因为该陈述*读起来*仍然是对的。而作为一行路径，它能挺过每一轮与每一次压缩，模型也只在真正去看它时才花费 Token。文本仍然是必需的：一张图片陈述不了任何目标，因此没有文本的目标输入会被拒绝。

在聊天中，第 1 轮会在其气泡下方完整展示这些附件，而之后各轮把它们收拢为一行芯片、点击展开——它们确实存在于每一轮的输入里，但一个二十轮的目标不该把同一张图片重复二十遍。

三条输入路径现在共用同一个折叠逻辑，每个 Session 绑定一次，由各条路径自行决定是否施加：提示词与转向消息只在没有视觉能力时折叠，目标陈述则总是折叠。这个开关此前是隐式的——「草稿区目录是否已配置」被拿来代替「模型是否缺少视觉能力」——而这只在有且仅有一条规则需要编码时才行得通。

## 运行中的按钮不再能把你困住

在任务运行期间，输入区那个唯一的操作按钮会在草稿有任何内容时从「停止」翻转为发送形态。转向模式并不能承载每一种草稿，于是一份它承载不了的草稿——一张没有文字的图片，也就是图片尚不可转向的那个年代——会产生一个**永久禁用**的发送按钮，而它还挤掉了「停止」：消息发不出去，运行也无法从输入区停止。唯一的出路是删掉那个附件。

在图片可转向之后，那种特定草稿就是直接转向。转向仍然承载不了的东西——只选了 Skill 而没有文字或图片（`[use_skills]` 区块属于任务级设置，不是能递给一个已经在进行中的轮次的东西），或者一个 `@` 交接目标——现在会在这一次发送上回退到**后续队列**：按钮保持可用并标注为队列操作，整份草稿作为一条消息发出并由服务端保留到运行结束，而 `@` 交接仍然直接打开它的新会话。「停止」是剩下的那部分：当两条通道都不接收框里的东西时，按钮就是这副面孔——空的输入区，还有目标陈述、模型 key 被拒之后的任何草稿，以及一个运行中会话仍在阻塞的、已暂存的 `/model` 分叉。「框里有东西」与「这次发送有地方可去」是两个不同的问题，而「停止」属于后一个。
