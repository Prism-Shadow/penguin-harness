# Changelog 细则

[English](README.md)

发布历史分两层：

1. [`../CHANGELOG.md`](../CHANGELOG.md)——每个版本一行，链接到它的目录。
2. `<version>/YYYY-MM-DD-<slug>.md`——每项改动一个详情文件，记录该改动做了什么。

这里**刻意不设逐版本的索引文件**。索引是一个每个 PR 都得改的单一文件，会把一次普通的批次变成一次合并冲突；而目录列表加上 `grep` 无需索引即可回答同样的问题。见[如何查找](#如何查找)。

尚未发布的一切都放进 `unreleased/`，它以状态而非编号命名，因为版本号在发布之前并不确定。绝不为未发布的工作创建带编号的目录，也绝不臆造下一个版本号。在发布准备时，把 `unreleased/` 改名为实际发布的版本，写好 `RELEASE.md`，向根文件添加该版本一行，而下一次改动会重新创建 `unreleased/`。

`<version>/RELEASE.md` 是作为 GitHub Release 正文逐字发布的公告：一句导语，然后是 `## Install`、`## Highlights`、`## Notable in this release`、`## Requirements`，以及结尾指向该目录的链接。只有带编号的目录才有它；它在发布时、版本号终于确定之后才写，并且**必须在创建 tag 之前提交**——发布工作流是从该 tag 自己的检出中读取它的，因此事后添加的文件永远不会被发布。缺失时，工作流会退回到 GitHub 依已合并 PR 生成的说明。它只有英文：那是一份发布产物，而不是 changelog 记录。

已发布的目录是冻结的。

## 详情文件格式

照此模板：

```markdown
# <标题：命名这次改动，而不是这个 PR>

- **Date:** YYYY-MM-DD
- **Type:** feature
- **Scope:** `module`, `module`
- **PR:** [#N](https://github.com/Prism-Shadow/penguin-harness/pull/N)
- **Issue:** [#N](https://github.com/Prism-Shadow/penguin-harness/issues/N)
- **Breaking:** yes — <一行说明什么被破坏了>

[English](<name>.md)

<导语段：这次改动做了什么>

## <自定义小节>

- ...
```

元数据块紧接在 H1 之下，每个字段一条 bullet，顺序恒如上，因此读者与 `grep` 都能在同一位置找到每个字段。

| 字段 | 何时必需 | 取值 |
| --- | --- | --- |
| `Date` | 总是 | 该条目的日期，与文件名前缀一致。 |
| `Type` | 总是 | 恰好是以下之一：`feature`（新的、用户可见的能力）、`fix`（缺陷修复）、`refactor`（不改变能力的重构）、`process`（工具链、文档、Skill、CI、发布管道）。 |
| `Scope` | 总是 | 1–5 个代码区域，用反引号包裹，按代码树中的叫法命名（`core`、`server`、`web`、`cli`、`desktop`、`landing`、`docs`、`skills`、`tooling`、`ci`、`model-catalog`、`trace-index` 等）。 |
| `PR` | 存在时 | 指向承载该改动的 PR 的完整链接。裸的 `#N` 在 Markdown 文件中不会渲染成链接，因此务必写出 URL——正文中也一样。为提供背景而在正文中提到的 PR 属于交叉引用，而非承载该改动的 PR，保持内联即可。 |
| `Issue` | 存在时 | 指向该改动关闭或回应的 issue 的完整链接。**写之前先确认某个号码到底是哪一种**——本仓库的缺陷报告与 PR 共用同一套编号空间，而以 issue 形式提交的报告属于这里，不属于 `PR`。多个链接以逗号分隔。 |
| `Breaking` | 仅当破坏性 | `yes — <一行说明>`。其他情况整条省略，使 `grep -rl 'Breaking:' changelog/` 恰好列出所有破坏性改动。 |

不适用的字段应整条省略，而不是写占位符。没有 PR 或 issue 的改动（约定确立之前的条目，或在 PR 之外落地的工作）就是没有那一行。

跨仓库的引用同样写成完整链接，并点名仓库：`agenthub [#162](https://github.com/Prism-Shadow/agenthub/pull/162)`。正文里一个裸的 `#162` 会被读作本仓库的 #162，那是完全不同的一次改动。

### 正文

条目记录的是**做了什么**，用过去时。它以一个导语段开场，随后是按内容命名的自定义小节——优先复用已有名称（`## 细节`、`## 兼容性`），再考虑发明新的。凡 `Breaking` 字段被设置的条目，都带一节 `## 兼容性`，说明什么被破坏以及迁移步骤：给出指令，而不是论证其余部分为何安全。

**推理不落盘。** 不要 `## 为什么`、`## 问题`、`## 决策`、`## 备选方案`、`## 验证`、`## 风险`。思考仍然必须发生——它在对话中汇报，并写进 PR 描述，而 PR 描述始终附着于它所描述的那份 diff。需要它的 Agent 会去拉 PR 描述、`git blame` 或 `git log`；那些都自带时间戳，因此无需先核实是否已经过时。

**不要描述代码库的当前状态。** 「`X` 未从 `Y` 导出」「客户端目录现在放着 `Z`」——这类句子读起来像事实，会随代码移动而悄然失真，并让此后每一位读者付出他们没要求过的一次核实。写这次改动在当时做了什么，而不是仓库今天是什么样。

用相对链接交叉引用其他条目，例如 `[向后兼容](2026-07-24-backward-compatibility.zh.md)`——从中文文件出发时链接中文对照本，使读者停留在同一种语言里。相对链接能挺过发布时的目录改名，也可以机械校验。

## 中文对照

每个条目都以两种语言提供：英文的 `<name>.md` 与中文的 `<name>.zh.md`，逐节对应。两者齐备才算完成——先写英文文件，再写对照本，同一个 PR 内完成。

以下内容保持英文原样，使一次 `grep` 能跨两种语言生效：

- 元数据的字段名及其取值——`- **Type:** feature`、`Scope` 中的标识符、`Date`，以及各链接。只有 `Breaking` 的原因是散文，因此只有它被翻译。
- 代码标识符、模型 id、参数名、错误类与文件路径。

需要翻译的：全部散文，以及小节标题。标准标题采用如下译法：

| English | 中文 |
| --- | --- |
| `## Details` | `## 细节` |
| `## Compatibility` | `## 兼容性` |

自定义标题自然翻译，并保持与英文文件相同的顺序与数量。每个文件在元数据块正下方那一行链接它的对照本：英文文件中写 `[中文版](<name>.zh.md)`，中文文件中写 `[English](<name>.md)`。

## 如何查找

| 问题 | 查询 |
| --- | --- |
| 某个版本发布了什么？ | `ls changelog/<version>/` |
| 历史上哪些改动破坏过兼容？ | `grep -rl 'Breaking:' changelog/` |
| 所有涉及模型目录的条目 | `grep -rl 'Scope:.*model-catalog' changelog/` |
| 只看缺陷修复 | `grep -rl 'Type:\*\* fix' changelog/` |
| 某个条目由哪个 PR 承载 | `grep 'PR:' changelog/<version>/<entry>.md` |
| 某个 PR 出现在哪些条目中 | `grep -rl 'pull/263' changelog/` |
| 回应了已报告 issue 的条目 | `grep -rl 'Issue:' changelog/` |

先写英文，再镜像为中文。历史从 v0.0.1 发布（2026-07-19）之后开始；更早的改动不做回填。
