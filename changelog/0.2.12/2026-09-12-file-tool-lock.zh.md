# edit_file 与 write_file 按文件串行

- **Date:** 2026-09-12
- **Type:** fix
- **Scope:** `core`, `docs`
- **PR:** [#709](https://github.com/Prism-Shadow/penguin-harness/pull/709)

[English](2026-09-12-file-tool-lock.md)

`edit_file` 与 `write_file` 的整段读-改-写现在由按文件的互斥锁护住。两个工具都是读入文件、算出新内容、再以临时
文件 + rename 原子替换，而引擎会并行执行一轮里已批准的工具调用——因此对同一文件的两次编辑，无论来自同一轮还是
同进程的两个子会话，都读到原始内容，最后落盘的 rename 胜出。其中一次编辑被静默丢弃，而两次调用都报告成功。

## 细节

- **锁以文件的真实路径为键**，因此指向同一文件的每个名字都归并到同一个键：软链接与它指向的文件，以及穿过软链接
  目录的路径。尚不存在的路径以其最深层可解析的祖先目录加上其下各段为键——`write_file` 会补建缺失的父目录，所在目录
  往往同样尚不存在——因此创建文件的 `write_file` 与随后的 `edit_file` 共用一个键。解析失败被吸收而不抛出，工具
  原有的报错文案得以保留。
- **锁覆盖读与写整段**：stat、读取、匹配、原子写入。diff 渲染与工具输出都在释放锁之后进行。在另一个写入者后面
  排队期间被中断的调用以 `aborted` 收尾，与在自己的读或写期间被中断一致。
- **先前编辑已删去的 `old_string` 现在会失败。** 不开 `replace_all` 时对同一 `old_string` 的两次并行编辑，结果
  是一次替换加上既有的 `old_string not found` 报错，而不是后者覆盖前者。
- **`read_file` 不加锁**——rename 原子替换已经保证读到的要么是旧内容、要么是新内容，不会是两者的混合。
- **锁只覆盖本进程。** 不使用操作系统级文件锁，因此另起的 CLI 进程、编辑器或用户自己的 shell 对同一文件的写入
  不与这两个工具串行。
