# AgentHub 0.4.14：DeepSeek 的工具链不再死在严格校验的 Responses 中转和「模型没思考」的那一轮上

- **Date:** 2026-09-12
- **Type:** fix
- **Scope:** `core`, `cli`
- **PR:** [#703](https://github.com/Prism-Shadow/penguin-harness/pull/703)
- **Issue:** [#404](https://github.com/Prism-Shadow/penguin-harness/issues/404)

[English](2026-09-12-agenthub-0.4.14.md)

`@prismshadow/agenthub` 从 0.4.12 升至 0.4.14（0.4.13 含 agenthub [#212](https://github.com/Prism-Shadow/agenthub/pull/212)，0.4.14 含 agenthub [#215](https://github.com/Prism-Shadow/agenthub/pull/215)）。两个 DeepSeek 上的故障随之结束。钉在 `deepseek-v4` 的行——直连的 `deepseek-flash` 预置，或 `client_type = "deepseek-v4"` 的中转条目——在严格校验的 Responses 端点后面不再于第一次工具调用之后的那个请求上以 `400 {"code":"invalid_json"}` 死掉：client 把纯文本工具结果作为纯字符串发送，只有带图片的结果才保留 content 部件列表。经 `openai-chat` 协议访问 DeepSeek 的任务也不再跑到一半以 `400 The reasoning_content in the thinking mode must be passed back to the API. (invalid_request_error)` 中断：「有工具调用但没产出思考」的那一轮会以空字符串发出 reasoning 字段。

## 细节

- 0.4.14：`deepseek_v4` 与 `gpt6` 客户端此前把每个工具结果都包进只有一个部件的 content 列表（多模态形态）；严格的 DeepSeek Responses 端点拒绝它，引擎把这个拒绝归类为 provider 4xx、即 `fatal`，Task 当场停住。两者现在采用通用 `openai-responses` 客户端自 0.4.11 起的形态，AgentHub 提供的所有 Responses 与 Chat Completions 客户端都以纯字符串发送纯文本工具结果。`deepseek_v4` 对模型不读图片的 id 依旧拒绝图片。
- 0.4.13：DeepSeek 只在无法从自己签发的 `tool_call` id 复原思考内容时才要求回传，因此这个拒绝只出现在会重签 id 的端点上——中转站，或架在 DeepSeek 前面的自定义 OpenAI 兼容条目——直连的 `provider = "deepseek"` 条目不会遇到。而触发它的那些轮次正是 DeepSeek 自己造的：长工具链跑过头几步之后，它会直接给出工具调用、一点 reasoning 都不带。修复在 AgentHub 的 `openai_chat` 客户端，因此所有钉在 `openai-chat` 的行、以及继承它的 vLLM 行都被覆盖。
- `pnpm-workspace.yaml` 的 `minimumReleaseAgeExclude` 条目改为 0.4.14，替换 0.4.12。
