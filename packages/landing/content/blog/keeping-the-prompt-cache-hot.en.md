> Written for PenguinHarness 0.2.16. Every measurement in this post comes from the harness's cache simulator, which applies Anthropic's published caching rules to recorded requests, not from a live provider.

An agent sends its model nearly the same request again and again: the system prompt, the tool definitions and the whole conversation so far, with one new turn at the end. Providers sell that repetition cheaply. A prefix they have processed recently is served from their prompt cache, the stored KV state of those tokens, at about a tenth of the input price. The condition is strict: each request has to repeat the previous one byte for byte from the front. When a change in the harness breaks that, nothing fails. The answer is the same, the screen looks the same, CI stays green, and the provider bills the whole history again on every request of every running conversation. This post is about how PenguinHarness keeps every request an extension of the last, and about the test system we built to catch the change that breaks it.

**TL;DR**

- A cache miss is invisible, and costly: at Anthropic's standard rates, writing a token to a 5-minute cache entry costs 12.5 times as much as reading one.
- Before [PR #700](https://github.com/Prism-Shadow/penguin-harness/pull/700), the compaction request read 3,241 of its 7,977 tokens from the cache. Today it reads 7,945.
- Three suites, 33 tests with no network and no keys, record the exact requests and replay them through an Anthropic-shaped cache simulator.
- A timestamp in the system prompt multiplies a ten-request task's input cost by 4.24.
- Explicit breakpoints after the tools and the system prompt would save 1,656 tokens on the first request after a thinking-level change or a compaction.

## What a prompt cache reuses

PenguinHarness reaches providers through MMSP (`@prismshadow/mmsp`). We work from Anthropic's rules, the most fully documented ones and the ones our simulator implements; other providers differ in detail, but every one needs the prefix to repeat exactly. A request is cached as one prefix in a fixed order: tools, then the system prompt, then the messages. The cache is written at breakpoints (`cache_control`), up to four per request. Automatic caching places one breakpoint at the last cacheable block and moves it forward as the conversation grows. MMSP's Claude client sends exactly that: a single top-level `cache_control: {"type": "ephemeral"}`. A read checks the prefix ending at each breakpoint, then walks back over at most 20 positions, counting the breakpoint itself as the first; a run of consecutive `tool_use` or `tool_result` blocks counts as one position. A prefix shorter than the model's minimum (1,024 tokens for Claude Sonnet 4.6, and from 512 to 4,096 across current models) is not cached at all. An entry lives five minutes and is refreshed for free each time it is read. A one-hour lifetime costs twice the base input price to write, and PenguinHarness does not request it.

In a healthy agent, each request reads its predecessor's whole prefix and writes only what it appended. We draw requests as strips coloured by cache state, with the same colours in every figure.

A change anywhere in the prefix invalidates everything after it. What survives follows from the order:

| What changes | Tools | System prompt | Messages |
| --- | --- | --- | --- |
| The model | lost | lost | lost |
| A tool definition (name, description, schema or order) | lost | lost | lost |
| Fast mode (`speed`) | kept | lost | lost |
| The system prompt | kept | lost | lost |
| `tool_choice` | kept | kept | lost |
| Thinking parameters | depends on the model | depends on the model | lost |
| An earlier message | kept | kept | kept up to the edit |

"Kept" means the bytes still match. For the provider to read them back, an entry must also end there, and an entry ends only at a breakpoint. So the property a harness has to keep is easy to state: every request extends the previous one, byte for byte, from the front. The first rule we checked against it had been written to protect it, and did the opposite.

## A rule that guarded the cache, and broke it

Compaction fires when a context is at its largest. In the engine's default mode, it asks the model to summarize the conversation, then continues in a fresh context that opens with the summary. Until [PR #700](https://github.com/Prism-Shadow/penguin-harness/pull/700), the compaction request was the one request that ignored the thinking level the user had pinned. It went out at the level the context had opened with. The reason was the cache: holding its parameters fixed was meant to keep its prefix identical to the context it summarizes, at the moment a miss would cost the most.

The rule held as long as nobody touched the level. Once the user moved it mid-context, every later turn went out at the new level, and the compaction request became the only request whose prefix differed. We recorded one Session, with one task, a thinking-level move, then a four-round task that crosses the compaction threshold. We replayed it twice through the simulator: once as sent today, and once with the compaction request's parameters set back to the opening level, as before #700. Before #700, the compaction request read 3,241 of its 7,977 tokens and wrote 4,736. Today it reads 7,945 and writes 40.

So the root cause was narrow: the compaction request was the only request still sending the opening level, and its parameters differed from every cache entry written since the move. A test did cover this request, and it asserted the old behavior as the contract: `engine.test.ts` expected the levels `["high", "high", undefined]`. It checked what the request carried, and nothing checked what that would cost. We needed a test that reads a request the way a provider bills it.

## Every request an extension of the last, measured in provider tokens

The redesign treats the request prefix as fixed for the life of a model context, with the thinking level as the one parameter allowed to move, and holds the engine to that with tests that count in the provider's own tokens.

The engine rules cover every place where a harness does something other than append a turn:

- **The prefix is fixed for a model context.** The system prompt, the toolset (MCP tools included) and the model are assembled when a context opens. An edit to `AGENTS.md`, a Skill or an MCP Server, whether by the user or by the agent, takes effect in the next context, and resuming an open context reuses the prompt recorded in the Trace's `session_meta`. The system prompt's `Date:` line holds a calendar date, and fast mode belongs to the context's model object.
- **History is append-only.** The compaction request goes out on the same model object with the same configuration, plus one appended user turn holding pending tool results and the compaction prompt. An unusable summary is retried with a corrective note appended.
- **Steering rides the tool-result turn.** A message sent while a task runs goes out as a `[user_steering]` block in the same user turn as the tool results of the round in flight.
- **Interruptions and retries change only the last user message.** An interrupted request keeps the tool results it carried, and the rest of the turn, the model's partial output included, is flattened into a `[turn_aborted]` block. A reconnect resends the original input with a `[turn_retried]` block appended.
- **The thinking level is the one parameter that moves inside a context.** It costs one miss and then holds; since #700, the compaction request and the next context use the moved level too, and the Web App offers **Compact, then switch**.
- **A model switch compacts on the old model**, which reads back its own prefix; the new model starts a new cache line.
- **`max_tokens` stays out of the key**, though it is recomputed for every request.

[PR #722](https://github.com/Prism-Shadow/penguin-harness/pull/722) added the test system that holds the engine to these rules. It replaces only the network: everything between the scripted stream and the recorded request is the code that ships.

`recordingModel` builds a real `GenerativeModel` whose provider client reads its stream from a script, so MMSP's stateful history and its transforms to Anthropic's request shape run for real. A scripted reply streams thinking closed by its signature, then text, then tool calls, and it can end cleanly, drop the connection or hang until aborted. `diagnoseCacheMiss(prev, next)` returns the earliest level at which `next` stops extending `prev`, in the precedence order Anthropic's [cache diagnostics](https://platform.claude.com/docs/en/build-with-claude/cache-diagnostics) use: `model_changed`, `system_changed`, `tools_changed`, `parameters_changed`, then `messages_changed` with the message, the block and an estimate of the input after it. `parameters_changed` is our addition; for a change to `thinking`, `output_config` or `tool_choice`, Anthropic's diagnostics answer `unavailable`.

The design has costs. The simulator models one provider's documented rules, so it can be wrong wherever a live deployment behaves differently, and it has to follow the documentation when that changes. A failing test also blocks a merge until a person decides whether the extra tokens are worth paying for, because nobody may edit the expected numbers to pass. In return, 33 tests run in CI whenever the core package changes, in under two seconds on our test machine, with no network and no keys, and a failure names the request, the tier and the tokens. The hard part was the simulator: a check that is too simple lets through the changes we wanted to catch, and fails the ones that are fine.

## Teaching a test to see a cache

Calling the live API from CI was the first idea we dropped: it costs money on every run, varies from run to run, and needs keys that contributors and forked pull requests do not have. The second was the diagnostic alone, asserting that each request is a byte-for-byte extension of the previous one. It fails in both directions. It cannot see a miss whose bytes did not change: an expired entry, a lookback that falls short, a prefix under the minimum. And it flags changes the provider does not care about. A retry or a mid-task interruption adds a `[turn_retried]` or `[turn_aborted]` block to the last user message, so the diagnostic, which compares whole messages, reports `messages_changed`. But that block comes after the cached `tool_result`, and a provider still reads everything up to it. So the diagnostic stays, to name the tier that moved, and the provider's half became a rule engine of its own, `PromptCacheSim`:

- **Blocks.** A request becomes one ordered block list: the model id, one block per tool definition, a virtual block for the fast-mode parameters (`speed`, `betas`), the system prompt, a virtual block for the remaining prompt-affecting parameters, then every content block of every message. That order reproduces the table above.
- **Positions.** A run of `tool_use` blocks, or of `tool_result` blocks, is one position; every other block is its own position.
- **Writes only at breakpoints.** A request writes one entry per breakpoint, the hash of the prefix ending there, readable once the request completes. Replay completes every recorded request, including one that dropped or was interrupted after its response began, since the documentation makes an entry available once the response begins. By default there is one breakpoint at the last block, as MMSP sends; `breakpoints: "tools-system-automatic"` adds explicit ones after the last tool and after the system prompt.
- **Reads.** Each breakpoint looks back over at most 20 positions from its own position. The longest live match wins, and reading refreshes it.
- **Limits.** Nothing under 1,024 tokens is cached, and an entry expires five minutes after its last use on an injected clock, so a test can advance time and show an expiry.

Tokens are estimated at four characters per token, and `prompt-cache-simulator.test.ts` pins each rule with hand-built requests. `prompt-cache-lifecycle.test.ts` then feeds every request of a real `Session` scenario, child Sessions included, through one simulator, because a provider does not keep a separate cache per Session. One assertion, `expectHits`, holds every scenario to the same rule: each request after the first of its context reads back the whole prefix of that context's previous request. A scenario that cannot meet the rule by design names the request and the reason:

```ts
const reason =
  "the context reopened and no breakpoint sits after the system prompt, so the fixed " +
  "prefix the new context resends is not addressable either";
expectHits(order, usages, new Map([[3, reason]]));
```

An exemption has to earn its place: if the named request in fact reads back the whole prefix, the test fails and asks for the exemption to be removed. When a request falls short, the report says by how much and why, here for a variant in which one word of the `exec_command` description changes at request #4:

```text
#4 should read back all of #3
prompt-cache report (tokens; previous = the same context's previous request):
...
#3  main  read=5085   creation=1556 input=0 hit=76.6%  full hit on #2
#4  main  read=0      creation=8199 input=0 hit=0.0%   short of #3 by 6641 tokens: tools_changed ("exec_command" definition changed)
#5  main  read=8199   creation=1556 input=0 hit=84.0%  full hit on #4
...
```

The three suites split the work:

| Suite | Tests | A failure means |
| --- | ---: | --- |
| `prompt-cache-invariants.test.ts` | 8 | A change made a request stop extending its predecessor on the wire. This is the regression itself. |
| `prompt-cache-lifecycle.test.ts` | 11 | The same regression, counted in provider tokens across a real Session's lifecycle. |
| `prompt-cache-simulator.test.ts` | 14 | The rule engine changed. That is correct only when the provider's documentation changed. |

Their numbers are never edited to make a test pass. Changing an expected number, or adding a request to the list of misses that exist by design, is a decision to spend users' money, and the repository's development guide says so in so many words. With the harness and the simulator in place, we could ask the questions that only the bill used to answer.

## What the cache sees now

These numbers come from a run made for this post, not from a live provider: a scenario script built only on the helpers above drove a real `Session` over a scripted stream at commit 6aa4ed195, replaying each request through `PromptCacheSim` with 10 seconds between requests. The agent is the suites' fixture, with model id `claude-sonnet-4-6` and a 1,673-token fixed prefix; the background-notice and subagent scenarios run on a real `Environment` with stub tool definitions instead. Every tool call returns the same 5.8 KB of output, about 1,556 tokens per round. Input cost is counted in base-price tokens: a token read counts 0.1 and a token written 1.25, Anthropic's 5-minute rates.

Across 14 Session scenarios, the tool loop reads 33,474 of its 44,501 input tokens from the cache, 75.2%, while every request writes only what it appended, and tokens are written a second time only where the prefix changes on purpose or an entry expires. A resume ten minutes later writes its whole history again although its bytes are identical: an expiry, not a divergence. One case is too small to see at the chart's scale: an interruption on a task's first request rewrites that prompt into `[turn_aborted]`, so the 36 tokens after the last reachable entry, the previous answer and the prompt, are written again.

Explicit breakpoints after the tools and the system prompt recover those two tiers on the first request after a thinking-level change or a compaction. A real subagent would gain nothing, because its child loses the subagent tools and names its own Session ID in its prompt. A breakpoint also needs the prefix before it to clear the minimum: with six tools (517 tokens including the model id) the timestamp variant stays at 4.24×, and with eighteen tools (2,269 tokens) it falls from 4.44× to 3.63×.

The simulator's token counts are estimates, so its ratios are more reliable than its absolute counts. It takes the optimistic reading where the documentation says the thinking-parameter rule depends on the model, and it keeps every entry for its full lifetime, which only a live endpoint can confirm; the Web App shows live hit rates for each conversation.

The three suites have been in [`packages/core/test`](https://github.com/Prism-Shadow/penguin-harness/tree/v0.2.16/packages/core/test) since PenguinHarness 0.2.13.
