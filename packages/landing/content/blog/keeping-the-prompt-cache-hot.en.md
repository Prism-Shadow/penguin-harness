> Written for PenguinHarness 0.2.16. Every measurement in this post comes from the harness's cache simulator, which applies Anthropic's published caching rules to recorded requests, not from a live provider.

Every agent turn resends nearly the same request, and providers serve the repeated prefix from their prompt cache at a tenth of the input price when it repeats byte for byte. A change that breaks this fails nothing but the bill. Here is how a coding agent catches it.

**TL;DR**

- A cache write costs 12.5 times a read (`claude-sonnet-4-6`).
- A system-prompt timestamp cuts the hit ratio from 83.0% to 0.0%.
- Before #700, the compaction request read 3,241 of 7,977 tokens; it now reads 7,945 of 7,985.

## A miss only the bill can see

A provider caches a request as one prefix in a fixed order: tools, then the system prompt, then the messages. In a healthy agent, each request reads its predecessor's whole prefix back and writes only what it appended. A change anywhere cuts the prefix at that point, and everything after the cut is written again. For `claude-sonnet-4-6`, a 5-minute cache write costs $3.75 per million tokens and a read costs $0.30, so every token after the cut costs 12.5 times as much. Yet a miss changes no answer, no screen and no log, and CI stays green. Until [PR #722](https://github.com/Prism-Shadow/penguin-harness/pull/722), the bill was the only place a miss ever showed up, so we built a test that sees it first.

## Record every request, then read it twice

The test system replaces only the network. Real Sessions run against a scripted model stream, so the code we ship assembles every request, and we record each request as the bytes a provider would receive. Two readers then judge each recording. One is a diagnostic that compares the recording's bytes with the previous request and names the first part that changed: the model, the tools, the system prompt, a parameter or the messages. The other is a simulator that applies Anthropic's [published caching rules](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) and reports what a provider would have read and written. A test fails when a request does not read back the whole prefix of the request before it. The repository's development guide sends a coding agent to these suites whenever it touches request assembly, history, compaction, the system prompt or a tool definition, so the check runs while the change is still being written.

Calling the live API from CI would cost money on every run and need keys that forked pull requests do not have. Checking bytes alone would miss an entry that expired while the bytes stayed the same. Reading each request both ways avoids both problems, at a price: the simulator follows one provider's documentation and has to change when that documentation does, and a failing test holds the merge until a person decides whether the extra tokens are worth paying.

The parts of a request follow the provider's order, so a change loses its own part and everything after it, and the report names the part where the loss begins.

## Four design choices, replayed both ways

Each pair below runs a design we did not take against the one PenguinHarness uses, through the same simulator and on one scale, so only the cache state changes. The first three replay one recorded ten-request task with six tool definitions, and the last replays the Session behind #700, all from a run made for this post at commit 6aa4ed195. Cost means input cost relative to the design we took, with a read counted at 0.1 and a write at 1.25 of the base price.

### Date the context, not the request

A timestamp in the system prompt looks harmless, but the system prompt comes before every message. Each request then diverges there and writes its whole history again: the hit ratio falls from 83.0% to 0.0%, and the input cost rises to 4.24 times the baseline. PenguinHarness writes the date into the system prompt once, when a context opens, and keeps that prompt until the context closes.

### Tool edits wait for the next context

Tools sit at the very front of the prefix, so even a tiny edit to them is expensive. One word changed in one tool description at request #4 makes that request write its whole prefix again, and the hit ratio falls to 75.2% at 1.30 times the cost. In PenguinHarness, an edit to the Agent's configuration, whether the user or the agent itself makes it, lands in the next context and never in the running one.

### Resume replays, it does not rebuild

Dropping the signatures at request #4 cuts the prefix at the first assistant turn, and the hit ratio falls to 77.5% at 1.21 times the cost. So PenguinHarness replays the recorded history byte for byte, and an invariants test checks that the signature survives.

### Compaction follows the Session's thinking level

Compaction asks the model to summarize a context at its largest, then opens a new context with the summary. Until [PR #700](https://github.com/Prism-Shadow/penguin-harness/pull/700), the compaction request went out at the thinking level the context had opened with, a rule meant to keep its prefix identical to the context it summarizes. Once the user moved the level mid-context, every turn carried the new level, so the compaction request became the one request that differed. Replayed as the code before #700 sent it, the Session fails `expectHits` and prints:

```text
#6 should read back all of #5
prompt-cache report (tokens; previous = the same context's previous request):
...
#5  context 1  read=6388  creation=1557 input=0 hit=80.4%  full hit on #4
#6  context 1  read=3241  creation=4736 input=0 hit=40.6%  short of #5 by 4704 tokens: parameters_changed [output_config]
#7  context 2  read=0     creation=1718 input=0 hit=0.0%   first request of this context: expected 3241 to be greater than or equal to 7945
```

The fix was one argument: `runCompactionRequest` now passes the Session's level exactly as a turn does. The compaction request reads 7,945 of its 7,985 tokens instead of 3,241 of 7,977, and the Session's hit ratio rises from 52.4% to 65.1%.

## Run it yourself

The 33 tests need no network and no keys, and ran in 1.6 seconds on our test machine:

```bash
pnpm --filter @prismshadow/penguin-core exec vitest run prompt-cache
```

The helpers are in [`packages/core/test/helpers/prompt-cache/`](https://github.com/Prism-Shadow/penguin-harness/tree/v0.2.16/packages/core/test/helpers/prompt-cache), and [The Agent Loop](https://penguin.ooo/docs/agent-loop) describes compaction.
