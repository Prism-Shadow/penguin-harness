> Written for PenguinHarness 0.2.16. Every measurement in this post comes from the harness's cache simulator, which applies Anthropic's published caching rules to recorded requests, not from a live provider.

An agent sends its model nearly the same request again and again: the system prompt, the tool definitions, and the whole conversation so far, with one new turn at the end. Providers sell that repetition cheaply. A prefix they have processed recently is served from their prompt cache, the stored KV state of those tokens, at about a tenth of the input price. The condition is strict: each request has to repeat the previous one byte for byte from the front. When a change in the harness breaks that, nothing fails. The answer is the same, the screen looks the same, CI stays green, and the provider bills the whole history again on every request of every running conversation. This post is about how PenguinHarness catches that change automatically, with a coding agent that runs the prompt-cache suites whenever it changes how a request is assembled and reports a miss as a failing test: why the suites exist, how they are built, how to use them, what they measured, and one regression they would have caught.

**TL;DR**

- A miss is invisible and costly: for `claude-sonnet-4-6`, writing a token to a 5-minute cache entry costs 12.5 times as much as reading one.
- Three suites, 33 tests, no network, no keys: real Sessions over a scripted stream, every request recorded and replayed through an Anthropic-shaped cache simulator.
- A timestamp in the system prompt multiplies a ten-request task's input cost by 4.24.
- Before [PR #700](https://github.com/Prism-Shadow/penguin-harness/pull/700), the compaction request read 3,241 of its 7,977 tokens from the cache; today it reads 7,945 of 7,985.

## Why a cache miss has to fail a test

PenguinHarness reaches providers through MMSP (`@prismshadow/mmsp`). We work from Anthropic's rules, the most fully documented ones and the ones our simulator implements; other providers differ in detail, but every one needs the prefix to repeat exactly. A request is cached as one prefix in a fixed order: tools, then the system prompt, then the messages. The cache is written at breakpoints (`cache_control`), at most four per request. Automatic caching puts one breakpoint at the last cacheable block and moves it forward as the conversation grows. MMSP's Claude client sends exactly that: a single top-level `cache_control: {"type": "ephemeral"}`.

A read checks the prefix ending at each breakpoint, then walks back over at most 20 positions, counting the breakpoint itself as the first. A run of consecutive `tool_use` or `tool_result` blocks counts as one position. Nothing shorter than the model's minimum is cached (1,024 tokens for Claude Sonnet 4.6, and from 512 to 4,096 across current models). An entry lives five minutes, refreshed for free each time it is read.

In a healthy agent, each request reads its predecessor's whole prefix and writes only what it appended. We draw requests as strips coloured by cache state, with the same colours in every figure below.

The economics follow from the prices. For `claude-sonnet-4-6`, a 5-minute cache write costs $3.75 per million tokens and a cache read $0.30, so every token after a divergence costs 12.5 times what it would have cost as a hit. A change that repeats on every request pays that on every request. A change at any tier loses that tier and everything after it. So the property a harness has to keep is easy to state: every request extends the previous one, byte for byte, from the front.

Yet nothing in the repository used to check it. A miss shows up in no signal the project produces: the tests pass, the screen is unchanged and the logs are clean. Until [PR #722](https://github.com/Prism-Shadow/penguin-harness/pull/722), the bill was the only reader of the request.

## How the test system is designed

The idea is to replace only the network, let the code that ships assemble every request, and read the result twice: once as bytes (does the request still extend the last one?) and once as a provider would (would it have hit?).

Two simpler designs fail. Calling the live API from CI costs money on every run, varies from run to run, and needs keys that contributors and forked pull requests do not have. Checking bytes alone is blind to a miss whose bytes did not change (an expired entry, a lookback that falls short, a prefix under the minimum), and it flags a `[turn_retried]` or `[turn_aborted]` block appended to the last user message, although a provider still reads everything up to that block.

The helpers live in [`packages/core/test/helpers/prompt-cache/`](https://github.com/Prism-Shadow/penguin-harness/tree/v0.2.16/packages/core/test/helpers/prompt-cache). `recordingModel(config, script, { label, onRequest })` in `recording.ts` returns a real `GenerativeModel` whose provider client reads its stream from a list of scripted replies. MMSP's stateful history and its transforms to Anthropic's request shape run for real, so each `RecordedRequest` holds the bytes the client would have sent. A scripted reply streams thinking closed by its signature, then text, then tool calls, and it can end cleanly, drop the connection or hang until aborted.

`diagnoseCacheMiss(prev, next)` in `diagnostics.ts` reads two consecutive recordings as bytes and returns the earliest divergence, in the precedence Anthropic's [cache diagnostics](https://platform.claude.com/docs/en/build-with-claude/cache-diagnostics) use: `model_changed`, `system_changed`, `tools_changed` (with the names, or which definition changed), `parameters_changed` (with the keys), or `messages_changed` (with the message, the block, and an estimate of the input after it at four characters per token). `parameters_changed` is our addition, for `thinking`, `output_config`, `tool_choice`, `speed` and `betas`. `max_tokens`, `stream` and the `cache_control` marker are outside the key.

`PromptCacheSim` in `simulator.ts` reads the same recordings as a provider would. It is a rule engine:

- **Blocks.** A request becomes one ordered list: the model id, one block per tool definition, a virtual block for the fast-mode parameters (`speed`, `betas`), the system prompt, a virtual block for `thinking`, `output_config` and `tool_choice`, then every content block of every message.
- **Positions.** A run of `tool_use` blocks, or of `tool_result` blocks, is one position.
- **Writes only at breakpoints.** A write is staged when a request begins and becomes readable when it completes, so a request issued mid-stream cannot read the one in flight.
- **Reads.** Each breakpoint looks back over at most 20 positions from its own position; the longest live match wins, and a read refreshes it.
- **Limits.** A 1,024-token minimum, and a five-minute lifetime on an injected clock.

By default there is one breakpoint at the last block, as MMSP sends; the `breakpoints: "tools-system-automatic"` option adds explicit ones after the last tool and after the system prompt, so a test can measure a policy the harness does not send. The output is a `CacheUsage` in the provider's own fields (`cache_read_input_tokens`, `cache_creation_input_tokens`, `input_tokens`) with the hit ratio, from tokens estimated at four characters each.

`fixtures.ts` holds the agent the Session suites drive (model id `claude-sonnet-4-6`, the tools `exec_command` and `read_file`, and a system prompt sized so that the fixed prefix clears the 1,024-token minimum on its own) and the one assertion every lifecycle scenario shares. `expectHits` requires each request after the first of its context to read back the whole prefix of that context's previous request. A scenario that cannot meet the rule by design names the request and the reason, and an exemption has to earn its place: if the named request in fact reads the whole prefix back, the test fails and asks for the exemption to be removed.

Three suites build on these parts. `prompt-cache-invariants.test.ts` runs eight cases on a real `ContextEngine` and asserts on the diagnosis: requests extend each other on the wire; steering rides the same user turn as the tool result (`[user_steering]`); a thinking-level move costs one `parameters_changed` and then holds, through the compaction request and the next context; a reconnect only grows the retried turn's input (`[turn_retried]`); a resumed Session replays the live history byte for byte; the compaction request extends the turn it follows; and a model switch compacts on the old model, leaving the old line intact if it does not complete. `prompt-cache-lifecycle.test.ts` runs eleven scenarios on a real `Session` through one simulator, child Sessions included, from an ordinary conversation and an interruption to a subagent, a resume from a Trace, a compaction and a model switch. `prompt-cache-simulator.test.ts` pins the rule engine with fourteen hand-built requests, one rule each.

The design has costs. The simulator models one provider's documented rules, so it can be wrong where a deployment behaves differently, and it has to follow the documentation when that changes. A failing suite also blocks a merge until a person decides whether the extra tokens are worth paying, because nobody may edit the expected numbers to pass. In return, the 33 tests need no network and no keys, and they ran in 1.6 seconds on our test machine for this post. What they print when one fails is the subject of the next section.

## How to use it

The repository's development guide routes request assembly, history rebuild, compaction, the system prompt, and a tool's description or schema to these three suites, and one file filter runs all of them:

```bash
pnpm --filter @prismshadow/penguin-core exec vitest run prompt-cache
```

CI runs the core package's tests on every pull request to `main` that touches the package, and on every push to `main`.

A failure attaches a report to the failing assertion. The invariants suite prints `formatDiagnostics`, one line per request with its message count, its thinking settings and the reason it diverged, while the lifecycle suite prints `formatCacheReport`, one line per request with what it read and wrote, then `full hit on #p` or `short of #p by N tokens` with the diagnostic's reason, where `#p` is the same context's previous request. Here is the real output for one edited word in the description of `exec_command` at request #4, from the run made for this post:

```text
#4 should read back all of #3
prompt-cache report (tokens; previous = the same context's previous request):
...
#3  main  read=5085   creation=1556 input=0 hit=76.6%  full hit on #2
#4  main  read=0      creation=8199 input=0 hit=0.0%   short of #3 by 6641 tokens: tools_changed ("exec_command" definition changed)
#5  main  read=8199   creation=1556 input=0 hit=84.0%  full hit on #4
...
```

The report names the request, the tier that moved and the tokens it cost, and which suite failed tells you what kind of problem it is:

| Suite | Tests | A failure means |
| --- | ---: | --- |
| `prompt-cache-invariants.test.ts` | 8 | A change made a request stop extending its predecessor on the wire. This is the regression itself. |
| `prompt-cache-lifecycle.test.ts` | 11 | The same regression, counted in provider tokens across a real Session's lifecycle. |
| `prompt-cache-simulator.test.ts` | 14 | The rule engine changed. That is correct only when the provider's documentation changed. |

A new feature that changes what a Session sends gets a lifecycle scenario. The idiom is short, and these lines come from the suite's ordinary-conversation case and its compaction case:

```ts
const { order, onRequest } = ordering();
const { model } = recordingModel(modelConfig(), [toolTurn(), { text: "…" }], { label: MAIN, onRequest });
const session = makeSession({ llm: model, environment: fakeEnvironment });
await collect(session.run([userText("…")], { approve: allowAll }));
expectHits(order, replay(order));
// A step that cannot hit by design names the request and the reason:
expectHits(order, usages, new Map([[3, reason]]));
```

An exemption comes with its own bound on the loss, through `prefixTokens`, `tokensBeforeLastUserMessage` or `toolsAndSystemTokens`, and a step the harness has to assemble as an extension also gets an invariants case that expects `diagnoseSeries` to return `none` for every pair. A case that depends on time injects the clock, as in `new PromptCacheSim({ now: () => clock })`, and `breakpoints: "tools-system-automatic"` measures a breakpoint policy without changing the harness.

One rule governs the expected numbers, and the development guide puts it this way: "**Never re-baseline these to green.** Editing an expected number, or adding a case to the list of misses that are there by design, is a decision about spending the user's money — not a fix." The contributor puts the tier that moved and its cost in front of whoever decides, and says so in the pull request, because no other signal in the repository would show it. With the suites in place, the question the bill used to answer can be asked of a whole Session, so we asked it.

## What it measured

These numbers come from a run made for this post, not from a live provider. A throwaway scenario script built only on the helpers above drove a real `Session` over a scripted stream at commit 6aa4ed195 and replayed each request through `PromptCacheSim`, with 10 seconds between requests. The agent is the suites' fixture, with a 1,673-token fixed prefix; the background-notice and subagent scenarios instead run on a real `Environment` with stub tool definitions. Every tool call returns the same 5.8 KB of output, about 1,556 tokens per round. Input cost is counted in base-price tokens: a token read counts 0.1 and a token written 1.25.

Across the 14 Session scenarios, the tool loop reads 33,474 of its 44,501 input tokens from the cache, 75.2%, while every request writes only what it appended. Tokens are written a second time only where the prefix moves on purpose or an entry expires. A resume ten minutes later writes its whole history again although its bytes are identical: an expiry, not a divergence. An interruption on a task's first request rewrites that prompt into `[turn_aborted]`, so the 36 tokens after the last reachable entry are written again, too few to see at the chart's scale. The compaction, the subagent and the model switch each open a new cache line by design.

We then injected anti-patterns into one recorded ten-request trace with six tool definitions. A change on every request bills the whole run as writes: a timestamp in the system prompt takes the input cost from 25,158 to 106,659 base-price tokens, 4.24 times the baseline, and the factor grows as the history outgrows each turn's new tokens, toward the 12.5× gap between a write and a read. A one-off change costs one rewrite of everything after it, wherever it lands.

The simulator's `breakpoints` option measures one more question: what explicit breakpoints after the tools and the system prompt change. With breakpoints on, the first request after a thinking-level change and the first request of a reopened context read 1,656 tokens instead of none, while the model switch reads nothing either way. Two limits apply to all of these numbers. Token counts are estimates, so ratios are more reliable than absolute counts. And the simulator keeps every entry for its full lifetime and takes the optimistic reading where the documentation marks the thinking-parameter rule model-specific. One of the scenarios in this run is the regression that started this work.

## One regression, start to finish

Compaction fires when a context is at its largest: in its default mode, the engine asks the model to summarize the conversation, then continues in a fresh context that opens with the summary. Until #700, the compaction request was the one request that ignored the thinking level the user had pinned. It went out at the level the context had opened with, and the reason was the cache: holding its parameters fixed was meant to keep its prefix identical to the context it summarizes, at the moment a miss would cost the most.

The rule was written to protect the cache, and it did the opposite. The exception only shows after the user moves the level mid-context. From then on every turn goes out at the new level, so the compaction request was the one request whose prefix differed. To reproduce the miss, we recorded one Session with one task, a thinking-level move, then a four-round task that crosses the compaction threshold. We replayed it twice: once as the code sends it today, and once with the compaction request's `output_config` removed, as the code sent it before #700. Today's run passes `expectHits` with two named exemptions: the request after the move and the context the compaction opens. The pre-#700 run fails:

```text
#6 should read back all of #5
prompt-cache report (tokens; previous = the same context's previous request):
...
#5  context 1  read=6388  creation=1557 input=0 hit=80.4%  full hit on #4
#6  context 1  read=3241  creation=4736 input=0 hit=40.6%  short of #5 by 4704 tokens: parameters_changed [output_config]
#7  context 2  read=0     creation=1718 input=0 hit=0.0%   first request of this context: expected 3241 to be greater than or equal to 7945
```

Before #700, the compaction request read 3,241 of its 7,977 tokens and wrote 4,736. Today it reads 7,945 of 7,985 and writes 40. Over the whole Session, that is 19,421 tokens read and 17,640 written before, against 24,125 and 12,944 today. Request #2 misses in both runs, because the level moved there.

Taking request #6 apart shows why. The cache entries that end inside its prefix were written by #0 and #1 at the opening level, and by #2 to #5 at the moved level. The parameters block sits after the system prompt and before the messages, so every entry written after the move differs from #6 at that block. The read falls back to #1's 3,241-token entry, and 4,696 tokens of history are written again, plus 40 new ones. In this short context the old entry was still inside the 20-position lookback, matching 10 of the request's 23 blocks; in a longer one, the request would have read nothing. The tools and the system prompt survive a parameters change only on models that render the thinking configuration after them, which the documentation marks model-specific.

The fix was one argument: `runCompactionRequest` now passes the Session's pinned level exactly as a turn does. A test did cover this request before, but it asserted the old behavior as the contract: `engine.test.ts` expected the levels `["high", "high", undefined]`, and #700 inverted it to `["high", "high", "high"]`. Since #722, the invariants case "moving the thinking level invalidates the prompt cache once and then holds" pins the same thing in cache terms: one `parameters_changed`, then `none`, with the compaction request carrying the same configuration as the turn before it and the moved level reaching the next context. The old test checked what the request carried, and the new one checks what it costs. The suites have been in `packages/core/test` since PenguinHarness 0.2.13.
