> 本文基于 PenguinHarness 0.2.16 撰写。文中所有测量数据都来自 Harness 的缓存模拟器：它把 Anthropic 公开的缓存规则套用到录制下来的请求上，并非线上供应商的实测。

Agent 发给模型的请求几乎每次都一样：系统提示词、工具定义、到目前为止的全部对话，末尾再加上新的一轮。供应商把这种重复卖得很便宜：最近处理过的前缀，直接从提示词缓存（Prompt Cache，即这些 Token 的 KV 状态）里取，只收一成左右的输入价。不过条件很严格：每个请求都必须从开头起与上一个请求逐字节一致。一旦 Harness 的某个改动破坏了这一点，什么错都不会报：回答不变，界面不变，CI 照样全绿；供应商却会在每个进行中的对话的每个请求上，把整段历史重新计费。本文讲 PenguinHarness 如何自动抓住这类改动：Coding Agent 每次改动请求的组装方式，都会运行提示词缓存测试集，并把未命中报告为一个失败的测试。下面依次讲这些测试为什么存在、怎么搭建、怎么用、测出了什么，以及一个它们本可以抓住的回归。

**要点速览**

- 缓存未命中看不见，代价却不小：对 `claude-sonnet-4-6` 来说，写入一个 5 分钟缓存条目的 Token 单价是读取的 12.5 倍。
- 三个测试集共 33 个测试，不联网、不需要密钥：真实的 Session 跑在脚本化的流上，每个请求都被录制下来，再放进按 Anthropic 规则构建的缓存模拟器里重放。
- 在系统提示词里放个时间戳，十个请求的任务输入成本就变成 4.24 倍。
- 在 [PR #700](https://github.com/Prism-Shadow/penguin-harness/pull/700) 之前，压缩请求的 7,977 个 Token 里只有 3,241 个能从缓存读取；现在 7,985 个里能读取 7,945 个。

## 为什么缓存未命中必须让测试失败

PenguinHarness 通过 MMSP（`@prismshadow/mmsp`）访问各家供应商。下面按 Anthropic 的规则来讲：它的文档最详细，我们的模拟器实现的也是这套规则；其他供应商在细节上各有不同，但都要求前缀完全一致。在这套规则下，请求按固定顺序缓存为一条前缀：先工具，再系统提示词，最后是消息。缓存在断点（`cache_control`）处写入，每个请求最多四个。自动缓存只在最后一个可缓存块上放一个断点，并随对话变长向后移动；MMSP 的 Claude 客户端发的正是这种请求：顶层一个 `cache_control: {"type": "ephemeral"}`。

这些断点在读取时派上用场。先检查以每个断点结尾的前缀，再往回看：每个断点最多 20 个位置，断点本身算第一个；连续的 `tool_use` 块或连续的 `tool_result` 块只算一个位置。短于模型最小长度的前缀不会被缓存（Claude Sonnet 4.6 是 1,024 个 Token，当前各模型在 512 到 4,096 之间）；条目存活 5 分钟，每读取一次就免费续期。

运转正常的 Agent，每个请求都读回前一个请求的完整前缀，只写入自己追加的部分。为了看清这种模式，我们把请求画成按缓存状态着色的请求条，下面每张图里，同一种颜色都表示同一种状态。

账算起来很直接。对 `claude-sonnet-4-6`，5 分钟缓存的写入价是每百万 Token 3.75 美元，读取价是 0.30 美元，所以分叉之后的每个 Token，都要付命中时 12.5 倍的价钱；而每次请求都会发生的改动，每次请求都要付这笔钱。任何一层发生改动，这一层及之后的内容都会失效。所以 Harness 要守住的性质，说起来很简单：每个请求都从开头起逐字节延续前一个请求。

可就是这么简单的一条性质，以前仓库里没有任何东西检查。缓存未命中不会体现在项目产生的任何信号里：测试通过，界面不变，日志干净。在 [PR #722](https://github.com/Prism-Shadow/penguin-harness/pull/722) 之前，唯一读过这些请求的，就是账单。

## 测试体系是怎么设计的

思路是只替换网络，让实际发布的代码来组装每一个请求，再把结果读两遍：一遍按字节读（这个请求还在延续上一个请求吗？），一遍按供应商的方式读（它会命中吗？）。

两种更简单的设计都行不通。一种是在 CI 里调用线上 API：每跑一次都要花钱，每次结果还不一样，而且需要密钥，可贡献者和 fork 过来的 Pull Request 都拿不到。另一种是只检查字节，但这样不仅看不见字节没变的未命中（条目过期、回看窗口够不着、前缀不到最小长度），还会把追加到最后一条用户消息末尾的 `[turn_retried]` 或 `[turn_aborted]` 块报成问题，尽管供应商照样能读回这个块之前的全部内容。

于是有了这套辅助模块，放在 [`packages/core/test/helpers/prompt-cache/`](https://github.com/Prism-Shadow/penguin-harness/tree/v0.2.16/packages/core/test/helpers/prompt-cache) 下。`recording.ts` 里的 `recordingModel(config, script, { label, onRequest })` 返回一个真实的 `GenerativeModel`，它的供应商客户端从一组脚本化的回复里读取流。MMSP 的有状态历史照常运行，转换成 Anthropic 请求格式的过程也一样，所以每个 `RecordedRequest` 里存的，就是客户端本来要发出的字节。脚本化的回复依次输出以签名结束的思考、文本和工具调用，可以正常结束，可以断开连接，也可以一直挂起，直到中断发生。

第一遍读取由 `diagnostics.ts` 完成。`diagnoseCacheMiss(prev, next)` 按字节读相邻的两次录制，返回最早的分叉点，优先级与 Anthropic 的[缓存诊断](https://platform.claude.com/docs/en/build-with-claude/cache-diagnostics)一致：`model_changed`、`system_changed`、`tools_changed`（附工具名，或指出是哪个定义变了）、`parameters_changed`（附变化的键），或者 `messages_changed`（附消息、块，以及分叉点之后的输入量，按每 4 个字符一个 Token 估算）。`parameters_changed` 是我们自己加的，覆盖 `thinking`、`output_config`、`tool_choice`、`speed` 和 `betas`。`max_tokens`、`stream` 和 `cache_control` 标记都不属于缓存键。

第二遍读取交给 `simulator.ts` 里的 `PromptCacheSim`。它按供应商的方式读同样的录制结果，是一个规则引擎：

- **块。** 一个请求展开成一串有序的块：模型 id，每个工具定义各一块，存放快速模式参数（`speed`、`betas`）的虚拟块，系统提示词，存放 `thinking`、`output_config` 和 `tool_choice` 的虚拟块，最后是每条消息的每个内容块。
- **位置。** 连续的 `tool_use` 块或连续的 `tool_result` 块算一个位置。
- **只在断点处写入。** 写入在请求开始时暂存，请求完成后才可读，所以流式输出途中发出的请求读不到尚未完成的写入。
- **读取。** 每个断点从自己的位置往回看，最多看 20 个位置；取最长的有效匹配，并在读取时续期。
- **限制。** 最小长度 1,024 个 Token；有效期 5 分钟，时钟由外部注入。

默认只有一个断点，放在最后一个块上，与 MMSP 的实际发送一致；`breakpoints: "tools-system-automatic"` 选项会在最后一个工具和系统提示词之后各加一个显式断点，让测试能测量 Harness 并不发送的断点策略。输出是 `CacheUsage`，用的是供应商自己的字段（`cache_read_input_tokens`、`cache_creation_input_tokens`、`input_tokens`），并附上命中率，Token 数按每 4 个字符一个估算。

把这套部件跑起来还需要两样东西，都在 `fixtures.ts` 里：一个是 Session 测试集驱动的 Agent（模型 id 为 `claude-sonnet-4-6`，工具为 `exec_command` 和 `read_file`，系统提示词足够长，固定前缀单独就超过 1,024 个 Token 的最小长度），另一个是所有生命周期场景共用的断言。`expectHits` 要求在一个上下文里，除第一个请求外，每个请求都读回该上下文中前一个请求的完整前缀。设计上就做不到的场景，必须写明是哪个请求、为什么；而且豁免必须名副其实：如果获得豁免的请求实际上读回了完整前缀，测试就会失败，要求删掉这条豁免。

三个测试集都建立在这些部件之上。`prompt-cache-invariants.test.ts` 在真实的 `ContextEngine` 上跑八个用例，对诊断结果做断言：线上的请求一个延续一个；插话和工具结果放在同一个用户轮次里送出（`[user_steering]`）；切换思考等级只造成一次 `parameters_changed`，之后保持稳定，压缩请求和下一个上下文也一样；重连只会让重试那一轮的输入变长（`[turn_retried]`）；恢复的 Session 逐字节重放线上的历史；压缩请求延续它所跟随的那一轮；切换模型时先在旧模型上压缩，切换没完成时旧的缓存线保持不变。`prompt-cache-lifecycle.test.ts` 在真实的 `Session` 上跑十一个场景，全部送进同一个模拟器（子 Session 也在内），覆盖普通对话、中断、子 Agent、从 Trace 恢复、上下文压缩和切换模型。`prompt-cache-simulator.test.ts` 用十四个手写的请求固定了规则引擎，一条规则一个测试。

这个设计有代价。模拟器模拟的是一家供应商的文档规则，凡是线上部署行为与文档不同的地方，它就可能出错；文档一改，它也得跟着改。测试失败还会挡住合并，直到有人判断这些多出来的 Token 值不值得花，因为谁都不能为了通过而改期望值。换来的是：这 33 个测试不联网、不需要密钥，本文写作时在我们的测试机上跑了一遍，用了 1.6 秒。至于某个测试失败时它们会打印什么，是下一节的内容。

## 怎么用这套测试

仓库里的开发指南规定，凡是改动请求组装、历史重建、上下文压缩、系统提示词，或者某个工具的描述和 Schema，都要跑这三个测试集。加一个文件名过滤就能把它们都跑起来：

```bash
pnpm --filter @prismshadow/penguin-core exec vitest run prompt-cache
```

CI 则会在每个改动了 core 包、目标为 `main` 的 Pull Request 上运行 core 包的测试，每次推送到 `main` 时也会运行。

一旦有测试失败，报告会直接附在失败的断言上。不变量测试集打印 `formatDiagnostics`，每个请求一行，写明消息数、思考设置和分叉原因；生命周期测试集打印 `formatCacheReport`，同样是每个请求一行，写明读了多少、写了多少，后面跟着 `full hit on #p`，或者 `short of #p by N tokens` 加上诊断给出的原因，这里的 `#p` 指同一上下文里的前一个请求。下面是专门为本文跑出来的真实输出，我们在第 #4 个请求上把 `exec_command` 的描述改了一个词：

```text
#4 should read back all of #3
prompt-cache report (tokens; previous = the same context's previous request):
...
#3  main  read=5085   creation=1556 input=0 hit=76.6%  full hit on #2
#4  main  read=0      creation=8199 input=0 hit=0.0%   short of #3 by 6641 tokens: tools_changed ("exec_command" definition changed)
#5  main  read=8199   creation=1556 input=0 hit=84.0%  full hit on #4
...
```

这份报告写清了哪个请求、哪一层变了、多花了多少 Token。而失败落在哪个测试集上，也说明了问题的性质：

| 测试集 | 测试数 | 失败意味着什么 |
| --- | ---: | --- |
| `prompt-cache-invariants.test.ts` | 8 | 某个改动让线上的请求不再延续前一个请求。这就是回归本身。 |
| `prompt-cache-lifecycle.test.ts` | 11 | 同一个回归，按真实 Session 的生命周期用供应商的 Token 数表示。 |
| `prompt-cache-simulator.test.ts` | 14 | 规则引擎变了。只有供应商文档变了，这才是对的。 |

这套测试也要跟着功能扩展：改变 Session 发送内容的新功能，要加一个生命周期场景。写法很短，下面几行取自测试集里的普通对话用例和压缩用例：

```ts
const { order, onRequest } = ordering();
const { model } = recordingModel(modelConfig(), [toolTurn(), { text: "…" }], { label: MAIN, onRequest });
const session = makeSession({ llm: model, environment: fakeEnvironment });
await collect(session.run([userText("…")], { approve: allowAll }));
expectHits(order, replay(order));
// A step that cannot hit by design names the request and the reason:
expectHits(order, usages, new Map([[3, reason]]));
```

每条豁免都要自带损失的上限，用 `prefixTokens`、`tokensBeforeLastUserMessage` 或 `toolsAndSystemTokens` 来写。Harness 必须组装成延续的步骤，不变量测试集里也要相应地加一个用例，期望 `diagnoseSeries` 对每一对请求都返回 `none`。另外，和时间有关的用例要注入时钟，比如 `new PromptCacheSim({ now: () => clock })`；`breakpoints: "tools-system-automatic"` 则能在不改 Harness 的情况下测量一种断点策略。

至于期望值，只有一条规矩。开发指南是这样写的：「**Never re-baseline these to green.** Editing an expected number, or adding a case to the list of misses that are there by design, is a decision about spending the user's money — not a fix.」也就是说，绝不为了变绿而改期望值：改一个期望值，或者把某个请求加进「设计上就会未命中」的名单，都是在决定花用户的钱，而不是修复。贡献者要把变化的那一层和它的代价摆到做决定的人面前，并在 Pull Request 里写明，因为仓库里没有别的信号会暴露它。有了这几个测试集，以前只有账单才能回答的问题，现在可以拿整个 Session 来问了，我们也就真的问了。

## 它测出了什么

这些数字来自专门为本文做的一次运行，不是线上供应商的数据。我们只用上述辅助模块写了一个一次性场景脚本，让它在提交 6aa4ed195 上驱动真实的 `Session` 跑脚本化的流，再把每个请求按相邻 10 秒的间隔送进 `PromptCacheSim` 重放。Agent 用的是测试集的固定配置，固定前缀 1,673 个 Token；后台任务通知和子 Agent 这两个场景改用真实的 `Environment`，配的是占位工具定义。每次工具调用都返回同样的 5.8 KB 输出，每轮大约增加 1,556 个 Token。输入成本按基础价 Token 计：每个读取的 Token 计 0.1，每个写入的 Token 计 1.25。

14 个 Session 场景跑下来，工具循环的 44,501 个输入 Token 里有 33,474 个从缓存读取，占 75.2%。每个请求都只写入自己追加的内容，只有有意改变前缀或条目过期的地方，才会把 Token 再写一遍。比如 10 分钟后恢复，字节完全相同，整段历史却要重写一遍：这是过期，不是分叉。中断任务的第一个请求时，这条 Prompt 会改写成 `[turn_aborted]`，于是最后一个可读条目之后的 36 个 Token 要重新写入，在图的比例尺下小到看不见。上下文压缩、子 Agent 和切换模型则按设计开启新的缓存线。

## 一次回归，从头到尾

上下文最大的时候会触发压缩：在默认模式下，引擎请模型总结对话，然后在一个以摘要开头的新上下文里继续。在 #700 之前，压缩请求是唯一一个不理会用户所选思考等级的请求：它用的是上下文开启时的等级。理由正是缓存：固定它的参数，本意是让它的前缀与要总结的上下文保持一致，而这正是未命中最贵的时刻。

这条规则本来是为了保护缓存而写的，结果却破坏了缓存。这个例外只在用户中途调整等级之后才会显现：从那以后每一轮都按新等级发出，压缩请求反倒成了唯一一个前缀不同的请求。我们录制了一个 Session（先跑一个任务，再调整思考等级，然后跑一个四轮、越过压缩阈值的任务），重放两次：一次按现在实际发送的样子，一次去掉压缩请求的 `output_config`，也就是 #700 之前代码发送的样子。现在这次重放通过了 `expectHits`，只豁免了两个请求：调整等级后的那个请求，以及压缩开启的新上下文。#700 之前的那次则失败了：

```text
#6 should read back all of #5
prompt-cache report (tokens; previous = the same context's previous request):
...
#5  context 1  read=6388  creation=1557 input=0 hit=80.4%  full hit on #4
#6  context 1  read=3241  creation=4736 input=0 hit=40.6%  short of #5 by 4704 tokens: parameters_changed [output_config]
#7  context 2  read=0     creation=1718 input=0 hit=0.0%   first request of this context: expected 3241 to be greater than or equal to 7945
```

#700 之前，压缩请求的 7,977 个 Token 里只读到 3,241 个，写入 4,736 个；现在 7,985 个里读取 7,945 个，只写入 40 个。按整个 Session 算，之前读取 19,421 个、写入 17,640 个，现在读取 24,125 个、写入 12,944 个。请求 #2 在两次重放里都未命中，因为等级正是在那里调整的。
