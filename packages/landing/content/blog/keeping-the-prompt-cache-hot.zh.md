> 本文基于 PenguinHarness 0.2.16 撰写。文中所有测量数据都来自 Harness 的缓存模拟器：它把 Anthropic 公开的缓存规则套用到录制下来的请求上，并非线上供应商的实测。

Agent 每一轮都会把几乎相同的请求再发一遍；只要前缀逐字节重复，供应商就从提示词缓存里读取这一部分，只收一成的输入价。但破坏这一点的改动不会让任何测试失败，只会体现在账单上。下面讲 Coding Agent 怎样在测试里抓住它。

**要点速览**

- 在 `claude-sonnet-4-6` 上，缓存写入的价格是读取的 12.5 倍。
- 系统提示词里带时间戳，命中率从 83.0% 降到 0.0%。
- #700 之前，压缩请求的 7,977 个 Token 只读到 3,241 个；现在 7,985 个读到 7,945 个。

## 只有账单看得见的未命中

供应商按固定顺序把一个请求当作一个前缀来缓存：先是工具，然后是系统提示词，最后是消息。在健康的 Agent 里，每个请求都会把上一个请求的整个前缀读回来，只写入新追加的部分。任何位置的改动都会在那里切断前缀，切口之后的内容全部要重新写入。以 `claude-sonnet-4-6` 为例，5 分钟缓存的写入价是每百万 Token 3.75 美元，读取价是 0.30 美元，所以切口之后的每个 Token 都要贵 12.5 倍。可未命中不会改变任何回答、界面或日志，CI 照样全绿。在 [PR #722](https://github.com/Prism-Shadow/penguin-harness/pull/722) 之前，未命中只会出现在账单上，所以我们做了一个能抢在账单之前看到它的测试。

## 录下每个请求，读两遍

这套测试体系只替换网络。真实的 Session 跑在脚本化的模型流上，所以每个请求都由实际发布的代码组装，并按供应商会收到的字节录制下来。随后由两个读者评判每份录制。诊断器把它的字节与上一个请求比较，指出最先变化的部分：模型、工具、系统提示词、某个参数或消息。模拟器套用 Anthropic [公开的缓存规则](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)，报告供应商会读取和写入多少。只要某个请求没有把上一个请求的整个前缀读回来，测试就失败。仓库的开发指南要求 Coding Agent 在改动请求组装、历史、压缩、系统提示词或工具定义时运行这些测试集，所以检查发生在改动还在编写的时候。

在 CI 里调用线上 API，每次运行都要花钱，还需要 fork 来的 PR 拿不到的密钥。只检查字节，又会漏掉字节没变、条目却已过期的情况。把每个请求按两种方式各读一遍，就避开了这两个问题，代价是：模拟器只遵循一家供应商的文档，文档变了它也得跟着改；测试失败时合并会被挡住，直到有人决定这些多出来的 Token 值不值得付钱。

请求的各个部分遵循供应商的顺序，所以一处改动会让它所在的部分及之后的全部内容失效，报告会指出损失从哪一部分开始。

## 四个设计选择，正反各回放一次

下面每一组都把我们没有采用的设计和 PenguinHarness 实际采用的设计放在一起，用同一个模拟器、同一个比例尺回放，变化的只有缓存状态。前三组回放同一条录制下来的任务：十个请求、六个工具定义；最后一组回放 #700 背后的那个 Session。数据都来自我们为本文在 commit 6aa4ed195 上做的一次运行。成本指的是相对于我们所采用设计的输入成本：读取按基础价的 0.1 倍计，写入按 1.25 倍计。

### 日期跟着上下文走，而不是跟着请求走

在系统提示词里放时间戳看似无害，但系统提示词排在所有消息之前，于是每个请求都在那里分叉，把整段历史重新写入一遍：命中率从 83.0% 降到 0.0%，输入成本升到基线的 4.24 倍。PenguinHarness 只在上下文开启时把日期写进系统提示词一次，并在上下文关闭之前一直沿用这份提示词。

### 压缩请求跟随 Session 的思考等级

压缩会在上下文最大时请模型总结这段对话，然后用这份总结开启新的上下文。在 [PR #700](https://github.com/Prism-Shadow/penguin-harness/pull/700) 之前，压缩请求用的是上下文开启时的思考等级，这条规则原本是为了让它的前缀与被总结的上下文保持一致。可一旦用户在上下文中途调整了等级，之后每一轮都带着新等级，压缩请求反倒成了唯一不一样的那个请求。按 #700 之前的代码回放，这个 Session 在 `expectHits` 上失败，输出如下：

```text
#6 should read back all of #5
prompt-cache report (tokens; previous = the same context's previous request):
...
#5  context 1  read=6388  creation=1557 input=0 hit=80.4%  full hit on #4
#6  context 1  read=3241  creation=4736 input=0 hit=40.6%  short of #5 by 4704 tokens: parameters_changed [output_config]
#7  context 2  read=0     creation=1718 input=0 hit=0.0%   first request of this context: expected 3241 to be greater than or equal to 7945
```

修复只改了一个参数：`runCompactionRequest` 现在和普通的一轮一样，传入 Session 的等级。压缩请求的 7,985 个 Token 里读到 7,945 个，而之前 7,977 个里只读到 3,241 个；整个 Session 的命中率从 52.4% 升到 65.1%。
