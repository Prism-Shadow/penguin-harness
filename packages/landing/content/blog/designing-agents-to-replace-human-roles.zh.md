最近 DeepSeek 团队分享了他们内部探索的 **Super-agent** 架构。里面一些具体的做法，不少做 Agent 的团队其实都有过类似的探索，但把整套设计放在一起看，还是能很清晰地看到现在 Agent 系统演进的大方向。

其实现在单任务 Coding Agent 的能力已经足够强了，写代码、跑测试越来越自主化，不需要人手把手盯着。现在限制多个 Agent 并行干活来提效的，主要是**人的注意力**——因为一个人同时最多只能专注于三到五个 Agent，没法切换不同的聊天窗口给十几个 Agent 发指令。

所以现在设计 Agent 系统，大体有两个方向：**一个方向是提升人机交互的效率；另一个方向，就是一步步吃掉原来由人负责的部分。**

第一个方向，是对 Agent 的执行过程和结果做各种直观的看板或可视化插件——比如 PenguinHarness 里的 **Agent 专属工作台**（如数据仪表盘、工单看板）和 **A2UI 可视化组件**，把满屏的文字对话变成一目了然的图表与状态面板，从而降低人在单个任务上消耗的注意力。

而 Super-agent 走的是第二个方向：**直接在干活的 Agent 上面再加一层系统**，把原本由人来做的接收信息、分配任务和异常排查全部接管过来。具体来说，我觉得它有三部分比较好的设计，下面我们逐个分析一下：

## 一、 事件驱动：替代原本由产品和测试负责的反馈跟进

传统的 Agent 是由人来驱动的：人给 Agent 发送任务指令，Agent 来执行，如果人不发 Prompt，Agent 就一直在那里等着。

比如，原来的软件迭代逻辑是：用户在群里提建议或报 Bug -> 产品经理或测试人员看到 -> 过滤掉群里的闲聊 -> 尝试复现问题 -> 确认是 Bug 后提单给开发 -> 开发再去开一个 Agent 窗口修代码。在这个链路里，产品、测试和开发其实承担了信息筛选和驱动 Agent 的工作。

而 Super-agent 的第一步，就是通过**事件驱动**（Event-driven）把这一步接管过来。它直接常驻在工作群聊和 GitHub 里监听所有的消息事件（Trigger），并做了两个很实用的技术处理：

1. **程序 + 模型的两级过滤**：群聊里绝大部分都是日常闲聊，如果每句话都调大模型去判断要不要干活，算力成本和延迟根本扛不住。所以它在前面加了一层写死的代码规则（白名单、关键词等），先筛掉大部分无关信息，剩下的候选消息才交给大模型去做语义判断。
2. **主动复现与静默尝试**：在群聊里，当有人反馈一个 Bug、群里还在讨论方案、甚至**根本没人 `@` Agent 的时候**，Super-agent 已经在后台静默拉起任务，自己尝试去复现这个 Bug 并写代码修复了。
   - 如果没复现出来，或者发现改起来太复杂，它就直接在后台把结果丢掉，全程保持安静，不在群里打扰大家；
   - 一旦它在后台成功复现并且跑通了修复方案，就会直接把写好的 Pull Request 发到群里。

这样，原本需要产品收集、测试复现、开发初步排查的前置流程，直接被 Super-Agent 事件驱动机制替代了。

## 二、 双层架构：替代人去管理多个窗口和分配任务

平时我们开发想要提高效率，最自然的做法就是**并行做很多任务**——也就是同时开很多个上下文窗口（Session）。但由于人的注意力有限，窗口开多了根本注意不过来，记不住哪个窗口做到了哪一步。所以人往往会把相似的任务塞进同一个上下文窗口里做；而把每个任务分配给哪个窗口、在群聊和 GitHub 之间同步信息，这一步原来完全是由人来决定的。

再比如说，在一个公共群聊里，这么多消息反馈涉及的方面都不一样，有的是前端问题，有的是后端 Bug，我们很难用同一个 Agent 窗口做所有事情：

- 一方面，单个窗口只能串行干活，前一个耗时的任务没跑完，后一个问题就得等着；
- 另一方面，不同领域的任务混在同一个上下文里很容易互相干扰，而且术业有专攻，最好也不要都让同一个 Agent 来做。

那么，**能不能把“开窗口、记上下文、分配任务”这一步也交给一个专门的 Router 来负责呢？这就是 Super-agent 的双层架构设计**：

- **上层是常驻的 Router 层**：它不执行具体的开发任务（甚至可以不给它配执行代码的工具），因此可以用更轻、更快的模型。它只负责维护全局上下文，对外跟人交互，并把具体任务分派下去。
- **下层是隔离的 Worker 层**：每来一个独立的任务，Router 就在底下分配一个上下文隔离的 Worker（配置最强的模型和完整的工具链）去并发执行。Worker 不直接跟人对话，做完后把结论汇报给 Router，由 Router 统一回复给用户。

通过这层设计，用户不再需要手动管理底层的多个 Session 窗口，任务的路由和并发完全由系统接管。

## 三、 Watchdog Agent：替代开发人员的异常排查与维护

当然，Agent 系统本身在长期运行中也会出问题，比如卡死。

传统的程序出问题，通常是进程崩溃或接口报错，用监控脚本重启就行。但 **Agent 系统的卡死往往不是进程挂了，而是模型陷入了死循环**（比如反复修改同一个错误），或者在执行过程中偏离了原本的目标。

原本遇到这种情况，需要开发人员自己去排查日志、手动叫停并调整方向。

而在 Super-agent 中，他们在主系统外部单独配置了一个 **Watchdog Agent**，用定时消息驱动它来解决这个问题。它不仅处理接口报错、状态恢复失败等基础故障，更关键的是，因为它本身也是一个 Agent，它会**定期检查各个 Worker 的执行情况，由模型来判断任务是否有实质进展、方向有没有跑偏**，并在发现异常时及时介入修复。维护人员甚至可以直接用自然语言向 Watchdog 询问故障原因，或者让它在线修改主系统的提示词和触发规则。

## 四、 模型越来越聪明，设计 Agent 就是思考怎么把人替掉

过去设计 Agent，是设计怎么让 Agent 作为工具辅助人完成任务——因为那时候模型还不够聪明，单任务执行经常出错，必须让人在中间盯着、做各种手动操作。但现在模型的能力越来越强，人已经可以把更高层次的操作让渡给 Agent 来做了。

所以往后看，要设计更先进的 Agent，一个很实用的思路就是：**去原有的工作流里看看人还剩哪些部分，然后多问自己一句——现在还要人亲手做的那一步，能不能再加一层 Agent 把它吃掉？**

如果沿着这个思路再往前想一步：Super-agent 替掉的是运行阶段发指令、管窗口和盯异常的人，但在 Agent 的评测与调优阶段，以前依然需要人来手动去做。

这其实正是 **PenguinHarness** 想要替掉的部分：它可以让 Agent 自主完成跑评测、看日志找问题、修改提示词和 Skill 等工作。当这些原本由人来负责的工作也交给 Agent 完成时，也就最终实现了 Agent 的自进化。
