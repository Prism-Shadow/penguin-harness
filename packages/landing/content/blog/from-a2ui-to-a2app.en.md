> Written for PenguinHarness 0.2.16. Later releases may differ in some details.

A2UI changed how agents and people interact within a single reply, letting agents hand people inline interfaces instead of only text. Google announced the A2UI project in December 2025 as a declarative data format for agent-driven UI, where clients render components from a trusted catalog rather than executing agent-supplied code.

A2APP changes that interaction at the level of software. It lets an agent host a dedicated app beside its chat, calling the agent turn by turn over a narrow server API. People and agents finish work together in one place, with no separate deployment required. "A2APP" is our term for this pattern, not an industry standard.

## The two edges of the current tradeoffs

We think A2UI blocks work well for single-turn interactions, but hit limits for repeated, dedicated job interfaces. Our own blocks, modelled on A2UI, send only field values for pre-approved components, never raw HTML, scripts or styles. Selections or form entries fill the composer rather than triggering action directly, and nothing sends until the user presses Send.

Only the latest reply in the main conversation accepts block input; older replies, subagent conversations, and the Trace view show blocks as read-only. Weather and metrics widgets are static snapshots the model supplies, with no client-side fetching; only clock and countdown widgets update locally after render.

We think vibe coding sits at the opposite edge. It trades guardrails for full code expressiveness, and treats code as a disposable handoff once written.

Andrej Karpathy coined the term in February 2025. He described a style of coding where you fully give in to the vibes, accept all generated changes, and forget the code even exists, judging it acceptable for throwaway weekend projects. Simon Willison later narrowed the definition to building software with an LLM without reviewing the code it writes.

Karpathy later wrote that building MenuGen as a local demo was an exhilarating escapade. Turning it into a deployed, real app meant spending most of his time configuring settings and gluing services together, which he called a bit of a painful slog.

In his end-of-year post eight months later, he wrote that code is suddenly free, ephemeral, malleable, and discardable after a single use.

Howie Liu at Airtable notes that vibe-coded apps often look polished on the surface but can hide bugs, edge cases, and data or security leaks underneath.

These two approaches leave a gap for job-specific tools. Blocks are too bounded for repeated, multi-step work. Vibe coding splits building the tool from using it with the agent. Once the code is written, the AI is not part of the running app.

## The workbench as A2APP in PenguinHarness

In PenguinHarness, this pattern is the Agent Workbench. Every agent can have its own dedicated application, stored as plain files in the agent's directory. The screenshot below shows the Contract desk workbench for the legal agent example, which opens as a tab beside Chat or fills the app window.

![The Contract desk workbench open in a tab next to Chat, showing an upload prompt and file status table for contract reviews.](/blog-assets/workflow-page-en.png)
_A workbench appears as a dedicated tab beside its agent's chat, with a custom interface built for one specific job._

Workbenches use the opposite trust trade from A2UI blocks. The agent writes a TypeScript server entry point and plain HTML, CSS, and JavaScript pages into a standard folder structure, with no separate build step, bundler, or deploy required. The server type-checks the TypeScript entry point on every load, hot-reloads the open tab on success, and keeps a rolling set of recent loaded revisions.

Unlike a vibe-coded app, a workbench is never separated from its agent. A narrow host API lets the workbench server create Sessions, start text-only agent turns, poll for result snapshots, and persist state. The agent never sees page clicks or UI state directly; the app calls it turn by turn, sending only text and polling for a snapshot of the latest task: running, final answer, or failure.

Workbench server code is not sandboxed, and this remains an unresolved engineering limitation. The TypeScript entry point, loaded with import() at runtime, runs in the main server process with the server's permissions — including code shipped by plugins, like the built-in support workbench.

The workbench's UI pages are plain HTML, CSS, and JavaScript served to the browser. They run as same-origin iframes, and can call any API as the signed-in user.

Sessions started by a workbench run in allow-all mode, with no per-step approval prompts. Only run workbench code you trust.

Two separate loops connect the agent to its workbench. One loop runs background tasks triggered from the workbench UI, and the other handles edits to the workbench itself requested in chat. The diagram below shows how these loops interact.

## Using and changing the app in the same place

The split between building a tool and doing work blurs with a workbench. A user can open the workbench tab to upload contracts, submit support questions, or view results before sending any chat message. Edits to the app are requested in the Chat tab beside the workbench. For example, asking the legal agent to add a Risk column to its Contract desk tab updates the table with no separate deploy or copy-paste, and the change is listed in the workbench bar's **History** panel.

![The workbench History panel open, listing two saved revisions above the updated Contract desk which now includes a Risk column.](/blog-assets/workflow-history-en.png)
_Edits requested in Chat update the workbench files, with recent loaded revisions kept in the History panel; Restore rolls back code, not saved data._

When a user requests a change, the agent edits the workbench files, and the open tab refreshes automatically when the new version loads. The same revision controls are also available in the agent settings Workbenches tab.

## Trying the pattern

Related approaches exist across the ecosystem. MCP Apps lets tools return interactive UI that renders in a conversation. Claude artifacts and Opal's agent step let models generate small interactive apps for users. Ink & Switch's Patchwork research project explores similar goals for malleable software, where users build and adjust small tools from chat.

Our focus is a specific combination: an agent generates and edits its own dedicated app, which lives beside its chat and calls the agent turn by turn to do work.

The builder Skills needed to generate a workbench come preinstalled on a new Project's default agent.

To try the pattern end to end:
- Open the start page and select "A legal agent app from one sentence", then press Send to generate a dedicated legal agent with its own workbench tab.
- Open the created agent, start a new chat, and select its workbench tab to use it.
- Ask for adjustments in that agent's Chat tab, for example adding a Risk column that sorts contracts by risk level.
- Use the **History** panel on the workbench bar to roll back to an earlier code version if needed.
