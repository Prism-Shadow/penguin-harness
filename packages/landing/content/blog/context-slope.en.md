> Written for PenguinHarness 0.2.16. Later releases may differ in some details.

We think controlling context slope is a core job of an agent harness. It measures how fast an agent's context grows per request. We use "context slope" as a named design lens. We did not discover the underlying growth effect. The Self-Manager paper measures it as context accumulation rate, and LangWatch names the associated cost the context tax. TraceLab has studied context growth and compaction in coding-agent workloads, and separate work tracks constant-context agent designs.

All size measurements here are character-based estimated tokens, not provider token counts. Context cost splits roughly into two designable quantities. The first is intercept: the fixed cost every request carries before work, covering system prompts, tool definitions, and static Skill and memory indexes. The second is slope: the cost added each request from tool results, loaded content, and replies. Finite windows, documented long-context accuracy drops, and compaction's documented costs motivate this focus.

## Intercept and slope

We ran a synthetic workload on our test machine to measure slope directly. A scripted agent ran `cat` on 16 generated build logs, one per turn, using the repository's prompt-cache test helper against a 200,000 estimated-token fixture window. Nothing was sent to a real provider.

In that stripped fixture, the first request carried 2,963 estimated tokens before any tool output. Of that, 1,493 estimated tokens covered five tool definitions plus the model-id block, alongside the fixture system prompt; no Skill index, memory index, or `AGENTS.md` was present.

When cumulative context hits the compaction threshold, the harness sends an extra request at the largest context size of the run. In our synthetic 64k-log uncapped run, that compaction request estimated above the 200,000-token fixture window; no real provider received the request. In our Anthropic-style cache simulation, the reopened context's first request starts with a full simulated cache miss, adding direct cost and user-visible delay. Compaction is a necessary safety net, but its extra cost, information loss, and cache miss make it a poor primary strategy.

## Progressive loading cuts the intercept

Progressive disclosure is the standard design for agent Skills, placing only a short index entry per Skill in the initial prompt. In PenguinHarness we apply this index-first pattern as progressive loading for Skills, and extend the same rule to memory, schedules, and vault keys. Two explicit exceptions exist: `AGENTS.md` is spliced into the prompt whole with no cap, and every discovered MCP tool definition rides every request. Full Skill bodies load only when the model chooses to use them, which cuts the starting intercept dramatically. As of 0.2.16, the full shipped library of 35 Skills adds 2,843 estimated tokens of index lines, plus a 99 estimated-token section header. The 25 Skills preinstalled on a default agent contribute 1,889 estimated tokens of index lines. Loading every `SKILL.md` for the full library up front would add 124,826 estimated tokens, 43.9 times the index size; reference docs add a further 58,577 estimated tokens, and shipped scripts are executed rather than read.

In PenguinHarness, a loaded Skill body remains in context as part of tool result history until compaction. Progressive loading shifts load from the fixed intercept to turns where a Skill is used, rather than eliminating per-turn growth entirely.

For memory, schedules, and vault keys, the index-first rule works the same way. Memory injects its index (capped at 200 lines or 25,000 characters), with topic bodies read on demand. Schedules inject only task names. Vault values are passed to subprocesses, and only their key names enter the prompt.

## Disk-backed caps cut the slope

In our synthetic test, per-turn slope was dominated by tool output, so a hard character cap on inline output stops per-turn growth from scaling with raw command output size. On our test machine, 64,000-character build logs added 16,297 estimated tokens per turn without a cap. With the 16,000-character default cap, each over-cap log added 4,163 estimated tokens, regardless of whether the raw log was 64,000 or 256,000 characters.

A cap alone risks data loss, so PenguinHarness saves full over-cap output to a recovery file and returns only the head, tail, and file path alongside the truncation marker. Claude Code and Cursor use the same file-backed pattern for oversized tool output. The recovery file holds up to 8 MiB per call, and text a producer's own buffer already dropped cannot be recovered. The model can read exactly the slice it needs with ordinary file tools instead of carrying the full output on every subsequent turn.

The same principle of avoiding carrying unnecessary content across turns applies at the conversation level, not just for individual tool outputs. Subagents apply this slope logic at the conversation level. A child runs in its own isolated context, and the parent receives the child's assistant text through a capped buffer, like any other tool result. The child's full tool traffic never adds to the parent's slope.

## CLI and MCP designs bend the curve too

CLIs built for model readers cut slope by returning only the small, structured slice of output a model needs for the next step. They avoid dumping full JSON or unfiltered page content by default. Simon Willison notes models can call `--help` on a CLI when needed, so little upfront description is required. Mario Zechner has measured upfront token cost differences: a 225-token CLI README against 13.7k and 18.0k tokens for two common browser MCP servers.

`penguin browser scan` defaults to simplified HTML output up to 35,000 characters, with `--text` returning plain text at a third of that budget. `penguin browser exec` caps return values to 8,000 characters, with a `--save` flag for full results. The `screenshot` command returns only a file path and size.

When MCP servers are configured, their discovered tool definitions add to the fixed intercept on every request. Every discovered tool schema rides every turn in today's PenguinHarness build. Mario Zechner's 120-run benchmark found MCP and CLI perform equally when built with care. Armin Ronacher notes that, as far as he knows, tool definitions must stay static for an entire conversation. Manus warns that changing tools mid-iteration breaks the KV-cache, since definitions sit near the front of the context. Any deferred loading scheme must keep the active tool set fixed within a context to keep the prompt prefix stable.

The slope principle points to a concrete direction for PenguinHarness MCP support. A fixed deferred tool set that keeps the prompt prefix byte-identical across turns could cut intercept without breaking cache, whether via tool search or a generic code-execution endpoint. Claude Code v2.1.7 introduced automatic deferral past a 10% context threshold via the MCPSearch tool. As of October 2026, its docs state only tool names and server instructions load at session start. Anthropic reports an 85% token reduction for its Tool Search feature in one internal example, from about 77K to about 8.7K tokens. Cloudflare reports its Code Mode exposes the whole Cloudflare API through two fixed tools, `search()` and `execute()`. The company estimates an equivalent MCP server without Code Mode would consume 1.17 million tiktoken-counted tokens, compared to about 1,000 tokens for Code Mode. Cursor presents MCP tools as files, reporting a 46.9% total agent token reduction in runs that called an MCP tool during an A/B test, with high variance based on the number of MCPs installed.
