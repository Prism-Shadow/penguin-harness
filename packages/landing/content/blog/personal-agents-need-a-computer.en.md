September 2026 brought three high-profile agent launches. Meta launched Muse on 2026-09-08, running on an isolated, dedicated Secure VM for each user. OpenAI announced dots at its DevDay event on 2026-09-29; each dot has its own computer and browser in the cloud, and can keep working when the user's computer is off. Microsoft announced Copilot Autopilot on 2026-09-25, which lives in a tenant with its own identity, memory, computer and workspace, and continues work while the user is away.

We read these launches as splitting a personal agent into three parts: a stronger model, an Agent Runtime, and an Agent-native Cloud Computer. Our bet is the runtime's core loop is largely settled. Near-term meaningful progress will come from two places. The first is vendor post-training on agentic tasks. The second is upgrading the host environment from disposable, task-scoped sandboxes to a long-lived, always-on cloud computer. It would come preloaded with software adapted for agent operation and own user app connections as a unified entry.

## We think the Agent Runtime core shape is settled

The core loop shape we describe is our reading of current designs. In PenguinHarness, one run drives one Task. Each run assembles context, calls the model, executes returned tool calls, appends results to a trace, and repeats until the model produces a final answer with no tool calls or the run aborts. When we use the term harness here, we mean the part of the Agent Runtime that decides what goes into each model request. Our 0.1.1 post argued post-training binds models to a shared function-calling contract, not to a specific harness, so lean designs keep working when you switch models.

Two caveats do not alter this core loop shape. First, harness tuning still moves benchmark scores. Fortune reports the same GPT-6 Astra model scored 66% on ARC-AGI-3 with the standard harness, and 99.9% with an enhanced harness. We do not know exactly what that harness changed. Second, our bet is permission and safety layers around the loop will keep growing as agents take higher-stakes actions. For example, Meta runs a separate Sentinel agent on each Muse VM as the sole permission authority for connector actions and network egress; we read this as a guard layer that sits outside the core loop.

## Model capability grows with post-training on agent environments

Our bet is the first source of near-term capability gains is model vendors' post-training work. VentureBeat reports OpenAI attributes GPT-6 Astra's capabilities to the combination of large-scale pretraining and reinforcement learning. Our bet is most near-term lifts come from reinforcement learning on curated agentic environments. DeepSeek-V3.2, released 2025-12-01, introduced a synthetic agent training data method covering 1,800+ environments. Anthropic notes flawed environments used in reinforcement learning are a major source of misaligned behavior.

Even with that training progress, open-ended GUI computer use remains limited. The best listed entry on the OSWorld 2.0 long-horizon computer-use benchmark, Claude Opus 4.8 with maximum thinking and batched tool calls, scores 20.6% on binary task completion at a 500-step budget. The benchmark authors note current agents are still far from professional-level computer use.

## Disposable sandboxes lack durability

The host environment is the other major area of change, starting with durability. A sandbox built for one task or one session spins up fresh, resets when the task or session ends, and discards the in-machine state it built up: files, running processes, RAM.

Manus's standard sandbox resets per chat, with no access to prior work. Claude Cowork destroys sandboxes when a session ends; sessions and files are saved to the member's Claude account. OpenAI's code interpreter containers expire after 20 minutes of inactivity, and their data is discarded with no recovery. Windows 365 for Agents evicts sessions after 30 minutes without MCP activity and resets Cloud PCs to their provisioned state after every session to enforce isolation and auditability.

Anthropic and Microsoft chose these reset designs deliberately, to simplify isolation, auditability, and failure recovery. We think this design leaves no place for an agent to leave a process running across days. Anthropic's Managed Agents redesign moved state out of long-lived "pet" containers into append-only session logs to simplify failure recovery; if a container dies, the harness catches the failure as a tool-call error and passes it back to the model.

Persistence is available as an option or default from some providers. Vercel Sandbox keeps filesystem snapshots by default; on resume, you use an `onResume` hook to restart services or rehydrate caches. E2B sandboxes time out and are killed after 5 minutes by default; if you explicitly pause a sandbox, both filesystem and memory state are saved indefinitely with no automatic expiry. Manus sells a persistent Cloud Computer tier that retains files and installed tools.

Against this backdrop of disposable sandboxes, the recent personal agent launches from Meta and OpenAI each assign a dedicated cloud host to their user. Meta describes its Muse Secure VM as the system of record for user data, with continuous backup. Microsoft's Copilot Autopilot runs inside an organization's tenant with its own identity, memory, computer and workspace; the company does not state whether that computer is assigned per user. Public documentation for Muse and dots does not list operating system, machine specs, or preinstalled applications. We found no public guarantees about how long running processes are retained on those hosts, even though dots can pause and wake to continue work.

The table below compares how much state common host designs retain across tasks.

| Host type | Keeps files | Keeps running processes | Resets by default |
| --- | --- | --- | --- |
| Per-task sandbox | ✗ (sandbox discarded; account storage may save files separately) | ✗ | Yes, after task/session end or idle timeout |
| Filesystem-persistent sandbox (Vercel Sandbox) | ✓ (snapshotted on stop) | ✗ (restarted via `onResume` hook) | No, filesystem persists across stops by default |
| Explicitly paused sandbox (E2B) | ✓ | ✓ (memory saved while paused) | No, kept indefinitely until resumed; default running timeout is 5 minutes with kill on timeout |
| Dedicated personal agent cloud host (Muse, dots) | ✓ (dedicated machine per user) | We found no public specification; dots can pause and wake to continue work | We found no public specification; vendors state work continues while the user is away |

## Many default sandboxes lack agent-adapted software

Durability alone is not enough to make a usable personal agent host. Many default sandbox images ship only developer toolchains, with no desktop or full office suite for everyday work. E2B's default base Debian image ships Python 3, Node, git and build-essential, with no desktop; an opt-in Ubuntu desktop template adds LibreOffice, Firefox, Chrome and VS Code. Anthropic's code-execution sandbox disables public internet and ships python-docx, python-pptx and openpyxl, but no LibreOffice in its documented package list.

Claude Managed Agents ships a default Ubuntu image with headless LibreOffice, pandoc, Playwright and Chromium preinstalled. Anthropic's public pptx Skill ships a custom wrapper to work around hangs when calling the raw `soffice` binary in its target sandbox. This is one documented case where preinstalled office software needed small adaptations for reliable agent use. Large vendors offer a mix of MCP servers, CLIs, and in-app add-ins for productivity work rather than preinstalled, agent-adapted suites. Microsoft's public Agent 365 Model Context Protocol (MCP) servers cover Outlook Mail and Calendar, Teams, and SharePoint/OneDrive; none is listed as editing Word, Excel or PowerPoint document content. Google's public Workspace agent tools list MCP servers for Gmail, Drive, Calendar, Chat and People, plus a CLI; no Docs, Sheets or Slides server is named.

Every's parity rule holds that whatever a user can do through the UI, an agent should be able to achieve through tools. This means preinstalled software needs adapted interfaces, not just a desktop to click on.

## What an Agent-native Cloud Computer requires

We think a usable host for a personal agent needs four concrete properties.

It must be always-on and durable. Files, installed tools, signed-in browser sessions, and long-running processes must survive across tasks and when the user is away.

It must ship with preinstalled everyday software, not just a developer toolchain.

It must prioritize adapted interfaces (CLI, API, MCP) for that software. Computer use remains a fallback for apps without a dedicated endpoint.

It must own the user's app connections as one unified entry. Connectors, website sign-ins and credentials are set up once and serve every task, rather than rebuilt per session or per device.

Meta already stores credentials for every connected service on the Muse Secure VM, where a separate Sentinel agent swaps in real tokens at the network boundary so the main agent never sees them.

OpenAI separates three kinds of link for dots: messaging channels, connected apps and plugins, and an optional local computer. Connecting a messaging channel does not grant access to inbox or app data.

This unified entry covers outbound access to the user's apps, not the inbound channels people use to message the agent.

We do not know of any existing product that meets the full spec above.

## Where PenguinHarness sits today

In PenguinHarness we built the Agent Runtime piece. The core loop, append-only JSONL Trace, and file-based Agent State all work today. On the desktop app, you do not need to keep the main window open: closing it hides the app to the tray by default, leaving the embedded server and its background tasks running.

The Machines feature lets you connect an existing Linux or macOS host over SSH that the server can reach; Windows hosts are not supported, and the page is admin-only. When connected, the remote host runs its own plain `penguin server` process; the install adds no sudo changes, no system service units, and no profile edits. The remote server is not supervised; a machine that reboots reads as "not running" on the next probe, and a full server shutdown aborts active runs and kills remaining background processes.

We do not build or host cloud machines, have no built-in OS-level computer use control, and ship no preinstalled set of adapted office applications.

For outbound connections to user apps, we ship per-agent MCP entries, a per-agent Vault, and browser access via the desktop app or paired Chrome extension.

For inbound messaging, we support Feishu/Lark, Telegram, QQ and WeChat channels. These channels relay messages to and from a conversation, and grant no access to those apps' own data.

These pieces sit at separate scopes. MCP servers and the Vault live per agent. Built-in browser sign-ins live per Project, paired Chrome access is tied to the individual user, and chat bots are configured per conversation.

There is no single unified entry for connections in the product today. We have no built-in connector catalogue, no OAuth support for MCP servers, and no credential broker that swaps secrets at the network boundary.

Vault values are kept out of initial prompts but passed into command environments. Shell command output is not scrubbed, so a command can print a secret into tool results the model reads.

Our core Environment interface is intended to swap backend implementations without touching the runtime loop, but today only the local process implementation ships. Remote machines run their own full server, rather than plugging in through that interface.
