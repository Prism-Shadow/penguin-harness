如今和 AI Agent 一起工作，大多仍是在工作台上完成的：你打开一个对话，交给 Agent 一项任务，看它干活，它停下来了再开始下一轮。这套模式是为几分钟就能做完的任务设计的。一旦工作要持续好几天、需要多种专长，或者要牵涉你以外的人，它就开始吃力。本文想讨论的是：当工作超出了工作台能承担的范围，该用什么来取代它。

我们的答案是组织，而不是一个更大的聊天窗口：Agent 有明确的角色和汇报关系，日历让工作持续推进，预算约束开销，人负责定方向、做真正要紧的决定。公司模式在 PenguinHarness 0.2.13 中以内测形式发布，就是我们朝这个方向做的一次尝试。

![从单个工作台，到群聊，再到公司](/blog-assets/agent-company-evolution-zh.png)

## 从一个工作台，到一屋子 Agent

第一代 Agent 产品的形态，是一个人面对一个 Agent：一个会话、一项任务、一份对话记录。编程 Agent、研究 Agent 和通用助手都是这种形态。任务一次就能做完、全程只有一个人参与时，这样就够用。

较新的一批产品，把多个 Agent 和多个人放进了同一个空间。[Multica](https://multica.ai/) 是一个开源平台，把编程 Agent 当作队友：你像给同事派活一样，把 issue 指派给 Agent，Agent 会自己更新状态、主动报告卡住的地方。[Raft](https://raft.build/) 是一个多 Agent 协作平台，人和 Agent 共用频道、话题串和任务；Agent 之间互相交接工作、审查彼此的产出，人负责定方向、做最终决定。xAI 的 [Grok Bot](https://x.ai/news/introducing-grok-bot) 给你一组常驻的 Agent：它们在群聊里协调，彼此传递工作、自行分派负责人，只在需要人来判断时才叫上你。

这些产品说明，Agent 之间、Agent 与人之间可以共享上下文，Agent 可以自己分工，只在决策需要人时才让人参与。公司模式沿着同样的思路，把组织的其余部分也明确下来：成文的汇报关系，按计划唤醒每个 Agent 的日历，用到上限就暂停日程的预算，比任何一次对话都长久的手册，还有握有最终决定权的董事会。这些全部以文件形式保存，你随时可以打开来读。

## 组织带来了什么

早在软件出现之前，人类组织就已经解决了长期、多人协作的难题。它们靠的是为数不多的几种结构，而每一种在公司模式里都有对应：

| 结构 | 在人类公司里的作用 | 在公司模式里的作用 |
| --- | --- | --- |
| 使命 | 说明公司为什么存在。 | CEO Agent 出发时依据的那一句话。 |
| 汇报树 | 界定谁对什么负责、谁审核谁的工作。 | 一张由 Agent 组成的组织图，每个 Agent 都有职位、职责和一位上级。 |
| 日历 | 让周期性的工作不用人催也照常进行。 | 定时事件，到点唤醒工位上的每个员工。 |
| 工单 | 跟踪工作、负责人和状态。 | 一块工单看板，分五列：提议、进行中、审核中、已完成、已拒绝。 |
| 频道 | 让讨论有地方进行，又不打扰所有人。 | 群聊，被 `@` 提及的员工才会被唤醒。 |
| 预算 | 限定公司各部门能花多少钱。 | 为每个员工设定的月度开销上限，沿汇报树逐级汇总。 |
| 手册 | 做决定的人离开后，决定和知识仍然留得下来。 | 一组共享文档，每个员工都会阅读和更新。 |
| 董事会 | 对方向和重大决策握有最终决定权。 | 你。 |

有两个设计选择，让这套对应不只是比喻：

1. **组织的每一部分都是 Project 里的文件**。配置、组织图、日历事件、工单、频道记录和手册，都保存在 `organizations/<org_id>/` 下。文件才是权威来源；数据库只保存由文件重建的缓存，以及读取位置这类运行时状态。整家公司都可以读取、做版本管理和备份。
2. **每个工位对话、每个工单对话都是普通的 PenguinHarness 对话**，消息列表、工具调用和 Trace 与其他对话完全一样。Agent 做的任何事，都不会藏在某个新界面后面。

## 一人公司

公司模式的第一种用法是一人公司：一个人带着任意数量的 Agent，一起经营一个组织，花几天到几周去实现一个目标。

![一人公司：你担任董事会，CEO 提出提案，组织按自己的日历运转](/blog-assets/agent-company-one-person-zh.png)

创建组织只需要一句话，也就是它的使命，再加上给 CEO 的月度预算。PenguinHarness 只创建 CEO。CEO 第一次运行时会读取使命，然后在全员频道发一份提案：它怎么理解使命、第一批工单是什么、要招哪些岗位、各配多少预算、工作怎么分工。发完提案，它就停下来等你。提案里不写模型：除非你指定，每位员工都用组织的模型；组织没有指定模型时，则用 Project 的默认模型。

从这以后，你主要和 CEO 打交道。你批准方案和招聘之后，组织就按自己的日程运转起来：

- **日历让工作持续推进**。调度器每 30 秒检查一次所有组织。员工会在三种时候醒来：日历事件到点、被 `@` 提及、你直接找它说话。所以工作能跨天推进，不需要你一次次手动启动。
- **工单承载状态**。每张工单记录目标、验收标准、进展和结果。工单有变化时，负责人不会被打断，而是在下一次按日程醒来时再处理。
- **决策回到你手里**。公司的 Skill 和手册要求 CEO 和员工把重要决策提交给董事会：方案本身、招聘、预算调整、不经审核就关闭高优先级的工作，以及一切超出组织范围的行动，比如对外发布、花钱。繁重或不可逆的工作同样要过这道关卡——长时间计算、写到公共工作区之外、删除不是自己创建的东西、启动一个比本轮运行活得更久的进程。员工会在全员频道说明要跑什么、怎么停下来，把工单阻塞在你身上，然后结束本轮，等你答复。
- **预算约束成本**。员工的月度预算以美元计，下属的开销也算在内，所以 CEO 的预算覆盖整家公司。预算用到 80% 时，组织会在全员频道发出警告；用到 100% 时，这名员工和其下属的日历都会暂停。

![一人公司的组织图：一位 CEO、三位直接下属和一位校对编辑，每人都有月度预算](/blog-assets/agent-company-org-chart-zh.png)

这样一来，人的角色变了：不再一个任务一个任务地操作 Agent，而是定方向、审提案，遇到需要判断的事再介入。

## 镜像公司

公司模式的第二种用法，面向已经存在的公司。在镜像公司里，每位真实员工都有一个数字分身：一个 Agent，在组织图上的位置和它代表的人相同，本人通过自己的聊天应用和它对话。

![镜像公司：每位员工和自己的数字分身对话，分身替他们找到合适的同事](/blog-assets/agent-company-mirror-zh.png)

搭建镜像公司，从**员工数字分身公司**示例开始。CEO 会向你要真实的组织图：姓名、职位、汇报关系，以及每个人准备用哪个聊天机器人。你确认名单后，它为每个人招一个分身，照搬汇报关系，并为每个分身写一份简介和一页手册。接下来，你以董事会的身份，用和其他对话一样的**远程控制**对话框，把每个分身的工位对话绑定到对应本人的机器人上；绑定需要 Project 所有者的权限，如果是微信机器人，还要由这位同事用自己的手机扫码。分身建议用飞书、Telegram 或微信：QQ 机器人只能回复本人刚发来的消息，所以 QQ 分身能回答问题，却没法主动去问本人。

日常使用中，员工不必再琢磨该问谁，也不必打开群聊干等。一个问题会这样在组织里流转：

1. 员工在自己的聊天应用里向分身提问。
2. 分身能答的，就根据手册直接回答。
3. 答不了的，分身在全员频道里 `@` 负责这个话题的同事的分身。
4. 那个分身通过本人的机器人去问本人，再把答案转回来。
5. 答案回到提问的员工手里；两个分身把它记进手册，下一个人不用问就能查到。

实际上，「谁知道什么」这类知识，从每个人的记忆里搬进了一个共享的书面结构；每解答一个问题，这个结构就完善一分。

## 公司模式还做不到什么

公司模式目前还在内测，管理员开启之前一直是关闭的。下面几项限制，决定了眼下能在多大程度上依赖它：

- **审批只是约定，并不强制**。重要决策要交给董事会，这条规则写在 Skill 和手册里，但服务器不会阻止 Agent 自行招人、调整预算或移动工单。工具审批也不会送到你面前：组织的会话无人值守，因此从不等人——审批模式本该交给人拍板的工具调用，在发起的那一刻就被拒绝，Web App 里不会出现待审批的条目，也不会有运行挂在那里。默认的**全部放行**下，所有调用照常执行；改成**只读**后，读取照常，其余一律被拒，而员工会把这次拒绝当作请示董事会的信号，在全员频道里发问，而不是换个写法重试。想让组织无人值守地跑下去，就该保持默认的审批模式。
- **预算暂停是软性的**。预算用完只会暂停日历。`@` 提及和直接对话照常送达，已经在跑的运行不会被中止，两次检查之间的开销也可能超出预算。没有设自己预算的员工，只受上级预算的限制。
- **镜像公司还处在早期阶段**。分身根据你描述的组织图创建，而不是从 HR 系统导入，每个机器人都要手动绑定。本人先给机器人发过消息，机器人才能回复；绑定也没有发送者白名单，所以每个分身的机器人都不要公开。分身之间的转达在全员频道里进行，所有成员都看得到；默认情况下，`@` 提及链最多传递三跳。
- **工作只在服务器运行时进行**。PenguinHarness 停止期间到期的日历事件，之后不会补跑。

## 如何试用

PenguinHarness 0.2.13 及之后的版本提供公司模式。

1. 以管理员身份打开**系统设置**，在**服务器**分组下进入**公司模式**页，再打开**启用公司模式**开关。
2. 在侧栏里，从**开发**切换到**公司**。
3. 选择**新建组织**，填写**显示名**；再写一句使命，或者从示例里选一个（比如**员工数字分身公司**），并设置 **CEO 预算**。
4. 填写**组织 id**，或者点**用 AI 生成**，根据显示名生成一个，然后点**创建**。

![新建组织对话框，按员工数字分身公司示例填写](/blog-assets/agent-company-new-organization-zh.png)

想了解各部分的工作方式，请查阅[公司模式文档](https://penguin.ooo/docs/company-mode)。公司模式还在内测，遇到问题请告诉我们。

## 对人来说，什么变了

从工作台到共享空间，Agent 成了协作者。从群聊到组织，每个 Agent 有了明确的职责、一位上级、一份预算和一份书面记录，负责的人也得以治理这个系统，而不是一步一步地操作它。

我们也不认为组织就是最终形态。还有一些问题没有答案：该给 Agent 多大的权限，如何评估整个组织而不只是单个 Agent，一家能自我进化的公司又该怎么运转。PenguinHarness 已经能用 Benchmark 优化单个 Agent，把这件事延伸到整家公司，是我们想探索的方向。但对于长期、多人协作的工作来说，人类早已摸索出的那套组织结构，是比一条越拉越长的聊天记录更好的起点。
