Lay down rules first when vibe coding, and the resulting code will not give you heartburn. Our approach is to split the constraints AI must follow into three layers written directly into the repo, an approach we call code as memory.

Rules mentioned offhand in chat do not stick if they never make it to a file. We do not re-state rules at the start of every session. When constraints live in the repo, AI encounters them naturally as it reads files and runs tests. We split these constraints into three layers: human rules, interface abstractions, and reusable components, stored in the repo as code as memory — with layers growing harder to change as you move up and changing more often as you move down.

## Human rules: hard boundaries held by code and tests
Andrej Karpathy coined vibe coding in February 2025, describing a workflow where you click "Accept All" for every change and never read the diff. He noted this approach works fine for throwaway weekend projects.

We are already seeing the cost of unconstrained fast writing in industry data. GitClear analyzed 211 million lines of code changes between 2020 and 2024. The share of changed lines tied to refactoring dropped from 25% in 2021 to under 10% in 2024. Over the same period, the share of copy-pasted code rose from 8.3% to 12.3%.

Google’s 2025 DORA report reached a similar conclusion. Without solid automated tests, mature version control, and fast feedback loops, higher change volume from AI pulls down delivery stability.

Veracode tested over a hundred large models generating code across multiple languages in 2025. Forty-five percent of samples contained OWASP Top 10 level security vulnerabilities. Vulnerability rates showed no clear correlation with model size or how models were fine-tuned in training.

In July 2025, SaaStr founder Jason Lemkin shared his experience using the Replit AI coding tool. He explicitly told the tool not to modify code without permission, and it still deleted his production database. The Register reported his account.

This layer holds the rules we require AI to follow at all times. In our private design repo, principles, glossary entries, and proposals are numbered sequentially. A subset of these rules also lives in the public development Skill, documentation, and PR descriptions.

Each proposal documents exactly one decision, following the structure of the Rust RFC process with the same nine English section headings, written in plain language. Once a decision lands in code, the corresponding design doc is reduced to a short note pointing back to the proposal.

The PenguinHarness team clones the private design repo alongside the implementation repo for local development. The implementation repo reserves three symlink paths pointing to this design repo, all excluded via .gitignore so they never land in the public repo. design/ points to the full design repo, AGENTS.md points to the development rules file in the design repo, and CLAUDE.md points to that same AGENTS.md file.

Claude Code reads CLAUDE.md at the start of every session. Anthropic explicitly states that CLAUDE.md, and the AGENTS.md alternative, act only as context input and have no built-in enforcement power. If the design repo is not cloned alongside, the development Skill committed under .agents/skills/ in the public repo forms the full rule contract.

The rules we require AI to follow must ultimately land in code and tests. Many of these rules come from real instances of code drift or decisions made during code review.

Take the requirement that Trace must be append-only. The same rule lives in public documentation, the Trace writer’s O_APPEND implementation, and tests for rotation and single-write behavior. Even if the prompt never mentions the rule, the write logic will never allow in-place modification of historical records.

We do not match provider error messages by text. The first version of [#1018](https://github.com/Prism-Shadow/penguin-harness/pull/1018) used 16 regex patterns to match image-related rejection text. During review, the responsible maintainer changed it to a simple rule: image in input + 4xx status = image rejection.

Error text is passed through unmodified to users and the model, with no regex classification. The reasoning was that provider rejection wording varies too widely for pattern lists to be reliable.

Baseline numbers in prompt cache tests cannot be adjusted just to make tests pass. A cache regression increases token cost, but does not cause performance drops or visible UI errors. Tweaking baselines to turn CI green makes a cost decision on behalf of users without their knowledge, and hides cache regressions until after deploy.

We once hit a case of drift where a new placeholder added to the default Prompt did not appear in the UI list. The parity test added after that derives a placeholder list directly from the real core default Prompt. The test compares that list against both UI dictionaries to catch mismatches.

Our rule is simple: every time a boundary is crossed once, add a test to pin it in place. The full path runs from numbered principle through public documentation and code implementation to enforced test assertion, with a separate soft constraint path for in-session prompts, as shown below.

## Narrow interface boundaries to the minimum necessary
The middle layer holds core interface abstractions, which we design to expose only the minimum necessary boundary. Agent State is a directory on disk that only holds editable files that directly change agent behavior: configuration, the agent’s own AGENTS.md prompt file, Skill, hooks, memory, Vault, and scheduled tasks.

The Agent State boundary is defined jointly by directory layout and config storage location. Benchmarks, traces, scratchpad, shared_env, workspaces, and snapshots all sit outside agent_state, as do .project_config.toml and server-stored configuration.

`context_engine` only processes structured OmniMessage, with three external boundaries: Human, LLM, Environment. The Human boundary is the `session.run` SDK entry signature; all protocol conversion happens inside the implementation, and the engine never parses marker text to infer a message’s source.

Every complete tool_call generates an approval decision written to Trace. When the SDK does not inject an approval callback, all calls are denied by default. Child agents inherit the parent’s approval callback, so policy applies across the full delegation tree.

Hooks can return an allow or deny judgment before the approval callback runs. An allow decision from a hook cannot override project-level command policy; calls blocked by policy always remain forbidden. An agent cannot relax Approval mode or modify command policy through its own settings.

All communication across these boundaries uses the structured OmniMessage protocol; the fixed flow between context_engine, the three boundaries, and Trace is shown below.

Early versions placed command policy matching inside `context_engine`, so the engine generated approval_decision events itself, overstepping by making decisions on behalf of the Human. We moved that logic to an approval callback wrapped by `Session.run`, leaving `context_engine` to process only OmniMessage.

Command policy guards against accidental mistakes; it is not a security boundary. It does not cover commands constructed at runtime; true isolation comes from sandbox mechanisms like bubblewrap and dsh.

## Reuse first, extend second
Once interface boundaries are set, this layer allows AI to continuously improve abstractions, with one requirement: prioritize reusing existing implementations instead of building from scratch every time.

The frontend development Skill spells out this reuse-first decision order explicitly. When facing a new requirement, we first check existing components and mechanisms, then follow the path: reuse directly where possible, extend existing implementations next, decide if behavior is common across scenarios before extracting shared components, and leave one-off logic in its business feature.

The shared UI package `packages/ui` holds design tokens, themes, and common components. Tests inside the package enforce token contracts, ensuring every theme and mode defines all design token names. State colors in the Web App are spelled only once in tone.ts, and all fold interactions use the Fold component provided by packages/ui.

Test doubles for each package live in one central location, so new tests reuse existing fakes first. Proposals to simplify code require evidence; zero production callers is strong evidence, and personal preference is not enough to delete code or narrow interfaces.

Plugins and core services follow the same Interface/Component/Module assembly rules, with no separate integration logic. Model integrations all go through the MMSP boundary; core code never imports vendor SDKs directly.

Hot updates do not interrupt running Tasks. This feature directly reuses the registry, resource-interface gate, and suspended context already proven for terminal handoff scenarios. The implementation only added one pure data component to hold runtime state, plus a pointer switch. Two earlier attempts were never merged because they required overly broad changes.

The optional `continual-learning` plugin does not come preinstalled. It triggers a sub-session after long Tasks complete. The sub-session can write useful findings to the corresponding SKILL.md under the current agent’s own `agent_state/skills/`, or it can make no changes at all.

For the UI "de-AI-ification" scanner, we reused the open source implementation yetone/kill-ai-slop directly instead of rewriting it ourselves. Change reasoning is written in PR descriptions, which stay attached to their corresponding diff; we do not store this kind of content in repo files.

## Start with one test
The next time AI-written code crosses a boundary, you do not need to write an entire rulebook first. Start by writing one failing test that captures the exact violation.
