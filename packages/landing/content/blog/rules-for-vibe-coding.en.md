> Written for PenguinHarness 0.2.16. Later releases may differ in some details.

The 2025 DORA Report finds AI adoption currently correlates negatively with software delivery stability. Teams missing automated tests, mature version control, and fast feedback loops face more instability as AI-generated change volume grows[^1].

Rules for agents during vibe coding belong in the repo, loaded at every session start. This is code as memory. **Organize rules across three layers, let code and tests carry hard constraints, and leave prompts only for passing context**.

**TL;DR**
- Chat agreements do not persist across sessions; rule files only provide context and cannot block violations
- Repo rules split across three layers, with stronger constraints and fewer changes higher up
- When an agent repeats a mistake, add a rule and test instead of lengthening prompts

## Code as memory
A longer prompt does not carry a rule into the next session; the repository does. Every agent session starts with a fresh context window. Rules shared in chat never carry over.

Project rule files load at session start as context, but cannot block actions on their own. Blocking needs code[^2].

Jason Lemkin reported Replit's AI deleted his production database though he told it not to change code without permission. He wrote there is no way to enforce a code freeze in vibe coding apps like Replit[^3].

A common response is to write longer, stricter prompts or rule files. Longer files consume more context and reduce adherence. **Actions that must be blocked need code-level enforcement**.

We organize repo rules across three layers.

## Ground human rules in code
This top layer holds a small set of non-negotiable rules, each paired with code and tests. **Short, enforced rules stick; long rule lists do not**.

We borrow from RFC practice, recording each rule as a numbered item that rarely changes once it lands.

Take the Trace rule: Trace is an append-only JSON Lines file where past entries are never modified in place[^4]. The Trace writer opens the file with O_APPEND for every record, using one `write(2)` call per entry. Core tests check old Trace files stay append-only after rotation, and a multi-megabyte record is appended in one write.

Critics call this bureaucracy that slows vibe coding. Only rules that must never break live here, each small enough to pin with one test. The rest stays out.

## Draw minimal core interface boundaries
Below that pinned top layer, start rules in code with minimal interface boundaries and set dependencies before logic. **Small interfaces cut accidental change scope; fixed dependencies block approval bypass**.

Agents may edit configuration, prompts, and Skills inside Agent State. Command policy, credentials, API toggles, and approval mode sit outside Agent State or on the server, out of reach of self-edits[^5].

Beyond directory layout, core engine boundaries stay equally minimal. Every complete tool call requires an approval decision passed via the `approve` callback on the Human interface. Without that callback, the engine rejects all tool calls by default[^6]. `Session.run` wraps the approval callback with the Project command policy, so vetoed commands are refused before the host is asked for an approval decision.

Critics say minimal interfaces limit agent power. We place only what an agent must never grant itself outside the boundary; all else stays open to agent edits.

## Prioritize reuse of existing abstractions
Within that editable scope, reusable components form the bottom layer, where **agents improve existing abstractions and reuse code before writing new, to avoid bloat**.

GitClear analyzed 211 million changed lines from 2020 to 2024[^7]. Refactored lines fell from 25% in 2021 to under 10% in 2024, while copy-pasted lines rose from 8.3% to 12.3%.

Frontend tests guard reuse: `test/icon-scale.test.ts` fails on a second copy of the caret, close cross, or collapse chevron. A hot update now hands running Tasks to the new build instead of aborting them, reusing what terminal handover already had[^8].

Some say copying is faster now code is cheap, and early abstraction is wasted work. Copies are cheap to write and costly to keep; every copy adds another place a rule must hold. Only behaviour shared across cases moves into a shared component; one-off logic stays in its feature.

## Start with one rule
Working this way across the three layers, you do not need to write every rule up front to get value. Mitchell Hashimoto describes his own practice: when an agent makes a mistake, he builds a fix so it never repeats[^9].

A rule in the repo, pinned by a test, is fixed once for every later session.

Next time an agent repeats a mistake, **put the rule in the right layer and pin it with a failing test, instead of making your prompt longer**.
