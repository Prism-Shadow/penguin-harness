> Written for PenguinHarness 0.2.16. Later releases may differ in some details.

When you build an agent harness, most failures throw, lag, or return a bad reply. One class does none of those: the code runs, the UI looks right, CI stays green, and requests with a diverged prefix silently pay full price for content the provider used to cache. This post walks through the design of PenguinHarness's core CI check for those failures, using our prompt-cache test suites as the worked example.

**TL;DR**
- The suites ran in 1.54 s on our test machine, need no keys or network, and run on three OSes in CI.
- Reverting #700 makes the invariant check fail, with estimated compaction request costs 1.13× to 10.2× the shipped value across two measured scenarios.
- We never re-baseline failures to green; cost changes go to a person.

## The prompt-cache regression that motivated the work
A one-line change to request assembly can shift a few bytes early in a request, with no effect on the reply the user sees.

PR #700 corrected an earlier deliberate design choice. Before the fix, compaction requests used the thinking level the context opened with, even after a user changed the Session's pinned thinking level. That created a parameter divergence exactly when the context was largest.

The suites shipped in PR #722 the day after #700 merged, citing that parameter drift as their reason. When we deliberately reverted #700 on the current codebase, two tests failed: the engine test that originally asserted the old contract, and one invariants suite case. The lifecycle suite passed entirely, because none of its shipped scenarios compact after a thinking-level move.

## What a cache check has to judge
A provider serves cached prefixes only when every byte from the start of the request up to a cache breakpoint matches exactly.

For Anthropic's Claude models, that match is necessary but not sufficient. The provider enforces a 1,024-token minimum cacheable prefix for Sonnet 4.6, a 20-position lookback window, and a default 5-minute TTL that can expire entries even when bytes stay identical.

OpenAI likewise requires the entire rendered prefix to match for cache reuse.

Divergence at an earlier tier invalidates all later content. A changed tool or system prompt, for example, forces a full re-read of every message after it.

## The test system, end to end
Our design runs unmodified production Session, ContextEngine, and GenerativeModel code. It replaces only the provider network stream with a script, and uses a fake tool environment for shape-only cases. Two readers interpret the recorded requests.

Scripted replies always report zero cache reads, so all external cache behavior is modeled entirely offline.

The byte diagnostic names the earliest structural divergence between consecutive requests in the same context. It uses vocabulary modelled on Anthropic's cache diagnostics, with a harness-specific `parameters_changed` reason for divergences the provider reports as `unavailable`.

The offline simulator applies Anthropic's documented cache rules. It accounts for block ordering, breakpoint placement, TTL, and the 20-position lookback window to report estimated cache read, write, and input tokens per request.

A single invariant ties the readers together. Every request after the first in a context must read back the whole prefix of the previous request in that context. Misses that exist by design go on a named allow-list. Every exemption is self-checking: it fails if the named request no longer falls short of the expected prefix, so stale exemptions cannot weaken the suite over time.

Suites split the work by concern. The invariants suite checks byte-level request assembly, the lifecycle suite applies cache rules to full Session flows, and the simulator suite pins the rule engine itself to documented provider behavior. CI selects the suites whenever it picks the core package for testing, and the dev skill requires running them locally whenever request assembly changes.

## Why we do not call live APIs for these checks
The most obvious way to check cache behavior is to send requests to a live provider and read returned usage metrics.

Live calls require API keys and network access, produce non-deterministic results from provider-side cache state, and return no root cause for parameter-only divergences like a shifted thinking level. Our scripted provider approach eliminates all three issues, though it cannot confirm live provider behavior — that limit is explicit, not hidden.

## Bytes alone cannot model provider cache behavior
A naive byte-equality check between consecutive requests catches structural divergences, but cannot translate those divergences into the token counts a provider will bill. It also fails to detect cache misses that happen with no byte change at all, like an expired TTL entry.

The difference shows up clearly on a parameter change like the #700 thinking-level drift. A byte-only check flags the `parameters_changed` divergence, but cannot report how many tokens the provider will actually read or write for that request.

## Pinned token counts are too brittle
A second naive approach pins exact per-request token counts as snapshots. This catches major cache breaks, but also fails on harmless edits that preserve the prefix match rule while shifting token counts slightly.

A harmless 49-character sentence appended to the fixture system prompt changes 10 of 20 per-request read and write counts across a ten-turn conversation, but leaves full prefix read-back intact. The simulated hit ratio shifts from 88.61% to 88.62%, a negligible change with no meaningful cost impact.

## Cost changes go to a person, not a test baseline
The final trap is treating a failing cache check as a test to update to green. Editing an expected token count or adding a new entry to the allow-list is a decision to spend user money, not a fix. The moved tier and its estimated cost must be put to a person to decide, and called out in the change reply, not only buried in a test log.

We measured the impact of reverting the #700 compaction thinking-level fix across two throwaway replay scenarios, comparing shipped code to the reverted state. Compaction request cost grows with content added after the level move, as older entries fall out of the provider's 20-position lookback window.

When the invariant catches a drift like the #700 revert, its report names the request index, the divergent `output_config` parameter, and the tier of the divergence, plus an estimate of how many tokens fall after the mismatch.
