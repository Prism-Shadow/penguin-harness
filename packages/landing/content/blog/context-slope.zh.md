> 本文基于 PenguinHarness 0.2.16 撰写，之后的版本在部分细节上可能有所不同。

上下文斜率 (context slope) 是我们提出的概念，指每发一次请求，Agent 的模型上下文会增长多少，这个量由 Harness 直接控制。我们的判断是，**Harness 应该先把这部分每轮增长压下来，在所有环节遵循索引先行，按需拉取** (index first, fetch on demand) 的模式，不要把增长问题全丢给有损的压缩机制解决[^1]。

**TL;DR**
- 把上下文拆成固定截距和每轮斜率，压缩只是有损兜底，不能当设计方案。
- 索引先行，按需拉取的规则能从 Skill、工具输出、CLI 三个层面压低斜率。
- MCP 需要固定、延迟加载的工具定义，才能缩小截距、保持缓存命中。

## 截距与斜率
每次请求上下文分两部分：**每轮固定截距含系统提示词、工具定义、Skill 名单行；每步累加斜率**含工具输出、按需拉取指令、回复。LangWatch 分析 287,748 条 Trace 发现，5 万 Token 以下每步增约 3,200，20 万以上稳在约 1,470，上下文每翻番，成本约涨 6 倍[^2]。

Anthropic 定义上下文腐烂：Token 越多，召回率越低。2025 年 arXiv 研究在五个大模型测得 13.9%–85% 性能下降，标称窗口内、检索完全准确也会发生。

斜率决定 Session 压缩触发速度。压缩是有损兜底，可能漏关键细节，耗一次请求成本；仓库缓存模拟器测得，压缩后首轮冷缓存。

我们在 PenguinHarness 0.2.16 跑合成测试，脚本驱动，Token 按字符估算，未调用真实模型[^3]。初始截距 2,963 估算 Token，变量为 16,000 字符默认输出上限。

## 渐进式 Skill 加载是通用模板
**更平缓的斜率能把压缩挡在外面，撬动所有优化杠杆的思路都来自索引先行，按需拉取**。Anthropic 的 Agent Skills 用渐进式披露机制，启动时只加载名称和描述，相关时才拉取完整 SKILL.md，附带文件仅在需要时加载[^4]。

PenguinHarness 沿用这个结构，系统提示词里每个 Skill 只放一行名单行，模型通过 `read_file` 或 shell 读取完整 SKILL.md，没有专门的 Skill 调用工具。拉取到的 Skill 内容会留在上下文里直到压缩，成本从所有请求都要承担的截距，转移到真正用到该 Skill 的轮次。0.2.16 还有两个未解决的截距膨胀点，`AGENTS.md` 会完整注入没有大小上限，所有配置好的 MCP schema 会随每次请求发送。

## 工具输出先落盘
Skill 层面的节省，来自活跃上下文里只保留指向完整内容的短指针，这个规则同样适用于原始工具输出。PenguinHarness 0.2.16 把默认内联工具输出上限设为 16,000 字符，只保留头尾窗口加截断标记，完整输出写入暂存区的恢复文件，文件路径打印在内联结果里。

## CLI 与 MCP 遵循同一规则
**索引先行，按需拉取适用于 CLI 和 MCP，二者默认配置易膨胀截距和斜率**。Willison 指出大模型会用 `--help`，CLI 无需预置过多说明；浏览器插件无 schema，模型经 `exec_command` 调用，输出有界、带 `--save`；`penguin run --json` 仅返回结果对象，委托流量不进上层上下文[^6]。

Zechner 发现设计得当的 MCP、CLI 都高效，但不少 MCP 包装冗余；Willison 称 GitHub 官方 MCP 占数万 Token[^7]。Anthropic Tool Search 延迟加载，初始开销从约 77K 降到约 8.7K，不破坏缓存；Cloudflare Code Mode 仅两工具，约 1,000 Token，全量 API 定义需 117 万。Manus 指出中途增删工具会使前缀缓存失效。
