> 本文基于 PenguinHarness 0.2.16 撰写，之后的版本在部分细节上可能有所不同。

我们认为，控制上下文斜率是 Agent Harness 的核心职责。上下文斜率指 Agent 每轮请求的上下文增长速度。我们并未新发现这一增长效应本身。

Self-Manager 论文把这个量测为上下文累积速率，LangWatch 将相关成本称作上下文税。TraceLab 研究过编码 Agent 工作负载下的上下文增长与压缩，另有独立工作在追踪恒定上下文的 Agent 设计。

本文所有体积测量都用字符计数换算估算 Token，与服务商返回的官方 Token 计数存在偏差。上下文成本大致拆成两个可设计的部分。第一部分是截距，即每次请求启动时携带的固定开销，包含系统提示词、工具定义、Skill 索引元数据和记忆索引。第二部分是斜率，即每次请求中工具结果、加载内容、模型回复带来的新增成本。

我们聚焦这个问题，基于三个现实约束。上下文窗口有上限，长上下文下精度会下降（Anthropic 把这类现象叫做 context rot，即上下文腐化），压缩操作本身也有明确成本。

## 截距与斜率

我们在测试机上跑了一组合成工作负载，直接测量斜率。测试用脚本驱动 Agent 逐轮对 16 份生成的构建日志执行 `cat`，调用仓库自带的提示词缓存测试辅助工具。整个测试运行在配置为 20 万估算 Token 窗口的测试夹具上。整个过程不向真实模型服务商发请求。

这个最小化测试夹具里，第一次请求还没加载任何工具输出，就携带了 2,963 个估算 Token。其中 1,493 个估算 Token 来自五个工具定义、模型标识块，以及夹具自带的系统提示词；测试场景没有加载 Skill 索引、记忆索引，也没有引入 `AGENTS.md`。

累计上下文触达压缩阈值时，Harness 会在整次运行的最大上下文体积处额外发一次请求。我们在 64k 日志、无输出上限的合成测试里测到，这次压缩请求的估算体积超过 20 万估算 Token 的夹具窗口。在模拟 Anthropic 风格提示词缓存的场景下，压缩后重建上下文的第一次请求会触发完整的模拟缓存未命中。压缩是必要的安全网，但它有额外开销、会造成信息损失、还会触发缓存失效，不适合作为主要策略。

## 渐进加载压低截距

渐进式披露是 Agent Skill 的标准设计思路，初始提示词里只给每个 Skill 留很短的索引条目。PenguinHarness 的 Skill 渐进加载采用这种索引优先模式，还把同样的规则延伸到记忆、定时任务和密钥库条目。

目前有两个明确例外。`AGENTS.md` 会完整拼进提示词，不做长度限制；所有探测到的 MCP (Model Context Protocol) 工具定义会随每次请求发送。

模型选中某个 Skill 调用时，才加载完整的 Skill 正文，压低初始截距。0.2.16 版本随包发布的 35 个 Skill，索引行总共占 2,843 个估算 Token，外加 99 个估算 Token 的分段标题。默认 Agent 预装的 25 个 Skill，索引行总共占 1,889 个估算 Token。如果启动时就加载全量库所有 `SKILL.md`，会多占 124,826 个估算 Token，是索引体积的 43.9 倍；参考文档还要再占 58,577 个估算 Token。随版本发布的脚本直接执行，不会读入上下文。

PenguinHarness 中，加载后的 Skill 正文会作为工具结果历史留在上下文里，直到触发压缩。渐进加载只是把开销从固定截距转移到实际使用 Skill 的轮次，不会彻底消除每轮的上下文增长。

记忆、定时任务和密钥库条目，同样遵循索引优先规则。记忆只注入索引（上限 200 行或 25,000 字符），主题正文按需读取。定时任务只注入任务名称。密钥值直接传给子进程，只有密钥名会进入提示词。

## 磁盘支撑的上限压低斜率

我们的合成测试显示，每轮斜率主要来自工具输出，给行内输出设置硬字符上限，能阻止每轮增长随原始命令输出体积线性放大。测试机上的测量结果是，不加限制时，64,000 字符的构建日志每轮会增加 16,297 个估算 Token。开启默认的 16,000 字符上限后，不管原始日志是 64,000 字符还是 256,000 字符，每个超上限的日志只会增加 4,163 个估算 Token。

只加上限会有数据丢失风险，PenguinHarness 会把超上限的完整输出存到恢复文件，只返回头部、尾部和文件路径，附带截断标记。Claude Code 和 Cursor 处理超大工具输出时，也用同样的文件支撑模式。恢复文件单次调用最多存 8 MiB，输出产生方自身缓冲区已经丢弃的文本无法恢复。模型可以用普通文件工具读取需要的精确切片，不用在后续每一轮都携带完整输出。

避免跨轮携带不必要内容的原则，不只适用于单个工具输出，也适用于会话层面。子 Agent 就在会话层面应用这套斜率逻辑。子 Agent 运行在各自的隔离上下文里，父 Agent 通过带上限的缓冲区接收子 Agent 的助手文本，流程和接收其他工具结果一致。子 Agent 的完整工具流量永远不会推高父 Agent 的斜率。

## CLI 与 MCP 设计同样能弯折曲线

面向模型调用设计的 CLI（命令行），只返回模型下一步需要的小型结构化输出切片，以此压低斜率。它们默认不会返回完整 JSON 或者未过滤的页面内容。Simon Willison 提过，模型有需要时可以自行调用 CLI 的 `--help`，不需要太多前置描述。Mario Zechner 测过前置 Token 成本的差异，一份 225 Token 的 CLI README，对比两个常见浏览器 MCP 服务器分别占 13.7k 和 18.0k Token。

`penguin browser scan` 默认返回简化 HTML 输出，最多 35,000 字符，加 `--text` 参数返回纯文本，预算是前者的三分之一。`penguin browser exec` 把返回值上限设为 8,000 字符，提供 `--save` 参数存储完整结果。`screenshot` 命令只返回文件路径和尺寸。

Mario Zechner 跑了 120 次基准测试，结果显示设计得当的 MCP 和 CLI 性能相当。

配置 MCP 服务器后，探测到的工具定义会计入每次请求的固定截距。当前版本的 PenguinHarness 会在每轮请求中携带所有探测到的工具 schema。Armin Ronacher 提过，据他所知，工具定义必须在整个会话中保持静态。

Manus 提醒过，迭代中途变更工具会破坏 KV 缓存，因为工具定义放在上下文靠前的位置。任何延迟加载方案都必须保证单个上下文内的活跃工具集固定，才能维持提示词前缀稳定。

斜率原则给 PenguinHarness 的 MCP 支持指明了具体方向。一套固定的延迟加载工具集，能跨轮次保持提示词前缀字节级一致，不管走工具搜索还是通用代码执行端点，都能在不破坏缓存的前提下压低截距。Claude Code v2.1.7 引入了自动延迟加载机制，上下文占用超过 10% 阈值后，通过 MCPSearch 工具触发。截至 2026 年 10 月，Claude Code 的文档说明会话启动时只加载工具名和服务器说明。Anthropic 公布其 Tool Search 功能在一个内部样例中降低了 85% 的 Token 占用，从约 77K 降至约 8.7K Token。

Cloudflare 提到，自家 Code Mode 通过两个固定工具 `search()` 和 `execute()` 暴露整个 Cloudflare API。Cloudflare 估算，不使用 Code Mode 的等效 MCP 服务器会消耗 117 万 tiktoken 计数的 Token，Code Mode 只需要约 1,000 Token。Cursor 把 MCP 工具呈现为文件，A/B 测试数据显示，调用过 MCP 工具的运行总 Agent Token 降低了 46.9%，具体数值随安装的 MCP 数量变化方差很大。
