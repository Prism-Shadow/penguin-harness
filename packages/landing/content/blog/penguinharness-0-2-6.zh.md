PenguinHarness 0.2.6 发布。预置模型库多了两个低价 Flash 模型和一整个新网关；智能体的触达范围则向三个方向各长了一截：子智能体面板从「看着子智能体跑」变成了「和它对话」，`penguin` CLI 变成了服务端的客户端——这正是智能体得以驱动运行着自己的那套 Harness 的前提，而 Session 可以绑定飞书应用或 Telegram 机器人，从聊天里对话。

## 两个 Flash 模型，其中一个出现了三次

`glm-5.3-flash` 与 `qwen3.8-flash` 进入预置模型库。两者都是百万 Token 上下文窗口，都能读图，价格也都比各自的非 Flash 版本低一个数量级左右。

GLM-5.3 Flash 在模型库里出现了三次，因为有三条通路在卖它——Z.AI 直连、OpenRouter，以及新增的 TokenDance——每条记录写的都是这条通路的收费。

![OpenRouter、TokenDance 与 Z.AI (GLM) 下各有一条 GLM-5.3 Flash，都带视觉标记，价格各不相同](/blog-assets/penguinharness-0-2-5-glm-flash-rows-zh.png)

三个价格不一致有两个原因，其中一个是值得知道的口径差异。TokenDance 只是按自己的费率收费；而 Z.AI 正在对这个模型做 50% 促销，有效期至 2026-09-09——两条记录对这次促销的处理是**有意不同**的：**直连厂商的记录写厂商的官方标价**，所以 Z.AI 那条是每百万 Token $0.03 / $0.15 / $0.50；**网关的记录写网关实际计费的价格**，所以 OpenRouter 那条是它的一半。促销结束之前，直连那条记录把 Z.AI 的实际收费高估了一倍。

直连那条上的「视觉」标记比看上去要新。AgentHub 0.4.8 让 GLM 客户端开始转发 `image_url` 部件——提示词里和工具结果里都转发——而且只对 `glm-5.3-flash` 一个 id 生效。其他每个 GLM id 面对图片都会直接报 `"GLM <id> does not support image inputs."`，而不是悄悄丢掉，这也是该分组其余模型仍标为不支持视觉的原因。

Qwen 3.8 Flash 位于 Qwen Pay-As-You-Go 分组，百万 Token 输入窗口、131K 输出上限，同样支持图片输入。

![Qwen Pay-As-You-Go 分组里并排的 Qwen 3.8 Flash 与 Qwen 3.8 Max](/blog-assets/penguinharness-0-2-5-qwen-flash-row-zh.png)

## TokenDance 网关，以及一把不用手抄的密钥

TokenDance 现在是独立的供应商分组，通过 Chat Completions 协议访问 `https://tokendance.space/gateway/v1`，随分组提供七个预置模型。

![TokenDance 分组：七个预置模型，分组头部有添加模型、自动获取密钥、手动设置密钥、测速与前往密钥管理](/blog-assets/penguinharness-0-2-5-tokendance-group-zh.png)

值得单独点出来的是**自动获取密钥**。它把你送到 TokenDance 自己的授权页，在你的账号下签发一把新密钥，并写入该分组的每一个模型——第一次使用不必再跑一趟控制台手工复制。PKCE 校验串在服务端生成、从不下发给浏览器，签发出的密钥也不经过浏览器直接进入分组的模型配置，不出现在任何响应、日志、URL 或错误信息里。回调到不了你这里的场景（桌面端，或某些部署形态）另有一种手动模式：授权页改为显示一次性验证码，粘贴即可。

该分组的价格记录的是**官方标价**，与下方两个 Qwen 分组同一口径；而其中两条正在促销：`glm-5.3-flash` 打五折、`qwen3.8-max` 打八折。也就是说这两条目前把实际花费算高了。两个促销都在 TokenDance 的公开模型接口里带标记，且该接口无需凭据，所以促销是否还在跑是可以查的，不用猜。

与该分组一同上线的还有应用归属：模型请求现在会向读取该类头部的网关表明自己是 PenguinHarness——OpenRouter 用 `HTTP-Referer` 与 `X-OpenRouter-Title`，TokenDance 用 `X-App-URL`。头部按端点的 host 选择，而非按供应商分组，因此一个归在 **custom** 下、却指向这两个网关的模型，会得到同样的归属标记。

以上这些都不会自动出现在你已有的 Project 里。预置模型是在创建 Project 时复制进 `.project_config.toml` 的，此后不再被改写；模型页的**同步预置**是唯一入口。它只补入缺失项、更新 catalog 所属字段，不删除任何东西，也不会动你保存的默认模型和任何凭据。

## 可以对话的子智能体

子智能体过去是「发出去，然后只能看着」。子会话还在运行时 `input_subagent` 会拒绝新的提示词；面板里既不能纠偏也不能停止；停掉主智能体，它的子会话还在跑。这些现在都没有了，取而代之的是同一套机制：把你本来就有的、对主会话的纠偏通道指向子会话，模型和你都能用。

![子智能体面板：上方是调用关系图，下方是子会话对话——一条纠偏消息与子会话的后续回复，底部是子会话自己的输入框](/blog-assets/penguinharness-0-2-5-subagent-steering-zh.png)

对模型来说，`input_subagent` 增强了不少。发给运行中子会话的提示词会作为纠偏消息在它下一步注入。新增的 `abort` 参数只停掉子会话**当前这一轮**——会话本身保留，还能继续对话——`abort` 与提示词一起给出，就是一次调用完成「打断并改道」。它的返回值现在是子会话**最近一条完整回复**，每次访问都是幂等快照，而不是增量抽取。已释放的 `subagent_id` 在模型再次给它发消息时会自动复活。

对你来说，选中的子会话由**与主对话完全相同的输入框**驱动：正文、技能与斜杠指令、按轮设置的思考档位、显示子会话自身用量的上下文环，以及审批模式选择器。无论子会话处于什么状态，你发的都是一条对它的用户输入——运行中是纠偏，空闲时是新一轮，已经结束的则被复活。「该子智能体已结束」不再是死路。

最后一处缺口是审批。后台子会话碰到工具审批过去会被自动拒绝：父任务结束时会把所有待审批一并收敛，而没有活动轮询窗口的子会话根本没地方发问。现在，无处可去的子会话审批会以普通审批卡片的形式升级给你；父任务结束时也只收敛主会话的审批——子会话的卡片会一直留在那里，等你决定。

随之而来的是一处取舍，而且是实打实的。既然子会话始终可恢复、从不销毁，「kill」这个概念对子智能体就不再成立：`kill_subagent` 已**移除**，`kill_command` 并入 `input_command`，改为 `kill: true`。这两个旧名字没有保留任何兼容——模型调用它们会得到标准的「未知工具」失败。详见下方[升级须知](#升级须知)。

## 能驱动 Harness 自己的智能体

`penguin run` 与 `penguin chat` 过去是在进程内直接调用 core 执行任务的：不经过服务端，Web App 也看不见。现在它们是 HTTP/SSE 客户端——CLI 负责解析参数与渲染流式输出，任务本身在服务端执行——因此终端里发起的对话会出现在侧边栏里，浏览器里发起的对话也能从终端接着聊。

这次重建是后面这些的前提。除 `run` 与 `chat` 外，现在还有一组用于查看和操作一套部署的命令——`ls`、`input`、`logs`、`agent`、`project`、`cost` 与 `schedule`——而 Agent 运行的每一条命令都会被交给使用它们所需的坐标。`PENGUIN_API_URL`、`PENGUIN_API_TOKEN`、`PENGUIN_PROJECT_ID`、`PENGUIN_AGENT_ID` 与 `PENGUIN_SESSION_ID` 会注入每一个工具子进程，因此在会话内部，一句不带任何参数的 `penguin agent ls` 访问的正是承载该会话的那个服务端，并且已经以该 Project 与该 Agent 为默认值。这条路径上没有任何登录步骤。

![智能体在自己的对话里执行 penguin agent create 与 penguin run --background，随后用 penguin ls 看到刚刚启动的会话](/blog-assets/penguinharness-0-2-5-orchestration-zh.png)

`penguin input` 正是它与上一节交汇的地方：同一个动作，只是往外挪了一层。发给**运行中**会话时，它会在下一步作为纠偏被吸收，与对子智能体发送纠偏消息完全一致；发给空闲会话则开启新一轮。不带 `-m` 时它转为轮询，打印该会话最近一条完整的助手回复——一份幂等快照，与 `input_subagent` 传空提示词时的语义相同。`--timeout` 为任何等待设定上限，到期是一次软让出：退出码 0、一行点名后续命令的提示，而任务仍在服务端继续跑。

智能体启动的会话会继承它自己的配置。`run` 会把你没有指定的每个字段，逐个从调用方会话的实时取值里补齐——工作区、模型对、审批模式、思考档位——与 `run_subagent` 对子会话的继承是同一套。因此在 Agent 内部，单独一句 `penguin run -m "…"` 通常就是对的，参数是用来偏离它的。

授权模型有意保持朴素。服务端每次启动都会签发一把 API 令牌，写入 `<data-root>/api-token`（权限 0600），同机的 CLI 直接读取它；这把令牌等同管理员权限，理由是能读写数据根的文件系统访问权本来就等同管理员权限。指向远程的 `--server` 没有这层便利，未显式提供 `PENGUIN_API_TOKEN` 时会被拒绝。

这些用法以 Skill 的形式随产品发布。**`penguin-orchestration`** 进入技能库的「AI 应用开发」分组，且没有预装标记，因此新建的 Agent 会像装其余技能一样装上它。它写明了惯例——动手改动之前先用只读列表命令摸清现状，大段材料通过工作区文件交给新会话，而不是塞进 `-m`——也写明了注意事项，那才是真正的边界：每个会话同时只有一个活动任务，因此发给繁忙会话的消息是纠偏而非排入第二个任务；派生的会话继承你的审批模式，因此无人值守的 `always-ask` 会话只会一直挂着，等一个并没有在看的人；能给智能体发消息的智能体，也能搭出一个永不终止的循环；以及它启动的一切都算在同一个 Project 的账上。

## 可以从飞书或 Telegram 联系的 Session

对话不再只能在浏览器标签页里读。Session 可以绑定到一个自建的飞书应用或一个 Telegram 机器人：发给机器人的消息会作为普通用户输入进入该 Session，助手的回复也会回到聊天里。

![Telegram 下的消息软件面板：先是渠道选择器，随后是带实时状态的启用开关与两个探测按钮，再往下才是 Bot Token 字段及其已存密钥掩码与清除勾选框](/blog-assets/penguinharness-0-2-5-messaging-zh.png)

两个渠道位于同一层连接器抽象之后，Session 为每个渠道各保存一份配置——飞书需要 App ID、App Secret 与 API 域名，Telegram 只需要一个 Bot Token——但**同时至多只有一个处于启用状态**，持有实时连接的就是它。想启用第二个时，开关会带着原因被拦住，服务端也会拒绝。

两个渠道都不需要公网 URL。飞书的入站事件走 SDK 的 WebSocket 长连接；Telegram 没有公网 webhook 就不会推送，因此连接器改为主动拉取，走基于 offset 的 `getUpdates` 长轮询。一台位于 NAT 之后的笔记本就够了——不必打隧道，也不必准备 webhook 端点。连接时，轮询会把无人连接期间积压的更新直接跳过，而不是把这段空窗期重放成一堆任务；飞书同理——错过的事件就是错过了。

回复是完成一条发一条，而不是在整轮结束时发一大块。每条完整的助手消息在完成的那一刻单独转发出去，因此一轮里在工具调用之间写下的工作笔记，到了聊天里也是同样的一串消息；同一个 Session 的发送被串行化，到达顺序与完成顺序一致，并按各渠道的文本长度上限分块（其中 Telegram 的 4096 字符上限最紧）。在群聊里，一轮中发出的第一段内容会挂在触发它的那条消息下形成话题回复，其后的一切——包括这条消息自身的后续分块——都是普通发送，这样长回答不会把话题埋进一堆引用块里。

凭据沿用模型页的那套交互：输入框永远从空开始，已保存的密钥只以掩码形式显示，旁边的「清除已保存的……」勾选框在保存时将其丢弃——而该渠道的连接处于启用状态时，清除会被拒绝，这样实时连接永远不会跑在它的凭据存量之前。保存与启用是两件独立的事：保存只写凭据，开关则用已存的凭据去连接或断开。表单把控件放在前面、凭据字段排在后面，这是有意为之：两个渠道的字段数量不同，控件若放在字段下方，在两个渠道里的高度就不一致，每次切换都会跳动。

一套表单，两个宿主——会话行的菜单，以及对话面板栏里紧邻 Trace 面板的**消息软件**面板。持有实时连接的 Session 会在侧栏行上带一个小小的纸飞机，所有渠道共用同一个标记，渠道本身由提示气泡与无障碍文本点名，而不是由图形区分。而模型看到的一切并无特别：入站文本以普通输入框内容的形式启动任务，没有任何标记、也没有特殊发送者，因此它不会知道这条消息来自聊天软件。遇到待审批的工具调用时，会发出一行提示指向 Web 界面——审批不是一条聊天消息能完成的事。

## 这一版还有

- **上下文环现在是个按钮。** 点开它，当前上下文被拆成六部分——系统提示词、工具定义、用户消息、模型消息、工具请求、工具结果——画成横跨整个窗口的一条，虚线标出压缩将在何处触发，并列出占用最多的五个工具。
- **一个红点带你走到更新本身。** 只要有可用的软件更新或 Agent 内核更新，界面上就会出现手机式的小红点；每个红点都沿着一条不断的路径通向真正执行更新的那个控件，而不是停在一句通知上。
- **分组按你排的顺序来。** 对话侧栏的会话分组与模型页的供应商分组都可以拖成手动顺序，按 Project 保存；对话的模型选择器跟随模型页的顺序。
- **侧栏按分组各算各的。** 每个分组分页读取自己的服务端流，展开行写的是该分组自己的隐藏数量，并配有**收起**；分组列表本身也按每页十个分页。
- **独立的轨迹页面已移除。** 轨迹在其所属对话的轨迹面板里查看；轨迹导入移入系统设置，并需明确指定目标 Project 与 Agent——导入的轨迹会成为一条正常列出的对话，而不是藏在过滤器后面。
- **新建 Agent 更省事。** 创建弹窗可以一次装好技能库里的多个技能，以及所选项目目录本来就带的技能；也可以直接用导出的快照包初始化一个 Agent，不必先建空 Agent 再导入。

## 升级须知

这一版有五处需要你做一次判断，而不是升级完就没事了。

**`kill_subagent` 与 `kill_command` 已移除。** 停止子会话当前这一轮用 `input_subagent` 的 `abort`；终止命令用 `input_command` 加 `kill: true`。旧名字没有任何转换：Agent 存量工具配置里若点名了它们，这些条目会直接装配不出来；模型调用它们则得到标准的「未知工具」失败。请把手工点名旧名字的地方一并改掉。

**改动设置标签页里的任何一个字段，会冻结整个标签页。** 内核更新的粒度从单个配置叶子改成了一个设置标签页。好处是你自定义过的标签页永远不会被覆盖；代价是只要一个内置工具被改过，该 Agent 就完全收不到新增的内置工具了。在该标签页上「恢复默认配置」，即可让它重新接受内核更新。

**Agent 运行的命令不再继承服务端的 `PENGUIN_*` 环境变量。** 任何 `PENGUIN_*` 变量（以及 `PORT`、`HOST`）都不会传到 Agent 运行的命令里，因此由 Agent 启动的 Harness 会使用默认数据根，而不是当前服务实例的数据根。出网代理相关的变量是有意保留的例外。命令确实需要某个变量时，请写进该 Agent 的 vault——它在剥离宿主环境之后再叠加。

**CLI 不再脱离服务端执行任务。** `penguin run` 与 `penguin chat` 都经由服务端 API；本机没有服务端在跑时，它们会自行拉起一个，而「完全离线、直连 core」不再是 CLI 的一种运行方式——这项能力仍由 SDK 为嵌入方保留。同一次重建中，按用户保存的「显示 CLI 会话」过滤开关被取消，所有会话一律列出，因此旧版 CLI 留下的 Session 现在会自行出现在侧边栏里。磁盘上没有任何数据需要迁移，旧版二进制在更新之前也仍能用它自带的 core 正常工作。

**模型库的新条目不会自动出现。** 预置模型是在创建 Project 时复制进 `.project_config.toml` 的，此后不再被改写。在模型页点**同步预置**即可补入 GLM-5.3 Flash、Qwen 3.8 Flash 与 TokenDance 分组。比该分组更早创建的 Project，需要先同步一次，这个分组——以及它的**自动获取密钥**——才会出现。

每一项改动的完整细节见 [`changelog/0.2.6/`](https://github.com/Prism-Shadow/penguin-harness/tree/main/changelog/0.2.6)。
