PenguinHarness 0.2.6 发布了。模型目录新增两款低价的 Flash 模型，以及一个支持自动获取密钥的 TokenDance 网关分组。Agent 能触及的范围也向三个方向扩展：你和模型都可以在子 Agent 运行中途向它插话；`penguin` CLI 改为经由服务端运行，Agent 因此可以操作运行着它自己的 Harness；你还可以在飞书或 Telegram 里直接和会话对话。升级时有五处改动需要你做判断，都列在文末的「升级须知」里。

## 模型目录新增两款 Flash 模型

内置模型目录新增了 `glm-5.3-flash` 和 `qwen3.8-flash`。两者都有百万 Token 的上下文窗口，都能读图，价格也都比各自的非 Flash 版本低一个数量级左右。

GLM-5.3 Flash 在目录里出现了三次，因为有三条渠道在卖它：Z.AI 直连、OpenRouter，以及新增的 TokenDance 分组。每条记录列的都是这条渠道自己的价格。

![OpenRouter、TokenDance 与 Z.AI (GLM) 下各有一条 GLM-5.3 Flash，都带视觉标记，价格各不相同](/blog-assets/penguinharness-0-2-5-glm-flash-rows-zh.png)

三个价格不一致有两个原因，其中一个是值得了解的记录口径。TokenDance 只是按自己的费率收费。Z.AI 则正在对这款模型做五折促销，有效期到 2026-09-09，而 Z.AI 和 OpenRouter 的两条记录有意采用了不同的处理方式：

- 直连厂商的记录写厂商的官方标价，所以 Z.AI 那条是每百万 Token $0.03 / $0.15 / $0.50。
- OpenRouter 的记录写 OpenRouter 实际收取的价格，所以是它的一半。

促销结束之前，直连那条记录把 Z.AI 的实际收费高估了一倍。

直连那条上的视觉标记，其实是最近才加上的。AgentHub 0.4.8 让 GLM 客户端开始转发 `image_url` 部件，提示词和工具结果里的都会转发，但只对 `glm-5.3-flash` 生效。其他 GLM 模型收到图片时，会直接报 `"GLM <id> does not support image inputs."`，而不是悄悄丢掉图片，所以这个分组的其余模型仍然标为不支持视觉。

Qwen 3.8 Flash 位于 Qwen Pay-As-You-Go 分组，输入窗口百万 Token，输出上限 131K，同样支持图片输入。

![Qwen Pay-As-You-Go 分组里并排的 Qwen 3.8 Flash 与 Qwen 3.8 Max](/blog-assets/penguinharness-0-2-5-qwen-flash-row-zh.png)

## TokenDance 网关，以及不用手动复制的密钥

TokenDance 现在是一个独立的供应商分组，带七个预置模型，通过 Chat Completions 协议访问 `https://tokendance.space/gateway/v1`。

![TokenDance 分组：七个预置模型，分组头部有添加模型、自动获取密钥、手动设置密钥、测速与前往密钥管理](/blog-assets/penguinharness-0-2-5-tokendance-group-zh.png)

**自动获取密钥**省掉了第一次使用时的例行步骤。它会打开 TokenDance 自己的授权页，在你的账号下签发一个密钥，并写进分组里的每一个模型，你不必先去控制台复制粘贴。如果授权后的回调到不了你这里，比如在桌面应用里或某些特殊的部署环境中，可以改用手动模式：页面会显示一个一次性验证码，把它粘贴回来即可。

整个密钥交换都在服务端完成。PKCE 校验串在服务端生成，从不发给浏览器；签发的密钥直接写进分组里的模型，同样不经过浏览器。任何响应、日志、URL 或错误信息里都不会出现这个密钥。

和 OpenRouter 不同，这个分组记录的是官方标价，与两个 Qwen 分组口径相同。其中两个模型正在促销：`glm-5.3-flash` 打五折，`qwen3.8-max` 打八折。所以对这两个模型，目录里的价格目前高于 TokenDance 的实际收费。两个促销在 TokenDance 的公开模型目录 API 里都有标记，这个 API 不需要凭据，促销还在不在，可以直接查到，不用猜。

模型请求现在还会向会读取应用归属请求头的网关表明自己来自 PenguinHarness：OpenRouter 用 `HTTP-Referer` 和 `X-OpenRouter-Title`，TokenDance 用 `X-App-URL`。用哪个请求头由端点的主机名决定，与供应商分组无关，所以放在 Custom 分组里、却指向这两个网关的模型，也会带上同样的归属信息。

以上这些都不会自动出现在已有的 Project 里。预置模型只在创建 Project 时复制进 `.project_config.toml`，之后不会再改写。模型页的**同步预置**是唯一的入口。它会补上缺少的条目，更新已有条目中由模型目录管理的字段；它不删除任何东西，也不会改动你保存的默认模型和任何凭据。

## 可以对话的子 Agent

以前，子 Agent 启动之后你就只能看着。子 Agent 还在运行时，`input_subagent` 会拒绝新的提示词；面板上既不能纠正它，也不能停止它；停掉主 Agent，它的子 Agent 还会继续运行。这些现在都改了。取而代之的是一套模型和你都能用的机制：你原本用来向主会话插话的通道，现在也能指向子会话。

![子 Agent 面板：上方是调用关系图，下方是子会话的对话，包括一条插话消息和子 Agent 随后的回复，底部是子会话自己的输入框](/blog-assets/penguinharness-0-2-5-subagent-steering-zh.png)

对模型来说，`input_subagent` 有四处变化：

- 发给运行中子 Agent 的提示词，会在它的下一步作为插话消息注入。
- 新增的 `abort` 参数只停止子 Agent 当前这一轮运行，会话本身保留，之后还能继续对话。`abort` 和提示词一起给出，一次调用就能打断子 Agent 并给它新的方向。
- 返回值改为子 Agent 最近一条完整的回复。在子 Agent 完成新的回复之前，重复调用返回的都是这同一条，而不是上次调用之后新增的内容。
- 已释放的 `subagent_id`，在模型再次给它发消息时会自动恢复。

对你来说，选中的子 Agent 由和主对话相同的输入框驱动。文字、Skill 和斜杠命令、按轮设置的思考等级、显示子 Agent 自身用量的上下文环，以及审批模式选择器，一样不少。不管子 Agent 处于什么状态，你发的消息都是给它的用户输入：运行中是插话，空闲时是新的一轮，会话已经结束时则会让它恢复。已经结束的子 Agent 不再是死路。

最后一处缺口是审批。后台子 Agent 碰到工具审批时，以前会被自动拒绝，原因有两个：父 Task 一结束，所有待处理的审批都会随之关闭；而在后台运行、没有父调用在等它的子 Agent，也没有地方发问。现在，子 Agent 没有别处可以处理的审批，会以普通审批卡片的形式交给你。父 Task 结束时，只会关闭主会话里待处理的审批，子 Agent 的卡片会一直留在界面上，等你决定。

这带来一个实实在在的取舍。子 Agent 的会话现在始终可以恢复、从不销毁，所以「终止子 Agent」这个概念不复存在。`kill_subagent` 已移除，`kill_command` 并入 `input_command`，改为 `kill: true`。两个移除的名字都没有保留兼容：模型调用其中任何一个，都会得到「未知工具」错误。详见下文的「升级须知」。

## 能操作 Harness 的 Agent

以前，`penguin run` 和 `penguin chat` 在进程内直接调用 core 执行 Task，不经过服务端，Web App 也看不到。现在它们是 HTTP/SSE 客户端：CLI 负责解析参数和渲染流式输出，Task 由服务端执行。从终端发起的对话会出现在侧栏里，浏览器里发起的对话也能在终端里接着聊。

这一节后面的内容都建立在这个基础上。除了 `run` 和 `chat`，现在还有一组用来查看和操作 PenguinHarness 实例的命令：`ls`、`input`、`logs`、`agent`、`project`、`cost` 和 `schedule`。Agent 运行的每一条命令，都能拿到使用这些命令所需的信息：每个工具子进程里都设置了 `PENGUIN_API_URL`、`PENGUIN_API_TOKEN`、`PENGUIN_PROJECT_ID`、`PENGUIN_AGENT_ID` 和 `PENGUIN_SESSION_ID`。在会话内部，一条不带参数的 `penguin agent ls` 访问的正是运行这个会话的服务端，而且已经以当前 Project 和当前 Agent 为默认值。这条路径上没有任何登录步骤。

![Agent 在自己的对话里运行 penguin agent create 和 penguin run --background，随后用 penguin ls 看到刚刚启动的会话](/blog-assets/penguinharness-0-2-5-orchestration-zh.png)

`penguin input` 相当于把给子 Agent 插话的做法往外挪了一层：

- 发给运行中的会话，消息会在下一步当作纠偏来处理，和发给子 Agent 的插话消息完全一样。
- 发给空闲的会话，会开始新的一轮。
- 不带 `-m` 时，它改为轮询，打印这个会话最近一条完整的助手回复。这和 `input_subagent` 收到空提示词时返回的快照相同。
- `--timeout` 为任何等待设定上限。到时间后命令会平稳退出：退出码为 0，打印一行提示写明后续可以运行的命令，Task 则继续在服务端运行。

在 Agent 内部启动的会话，会继承发起调用的那个会话的设置。你没有指定的字段，`run` 都会取那个会话的当前值：Workspace、模型对、审批模式和思考等级。这和 `run_subagent` 对子 Agent 的继承规则相同。所以在 Agent 内部，单独一句 `penguin run -m "…"` 通常就是对的，参数只在需要改动某一项时才加。

授权的设计有意保持简单。服务端每次启动都会签发一个 API Token，写入 `<data-root>/api-token`，权限为 0600，同一台机器上的 CLI 直接读取它。这个 Token 等同管理员权限，理由是能访问数据根目录的文件系统权限，本来就相当于管理员权限。远程的 `--server` 没有这种便利：没有显式提供 `PENGUIN_API_TOKEN` 时，CLI 会直接拒绝连接。

这些用法以 Skill 的形式提供。`penguin-orchestration` 加入了技能库的「AI 应用开发」分组，属于预装的那一批，所以新建的 `default_agent` 会和技能库里的其他 Skill 一起装上它，其他 Agent 也可以从技能库里安装。它写明了惯例：改动任何东西之前，先用只读的列表命令了解现状；大段材料通过 Workspace 文件交给新会话，而不是塞进 `-m`。它也写明了注意事项，这些才是真正的边界：

- 一个会话同一时间只运行一个活动 Task，所以发给忙碌会话的消息会作为插话送达，而不是排进第二个 Task。
- 派生出的会话会继承你的审批模式，所以无人值守的 `always-ask` 运行只会一直卡住，等一个并没有在看的人。
- 能给 Agent 发消息的 Agent，可能搭出一个永远不会结束的循环。
- 它启动的一切，都记在同一个 Project 的账上。

## 可以从飞书或 Telegram 联系的会话

对话不再只能在浏览器标签页里看。会话可以绑定一个自建的飞书应用或一个 Telegram 机器人：发给机器人的消息会以普通用户输入的形式进入这个会话，助手的回复也会发回聊天里。

![Telegram 下的消息软件面板：先是渠道选择器，然后是带实时状态和两个探测按钮的启用开关，再往下才是 Bot Token 字段，以及已存密钥的掩码和清除勾选框](/blog-assets/penguinharness-0-2-5-messaging-zh.png)

会话为每个渠道各保存一份配置。飞书需要 **App ID**、**App Secret** 和 **API 域名**，Telegram 只需要一个 **Bot Token**。同一时间最多只能启用一个渠道，启用的那个持有实时连接。要启用第二个时，界面会阻止你并说明原因，服务端也会拒绝。

两个渠道都不需要公网 URL。飞书的入站事件通过 SDK 的 WebSocket 长连接送达。Telegram 没有公网 webhook 就不会主动推送，所以连接器改为用基于 offset 的 `getUpdates` 长轮询主动拉取。一台在 NAT 后面的笔记本就够了，不用打隧道，也不用准备 webhook 端点。Telegram 连接器连上时，会跳过无人监听期间积压的消息，而不是把这段空窗期重放成一大堆 Task。飞书也是这样，错过的事件就是错过了。

回复是完成一条发一条，而不是整轮结束后一次发出一大段。每条助手消息一完成就转发出去，所以一次运行中在工具调用之间写下的工作笔记，到了聊天里也是同样的一串消息。同一个会话的消息按完成的先后到达，并按各渠道的文本长度上限拆分，其中 Telegram 的 4096 字符上限最紧。在群聊里，一次运行发出的第一条消息会回复触发它的那条消息，之后的消息（包括拆分出来的后续部分）都直接发送，这样长回答就不会把话题埋进一堆引用块里。

凭据的交互方式和模型页一样。输入框总是从空白开始，已保存的密钥只显示掩码；勾选**清除已存 App Secret** 或**清除已存 Bot Token**，保存时就会删掉它。渠道连接处于启用状态时不能清除，这样实时连接就不会在它的凭据删掉之后继续存在。保存和启用是两件独立的事：**保存**只写入凭据，开关则用已保存的凭据去连接或断开。表单有意把连接控件（开关、实时状态和两个探测按钮）放在凭据字段上方：两个渠道的字段数量不同，控件如果放在字段下面，在两个渠道里的高度就不一样，每次切换渠道都会跳动。

同一套表单有两个入口：会话行的菜单，以及对话右侧栏里紧挨 Trace 面板的**消息软件**面板。在之后的版本里，这个面板改名为**远程控制**。持有实时连接的会话，会在侧栏那一行上显示一个小纸飞机。所有渠道用的都是这个标记，具体是哪个渠道，写在提示气泡和读屏文本里。

模型看到的东西没有任何特别之处。入站文本就像在输入框里输入的一样启动 Task，没有标记，也没有特殊的发送者，所以模型不会知道消息来自聊天软件。遇到待审批的工具调用时，会发出一行提示，引导你去 Web App 处理，因为聊天消息没法完成审批。

## 这一版还有

- **上下文环现在是个按钮。** 点击它，会把当前上下文拆成六部分：系统提示词、工具定义、用户消息、模型消息、工具请求和工具结果。它们画成一条横跨整个上下文窗口的长条，用虚线标出压缩会在哪里触发，并列出占用最多的五个工具。
- **红点会一路带你找到更新。** 有软件更新或 Agent 内核更新时，界面上会出现手机上那样的小红点。顺着任何一个红点一路点下去，都能走到真正执行更新的那个控件，不会停在一条通知上。
- **分组按你排好的顺序显示。** 对话侧栏里的会话分组和模型页的供应商分组，都可以拖成自己想要的顺序，按 Project 保存。对话里的模型选择器沿用模型页的顺序。
- **侧栏按分组计数。** 每个分组各自分页加载，所以展开行显示的是这个分组自己的隐藏数量，点击**收起**即可折叠回去。分组列表本身每次显示十个分组。
- **独立的 Trace 页面已移除。** Trace 在所属对话的 Trace 面板里查看。Trace 导入移到了**系统设置**里，并且需要指定一个 Project 和一个 Agent，导入的 Trace 会成为列表里的一条对话，而不是藏在过滤器后面。
- **新建 Agent 更省事。** 创建弹窗可以安装技能库里的 Skill，以及所选项目目录里已有的 Skill。它还能直接用导出的快照包初始化 Agent，不必先建一个空 Agent 再导入。

## 升级须知

这一版有五处改动需要你做判断，不是升级完就没事了。

- **`kill_subagent` 和 `kill_command` 已移除。** 要停止子 Agent 的运行，用 `input_subagent` 加 `abort`；要终止一条命令，用 `input_command` 加 `kill: true`。旧名字不会自动转换：Agent 已保存的工具配置里如果写了它们，这些条目就不再加载；模型调用旧名字，会得到标准的「未知工具」错误。手动写死了这两个名字的地方，都需要改掉。
- **改动设置标签页里的任何一个字段，整个标签页都会冻结。** 内核更新现在以设置标签页为单位，而不是以单个配置值为单位。好处是更新永远不会覆盖你改过的标签页；代价是，只要改过一个内置工具，这个 Agent 就再也收不到新增的内置工具。在该标签页点击**还原为默认配置**，它就会重新接受内核更新。
- **Agent 运行的命令不再继承服务端的 `PENGUIN_*` 环境变量。** 服务端自己的 `PENGUIN_*` 变量都不会传给 Agent 运行的命令，`PORT` 和 `HOST` 也不会。`PENGUIN_*` 变量里，Harness 只会设置前面提到的五个控制变量。所以 Agent 启动的 Harness 会使用默认的数据根目录，而不是当前服务实例的数据根目录。出站代理相关的变量是有意保留的例外。如果某条命令确实需要这些变量，请写进该 Agent 的密钥保险柜，保险柜里的变量会在剥离宿主环境变量之后注入。
- **CLI 不再脱离服务端执行 Task。** `penguin run` 和 `penguin chat` 都经由服务端 API；本机没有服务端在运行时，它们会在本地启动一个。完全离线、直接调用 core 的执行方式不再是 CLI 的一种模式，这项能力保留在 SDK 里，供嵌入方使用。在这次重构中，按用户保存的「显示 CLI 会话」过滤开关也取消了，所有会话一律列出，旧版 CLI 留下的会话现在会出现在侧栏里。磁盘上没有任何数据需要迁移，旧版二进制在你更新之前，也仍能用它们自带的 core 正常工作。
- **模型目录的新条目不会自动出现。** 预置模型只在创建 Project 时复制进 `.project_config.toml`，之后不会再改写。请在模型页点击**同步预置**，补入 GLM-5.3 Flash、Qwen 3.8 Flash 和 TokenDance 分组。比这个分组更早创建的 Project 需要先同步一次，这个分组和它的**自动获取密钥**才会出现。

每一项改动的完整细节见 [`changelog/0.2.6/`](https://github.com/Prism-Shadow/penguin-harness/tree/main/changelog/0.2.6)。
