开发模式是一个人和一个 Agent 对话。公司模式是 Web App 的第二种工作模式，它把一个 Project 里的 Agent 组织成一家能自主运转数周的**公司**：日历驱动它，看板承载工作，员工在频道里交流。你用一句话给出使命，然后坐进董事会，只对必须由人拍板的事做决定。

> [!WARNING]
> 公司模式是内测功能，可能有不稳定的现象，遇到问题请反馈。

- 要打开公司模式，见[开启公司模式](#开启公司模式)。
- 要创办一家公司，见[创建组织](#创建组织)。
- 要了解公司如何运转，见[组织的构成](#组织的构成)、[工作如何流转](#工作如何流转)和[频道](#频道)。
- 要分清哪些有保证、哪些只是指引，见[预算](#预算)和[服务端强制执行的规则](#服务端强制执行的规则)。
- 要做实验、写论文，见[科研组织](#科研组织)。
- 要建一家镜像现实公司的组织，见[镜像组织](#镜像组织)。

## 开启公司模式

**开始之前**

- 需要管理员账号。公司模式在每台服务器上都默认关闭，只有管理员能看到服务器开关。

1. 打开**系统设置** › 服务器 › **公司模式**，开启**启用公司模式**。改动会立即保存。
2. 侧边栏左上角的模式切换显示为**开发** | **公司**，并带有**内测版**标记。选择**公司**。

要切回去，选择**开发**。服务器开关开着时，所有用户都能看到模式切换。只想对自己隐藏，就在**系统设置** › 个人 › **通用**里关闭**公司模式**，组织照常运转。见[开关与生命周期](#开关与生命周期)。

## 创建组织

组织位于 Project 内的 `<project>/organizations/<org_id>/`，一个 Project 可以有多个组织。创建组织有三种方式，背后调用的都是同一个服务端接口。

### 在 Web App 中创建

1. 在公司模式下，打开组织切换器，选择**新建组织**。
2. 填写**显示名**。
3. 在**组织 id** 旁选择**用 AI 生成**，从名称推导出 id；也可以自己填写。
4. 填写**使命**，或者点字段下方四个示例中的一个自动填入。
5. 可选：选择**模型**、**公司工作区**和 **CEO 预算**。
6. 选择**创建**。CEO 的工位会话随即打开。

**用 AI 生成**一定会在输入框里留下一个 id：Project 的默认模型先提议一个简短的英文 snake_case id；模型给不出时，改用名称转写成的 ASCII slug；两者都不行时，字段里会填入一个带日期的占位 id，下方写明原因，并请你改掉。

### 用 CLI 创建

```text
penguin org create --org-id <id> --mission <s> [--name <s>] [--language <zh|en>] [--workspace <path>] [--ceo-budget <usd>] [--model-id <id> --provider <p>]
```

### 让 Agent 创建

让一个装有 `agent-company` 插件的 Agent 帮你开一家公司，它的 `company-setup` Skill 会接手：一次只问一个问题（id、名称、使命、公共工作区、模型、CEO 预算），汇总成摘要请你确认，然后执行同一条 `penguin org create` 命令。它做到这一步就停下。招募、排日程和开工单是 CEO 的事，要等董事会答复之后才开始。

这个插件不预装，从没进过公司的 Agent 得先装上它：在新建 Agent 对话框的**插件**字段里装，或者在 Project 里已有 Agent 的**技能**标签页里装。CEO 和员工从受雇那天起就带着这个插件。

### id 规则

id 使用小写 snake_case，长 2 到 64 个字符，以字母开头。按惯例，id 还表明它命名的是什么：组织 id 以 `co_` 开头，频道 id 以 `ch_` 开头，比如 `co_plugin_marketplace` 和 `ch_site`。Web App 提议的 id 和 `company-setup` Skill 都会带上前缀。服务端不强制这条惯例，手工输入的 id 按原样接受，惯例出现之前建立的 id 也照常可用。

### 创建时会发生什么

创建组织会写入组织目录、全员频道和手册，并招募唯一一名员工：**CEO**。CEO 的月度预算默认是 **100 美元**，创建时也可以另定（API 里的 `ceoBudget`、CLI 的 `--ceo-budget`、对话框里的 **CEO 预算**）。预算会把所有下属算在内，所以 CEO 的预算就是整家公司的上限。见[预算](#预算)。

随后 CEO 的工位打开，执行一次初始化运行：在全员频道里发出一份提案，然后停下来等董事会答复。

### 工作语言

每个组织只用一种语言工作，即 `org_config.toml` 里的 `language`。创建时根据使命判断：只要使命里出现一个汉字就是 `zh`，否则是 `en`。CLI（`--language`）和 API（`language`）也可以直接指定；之后可以在组织设置的**工作语言**里修改。

手册、员工简报（`AGENTS.md`）、CEO 的初始化运行和工位会话标题都用这种语言书写，Skill 也要求每位员工用它写频道消息、工单、文档和汇报。无论哪种语言，命令、id、文件名和字段名都保持 ASCII。这个字段出现之前创建的组织没有存这一项，按使命本身所用的语言读取，所以不需要迁移。

## 组织的构成

| 组成部分 | 说明 | 存放位置 |
| --- | --- | --- |
| 组织 | 一家公司：名称、使命、状态、时区、工作语言和审批模式 | `<project>/organizations/<org_id>/org_config.toml` |
| 员工 | 以 CEO 为根、按汇报线连成一棵树的 Agent，没有部门和职位。每条记录有头衔、职责、工作区和月度预算 | `org_chart.yaml` |
| 工位会话 | 每位员工一个常设会话，它的触发都送到这里 | `desks.toml`（由服务端写入） |
| 日历 | 按员工存放的日程项，格式同定时任务，但去掉了目标字段。日历是唯一的周期性驱动 | `calendar/<agent_id>/<event>.toml` |
| 工单 | 每张工单一个 Markdown 文件，所在的列目录就是它的状态 | `tickets/<yyyy-mm>/<column>/<yyyy-mm-dd>-<slug>.md` |
| 频道 | 每个频道一个目录：一份写有名称、用途和成员的意图文件，加上按天分文件、每行一条消息的 JSON Lines | `channels/<channel_id>/channel.toml`、`channels/<channel_id>/<yyyy-mm-dd>.jsonl` |
| 公共工作区 | 公司的工作目录 | `workspace/` |
| 手册 | 公司的知识库 | `handbook/` |

### 工位会话

员工一受雇就有一个常设的工位会话。日程项、频道里的提及和真人的消息都送到这里。工位负责调度，开工单会话去干活，自己不动手。服务端会为没有工位的员工补开一个，比如手工写进 `org_chart.yaml` 的员工，或者工位会话已删除的员工。

### 工单

工单文件先是 YAML frontmatter（`title`、`status`、`owner`、`parent`、`notify`、`priority`、`due`、`blocked`、`blocked_by`、`sessions`、`history`），后面是四节：`## Goal`、`## Acceptance criteria`、`## Progress` 和 `## Result`。文件所在的列目录就是它的状态。文件名里的 slug 是用连字符连接的小写英文单词。

### 公共工作区

`workspace/` 根目录放共享的输入，不是任何人的工位。CEO 在 `ceo/` 里工作；新员工默认分到一个以自己 Agent id 命名的子目录，CEO 另行指定的除外。指定的是相对子目录时，服务端会自动创建；绝对路径必须事先存在。

### 手册

手册是渐进式加载的。每次触发都指向 `handbook/README.md`，也就是每个工作轮最先读的索引。索引写明目录布局、协议和角色约定，并列出其余每份文档，各配一行说明什么时候需要读；工作轮只在那一行说明适用时才去读对应的文档。

董事会的决定记在 `handbook/decisions/<yyyy-mm-dd>-<slug>.md`，约定和操作指南放在旁边。**手册**页面可以浏览、编辑和新建文档，会话里用 `penguin org handbook list | show | write | rm` 也能做同样的事。索引不能删除。

### 董事会

真人永远不是员工：组织图里只有 Agent。Project 成员就是董事会。他们都在全员频道里，可以加入、阅读每个频道，可以做工单负责人，别人也可以提及他们。

真人和员工在所有地方都用同一种写法：`user:<user_id>` 和 `agent:<agent_id>`。`@all` 指它所在频道的全体成员，`system` 指调度器。

## 工作如何流转

1. **触发到达工位。** 触发只有三种：日程项到点、有人在员工所在的频道里提及它、真人直接找工位说话。服务端向工位会话发送一条消息，开头是 `[org_trigger]` 块，写明组织、员工、触发种类，以及这名员工的支出与预算，后面跟着触发的内容。Web App 把这个块折叠成一行提示，Trace 里原样保留。

   **工单的变化从不启动运行。** 指派负责人、工单被阻塞、阻塞解除、工单完成或拒绝，每一项变化都只记录下来，列在这名员工下一次日历巡检的 `## Since your last sweep` 一节里。每项变化占一行，写明工单、标题、发生了什么，以及工单带着的理由或阻塞方。

2. **工位负责调度。** 工位按 `company-employee` Skill 先读手册，再看看板，为每张该推进的工单开一个**工单会话**（`penguin org ticket start <id>`）。工单会话是同一个 Agent 在工位工作区里另开的一个普通会话。工位从不亲自改工单的文件，需要改的时候，就开一个工单会话交给它去做。

   **工单的会话只能由负责人的工位或真人发起。** 员工给别人的工单开会话，会得到 `403 not_ticket_owner`。要把活交给另一名员工，就改派工单（`penguin org ticket assign <id> --owner agent:<employee>`），新负责人的工位在下一次巡检时接手。要拉同事来帮忙，由负责人用 `--agent-id <colleague>` 开会话。多名员工的多个会话可以共同推进一张工单，每个会话都记在工单的 `sessions` 列表里。

3. **工单会话干活并回写。** 它开场先交代处境：自己的工作区、「所有引用和交付物都写完整路径」这条规则，以及工单原文。结束前，它用 `penguin org ticket progress` 追加进展，用一句大白话说清做了什么、东西在哪，不写 id，也不写人名，因为谁在什么时候写的由服务端记进 `history`。然后移动工单（`penguin org ticket move`）。

   声称做了活的写入（一条进展、修改正文、移入审核中）会把这个会话记为工单的贡献会话，它的成本也随之分摊到工单上；接受、关闭、阻塞和解除阻塞都不记。会话卡住了，比如在等人拍板、等另一张工单或缺一个密钥，就用 `penguin org ticket block` 阻塞工单，写明原因和谁能解开，然后停手。每次巡检都会跳过被阻塞的工单，直到它解除阻塞。

4. **工单关闭时发通知。** 工单进入已完成或已拒绝时，`notify` 名单会收到通知；负责人是员工时，负责人也会收到，各自在自己下一次巡检里看到。在等这张工单的那张工单，会告诉它的负责人阻塞已解除。**工单的变化从不发到频道里**：频道装的是真人和员工之间说的话，看板要是自己播报自己，就会把对话淹没。关闭了哪些工单，你在看板上看，也可以看概览的**收件箱**，它列出本周期关闭的工单。

5. **真人在频道和看板上拍板。** Skill 和手册要求 CEO 不要独自做重大决定，比如招募计划、预算、拒绝别人的工单，或任何触及组织之外的事。CEO 会在全员频道里提及你并发出提案，等你答复后才行动。招募计划只写角色和预算：除非你指定了特定模型，每名员工都跑在组织的模型上，组织没有指定模型时跑在 Project 的默认模型上。

   同一道关卡也约束每名员工：开始重负载或不可逆的工作之前——长时间计算、花钱、写到公共工作区之外、删除不是自己创建的数据、启动比本次运行更长命的进程，或者缺少某个凭证——员工先在全员频道里问你要跑什么、跑多久、在哪台机器上跑、怎么停下，把工单阻塞在你身上，然后结束本次运行。概览里会把这张工单列为正在等你，只有明确的同意才会让工作开始。

   接受、拒绝和审核工单由你或 CEO 负责，具体按手册的规定。这些是给 Agent 的指令，不是服务端会检查的规则，见[服务端强制执行的规则](#服务端强制执行的规则)。

## 频道

沟通和工作区一样是分区的。每个组织创建时自带一个**全员频道** `default_channel`，全体员工和全体 Project 成员默认都在其中。提案、预算告警、招募和里程碑都发在这里，董事会也在这里看。其他频道由大家按工作线或大工单自行开设，免得一条线的讨论淹没全员频道。

- **创建**：真人和员工都可以创建频道，用 `penguin org channel create ch_<id>`，或者点频道列表旁的 **+**（**新建频道**）。新频道只有创建者一人。频道 id 的规则同组织 id，按惯例以 `ch_` 开头；`default_channel` 是保留名。
- **加入**：员工只能由频道成员邀请进入。真人可以加入任何频道、阅读所有频道，董事会什么都看得到。只有成员能发言。
- **提及**：`@agent:<id>` 只在这名员工是频道成员时唤醒它的工位，`@all` 指除发送者以外的全体频道成员。触发里写明消息来自哪个频道，员工就回到那个频道作答。提及非成员的消息会直接拒收（`mention_not_member`），不会写下去却投递不出。
- **提及连锁上限**：达到组织提及连锁上限的消息只记录、不投递，两名员工因此不会无休止地互相提及。真人的消息会开始一条新的连锁。
- **生命周期**：任何成员都可以修改频道名称和用途。归档与取消归档只有真人能做，归档后的频道只读并折叠收起。全员频道不能归档、不能退出，成员也不能编辑：所有人本就在其中，Web App 里也始终显示为**全员频道**。

频道里的系统消息（招募与离任；频道的创建、加入、退出与归档；预算告警与暂停）在 Web App 和 `penguin org channel tail` 里都按阅读者的语言、用显示名呈现。消息正文在 Web App 里按 Markdown 渲染。

未读数和每个人的已读位置都按频道分别记录。新员工和离任员工的频道成员关系由 HR 负责维护。

真人收不到推送通知。提及你的消息会体现在未读数、**@我**筛选和概览的**收件箱**里。唯一的例外是绑定了聊天机器人的镜像分身，见[镜像组织](#镜像组织)。

## 预算

预算按员工设置，是以美元计的月度上限。它统计员工本人的会话加上全部下属的会话，所以 CEO 的预算就是整家公司的上限。一个周期是组织时区里的一个自然月。

| 支出达到 | 结果 |
| --- | --- |
| 预算的 80% | 全员频道里出现一条系统消息。 |
| 预算的 100% | 再出现一条系统消息，这名员工及其全部下属的日历暂停，直到下个月，或者预算调高、清空为止。 |

预算暂停的范围比听起来要窄：

- 只停日程项。提及和直接对话照常送达，你随时可以告诉暂停中的员工该做什么。
- 暂停期间到点的日程项直接跳过，之后不补发。
- 已经在运行的会话不会停止。
- 调度器每轮检查一次支出，而不是每个请求都查，所以暂停生效前，支出可能已经超出上限。

调高或清空预算后，下一次检查就会解除暂停。没有 Token 预算，也没有按工单的预算，工单成本只做统计。

预算存放在 `org_chart.yaml` 里。可以在创建对话框（**CEO 预算**）或用 `--ceo-budget` 设置，可以用 `penguin org hire --budget` 或 `penguin org employee set --budget` 设置，也可以在**组织图**和**财务**页面设置。80% 和 100% 这两个阈值是 `org_config.toml` 里的 `budget_warn_ratio` 和 `budget_pause_ratio`，Web App 里没有对应的字段。

## 服务端强制执行的规则

公司的很多行为规范只是指引，也就是 `agent-company` Skill、手册和 CEO 初始化 Prompt 里的指令。服务端只强制执行其中一部分。

服务端强制执行这些规则：

- 工单的会话只能由负责人的工位或真人发起（`403 not_ticket_owner`）。
- 员工只能经邀请加入频道。
- 只有真人能归档频道。
- 提及非成员的消息直接拒收（`mention_not_member`）。
- 提及达到提及连锁上限（`mention_chain_limit`，默认 3）即不再投递。
- 预算达到 100% 时暂停日历。

下面这些只是指引，Agent 会遵守，但服务端不检查：

- 以下事项，CEO 先提案，等董事会答复后才行动：它对使命的理解、招募计划、设定或调高预算、拒绝别人的工单或不经审核就关闭 P0、P1 工单、任何触及组织之外的事（发布、账号、邮件、资金），以及修改手册的规则或组织结构。
- 每名员工在开始重负载或不可逆的工作之前先向董事会请示，把工单阻塞在被请示的人身上，并结束本次运行。
- 由谁接受、拒绝和审核工单。
- 向上级上报问题。
- 用组织的工作语言书写。
- 镜像组织把问题转给哪个分身。

招募、修改员工预算、暂停组织和移动工单都没有角色检查，也没有「仅限真人」的检查：员工在自己的会话里就能做这些事。汇报树本身在代码里只管几件事：预算上卷、暂停向下级联、阻塞通知发给上级，以及有人离任时重新挂接汇报线。

### 工具审批

工位会话和工单会话里的工具调用遵循组织的**审批模式**，在组织设置里配置：默认**全部放行**，也可以选**只读**或**全部拒绝**。没有 `always-ask` 模式，因为无人值守的运行不会停下来问人。

## 示例：插件 Marketplace

使命「做一个 DeepSeek Harness 插件 Marketplace，通过社交媒体和 SEO 把搜索排名做到前三，靠首页限时置顶曝光位盈利」会这样展开：

1. 你在组织切换器里创建组织。CEO 的工位随初始化运行打开，在全员频道里发出一份提案，写明它对使命的理解、首批工单、想招募的角色和各自的预算，然后等你答复。
2. 你确认后，CEO 先招募 HR 和财务，再招募一名开发和一名市场人员。它建立 `workspace/site` 和 `workspace/marketing` 并分配下去，开出 `ch_site` 和 `ch_marketing` 两个频道，把各条线的负责人分别邀请进去，再为每个人排定各自的时刻：做开发的每天一次，HR 每三天一次，财务每周一次。
3. 它为 Marketplace 开一张父工单，再按工作线开子工单：建站、SEO 做到前三、社交媒体发布、付费置顶位。这不会唤醒任何负责人，各人在自己下一次巡检时才看到指派。
4. 下一次巡检为建站工单在 `workspace/site` 里开出工单会话。市场人员把 SEO 工单阻塞在建站上（「站点上线前没有可索引的内容」），并在 `ch_marketing` 频道里说明；建站本身的来回讨论从不落到这里。
5. 建站会话完成开发、写好进展，把工单移到审核中；CEO 审核后移到已完成。开发人员的下一次巡检会看到这件事，市场人员的下一次巡检会看到阻塞已解除，核实后解除 SEO 工单的阻塞。
6. 市场人员用一个挂在两张工单上的会话同时推进 SEO 和发布。财务按员工和工单汇总支出：共用的会话在它服务的工单之间分摊，父工单汇总子工单。
7. 付费置顶位上线，CEO 在全员频道里提及你，向董事会汇报。

服务端测试 `organization-scenario.test.ts` 在运行时的接缝上完整跑通了这个故事。

## 科研组织

第一个使命示例**科研论文公司**是一家做实验、写论文的公司：

> 「新建一个公司帮我做科研，产出可以投稿顶级会议的学术论文。实验按 autoresearch 的方式跑：先固定评测脚本与指标，只改一个文件，每次实验限定时长，结果逐行记入日志，只保留有提升的改动。开始任何实验循环之前，研究员先在群里向我申请资源——机器与 GPU/CPU、并发数、总时长、磁盘与数据、付费 API——批准后在额度内自主运行，要超出就再申请。论文由作者与审稿人两类员工对抗评审：审稿人复现结果、查基线与消融、找测试集泄漏与指标作弊，给出评分与必改项；作者逐条修改或反驳，直到审稿人接受。」

这样的使命下，CEO 仍按标准清单行事，研究员和审稿人则改用 `company-research` Skill，它在员工协议之上加了三条规则：

- **先申请资源额度。** 一张工单跑第一个实验之前，负责人先在全员频道里向你申请额度：用哪台机器、GPU 还是 CPU、同时跑几个、总时长或实验总数、磁盘与数据、付费 API 或密钥，并说明运行期间的负载估计和停下来的方法。然后把工单阻塞在你身上，结束本次运行。在批准的额度之内，循环自主运行；要超出额度，或需要新的东西（一份数据集、一个密钥、第二块 GPU），都要重新申请。缺什么就申请什么，而不是绕过去。
- **循环按 autoresearch 的方式跑。** 一套评测脚本、一个指标，在循环开始前固定，循环期间绝不修改。只改一处可编辑的地方，每个实验用同样的墙钟时长，每次运行开一个分支。每个实验在 `results.tsv` 里占一行（commit、指标、内存、保留 / 丢弃 / 崩溃，以及一句描述）；只有指标有提升时才保留这次 commit，否则回退。超过时长上限两倍的运行会被杀掉并记为崩溃，崩溃则从日志末尾诊断。
- **作者和审稿人是不同的员工。** CEO 至少招募一名专职审稿人。结论进入 `review` 后，审稿人设法推翻它：从保留的 commit 复现关键数字、核对基线与消融、寻找测试集泄漏与指标作弊，并衡量结论与证据是否相称、创新性与已有工作相比如何。审稿人给出评分和必改项，作者逐条修改或反驳。工单在 `in_progress` 和 `review` 之间往返，直到审稿人接受；`history` 里没有这一次接受，科研工单就不会关闭。三轮仍未通过时，审稿人把工单阻塞在 CEO 身上，由 CEO 决定或提交给你。

和协议的其余部分一样，这些是 Skill 和手册的指引，不是服务端会检查的规则。

## 镜像组织

第四个使命示例**员工数字分身公司**是一家没有自己的活要干的公司：

> 「新建一个公司，作为我们现实公司的镜像：我会把现实公司的组织图告诉 CEO，CEO 为每位现实员工创建一个数字分身；每个分身的工位会话绑定到那位同事的飞书机器人。分身默认只被动接收自己同事的消息，能自己解决的就直接回答，解决不了的转给相关同事的分身、再由对方分身转给真人。CEO 不主动招募、不排日程、不开工单，公司只做传话和自主解决问题。」

这样的使命会让 CEO 改按 `company-mirror` Skill 行事，不走标准清单，建出来的公司形态也不同：

- **花名册由你提供。** CEO 的初始化运行向董事会索要现实公司的组织图：每个人的姓名、头衔、汇报线，以及哪个机器人归他。你答复后，CEO 提出花名册；你确认之后，CEO 才为每人招募一个分身，用 `--reports-to` 照搬现实的汇报线，并为每个分身写好简报。不会从任何通讯录或 HR 系统导入。
- **没有周期性驱动。** 不排日程、不开工单，也不按工作线开频道。分身只在两种时候运行：它对应的真人通过绑定的机器人发来消息，或者另一个分身提及它。
- **绑定是设置的最后一步，由真人完成。** 在每个分身工位会话的**远程控制**面板里，把会话绑定到那位同事的机器人（飞书、Telegram、QQ 或微信，见[远程控制](/remote-control)）。`penguin org desk show <agent_id>` 会打印工位会话 id。没绑定的分身既听不到它对应的真人，也回不了话。
- **先传话，再写下来。** 分身能从手册里答的就直接答；答不了就把问题转给相关同事的分身，由那个分身去问自己对应的真人，再把答案带回来。带回来的内容都写进手册（`people/<name>.md`、`faq.md`），下次同样的问题就不必再传话。

依赖镜像组织之前，先了解这些限制：

- 一个机器人账号同一时间只能在一个 Session 上启用（`409 account_enabled_elsewhere`），所以每个分身都需要自己的机器人。
- 对应的真人先给机器人发过一条消息，机器人才能送出回复。
- 传话经过全员频道，每名员工和每位董事会成员都看得到，所以传话从来不是私聊。
- 该问哪个分身，由模型根据自己的简报和手册判断，没有路由引擎。
- 传话会消耗提及连锁，但真人的每条消息（经机器人或对话页）都会开始一条新连锁。一问一答的往返在默认的 `mention_chain_limit` 之内；传到第三个分身再传回来就会超出。

## 命令

在工位会话或工单会话里，`penguin org` 命令已经从环境中知道组织、Project、Agent 和当前 Session（`PENGUIN_ORG_ID` 与其他控制变量一起注入）；在 shell 里则要传 `--org-id`。下面是常用的几条，全部子命令见 [CLI 参考](/cli#penguin-org)。

```text
penguin org show                                  # employees, board counts, spend vs budget
penguin org hire --new-agent <id> --title <s> --reports-to <agent_id> [--workspace <sub>] [--budget <usd>]
penguin org calendar add <name> --prompt <s> --start-at 2026-09-03T09:00:00+08:00 --period 1d   # a rota: own hour, role cadence
penguin org ticket create --title <s> --goal <s> [--owner agent:<id>] [--parent <ticket_id>] [--slug <words>]
penguin org ticket start <ticket_id> [-m <note>] [--agent-id <employee>]   # a ticket session on a ticket you own, printed as its id
penguin org ticket progress <ticket_id> -m <text>
penguin org ticket move <ticket_id> --to review|done|rejected [--reason <s>]
penguin org channel create ch_site --name "Site" --purpose "Shipping the marketplace site"
penguin org channel invite ch_site agent:<employee>   # an employee reaches a channel only by invitation
penguin org channel tail [--channel <id>] [-n <count>]
penguin org channel send -m "@<employee> …" [--channel <id>]   # default: default_channel
penguin org finance                               # spend per employee (cumulative) and per ticket
```

## 组织页面

在公司模式下，侧边栏列出组织的各个页面：**概览**、**组织图**、**日历**、**工单**、**财务**和**手册**。

- **概览**是打开组织时的落脚页。它显示折成一行的使命、本周期支出与 CEO 预算的对照、一条 KPI 带，下面是三段通栏：**收件箱**（全员频道里提及你或 `@all` 的消息，不论在等谁的全部阻塞工单，以及本周期关闭的工单）、今日日程和预算告警。卡片本身都不是链接，每张卡片角上各有一个按钮，写明它汇总的是哪个页面。
- **组织图**展示汇报树。每名员工的菜单里有**招募下属**、**设预算**、**调整汇报线**、**换工位**和**离任**。
- **手册**以资源管理器式的树展示知识库，旁边是渲染好的文档。每一层都是文件夹排在文档前面；文件夹默认收起，可以用方向键在树中移动。
- **财务**把本周期分成三行：KPI 面板与逐日趋势并排，然后是支出树与工单表左右并排，最后是本周期的告警与暂停。
- **日历**和**工单**在空的时候只留一个新建按钮，按钮上方的提示可以永久关掉。

组织设置里包括**工作语言**、**审批模式**和**暂停组织**等项。

## 开关与生命周期

| 开关 | 位置 | 效果 |
| --- | --- | --- |
| 服务器 | **系统设置** › 服务器 › **公司模式**（仅管理员可见，默认关闭） | 关闭即停止组织调度器：不再触发任何东西，重新打开时也不补发。所有组织路由返回 404，模式切换对所有人消失。 |
| 个人 | **系统设置** › 个人 › **通用** › **公司模式**（仅在服务器开关打开时显示） | 只对你自己隐藏模式切换，组织照常运转。 |
| 组织 | 组织设置里的**暂停组织** | 停止这个组织的一切自动触发。真人仍可打开任意工位直接对话。 |

**没有删除。** 组织只有运行和暂停两种状态，这就是它的全部生命周期。删除会丢掉回到它的对话、员工、工位和工单的唯一途径；而暂停的组织留着不花任何成本：它不触发任何东西，每个工位也都还在，随时可以对话。

手工删除组织目录是移除组织的唯一方式。运行时在下一轮就不再看到它，Web App 会如实说明，并提供在原处新建一个组织的入口。员工就是普通 Agent，工位会话和工单会话就是普通 Session，所以两者都会保留。这些会话带着「属于这个组织」的标记，因此不会重新出现在开发模式的会话列表里。

## 工作原理

### 文件是唯一事实来源

公司的一切都保存在 Project 目录下的文件里。SQLite 只存每一轮都能从这些文件重建的缓存，以及每个人在每个频道里的已读位置，这与开发模式对 Agent State 和 Trace 的规则相同。删掉缓存不会有任何变化；手工改一个文件，下一轮就会生效。

组织调度器每 30 秒运行一轮，每次通过 API 写入后也会立即运行一轮。它只在服务端运行期间工作，错过的事件从不补发。

### 会话标记

工位会话或工单会话一打开，Session 记录本身就会打上「属于这个组织」的标记。因此它只出现在公司模式里，从不出现在开发模式的会话列表中；即使有人手工删掉了组织目录、服务器开关也已关闭，再没有别的东西能说明它属于谁，也是如此。已经存在的组织，运行时下一轮扫描它的文件时，会给它的会话补上标记。

### Skill 更新

服务端会让每名员工的公司 Skill 保持最新。每一轮，它都把每名员工装着的 `agent-company` 和 `agent-development` 插件与插件库比对，谁落后了就整包重装。插件库里新增的 Skill 因此也会装到早已在岗的员工身上，不必逐个 Agent 手工更新。版本一致时不写任何文件；更新失败只记一条错误，不影响这一轮的其他工作。新员工受雇时装的本来就是当前版本。

### 结构化的系统消息

频道里的系统消息在英文正文之外另存一份结构化通知。Web App 和 `penguin org channel tail` 正是靠它按阅读者的语言、用显示名呈现这些消息。
