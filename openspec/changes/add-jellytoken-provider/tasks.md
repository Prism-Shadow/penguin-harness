开发分支：`feat/add-jellytoken-provider`；目标分支：`main`。以下复选框仅记录实施进度，完成方案改写不算完成实施。

## 1. 核验接口与模型资料

- [x] 1.1 在隔离临时环境中，用授权账号的 `/v1/models` 或 `/api/ai/models` 核对技术设计表中的九个模型标识和 Chat Completions 可用性。密钥只能通过临时环境变量或权限受限的临时文件注入，禁止写入仓库、日志、OpenSpec、钉钉文档或命令行参数；只保存脱敏的模型标识、状态和来源，完成后删除临时凭据与响应文件，并撤销本次测试密钥。
- [x] 1.2 对照首版约定验收九条预设：上下文窗口均为 1M（1,000,000 个词元），模型库和选择器均不展示视觉能力标签或说明。
- [x] 1.3 核对价目表的三类报价及九个模型各自的「几折起」标签。为预设提供独立展示信息并在模型卡片渲染；逐项核对文字与归属，用同名模型验证标签不串组，用费用样例验证不因标签再次打折。

## 2. 登记供应商与九条预设

- [x] 2.1 在 `packages/server/src/model-catalog/catalog.ts` 登记 JellyToken 网关，启用手动添加模型。检查 `presetProviderTable()` 生成的地址和协议，并核对两个官网链接均为指定登录页。
- [x] 2.2 依技术设计表的顺序添加九条预设，保留原始标识。用 `model-catalog.test.ts` 检查分组与标识组合唯一、顺序正确、协议与端点明确、价格换算正确，九条窗口值均为 `1000000`。
- [x] 2.3 用新项目配置验证 `seed.ts` 的已有逻辑：公共连接只存于分组，九条预设解析后的目标均为 JellyToken；项目默认模型保持不变。
- [x] 2.4 模拟网络请求，验证现有 MMSP 客户端使用配置的 Bearer 密钥调用 `/v1/chat/completions`，请求中的模型标识未被改写。若不兼容，记录协议差异并停止，不在核心层增加特判。
